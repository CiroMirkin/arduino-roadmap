Hay dos formas comunes de comunicar un equipo IoT con un servidor. Con **HTTP y consultas periódicas** (*polling*), el equipo inicia cada intercambio: envía sus datos y, si quiere saber si hay órdenes, pregunta cada tanto. Con **MQTT**, el equipo mantiene una conexión abierta con un intermediario (el **broker**) y se comunica por **temas**: publica sus lecturas en un tema y se **suscribe** a otro donde le llegan las órdenes al instante. Ninguna es mejor en todo; la elección depende de cuánto importa la demora de las órdenes, cuántos equipos hay y qué infraestructura se quiere mantener.

## Por qué te importa

El controlador del invernadero envía lecturas cada minuto, y eso funciona bien con HTTP. La pregunta aparece con las órdenes que van **hacia** el equipo: "regar ahora", "cerrar las ventanas que viene granizo", "actualizar la configuración". Con HTTP, el equipo se entera recién cuando consulta; si consulta cada minuto, la orden puede tardar un minuto en llegar. Si consulta cada pocos segundos para que sea más rápido, multiplica las peticiones de cada equipo, y con cien invernaderos, el backend recibe miles de consultas por minuto que casi siempre responden "no hay nada".

MQTT resuelve eso con una conexión permanente, a cambio de mantener un broker y de que el equipo sostenga esa conexión. Conocer las dos opciones permite elegir con criterio.

## Cómo funciona

**HTTP con consultas periódicas**:

- Cada intercambio es una petición nueva: `POST` para enviar, `GET` para preguntar.
- Simple de implementar y de depurar, funciona con cualquier backend web y atraviesa cualquier red.
- Las órdenes llegan con una demora de hasta el intervalo de consulta.
- Cada consulta tiene un costo fijo (conexión, encabezados, y si es HTTPS, el saludo TLS).

**MQTT**:

- El equipo abre una conexión TCP con el broker y la mantiene abierta (con mensajes de "sigo vivo" cada tanto).
- Publica en **temas** con nombres jerárquicos, como `invernaderos/2/controlador/lecturas`, y se suscribe a otros, como `invernaderos/2/controlador/comandos`.
- El broker reparte cada mensaje a todos los suscriptos a ese tema: el backend, un panel, otro equipo.
- **QoS** define la garantía de entrega: 0 (como mucho una vez), 1 (al menos una vez), 2 (exactamente una vez, más costoso).
- Un mensaje **retenido** queda guardado en el broker y se entrega a quien se suscriba después (útil para "la configuración actual").
- El **último mensaje** (*last will*) se registra al conectarse, y el broker lo publica si el equipo desaparece sin despedirse.

## Ejemplo

El controlador con la librería **PubSubClient**, una de las más usadas en Arduino. Publica sus lecturas, se suscribe a los comandos y registra un último mensaje de "offline".

```cpp mqtt.ino
#include <WiFi.h>
#include <PubSubClient.h>

constexpr const char* TEMA_LECTURAS = "invernaderos/2/controlador/lecturas";
constexpr const char* TEMA_COMANDOS = "invernaderos/2/controlador/comandos";
constexpr const char* TEMA_ESTADO   = "invernaderos/2/controlador/estado";

WiFiClient red;
PubSubClient mqtt(red);

void alRecibirComando(char* tema, byte* datos, unsigned int largo) {
  char comando[32];
  size_t n = largo < sizeof(comando) - 1 ? largo : sizeof(comando) - 1;
  memcpy(comando, datos, n);
  comando[n] = '\0';
  Serial.printf("comando recibido: %s\n", comando);   // validar antes de actuar (ver 6.3)
  // anotar el comando para que el control lo procese; no actuar desde acá
}

bool conectarMqtt() {
  // id, usuario, clave, tema del last will, QoS, retenido, mensaje del last will
  if (!mqtt.connect("controlador-inv2", "usuario", "clave", TEMA_ESTADO, 1, true, "offline")) {
    return false;
  }
  mqtt.publish(TEMA_ESTADO, "online", true);          // retenido: quien se suscriba lo ve
  mqtt.subscribe(TEMA_COMANDOS, 1);
  return true;
}

void setup() {
  Serial.begin(115200);
  WiFi.persistent(false);
  WiFi.begin("invernadero", "clave-del-wifi");
  mqtt.setServer("192.168.0.10", 1883);
  mqtt.setCallback(alRecibirComando);
}

void loop() {
  static uint32_t ultimoIntento = 0;
  if (WiFi.status() == WL_CONNECTED && !mqtt.connected() && millis() - ultimoIntento >= 10000) {
    ultimoIntento = millis();
    Serial.println(conectarMqtt() ? "MQTT conectado" : "MQTT sin conexión");
  }
  mqtt.loop();                                         // mantiene la conexión y recibe mensajes

  static uint32_t ultimaLectura = 0;
  if (mqtt.connected() && millis() - ultimaLectura >= 60000) {
    ultimaLectura = millis();
    char json[64];
    snprintf(json, sizeof(json), "{\"temp\":%.1f,\"suelo\":%d}", 24.5f, 41);
    mqtt.publish(TEMA_LECTURAS, json);
  }
}
```

`mqtt.loop()` tiene que llamarse seguido: es lo que recibe los mensajes y mantiene viva la conexión. Si el controlador se queda sin luz, el broker publica "offline" en el tema de estado, y el backend se entera al instante. En producción, la conexión va cifrada (MQTT sobre TLS, puerto 8883) y con credenciales por equipo (ver [3.4](/conceptos/3-4)). PubSubClient tiene un límite de 256 bytes por mensaje por defecto; `mqtt.setBufferSize()` lo cambia.

## Cuándo sí y cuándo no

**HTTP con consultas periódicas** conviene cuando:

- las órdenes pueden esperar uno o varios minutos,
- hay pocos equipos, o envían poco,
- se quiere un solo backend web, sin otra pieza que mantener.

**MQTT** conviene cuando:

- las órdenes tienen que llegar en segundos (alarmas, accionamiento remoto),
- hay muchos equipos, o varios consumidores de los mismos datos (backend, paneles, otros equipos),
- importa saber al instante si un equipo se desconectó.

Una combinación frecuente: lecturas y configuración por HTTP, y un canal MQTT solo para órdenes y estado de conexión. Para nodos a batería que duermen la mayor parte del tiempo (ver [0.12](/conceptos/0-12)), una conexión permanente no tiene sentido: ahí manda HTTP, o MQTT conectándose solo al despertar.

## Resumen

- Con HTTP el equipo inicia todo: las órdenes le llegan recién cuando consulta.
- MQTT mantiene una conexión con un broker y usa temas: el equipo publica lecturas y recibe órdenes al instante.
- QoS, mensajes retenidos y el último mensaje (*last will*) resuelven entrega garantizada, estado actual y detección de desconexiones.
- MQTT agrega una pieza (el broker) y una conexión permanente que mantener.
- Elegí según la demora aceptable para las órdenes, la cantidad de equipos y si duermen o no.
