Un programa de C++ se reparte en archivos de dos tipos. Los headers (`.h`) **declaran**: dicen que algo existe y cómo se usa. Los archivos fuente (`.cpp`) **definen**: tienen el cuerpo de las funciones y reservan la memoria de las variables. Cada `.cpp` se compila por separado, y al final el **linker** une todo en un solo programa.

## Por qué te importa

Cuando empezás, todo va en un `.ino`. Pero el controlador del invernadero tiene riego, ventilación, pantalla, conexión BLE con los nodos y envío al backend, y a las mil líneas ese archivo se vuelve imposible de leer. Dividirlo en archivos es el primer paso para ordenarlo, como se ve en [2.1](/conceptos/2-1).

Apenas lo dividís aparecen tres errores que al principio desconciertan: `'X' was not declared in this scope`, `undefined reference to X` y `multiple definition of X`. Los tres se explican con una sola idea: la diferencia entre declarar y definir, y quién se queja de cada cosa, el compilador o el linker.

## Paso a paso

### 1. Declarar y definir

Una **declaración** presenta un nombre: le dice al compilador que existe y de qué tipo es. Una **definición** además lo crea: escribe el cuerpo de la función o reserva la memoria de la variable.

```cpp
// Declaraciones: "esto existe"
void encenderBomba();                // prototipo de función
extern uint32_t riegosHoy;           // variable definida en otro archivo
class Rele;                          // "existe una clase llamada Rele"

// Definiciones: "esto es así"
void encenderBomba() {
  digitalWrite(26, HIGH);
}
uint32_t riegosHoy = 0;
```

Toda definición es también una declaración. Al revés no: una declaración puede aparecer muchas veces, pero cada cosa se puede definir **una sola vez** en todo el programa. Esa regla se llama *One Definition Rule* (ODR).

### 2. Cada `.cpp` se compila solo

El compilador toma un `.cpp`, le pega sus `#include` (ver [B.5](/conceptos/b-5)) y lo compila sin mirar ningún otro `.cpp`. Ese texto completo se llama *unidad de traducción*.

Para compilar una llamada a `encenderBomba()`, al compilador le alcanza con la declaración: con el nombre, los parámetros y el tipo de retorno ya puede generar la instrucción de llamada. No necesita saber qué hay adentro. Si no encuentra ni siquiera la declaración, se queja:

```text
error: 'encenderBomba' was not declared in this scope
```

Ese es un error del **compilador**: falta un `#include`, o hay un error de tipeo en el nombre.

### 3. El linker une las piezas

Cada `.cpp` compilado queda como un archivo objeto con huecos: "acá se llama a `encenderBomba`, que está en algún otro lado". El linker junta todos los objetos y completa esos huecos. Puede fallar de dos formas:

```text
undefined reference to `encenderBomba()'
```

Algo se declaró y se usó, pero nadie lo definió. O el `.cpp` que lo define no se está compilando, o la definición tiene una firma distinta de la declaración.

```text
multiple definition of `riegosHoy'
```

Algo se definió en más de un `.cpp`. Casi siempre es una definición escrita en un header que incluyen varios archivos.

### 4. Qué va en cada archivo

| En el `.h` | En el `.cpp` |
|---|---|
| `#pragma once` | `#include` de su propio `.h` |
| prototipos de funciones | cuerpos de las funciones |
| declaraciones de clases y `struct` | definiciones de los métodos (`Clase::metodo`) |
| `extern` de variables compartidas | la definición de esas variables |
| constantes `constexpr` | variables y funciones internas, con `static` |

El `.h` es lo que el resto del programa necesita saber para usar tu código. El `.cpp` es cómo funciona por dentro.

### 5. Clases repartidas en dos archivos

```cpp Rele.h
#pragma once
#include <Arduino.h>

class Rele {
public:
  explicit Rele(uint8_t pin);
  void begin();
  void encender();
  void apagar();
  bool encendido() const { return _encendido; }   // corto: puede quedar en el header

private:
  uint8_t _pin;
  bool _encendido = false;
};
```

```cpp Rele.cpp
#include "Rele.h"

Rele::Rele(uint8_t pin) : _pin(pin) {}

void Rele::begin() {
  pinMode(_pin, OUTPUT);
  apagar();
}

void Rele::encender() {
  digitalWrite(_pin, HIGH);
  _encendido = true;
}

void Rele::apagar() {
  digitalWrite(_pin, LOW);
  _encendido = false;
}
```

`Rele::` indica que estás definiendo el método de la clase `Rele`, no una función suelta. Los métodos cortos escritos dentro de la clase en el header, como `encendido()`, son una excepción permitida a la regla: el lenguaje los trata como `inline`, y eso permite que su definición aparezca en varios `.cpp`.

### 6. Cómo arma el Arduino IDE tu proyecto

El Arduino IDE agrega un paso propio. Todos los `.ino` de la carpeta se juntan en un solo archivo, en orden alfabético después del principal, y el IDE genera prototipos automáticamente para las funciones que encuentra. Por eso en un `.ino` podés llamar a una función que está definida más abajo.

Los `.h` y `.cpp` que agregues como pestañas, o dentro de una subcarpeta `src/`, se tratan como C++ normal: no hay prototipos automáticos y cada `.cpp` se compila por separado. Lo que aprendiste en esta lección aplica a esos archivos. PlatformIO no tiene la excepción de los `.ino`: todo se compila como C++ normal desde el principio.

## Ejemplos

### Ejemplo 1. Una función en tres archivos

```cpp conversiones.h
#pragma once

float celsiusAFahrenheit(float celsius);
```

```cpp conversiones.cpp
#include "conversiones.h"

float celsiusAFahrenheit(float celsius) {
  return celsius * 9.0f / 5.0f + 32.0f;
}
```

```cpp controlador.ino
#include "conversiones.h"

void setup() {
  Serial.begin(115200);
  Serial.println(celsiusAFahrenheit(24.5f));   // 76.10
}

void loop() {}
```

`controlador.ino` solo ve la declaración y compila igual. `conversiones.cpp` se compila aparte. El linker conecta la llamada con el cuerpo.

### Ejemplo 2. Usar la clase `Rele`

Con `Rele.h` y `Rele.cpp` del paso 5 en la carpeta del proyecto, el sketch principal queda así:

```cpp controlador.ino
#include "Rele.h"

Rele bomba(26);
Rele ventilador(27);

void setup() {
  bomba.begin();
  ventilador.begin();
}

void loop() {
  if (!ventilador.encendido()) {
    ventilador.encender();
  }
}
```

El sketch no sabe cómo funciona un relé por dentro y no lo necesita. Si mañana el relé pasa a ser activo en bajo (se enciende con `LOW`), cambia solo `Rele.cpp`, y `controlador.ino` no se toca.

### Ejemplo 3. Estado compartido entre módulos

El módulo de riego cuenta los riegos del día, y la pantalla los muestra. Los dos necesitan la misma variable. Se declara en un header con `extern` y se define una sola vez.

```text
controlador/
├── controlador.ino
├── config.h
├── estado.h
├── estado.cpp
├── riego.h
├── riego.cpp
├── pantalla.h
└── pantalla.cpp
```

```cpp estado.h
#pragma once
#include <Arduino.h>

struct Estadisticas {
  float temperaturaMaxima;
  float temperaturaMinima;
  uint32_t riegosHoy;
};

extern Estadisticas estadisticasHoy;   // declaración: existe, está en estado.cpp
```

```cpp estado.cpp
#include "estado.h"

Estadisticas estadisticasHoy = {-100.0f, 100.0f, 0};   // la única definición
```

```cpp riego.cpp
#include "riego.h"
#include "estado.h"
#include "config.h"

void regar() {
  digitalWrite(PIN_BOMBA, HIGH);
  estadisticasHoy.riegosHoy++;
}
```

```cpp pantalla.cpp
#include "pantalla.h"
#include "estado.h"

void mostrarEstadisticas() {
  Serial.print("riegos hoy: ");
  Serial.println(estadisticasHoy.riegosHoy);
}
```

`riego.cpp` y `pantalla.cpp` trabajan sobre la misma variable porque los dos ven la misma declaración `extern` y existe una sola definición en `estado.cpp`. Las variables globales compartidas son cómodas, pero cualquier archivo puede modificarlas; en [2.1](/conceptos/2-1) vas a ver formas de ordenar esto mejor.

## Errores comunes

### Definir una función en un header

```cpp
// Mal: conversiones.h, incluido desde dos .cpp
float celsiusAFahrenheit(float c) { return c * 9.0f / 5.0f + 32.0f; }
// multiple definition of `celsiusAFahrenheit(float)'

// Bien, opción 1: prototipo en el .h y cuerpo en el .cpp (ejemplo 1)
// Bien, opción 2: marcarla inline si es corta y querés dejarla en el header
inline float celsiusAFahrenheit(float c) { return c * 9.0f / 5.0f + 32.0f; }
```

`inline` le dice al linker que esa función puede aparecer definida en varios archivos con el mismo cuerpo, y que se quede con una.

### Definir una variable global en un header

```cpp
// Mal: estado.h
uint32_t riegosHoy = 0;

// Bien: estado.h
extern uint32_t riegosHoy;
// y en estado.cpp
uint32_t riegosHoy = 0;
```

Si la variable no necesita compartirse, no la pongas en el header: dejala en el `.cpp` como `static`, como se ve en la próxima lección, [B.7](/conceptos/b-7).

### Olvidar `Clase::` en el `.cpp`

```cpp
// Mal: Rele.cpp
void encender() {          // función suelta, no el método
  digitalWrite(_pin, HIGH);   // error: '_pin' was not declared
}

// Bien
void Rele::encender() {
  digitalWrite(_pin, HIGH);
}
```

A veces el error aparece como `'_pin' was not declared`, y si el cuerpo no usa miembros, como `undefined reference to Rele::encender()`. En los dos casos, revisá que esté el `Rele::`.

### Firma distinta entre declaración y definición

```cpp
// Mal
// riego.h
void regar(uint32_t duracionMs);
// riego.cpp
void regar(int duracionMs) { /* ... */ }   // otra función: regar(int)

// Bien: la misma firma en los dos lados
void regar(uint32_t duracionMs) { /* ... */ }
```

C++ permite varias funciones con el mismo nombre y distintos parámetros, así que `regar(int)` es una función distinta de `regar(uint32_t)`. El compilador no se queja, y el linker no encuentra la versión que recibe un `uint32_t`.

## Ejercicio

Un compañero dividió el control de ventilación en archivos y el build falla. Estos son los archivos:

```cpp ventilacion.h
#pragma once
#include <Arduino.h>

uint32_t aperturasHoy = 0;

bool hayQueVentilar(float temperatura) {
  return temperatura >= 30.0f;
}

class Ventilador {
public:
  void abrir();
};
```

```cpp ventilacion.cpp
#include "ventilacion.h"

void abrir() {
  digitalWrite(27, HIGH);
  aperturasHoy++;
}
```

```cpp controlador.ino
#include "ventilacion.h"

Ventilador ventilador;

void setup() {
  pinMode(27, OUTPUT);
}

void loop() {
  if (hayQueVentilar(31.0f)) {
    ventilador.abrir();
  }
}
```

¿Qué errores va a dar el linker? Corregí los archivos para que compile.

<details>
<summary>Pista</summary>

Hay dos definiciones en el header que se pegan en dos unidades de traducción, y un método que se declaró pero nunca se definió.

</details>

<details>
<summary>Ver solución</summary>

El linker va a dar tres errores: `multiple definition of aperturasHoy`, `multiple definition of hayQueVentilar(float)` (las dos están definidas en el header, que se incluye desde `ventilacion.cpp` y desde `controlador.ino`) y `undefined reference to Ventilador::abrir()` (en el `.cpp` falta `Ventilador::`).

```cpp ventilacion.h
#pragma once
#include <Arduino.h>

extern uint32_t aperturasHoy;

bool hayQueVentilar(float temperatura);

class Ventilador {
public:
  void abrir();
};
```

```cpp ventilacion.cpp
#include "ventilacion.h"

uint32_t aperturasHoy = 0;

bool hayQueVentilar(float temperatura) {
  return temperatura >= 30.0f;
}

void Ventilador::abrir() {
  digitalWrite(27, HIGH);
  aperturasHoy++;
}
```

`controlador.ino` no cambia. `hayQueVentilar` también podría haber quedado en el header como `inline bool hayQueVentilar(...)`, porque es corta. El `27` y el `30.0f` deberían venir de constantes en `config.h`, pero eso no causa errores de compilación.

</details>

## Resumen

- Declarar es decir que algo existe; definir es crearlo. Cada cosa se declara las veces que haga falta y se define una sola vez.
- Cada `.cpp` se compila por separado y solo necesita las declaraciones. El linker une las piezas al final.
- `was not declared` es del compilador: falta un `#include` o hay un error de tipeo. `undefined reference` y `multiple definition` son del linker.
- En el `.h` van prototipos, clases, `extern` y `constexpr`. En el `.cpp`, cuerpos y definiciones.
- Los métodos de una clase se definen en el `.cpp` con `Clase::metodo`.
