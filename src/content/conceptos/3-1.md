En [0.10](/conceptos/0-10) viste lo básico: conectarse con `WiFi.begin`, consultar el estado y hacer peticiones con `HTTPClient`. Un controlador instalado necesita más: reconectarse solo cuando el router se reinicia, distinguir "estoy conectado al WiFi" de "el backend me responde", no castigar a la red con reintentos sin pausa, y que el resto del firmware pueda preguntar "¿puedo enviar?" sin saber nada de WiFi. Todo eso se organiza en un **servicio de conectividad**: un módulo con su propia máquina de estados (ver [2.2](/conceptos/2-2)) que es el único que toca el WiFi.

## Por qué te importa

En un invernadero, la conectividad falla todo el tiempo y de muchas formas: el router se reinicia por un corte de luz, la señal baja cuando las plantas crecen y absorben más, el proveedor de internet se cae una tarde entera, el backend está en mantenimiento. Un controlador con conectividad frágil se queda "conectado" a una red sin salida, o queda intentando reconectar en un bucle que interrumpe todo, o deja de reconectarse después del primer corte.

El objetivo es que la comunicación se recupere sola de cualquiera de esas situaciones, sin intervención de nadie, y que mientras tanto el control del invernadero siga funcionando sin enterarse (ver [2.4](/conceptos/2-4)).

## Paso a paso

### 1. Tres niveles de "estar conectado"

| Nivel | Cómo se sabe | Qué puede fallar |
|---|---|---|
| Asociado al router | `WiFi.status() == WL_CONNECTED` | clave incorrecta, señal débil, router apagado |
| Con internet | se resuelve un nombre y hay respuesta | el router no tiene salida, DNS caído |
| Backend disponible | `GET /salud` responde 200 | servidor caído, en mantenimiento, certificado vencido |

El resto del firmware necesita saber el tercer nivel: si se puede enviar. Un servicio de conectividad lo verifica con una consulta liviana al backend cada cierto tiempo, y responde a una sola pregunta: `backendDisponible()`.

### 2. Eventos del WiFi

En lugar de consultar `WiFi.status()` todo el tiempo, el core avisa los cambios con **eventos**:

```cpp
WiFi.onEvent([](arduino_event_id_t evento, arduino_event_info_t info) {
  if (evento == ARDUINO_EVENT_WIFI_STA_GOT_IP) {
    // conectado y con IP
  } else if (evento == ARDUINO_EVENT_WIFI_STA_DISCONNECTED) {
    uint8_t motivo = info.wifi_sta_disconnected.reason;   // por qué se cortó
  }
});
```

El callback corre en la tarea de eventos del sistema, no en la tuya: igual que con las interrupciones, tiene que anotar lo que pasó y volver (ver [2.5](/conceptos/2-5)). El **motivo** de la desconexión es muy útil para diagnosticar: una clave incorrecta, un router que no se encuentra o una señal perdida tienen códigos distintos.

### 3. No reintentar en cada vuelta

Una conexión WiFi tarda de uno a varios segundos. Si se llama a `WiFi.begin` de nuevo antes de que termine, el intento en curso se cancela. El patrón correcto es: iniciar, esperar el resultado **con un tiempo máximo**, y si falla, esperar un rato antes de reintentar.

Además, por defecto el core puede guardar las credenciales en la flash en cada `WiFi.begin`. Con `WiFi.persistent(false)` se evitan esas escrituras, que desgastan la flash (ver [0.11](/conceptos/0-11)); las credenciales las maneja tu configuración.

### 4. Esperas crecientes entre reintentos

Si la conexión falla, el siguiente intento se espera 5 segundos; si vuelve a fallar, 10; después 20, y así hasta un máximo (por ejemplo, 5 minutos). Cuando la conexión se logra, la espera vuelve a 5. Esto es **backoff exponencial**: reacciona rápido a cortes breves, y no gasta energía ni castiga al router durante cortes largos. Se ve con detalle, junto con los reintentos de envíos, en [3.5](/conceptos/3-5).

### 5. La máquina de estados de la conectividad

```text
Desconectado ──► ConectandoWifi ──(IP)──► VerificandoBackend ──(200)──► Disponible
     ▲                 │                         │                          │
     │           (tiempo máximo)          (falla / sin respuesta)     (falla la verificación
     │                 ▼                         ▼                     o se cae el WiFi)
     └──────── EsperandoReintento ◄──────────────┴──────────────────────────┘
```

Cada estado tiene sus reglas y tiempos máximos, como en [2.2](/conceptos/2-2). En `Disponible`, el servicio repite la verificación de vez en cuando (y cada vez que un envío falla), para darse cuenta si el backend dejó de responder.

### 6. Una interfaz chica para el resto del sistema

```cpp
class ServicioConectividad {
public:
  void begin(const char* ssid, const char* clave);
  void actualizar();                 // llamar seguido desde la tarea de comunicación
  bool backendDisponible() const;
  void informarFallaDeEnvio();       // un envío falló: verificar de nuevo
  int rssi() const;
};
```

El reporte (ver [0.10](/conceptos/0-10)) solo pregunta `backendDisponible()` antes de intentar. La pantalla puede mostrar el estado. Nadie más llama a funciones de `WiFi`.

## Ejemplos

### Ejemplo 1. Ver los eventos del WiFi y sus motivos

Para conocer cómo se comporta la conexión en un lugar, conviene ver los eventos con sus motivos durante un rato.

```cpp eventos-wifi.ino
#include <WiFi.h>

volatile bool hayCambio = false;
volatile uint8_t ultimoMotivo = 0;
volatile bool conIp = false;

void setup() {
  Serial.begin(115200);
  WiFi.persistent(false);
  WiFi.mode(WIFI_STA);

  WiFi.onEvent([](arduino_event_id_t evento, arduino_event_info_t info) {
    if (evento == ARDUINO_EVENT_WIFI_STA_GOT_IP) {
      conIp = true;
      hayCambio = true;
    } else if (evento == ARDUINO_EVENT_WIFI_STA_DISCONNECTED) {
      conIp = false;
      ultimoMotivo = info.wifi_sta_disconnected.reason;   // solo anotar
      hayCambio = true;
    }
  });

  WiFi.begin("invernadero", "clave-del-wifi");
}

void loop() {
  if (hayCambio) {
    hayCambio = false;
    if (conIp) {
      Serial.printf("conectado: IP %s, señal %d dBm\n",
                    WiFi.localIP().toString().c_str(), WiFi.RSSI());
    } else {
      Serial.printf("desconectado, motivo %u\n", ultimoMotivo);
    }
  }
}
```

El callback solo anota; `loop()` imprime. Algunos motivos comunes: 201 (no se encontró la red), 15 (clave incorrecta durante el saludo inicial), 200 (se perdió la señal del router). Ver el motivo en el monitor serie ahorra mucho tiempo al diagnosticar en el lugar.

### Ejemplo 2. El servicio de conectividad

El servicio completo: máquina de estados, tiempo máximo de conexión, esperas crecientes y verificación del backend.

```cpp conectividad.ino
#include <WiFi.h>
#include <HTTPClient.h>

class ServicioConectividad {
public:
  enum class Estado : uint8_t { Desconectado, ConectandoWifi, VerificandoBackend, Disponible, EsperandoReintento };

  void begin(const char* ssid, const char* clave, const char* urlSalud) {
    _ssid = ssid;
    _clave = clave;
    _urlSalud = urlSalud;
    WiFi.persistent(false);
    WiFi.mode(WIFI_STA);
  }

  void actualizar() {
    uint32_t t = millis() - _desdeMs;
    switch (_estado) {
      case Estado::Desconectado:
        WiFi.begin(_ssid, _clave);
        cambiarA(Estado::ConectandoWifi);
        break;

      case Estado::ConectandoWifi:
        if (WiFi.status() == WL_CONNECTED) cambiarA(Estado::VerificandoBackend);
        else if (t > 15000) fallo("sin WiFi");
        break;

      case Estado::VerificandoBackend:
        if (backendResponde()) {
          _esperaMs = ESPERA_MINIMA_MS;             // éxito: reiniciar el backoff
          cambiarA(Estado::Disponible);
        } else {
          fallo("backend sin respuesta");
        }
        break;

      case Estado::Disponible:
        if (WiFi.status() != WL_CONNECTED) fallo("se perdió el WiFi");
        else if (_verificarPronto || t > 5UL * 60UL * 1000UL) {
          _verificarPronto = false;
          cambiarA(Estado::VerificandoBackend);
        }
        break;

      case Estado::EsperandoReintento:
        if (t >= _esperaMs) {
          _esperaMs = min(_esperaMs * 2, ESPERA_MAXIMA_MS);
          cambiarA(WiFi.status() == WL_CONNECTED ? Estado::VerificandoBackend : Estado::Desconectado);
        }
        break;
    }
  }

  bool backendDisponible() const { return _estado == Estado::Disponible; }
  void informarFallaDeEnvio() { _verificarPronto = true; }
  Estado estado() const { return _estado; }

private:
  static constexpr uint32_t ESPERA_MINIMA_MS = 5000;
  static constexpr uint32_t ESPERA_MAXIMA_MS = 5UL * 60UL * 1000UL;

  bool backendResponde() {
    HTTPClient http;
    http.begin(_urlSalud);
    http.setConnectTimeout(3000);
    http.setTimeout(3000);
    int codigo = http.GET();
    http.end();
    return codigo == 200;
  }

  void fallo(const char* motivo) {
    Serial.printf("conectividad: %s, reintento en %u s\n", motivo,
                  static_cast<unsigned>(_esperaMs / 1000));
    if (WiFi.status() != WL_CONNECTED) WiFi.disconnect();
    cambiarA(Estado::EsperandoReintento);
  }

  void cambiarA(Estado e) { _estado = e; _desdeMs = millis(); }

  const char* _ssid = nullptr;
  const char* _clave = nullptr;
  const char* _urlSalud = nullptr;
  Estado _estado = Estado::Desconectado;
  uint32_t _desdeMs = 0;
  uint32_t _esperaMs = ESPERA_MINIMA_MS;
  bool _verificarPronto = false;
};

ServicioConectividad conectividad;

void setup() {
  Serial.begin(115200);
  conectividad.begin("invernadero", "clave-del-wifi", "http://192.168.0.10:3000/salud");
}

void loop() {
  conectividad.actualizar();

  static bool anterior = false;
  if (conectividad.backendDisponible() != anterior) {
    anterior = conectividad.backendDisponible();
    Serial.println(anterior ? "backend disponible" : "backend NO disponible");
  }
}
```

La verificación del backend (`GET /salud`) tarda como mucho unos segundos y se hace cada 5 minutos o cuando un envío falla. Como hace una petición HTTP, este servicio va en la tarea de comunicación de [2.4](/conceptos/2-4), no en el `loop()` del control; acá está en `loop()` para que el ejemplo sea corto. La espera crece de 5 segundos a 5 minutos durante un corte largo, y vuelve a 5 segundos apenas se recupera.

### Ejemplo 3. La tarea de comunicación usando el servicio

La tarea de comunicación de [2.4](/conceptos/2-4), ahora apoyada en el servicio: solo intenta enviar cuando el backend está disponible, agrupa las lecturas pendientes en un solo envío, y le avisa al servicio si un envío falla.

```cpp tarea-comunicacion.ino
#include <WiFi.h>
#include <HTTPClient.h>

// ServicioConectividad: la clase del ejemplo 2

struct Lectura {
  uint32_t momentoS;
  float temperatura;
  float humedadSuelo;
};

QueueHandle_t colaEnvios = nullptr;
ServicioConectividad conectividad;

bool enviarLote(const Lectura* lote, size_t n) {
  char cuerpo[512];
  size_t usado = snprintf(cuerpo, sizeof(cuerpo), "[");
  for (size_t i = 0; i < n && usado < sizeof(cuerpo); i++) {
    usado += snprintf(cuerpo + usado, sizeof(cuerpo) - usado,
                      "%s{\"t\":%lu,\"temp\":%.1f,\"suelo\":%.0f}", i ? "," : "",
                      static_cast<unsigned long>(lote[i].momentoS), lote[i].temperatura,
                      lote[i].humedadSuelo);
  }
  if (usado + 2 > sizeof(cuerpo)) return false;            // no entró: lote demasiado grande
  snprintf(cuerpo + usado, sizeof(cuerpo) - usado, "]");

  HTTPClient http;
  http.begin("http://192.168.0.10:3000/api/invernaderos/2/lecturas");
  http.setConnectTimeout(3000);
  http.setTimeout(5000);
  http.addHeader("Content-Type", "application/json");
  int codigo = http.POST(cuerpo);
  http.end();
  return codigo >= 200 && codigo < 300;
}

void tareaComunicacion(void*) {
  constexpr size_t LOTE_MAXIMO = 8;
  Lectura lote[LOTE_MAXIMO];
  size_t n = 0;

  for (;;) {
    conectividad.actualizar();

    // juntar lo que haya en la cola, sin esperar
    while (n < LOTE_MAXIMO && xQueueReceive(colaEnvios, &lote[n], 0) == pdTRUE) n++;

    if (n > 0 && conectividad.backendDisponible()) {
      if (enviarLote(lote, n)) {
        n = 0;                                    // enviado
      } else {
        conectividad.informarFallaDeEnvio();      // el lote se conserva para el próximo intento
      }
    }
    vTaskDelay(pdMS_TO_TICKS(500));
  }
}

void setup() {
  Serial.begin(115200);
  colaEnvios = xQueueCreate(60, sizeof(Lectura));
  conectividad.begin("invernadero", "clave-del-wifi", "http://192.168.0.10:3000/salud");
  xTaskCreatePinnedToCore(tareaComunicacion, "comunicacion", 8192, nullptr, 1, nullptr, 0);
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 60000) {
    ultimo = millis();
    Lectura l{millis() / 1000, 24.5f, 41.0f};
    xQueueSend(colaEnvios, &l, 0);   // el control nunca espera a la red
  }
}
```

Mientras el backend no está disponible, las lecturas se acumulan en la cola (hasta una hora) y el lote en memoria. Cuando vuelve, se envían agrupadas, de a 8 por petición, lo que reduce mucho el tiempo de red. Si un envío falla, el servicio verifica el backend en la siguiente vuelta en lugar de esperar 5 minutos. Si el envío llegara al servidor pero se perdiera la respuesta, el lote se reenviaría: el backend tiene que poder detectar duplicados, como se ve en [3.5](/conceptos/3-5).

## Errores comunes

### Confundir WiFi con backend

```cpp
// Mal
if (WiFi.status() == WL_CONNECTED) enviar();   // ¿y si no hay internet?

// Bien
if (conectividad.backendDisponible()) enviar();
```

### `WiFi.begin` en cada vuelta

```cpp
// Mal
void loop() {
  if (WiFi.status() != WL_CONNECTED) WiFi.begin(ssid, clave);
}

// Bien: iniciar una vez, esperar con tiempo máximo, reintentar con backoff (ejemplo 2)
```

### Trabajo pesado en el callback de eventos

El callback de `WiFi.onEvent` corre en una tarea del sistema. Anotá el evento y reaccioná desde tu tarea.

### Reintentos sin espera ni máximo

Reintentar cada segundo durante un corte de una tarde son miles de intentos que no sirven y consumen energía. Con muchos equipos, además, todos golpean al backend juntos cuando vuelve. Backoff con máximo.

### Todo el firmware tocando el WiFi

Si la pantalla, el reporte y la OTA llaman cada uno a `WiFi.status()` y a `WiFi.reconnect()`, se pisan entre sí. Un solo servicio maneja la conexión; los demás preguntan.

## Ejercicio

Este código maneja la conexión del controlador. En un invernadero con internet inestable, el equipo deja de enviar datos después del primer corte y no se recupera hasta que alguien lo reinicia. Además, cuando el router está apagado, la pantalla se congela. Encontrá los problemas y describí cómo los resuelve el servicio del ejemplo 2.

```cpp conexion-fragil.ino
void setup() {
  WiFi.begin("invernadero", "clave");
  while (WiFi.status() != WL_CONNECTED) delay(500);
}

void loop() {
  actualizarPantalla();
  if (WiFi.status() != WL_CONNECTED) {
    WiFi.begin("invernadero", "clave");
    while (WiFi.status() != WL_CONNECTED) delay(500);
  }
  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 60000) {
    ultimo = millis();
    if (!enviarLectura()) {
      Serial.println("falló el envío");
    }
  }
}
```

<details>
<summary>Pista</summary>

Mirá los dos `while`, qué pasa cuando el WiFi está bien pero internet no, y qué se hace con la lectura que no se pudo enviar.

</details>

<details>
<summary>Ver solución</summary>

1. **Esperas infinitas**: los dos `while (WiFi.status() != WL_CONNECTED) delay(500);` bloquean todo mientras no haya WiFi. Con el router apagado, la pantalla se congela y el control se detiene. El servicio inicia la conexión y vuelve enseguida, con un tiempo máximo de 15 segundos por intento, y todo eso corre en la tarea de comunicación, no en el `loop()` del control.
2. **Solo mira el WiFi**: cuando el router sigue conectado pero internet se cae, `WiFi.status()` sigue en `WL_CONNECTED`, así que el código nunca reintenta nada y los envíos fallan para siempre. Ese es el "deja de enviar después del primer corte". El servicio verifica el backend con `GET /salud` periódicamente y cuando un envío falla.
3. **Reintento sin pausa**: si el WiFi se cae, llama a `WiFi.begin` y espera; si nunca vuelve, queda trabado. El servicio espera cada vez más entre intentos, hasta 5 minutos.
4. **Lecturas perdidas**: la lectura que no se pudo enviar se descarta. Con la cola de [2.4](/conceptos/2-4) y el lote del ejemplo 3, se conserva y se envía cuando vuelve el backend.

</details>

## Resumen

- Hay tres niveles: asociado al router, con internet, y backend disponible. El resto del firmware necesita el tercero.
- Un servicio de conectividad, con su máquina de estados, es el único que toca el WiFi; los demás preguntan `backendDisponible()`.
- Iniciar la conexión una vez y esperar con tiempo máximo; reintentar con esperas crecientes hasta un máximo. `WiFi.persistent(false)` evita escrituras en la flash.
- Los eventos de `WiFi.onEvent` dicen qué pasó y por qué; el callback solo anota.
- La comunicación va en su propia tarea, agrupa envíos y conserva lo que no se pudo enviar.
