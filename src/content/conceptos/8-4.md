En el modelo habitual, una tabla guarda el **estado actual**: la fila de la zona 4 dice que su umbral mínimo es 38 %. Cuando cambia, se pisa el valor anterior. **Event sourcing** invierte esto: lo que se guarda es la **secuencia de eventos** que ocurrieron ("se creó la zona con 35 %", "se cambió a 30 %", "se cambió a 38 %"), en una tabla donde solo se agregan filas. El estado actual es un resultado: se calcula aplicando los eventos en orden. Como nada se pisa, el sistema puede responder qué pasó, cuándo, y cómo estaba todo en cualquier momento del pasado.

## Por qué te importa

En el invernadero hay preguntas que el estado actual no responde. "¿Qué umbral tenía la zona 4 el día que se secaron los almácigos?" "¿Quién desactivó el riego automático y cuándo lo volvió a activar?" "¿Cuántas veces se cambió la configuración este mes?" Ya viste dos respuestas parciales: el registro de auditoría de [4.2](/conceptos/4-2) y la configuración con historial de [5.3](/conceptos/5-3). Event sourcing lleva la idea al extremo: la historia es la fuente de verdad, y todo lo demás se deriva de ella. Conocerlo te ayuda a decidir hasta dónde ir.

## Cómo funciona

*Los eventos* son hechos en pasado, con nombre del negocio (`umbrales_cambiados`, `riego_iniciado`, `riego_terminado`), los datos del cambio, el momento y quién lo hizo. Nunca se modifican ni se borran.

*El estado* se reconstruye con una función que recorre los eventos de una entidad y aplica cada uno. Para no recorrer miles de eventos cada vez, se guardan **instantáneas** (*snapshots*) cada tanto, y se aplican solo los eventos posteriores.

*Las proyecciones* son tablas de lectura que se actualizan a medida que llegan eventos: el estado actual de cada zona, el consumo por día, la lista de cambios recientes. Es la combinación natural con CQRS (ver [8.3](/conceptos/8-3)): los eventos son el modelo de escritura y las proyecciones, el de lectura. Si una proyección tiene un bug, se borra y se recalcula desde los eventos.

*La concurrencia* se maneja con un número de versión por entidad: un evento nuevo se guarda solo si la versión es la siguiente a la última que leíste. Si otro pedido se adelantó, el tuyo falla y se reintenta con el estado nuevo.

## Ejemplo

Los eventos de configuración de una zona, y la función que reconstruye su estado en cualquier momento:

```sql eventos.sql
CREATE TABLE eventos_zona (
  zona_id          BIGINT NOT NULL,
  version          INTEGER NOT NULL,          -- 1, 2, 3... por zona
  tipo             TEXT NOT NULL,
  datos            JSONB NOT NULL,
  momento          TIMESTAMPTZ NOT NULL DEFAULT now(),
  usuario_id       BIGINT,
  PRIMARY KEY (zona_id, version)             -- dos eventos con la misma versión: uno falla
);
```

```js estado-zona.js
function aplicar(estado, evento) {
  switch (evento.tipo) {
    case "zona_creada":
      return { ...evento.datos, riegoAutomatico: true };
    case "umbrales_cambiados":
      return { ...estado, ...evento.datos };
    case "riego_automatico_desactivado":
      return { ...estado, riegoAutomatico: false };
    case "riego_automatico_activado":
      return { ...estado, riegoAutomatico: true };
    default:
      return estado;                         // eventos que esta versión no conoce
  }
}

// eventos ordenados por versión; sin "hasta", el estado actual
function estadoEn(eventos, hasta) {
  return eventos
    .filter((e) => !hasta || new Date(e.momento) <= hasta)
    .reduce(aplicar, undefined);
}

module.exports = { aplicar, estadoEn };

// estadoEn(eventos)                                  -> el estado actual
// estadoEn(eventos, new Date("2026-03-03T23:59:59Z")) -> cómo estaba el 3 de marzo
```

Responder "¿qué umbral había el día que se secaron los almácigos?" es llamar a `estadoEn` con esa fecha. La clave primaria `(zona_id, version)` resuelve la concurrencia: dos pedidos que leyeron la versión 7 intentan guardar la 8, y la base rechaza al segundo. `aplicar` ignora los tipos que no conoce, así un evento nuevo no rompe el código viejo. Con pocos eventos por zona, reconstruir desde cero es instantáneo; con miles, se agregan instantáneas.

## Cuándo sí y cuándo no

Conviene cuando:

- la historia es un requisito del negocio (auditoría estricta, regulaciones, "¿cómo estaba en tal fecha?"),
- se necesitan muchas vistas distintas de los mismos hechos, y poder recalcularlas,
- el dominio ya se piensa en términos de eventos ("se inició el riego", "se agotó el cupo").

No conviene cuando:

- alcanza con saber el estado actual, más una tabla de auditoría para las acciones importantes (el caso más común),
- el equipo no tiene experiencia: versionar los eventos, mantener proyecciones y corregir datos sin `UPDATE` es trabajo permanente,
- los datos personales tienen que poder borrarse de verdad: con eventos inmutables, requiere técnicas especiales.

Un punto medio muy útil: tablas normales para el estado, y una tabla de historial o de eventos solo para lo que necesita historia, como la configuración de riego.

## Resumen

- Event sourcing guarda la secuencia de eventos; el estado actual se calcula aplicándolos en orden.
- Los eventos son inmutables: las correcciones son eventos nuevos.
- Permite reconstruir el estado en cualquier momento del pasado y recalcular proyecciones.
- Se combina con CQRS: los eventos para escribir, las proyecciones para leer.
- Cuesta mantenerlo; para la mayoría de los casos alcanza con estado actual más auditoría o historial.
