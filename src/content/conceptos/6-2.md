La interfaz (la app, la página web, la pantalla del controlador) **muestra** lo que cada usuario puede hacer; el backend **decide** lo que puede hacer. Ocultar el botón "eliminar usuario" a un operario es una ayuda para que no se equivoque, pero no le impide nada: cualquiera puede mandar el mismo pedido HTTP con `curl`, con las herramientas del navegador o con un script. Por eso cada ruta verifica en el servidor, en cada pedido, tres cosas: quién es, si su rol le permite la acción, y si el objeto que toca le pertenece. Y trata todo lo demás que viene del cliente (la URL, el cuerpo, los encabezados) como algo que el usuario pudo haber escrito a mano.

## Por qué te importa

En [4.2](/conceptos/4-2) armaste RBAC: roles, permisos y un middleware `requierePermiso` en cada ruta. En [4.1](/conceptos/4-1), el filtro por organización. Esta lección es sobre los huecos que quedan aunque eso exista, que son los más comunes en las APIs reales:

- una ruta que verifica el permiso pero no de quién es el objeto, y un operario modifica una zona de otro productor cambiando un número en la URL;
- una ruta que guarda todo lo que llega en el cuerpo, y alguien se agrega un campo que la app nunca manda;
- un límite que solo existe en la interfaz, y alguien pide un riego de un día entero.

Ninguno se ve usando la app normalmente. Todos se encuentran en cinco minutos con un `curl`.

## Paso a paso

### 1. El cliente lo controla el usuario

Todo lo que llega en un pedido lo puede elegir quien lo envía: la ruta y sus parámetros, el cuerpo, los encabezados, las cookies. La app que vos escribiste es solo una forma de mandar pedidos; hay infinitas otras. Lo único confiable es lo que el backend obtiene por su cuenta: la sesión verificada, la membresía leída de la base, el dueño de un objeto según la base.

### 2. Tres verificaciones en cada pedido

1. Autenticación: ¿quién es? Si no se sabe, `401`.
2. Permiso de la acción: ¿su rol le permite `riego.accionar`? Si no, `403`. Es lo que hace `requierePermiso` (ver [4.2](/conceptos/4-2)).
3. Acceso al objeto: ¿el invernadero, la zona o la alarma que toca son de su organización? Si no, `404`.

La tercera es la que más se olvida. Tiene nombre propio: IDOR (*Insecure Direct Object Reference*), o BOLA (*Broken Object Level Authorization*), y encabeza la lista de problemas de seguridad de APIs de OWASP. Ocurre cuando una ruta recibe un identificador y lo usa sin preguntar de quién es.

### 3. Cada identificador de la URL se verifica

En una ruta como `/invernaderos/:invId/zonas/:zonaId` hay dos objetos. Verificar el invernadero no alcanza: la zona también tiene que ser de ese invernadero, y de la organización. La forma más segura es que la consulta que lee o modifica el objeto incluya la condición de pertenencia, así no hay un paso que se pueda olvidar:

```sql
UPDATE zonas SET nombre = $1
 WHERE id = $2 AND invernadero_id = $3 AND organizacion_id = $4
```

Si no modificó ninguna fila, el objeto no existe para ese usuario: `404`. El repositorio de [4.1](/conceptos/4-1) y la seguridad a nivel de fila de PostgreSQL son formas de que esa condición esté siempre.

### 4. Solo los campos que esa ruta permite

Copiar el cuerpo del pedido a la base de datos (`UPDATE ... SET` con todas las claves que llegaron) deja que el usuario decida qué columnas cambia. Se llama **asignación masiva** (*mass assignment*). Cada ruta tiene una lista explícita de campos permitidos, y el resto se ignora o se rechaza. Los campos que definen el acceso (`organizacion_id`, `rol`, `usuario_id`) nunca vienen del cuerpo: salen de la sesión o de la base (ver [3.4](/conceptos/3-4) y [4.3](/conceptos/4-3)).

### 5. Los límites de la interfaz se repiten en el backend

Un deslizador de 10 a 600 segundos, un campo deshabilitado, un menú con tres opciones, una validación en el formulario: todo eso mejora la experiencia, y nada de eso llega al servidor como garantía. Cada límite que importa se verifica en la ruta (ver [6.3](/conceptos/6-3)).

### 6. 404 en lugar de 403 para objetos ajenos

Si un usuario pide un invernadero de otra organización y la respuesta es `403`, le estás confirmando que existe. Con identificadores consecutivos, puede recorrerlos y contar cuántos clientes tenés. Para objetos fuera de su organización, la respuesta es la misma que si no existieran: `404`. El `403` queda para acciones que su rol no permite sobre objetos que sí puede ver.

### 7. Probar la autorización

Un error de autorización no rompe nada visible: la app sigue funcionando. Solo se detecta probándolo a propósito. Una tabla de pruebas automáticas que recorra rutas por roles, más casos con objetos de otra organización, convierte cada hueco en un test que falla.

## Ejemplos

### Ejemplo 1. Verificar todos los objetos de la ruta

La ruta de zonas del paso 3, completa. La condición de pertenencia va dentro de la misma consulta que modifica.

```js rutas-zonas.js
const express = require("express");
const { requierePermiso } = require("./autorizacion");   // 4.2
const { auditar } = require("./sesion");                 // 4.2

const router = express.Router();

function idValido(texto) {
  const n = Number(texto);
  return Number.isSafeInteger(n) && n > 0 ? n : null;
}

router.put("/api/invernaderos/:invId/zonas/:zonaId", requierePermiso("config.editar"), async (req, res) => {
  const invId = idValido(req.params.invId);
  const zonaId = idValido(req.params.zonaId);
  if (!invId || !zonaId) return res.status(404).json({ error: "zona no encontrada" });

  const nombre = typeof req.body.nombre === "string" ? req.body.nombre.trim() : "";
  if (nombre.length < 1 || nombre.length > 60) {
    return res.status(400).json({ error: "el nombre tiene entre 1 y 60 caracteres" });
  }

  const { rowCount } = await req.db.query(
    `UPDATE zonas SET nombre = $1
      WHERE id = $2 AND invernadero_id = $3 AND organizacion_id = $4`,
    [nombre, zonaId, invId, req.usuario.organizacion_id]
  );
  if (rowCount === 0) return res.status(404).json({ error: "zona no encontrada" });

  await auditar(req, "zonas.renombrar", { zona: zonaId, nombre });
  res.json({ ok: true });
});

module.exports = router;
```

Qué observar: la organización sale de `req.usuario`, que cargó el backend desde la membresía; nada en la URL ni en el cuerpo la puede cambiar. Una zona de otro invernadero, de otra organización o inexistente dan el mismo `404`. Los identificadores que no son números se cortan antes de llegar a la base (si no, PostgreSQL rechazaría la consulta con un error 500). El largo del nombre coincide con la restricción de la tabla de [5.1](/conceptos/5-1): la base es la última barrera, pero el usuario recibe un mensaje claro antes.

### Ejemplo 2. Lista de campos permitidos

El perfil de un usuario tiene columnas que el propio usuario puede editar (nombre, teléfono, preferencias de aviso) y otras que no (email verificado, si es personal de soporte, fechas de alta). La ruta toma solo las permitidas:

```js perfil.js
const CAMPOS_EDITABLES = {
  nombre: (v) => typeof v === "string" && v.trim().length >= 1 && v.length <= 80,
  telefono: (v) => v === null || (typeof v === "string" && /^\+?[0-9 ]{6,20}$/.test(v)),
  avisos_por_correo: (v) => typeof v === "boolean",
};

function elegirCampos(cuerpo) {
  const cambios = {};
  for (const [campo, esValido] of Object.entries(CAMPOS_EDITABLES)) {
    if (Object.hasOwn(cuerpo, campo)) {
      if (!esValido(cuerpo[campo])) return { error: `${campo} inválido` };
      cambios[campo] = cuerpo[campo];
    }
  }
  const desconocidos = Object.keys(cuerpo).filter((c) => !Object.hasOwn(CAMPOS_EDITABLES, c));
  if (desconocidos.length > 0) return { error: `campos no editables: ${desconocidos.join(", ")}` };
  return { cambios };
}

router.patch("/api/perfil", async (req, res) => {
  const cuerpo = req.body && typeof req.body === "object" ? req.body : {};
  const { cambios, error } = elegirCampos(cuerpo);
  if (error) return res.status(400).json({ error });

  const columnas = Object.keys(cambios);           // solo nombres de CAMPOS_EDITABLES
  if (columnas.length === 0) return res.json({ ok: true });
  const asignaciones = columnas.map((c, i) => `${c} = $${i + 2}`).join(", ");

  await req.db.query(
    `UPDATE usuarios SET ${asignaciones} WHERE id = $1`,
    [req.usuario.id, ...columnas.map((c) => cambios[c])]
  );
  res.json({ ok: true });
});

// elegirCampos({ nombre: "Ana" })                     -> { cambios: { nombre: "Ana" } }
// elegirCampos({ nombre: "Ana", es_soporte: true })   -> { error: "campos no editables: es_soporte" }
```

Los nombres de columna que se interpolan en el `UPDATE` salen de `CAMPOS_EDITABLES`, nunca del cuerpo: si salieran del cuerpo, además de la asignación masiva habría una inyección de SQL a través del nombre de la columna. El usuario que se modifica es `req.usuario.id`: la ruta no recibe un `id` porque cada uno edita solo su perfil. Rechazar los campos desconocidos (en lugar de ignorarlos) ayuda a detectar errores en la app y pedidos armados a mano.

### Ejemplo 3. Una tabla de pruebas de autorización

Con `node:test` y `supertest`, se recorren las rutas con cada rol, y se agregan los casos de otra organización. Las funciones `crearApp` y `sesionDePrueba` son del proyecto: la segunda crea un usuario con una membresía en la base de pruebas y devuelve su cookie de sesión. En los datos de prueba, el invernadero 2 es de la organización 1 y el 9 de la organización 3.

```js autorizacion.test.js
const test = require("node:test");
const assert = require("node:assert");
const request = require("supertest");
const { crearApp } = require("../app");
const { sesionDePrueba } = require("./ayudas");

const ROLES = ["solo_lectura", "operario", "admin"];
const CASOS = [
  // método, ruta, roles que pueden
  ["get", "/api/invernaderos/2/lecturas", ["solo_lectura", "operario", "admin"]],
  ["post", "/api/invernaderos/2/riego", ["operario", "admin"]],
  ["put", "/api/invernaderos/2/config", ["admin"]],
  ["post", "/api/usuarios", ["admin"]],
];

const app = crearApp();

for (const [metodo, ruta, pueden] of CASOS) {
  for (const rol of ROLES) {
    const permitido = pueden.includes(rol);
    test(`${rol} ${metodo.toUpperCase()} ${ruta} -> ${permitido ? "permitido" : "403"}`, async () => {
      const cookie = await sesionDePrueba({ rol, organizacionId: 1 });
      const res = await request(app)[metodo](ruta).set("Cookie", cookie).send({});
      if (permitido) assert.notStrictEqual(res.status, 403);
      else assert.strictEqual(res.status, 403);
    });
  }
}

test("un admin de la organización 1 no ve el invernadero 9 (organización 3)", async () => {
  const cookie = await sesionDePrueba({ rol: "admin", organizacionId: 1 });
  const res = await request(app).get("/api/invernaderos/9/lecturas").set("Cookie", cookie);
  assert.strictEqual(res.status, 404);
});

test("sin sesión, 401", async () => {
  const res = await request(app).post("/api/invernaderos/2/riego").send({ segundos: 60 });
  assert.strictEqual(res.status, 401);
});
```

En los casos permitidos, la prueba solo exige que la respuesta no sea `403`: con un cuerpo vacío, la ruta puede responder `400` por la validación, y eso está bien, porque significa que pasó la autorización. Cada ruta nueva agrega una fila a `CASOS`. El caso del admin es el más importante: tiene todos los permisos, y aun así no puede tocar lo que no es de su organización.

## Errores comunes

### Verificar el permiso y no el objeto

```js
// Mal: un operario puede reconocer alarmas de cualquier organización
await req.db.query("UPDATE alarmas SET reconocida = now(), reconocida_por = $2 WHERE id = $1",
                   [alarmaId, req.usuario.id]);

// Bien
await req.db.query(
  `UPDATE alarmas SET reconocida = now(), reconocida_por = $2
    WHERE id = $1 AND organizacion_id = $3 AND reconocida IS NULL`,
  [alarmaId, req.usuario.id, req.usuario.organizacion_id]);
```

### Tomar del cuerpo lo que define el acceso

```js
// Mal: el cliente dice a qué organización pertenece
const organizacionId = req.body.organizacion_id;

// Bien: lo dice la membresía que cargó el backend
const organizacionId = req.usuario.organizacion_id;
```

### Confiar en lo que la interfaz no deja hacer

Un botón oculto, un campo deshabilitado o un deslizador con límites no protegen nada. Cada ruta verifica su permiso (ver [4.2](/conceptos/4-2)) y sus límites, aunque la app nunca mande algo fuera de ellos.

### Copiar el cuerpo entero a la base

`Object.assign(usuario, req.body)` o un `UPDATE` armado con todas las claves del cuerpo le dan al cliente el control de las columnas. Lista de campos permitidos por ruta.

### Decir que existe lo que no puede ver

Un `403` para un objeto de otra organización confirma que existe. `404`, igual que si no existiera.

<summary>Ver solución</summary>

1. No verifica el objeto: actualiza cualquier alarma por su `id`, aunque sea de otra organización.
2. Hay asignación masiva: el cliente elige las columnas. Puede cambiar `tipo`, `organizacion_id` o `invernadero_id`, poner `reconocida_por` con el id de otro usuario (la auditoría miente), o "des-reconocer" una alarma.

Además, la hora y el usuario los pone el cliente, cuando los tiene que poner el servidor.

```js reconocer-alarma.js
router.post("/api/alarmas/:id/reconocer", requierePermiso("alarmas.reconocer"), async (req, res) => {
  const id = Number(req.params.id);
  if (!Number.isSafeInteger(id) || id <= 0) return res.status(404).json({ error: "alarma no encontrada" });

  const { rowCount } = await req.db.query(
    `UPDATE alarmas SET reconocida = now(), reconocida_por = $2
      WHERE id = $1 AND organizacion_id = $3 AND reconocida IS NULL`,
    [id, req.usuario.id, req.usuario.organizacion_id]
  );
  if (rowCount === 0) {
    return res.status(404).json({ error: "alarma no encontrada o ya reconocida" });
  }
  await auditar(req, "alarmas.reconocer", { alarma: id });
  res.json({ ok: true });
});
```

La ruta ahora es una acción (`POST .../reconocer`) que no recibe ningún campo: el servidor sabe qué columnas cambiar, con qué hora y por quién. `reconocida IS NULL` hace que reconocer dos veces no pise al primero que la reconoció, lo que también hace que repetir el pedido no cambie nada.

## Resumen

- La interfaz muestra lo que cada usuario puede hacer; el backend lo decide. Todo lo que llega en un pedido lo pudo escribir el usuario.
- Cada pedido verifica quién es, si su rol permite la acción y si cada objeto que toca es de su organización.
- La condición de pertenencia va dentro de la consulta que lee o modifica; si no hay filas, `404`.
- Cada ruta acepta una lista explícita de campos; lo que define el acceso sale de la sesión y de la base, nunca del cuerpo.
- Los límites de la interfaz se repiten en el backend, y la autorización se prueba con una tabla de rutas por roles.
