El backend del invernadero no es de un solo productor: atiende a **varias organizaciones** (productores, cooperativas, empresas), cada una con sus invernaderos, sus equipos y sus usuarios. A cada una de esas organizaciones se la llama **tenant** (inquilino), y un sistema que atiende a varias desde la misma instalación es **multi-tenant**. El requisito central es el **aislamiento**: ningún usuario ni equipo de una organización puede ver ni modificar datos de otra, aunque todos compartan el mismo servidor y la misma base de datos.

## Por qué te importa

En un sistema multi-tenant, el error más grave no es que algo falle: es que un productor vea las lecturas, los rendimientos o la configuración de su competidor. Ese tipo de error suele venir de un detalle chico, una consulta a la que le faltó un `WHERE`, o una ruta que confió en un número de la URL, y puede pasar desapercibido mucho tiempo.

Por eso el aislamiento no puede depender de que cada desarrollador se acuerde, en cada consulta, de filtrar por organización. Tiene que estar en el diseño: en el modelo de datos, en una capa de acceso que filtre siempre, y en una red de seguridad de la base de datos para cuando todo lo demás falle.

## Paso a paso

### 1. Tres formas de separar a los tenants

| Estrategia | Cómo es | A favor | En contra |
|---|---|---|---|
| Una base de datos por organización | cada cliente, su base | aislamiento total | muchas bases que mantener, migrar y respaldar |
| Un esquema por organización | una base, un esquema (`org_3.lecturas`) por cliente | buen aislamiento | migraciones repetidas por esquema, muchos objetos |
| Tablas compartidas | todas las organizaciones en las mismas tablas, con `organizacion_id` | simple de operar, escala a muchas organizaciones | el aislamiento depende de filtrar bien |

Para un sistema con muchas organizaciones chicas o medianas, como este, lo habitual son las **tablas compartidas**. El resto de la lección muestra cómo hacer que su punto débil (el filtro) sea confiable.

### 2. `organizacion_id` en el modelo de datos

Cada tabla con datos de un cliente lleva la organización a la que pertenece:

```text
organizaciones ─┬─< invernaderos ─┬─< dispositivos
                │                 └─< lecturas
                └─< membresias >─── usuarios
```

Las lecturas, los invernaderos y los dispositivos tienen `organizacion_id`. Aunque la organización de una lectura se podría deducir del dispositivo, tenerla en la propia tabla hace que filtrar, indexar (ver [4.5](/conceptos/4-5)) y aplicar políticas sea directo.

Para que la columna nunca contradiga las relaciones, se usan **claves foráneas compuestas**: un dispositivo no solo apunta a un invernadero, apunta a "ese invernadero de esa organización". La base de datos rechaza un dispositivo cuyo invernadero sea de otra organización.

### 3. La organización sale de la autenticación

La regla de oro: **la organización de un pedido se deduce de quién lo hace, nunca de lo que dice el pedido**.

- Para un equipo, de su clave (ver [3.4](/conceptos/3-4)): el middleware deja `req.equipo.organizacion_id`.
- Para un usuario, de su sesión y su membresía: `req.usuario.organizacion_id` (y su rol, ver [4.2](/conceptos/4-2)).

Un número de organización en la URL (`/organizaciones/7/...`) o en el cuerpo (`"organizacionId": 7`) es solo lo que el cliente **dice**. Se puede usar para saber qué pidió, pero siempre se compara con la organización autenticada.

### 4. Una capa de acceso que siempre filtra

En lugar de escribir el `WHERE organizacion_id = $1` en cada ruta, las consultas pasan por un módulo que lo agrega siempre:

```js
function repositorioDe(db, organizacionId) {
  return {
    invernaderos: () =>
      db.query("SELECT id, nombre FROM invernaderos WHERE organizacion_id = $1", [organizacionId]),
    invernadero: (id) =>
      db.query("SELECT id, nombre FROM invernaderos WHERE organizacion_id = $1 AND id = $2",
               [organizacionId, id]),
  };
}
```

Las rutas reciben un repositorio ya atado a la organización autenticada y no pueden pedir datos de otra: no tienen cómo pasarle una organización distinta.

### 5. Row Level Security: la red de seguridad

PostgreSQL permite definir **políticas por fila** (*Row Level Security*, RLS): reglas que la propia base aplica a toda consulta sobre una tabla, sin importar quién la escribió.

```sql
ALTER TABLE lecturas ENABLE ROW LEVEL SECURITY;

CREATE POLICY aislamiento_por_organizacion ON lecturas
  USING (organizacion_id = current_setting('app.organizacion_id')::bigint);
```

Antes de cada pedido, el backend le dice a la base de qué organización es (`set_config('app.organizacion_id', ...)`), y a partir de ahí, aunque una consulta olvide el filtro, solo ve las filas de esa organización. Es una segunda línea de defensa, no un reemplazo de la primera. Dos detalles importan: el backend tiene que conectarse con un usuario de base de datos que **no sea el dueño** de las tablas (los dueños, por defecto, no están sujetos a las políticas), y la configuración tiene que valer solo para la transacción del pedido.

### 6. IDs que no se pueden recorrer

Si los IDs son secuenciales y una ruta olvida verificar la organización, basta con probar `/invernaderos/41`, `/42`, `/43` para encontrar datos ajenos. A ese tipo de falla se la llama **IDOR** (*Insecure Direct Object Reference*). La defensa principal es verificar siempre la pertenencia; usar identificadores no adivinables (como UUID) en las URLs públicas reduce el daño cuando algo se escapa.

## Ejemplos

### Ejemplo 1. El modelo de datos

```sql modelo.sql
CREATE TABLE organizaciones (
  id      BIGSERIAL PRIMARY KEY,
  nombre  TEXT NOT NULL
);

CREATE TABLE invernaderos (
  id               BIGSERIAL PRIMARY KEY,
  organizacion_id  BIGINT NOT NULL REFERENCES organizaciones(id),
  nombre           TEXT NOT NULL,
  UNIQUE (organizacion_id, id)              -- permite claves foráneas compuestas
);

CREATE TABLE dispositivos (
  id               BIGSERIAL PRIMARY KEY,
  organizacion_id  BIGINT NOT NULL,
  invernadero_id   BIGINT NOT NULL,
  tipo             TEXT NOT NULL CHECK (tipo IN ('controlador', 'nodo')),
  clave_hash       TEXT NOT NULL UNIQUE,
  revocado         BOOLEAN NOT NULL DEFAULT false,
  -- el invernadero tiene que ser de la misma organización
  FOREIGN KEY (organizacion_id, invernadero_id) REFERENCES invernaderos (organizacion_id, id),
  UNIQUE (organizacion_id, id)
);

CREATE TABLE lecturas (
  id_envio         TEXT PRIMARY KEY,
  organizacion_id  BIGINT NOT NULL,
  dispositivo_id   BIGINT NOT NULL,
  momento          TIMESTAMPTZ NOT NULL,
  temperatura      NUMERIC(4,1),
  humedad_suelo    SMALLINT,
  FOREIGN KEY (organizacion_id, dispositivo_id) REFERENCES dispositivos (organizacion_id, id)
);
```

`BIGSERIAL` es un entero de 64 bits que se autoincrementa. La restricción `UNIQUE (organizacion_id, id)` en invernaderos y dispositivos existe para que otras tablas puedan referenciarlos por el par. Con eso, es imposible guardar un dispositivo de la organización 3 en un invernadero de la 7, o una lectura de la organización 3 con un dispositivo de la 7: la base de datos lo rechaza.

### Ejemplo 2. Rutas que nunca reciben la organización del cliente

Un middleware arma un repositorio atado a la organización del usuario autenticado. Las rutas solo usan ese repositorio.

```js repositorio.js
// Todas las consultas filtran por la organización con la que se creó el repositorio
function repositorioDe(db, organizacionId) {
  return {
    async invernaderos() {
      const { rows } = await db.query(
        "SELECT id, nombre FROM invernaderos WHERE organizacion_id = $1 ORDER BY nombre",
        [organizacionId]
      );
      return rows;
    },

    async invernadero(id) {
      const { rows } = await db.query(
        "SELECT id, nombre FROM invernaderos WHERE organizacion_id = $1 AND id = $2",
        [organizacionId, id]
      );
      return rows[0] || null;
    },

    async lecturasDeInvernadero(invernaderoId, desde) {
      const { rows } = await db.query(
        `SELECT l.momento, l.temperatura, l.humedad_suelo
           FROM lecturas l
           JOIN dispositivos d ON d.organizacion_id = l.organizacion_id AND d.id = l.dispositivo_id
          WHERE l.organizacion_id = $1 AND d.invernadero_id = $2 AND l.momento >= $3
          ORDER BY l.momento`,
        [organizacionId, invernaderoId, desde]
      );
      return rows;
    },
  };
}

module.exports = { repositorioDe };
```

```js rutas.js
const express = require("express");
const { repositorioDe } = require("./repositorio");

const router = express.Router();

// Después de autenticar al usuario (sesión), req.usuario tiene su organización
router.use((req, res, next) => {
  req.repo = repositorioDe(req.db, req.usuario.organizacion_id);
  next();
});

router.get("/invernaderos", async (req, res) => {
  res.json(await req.repo.invernaderos());
});

router.get("/invernaderos/:id/lecturas", async (req, res) => {
  const invernadero = await req.repo.invernadero(req.params.id);
  if (!invernadero) {
    return res.status(404).json({ error: "invernadero no encontrado" });   // ajeno o inexistente: igual
  }
  const desde = req.query.desde || new Date(Date.now() - 24 * 3600 * 1000).toISOString();
  res.json(await req.repo.lecturasDeInvernadero(invernadero.id, desde));
});

module.exports = router;
```

Las URLs ya no llevan la organización: sale de la sesión. Si el usuario pide un invernadero que existe pero es de otra organización, recibe un 404, igual que si no existiera: así no se revela qué IDs existen. En el `JOIN`, la condición incluye la organización en los dos lados, para que ni siquiera un dato mal cargado cruce organizaciones. `req.db` es el *pool* de conexiones de PostgreSQL (librería `pg`), que un middleware anterior deja en cada pedido.

### Ejemplo 3. Row Level Security como segunda línea

Las políticas de PostgreSQL ocultan las filas de otras organizaciones a cualquier consulta, incluso a una que alguien escribió por fuera del repositorio.

```sql politicas.sql
-- El backend se conecta con este rol, que NO es dueño de las tablas
CREATE ROLE backend_app LOGIN PASSWORD '...';
GRANT SELECT, INSERT, UPDATE, DELETE ON invernaderos, dispositivos, lecturas TO backend_app;

ALTER TABLE invernaderos ENABLE ROW LEVEL SECURITY;
ALTER TABLE dispositivos ENABLE ROW LEVEL SECURITY;
ALTER TABLE lecturas     ENABLE ROW LEVEL SECURITY;

CREATE POLICY por_organizacion ON invernaderos
  USING (organizacion_id = current_setting('app.organizacion_id', true)::bigint);
CREATE POLICY por_organizacion ON dispositivos
  USING (organizacion_id = current_setting('app.organizacion_id', true)::bigint);
CREATE POLICY por_organizacion ON lecturas
  USING (organizacion_id = current_setting('app.organizacion_id', true)::bigint)
  WITH CHECK (organizacion_id = current_setting('app.organizacion_id', true)::bigint);
```

```js tenant.js
// Ejecuta el trabajo de un pedido dentro de una transacción "marcada" con la organización
async function conOrganizacion(pool, organizacionId, trabajo) {
  const cliente = await pool.connect();
  try {
    await cliente.query("BEGIN");
    // true = el valor vale solo para esta transacción
    await cliente.query("SELECT set_config('app.organizacion_id', $1, true)", [String(organizacionId)]);
    const resultado = await trabajo(cliente);
    await cliente.query("COMMIT");
    return resultado;
  } catch (error) {
    await cliente.query("ROLLBACK");
    throw error;
  } finally {
    cliente.release();
  }
}

// Uso: aunque esta consulta no tiene WHERE, solo ve las lecturas de la organización 3
// await conOrganizacion(pool, 3, (db) => db.query("SELECT count(*) FROM lecturas"));

module.exports = { conOrganizacion };
```

`USING` filtra lo que se puede leer; `WITH CHECK` impide insertar o modificar filas de otra organización. `current_setting(..., true)` no da error si el valor nunca se configuró: devuelve nulo, la comparación no coincide con nada, y una consulta "sin organización" no ve ninguna fila en lugar de verlas todas. (Si en esa conexión el valor ya se usó antes, queda como texto vacío y la conversión a número falla: la consulta da error, que también es un resultado seguro.) Como el valor se configura con `set_config(..., true)`, dura solo esa transacción: la conexión vuelve al pool limpia, sin arrastrar la organización al pedido siguiente. Las transacciones se ven en [5.2](/conceptos/5-2).

## Errores comunes

### Confiar en la organización que manda el cliente

```js
// Mal
router.get("/organizaciones/:orgId/invernaderos", async (req, res) => {
  const { rows } = await req.db.query("SELECT * FROM invernaderos WHERE organizacion_id = $1", [req.params.orgId]);
  res.json(rows);
});

// Bien: la organización sale de la sesión
router.get("/invernaderos", async (req, res) => res.json(await req.repo.invernaderos()));
```

### Buscar por ID sin la organización

```js
// Mal: devuelve el invernadero 42 sea de quien sea
db.query("SELECT * FROM invernaderos WHERE id = $1", [req.params.id]);

// Bien
db.query("SELECT * FROM invernaderos WHERE organizacion_id = $1 AND id = $2", [org, req.params.id]);
```

### Un `JOIN` que cruza organizaciones

Una consulta que une lecturas con dispositivos solo por `dispositivo_id` puede, ante un dato mal cargado, mezclar organizaciones. Con claves foráneas compuestas y la organización en las condiciones del `JOIN`, no puede pasar.

### Revelar que un recurso ajeno existe

Responder 403 ("no tenés permiso") a un invernadero ajeno y 404 a uno inexistente le permite a un usuario descubrir qué IDs existen. Respondé igual en los dos casos.

### Conectarse como dueño de las tablas con RLS

Si el backend se conecta con el usuario dueño de las tablas, las políticas no se aplican (salvo que se use `FORCE ROW LEVEL SECURITY`), y la red de seguridad no existe aunque esté definida.

Los dos problemas: la organización de la URL (`orgId`) ni siquiera se usa, y la consulta filtra solo por `invernadero_id`. Cualquier usuario autenticado puede ver los dispositivos de cualquier invernadero del sistema cambiando `invId`.

```js repositorio.js (método nuevo)
async dispositivosDeInvernadero(invernaderoId) {
  const { rows } = await db.query(
    `SELECT id, tipo, revocado
       FROM dispositivos
      WHERE organizacion_id = $1 AND invernadero_id = $2
      ORDER BY id`,
    [organizacionId, invernaderoId]
  );
  return rows;
},
```

```js dispositivos.js
router.get("/invernaderos/:id/dispositivos", async (req, res) => {
  const invernadero = await req.repo.invernadero(req.params.id);
  if (!invernadero) return res.status(404).json({ error: "invernadero no encontrado" });
  res.json(await req.repo.dispositivosDeInvernadero(invernadero.id));
});
```

La organización sale de la sesión (a través de `req.repo`), la ruta verifica primero que el invernadero sea de esa organización, y la consulta filtra por organización de todas formas. La URL ya no lleva `orgId`. Con las políticas del ejemplo 3, incluso una consulta escrita por error sin el filtro devolvería solo los dispositivos propios.

## Resumen

- Multi-tenant: muchas organizaciones en el mismo sistema, con aislamiento total entre ellas.
- Con tablas compartidas, cada tabla lleva `organizacion_id`, y las claves foráneas compuestas impiden relaciones entre organizaciones.
- La organización de un pedido sale de la autenticación, nunca de la URL ni del cuerpo.
- Una capa de acceso a datos atada a la organización filtra siempre; Row Level Security en PostgreSQL es la red de seguridad.
- Respondé igual a recursos ajenos e inexistentes, y no dependas de que los IDs sean difíciles de adivinar.
