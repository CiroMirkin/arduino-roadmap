El ESP32 no corre tu programa solo: corre **FreeRTOS**, un sistema operativo de tiempo real. Tu `loop()` es una de varias **tareas**; otras manejan el WiFi y el BLE. Podés crear tareas propias, que corren "al mismo tiempo" que `loop()`: el sistema las va alternando, y si una espera (una respuesta de red, un `vTaskDelay`), las demás siguen. Para que las tareas se comuniquen sin pisarse, FreeRTOS ofrece **colas** (para pasar datos) y **mutex** (para turnarse un recurso compartido). Es la herramienta para lo que el scheduler cooperativo de [2.3](/conceptos/2-3) no puede resolver: operaciones que bloquean y no se pueden dividir.

## Por qué te importa

En el controlador del invernadero, el envío al backend es el ejemplo típico: una petición HTTP puede tardar varios segundos si la red anda mal, y no hay forma de partirla en pasos. Si corre dentro de `loop()`, durante esos segundos la pantalla no responde y el control de riego se atrasa. Con una tarea de FreeRTOS para la comunicación, el envío puede tardar lo que tarde: el control sigue funcionando en paralelo.

Las tareas traen problemas que el código cooperativo no tenía. Dos tareas que escriben la misma variable, o que usan el mismo bus I2C, pueden mezclarse en cualquier momento. Cada tarea tiene su propio stack, y si es chico, se desborda. Las colas y los mutex existen para resolver esto de forma ordenada, en lugar de con banderas y `volatile` por todos lados.

## Paso a paso

### 1. Tareas, prioridades y núcleos

FreeRTOS reparte el procesador entre las tareas listas para correr. Cada tarea tiene una **prioridad**: si una de prioridad alta está lista, corre antes que las de prioridad baja, y puede **interrumpirlas** en cualquier momento (eso es *preemptivo*, a diferencia del scheduler cooperativo). Las tareas de igual prioridad se turnan.

El ESP32 clásico y el S3 tienen **dos núcleos**. En el core de Arduino, el WiFi y el BLE corren en el núcleo 0, y `loop()` en el núcleo 1, con prioridad 1. Al crear una tarea podés elegir en qué núcleo corre.

### 2. Crear una tarea

```cpp
void tareaComunicacion(void* parametro) {
  for (;;) {                                  // una tarea nunca termina
    enviarPendientes();
    vTaskDelay(pdMS_TO_TICKS(1000));          // esperar 1 s sin frenar a nadie
  }
}

void setup() {
  xTaskCreatePinnedToCore(
      tareaComunicacion,   // función de la tarea
      "comunicacion",      // nombre, para depurar
      8192,                // tamaño del stack, en bytes (en el ESP32)
      nullptr,             // parámetro que recibe la función
      1,                   // prioridad
      nullptr,             // donde guardar el handle (opcional)
      0);                  // núcleo: 0 o 1
}
```

La función recibe un `void*` (para pasarle un objeto, como el `this` de [B.7](/conceptos/b-7)) y tiene un bucle infinito. Si una tarea tiene que terminar, llama a `vTaskDelete(nullptr)`; nunca debe simplemente retornar.

`vTaskDelay` suspende **solo esa tarea**. En el core de Arduino para ESP32, `delay()` llama por dentro a `vTaskDelay`, así que dentro de una tarea propia también es aceptable: bloquea esa tarea, no al resto.

### 3. Colas: pasar datos entre tareas

```cpp
QueueHandle_t colaLecturas = xQueueCreate(20, sizeof(Lectura));   // hasta 20 lecturas

// En la tarea que produce (por ejemplo, loop):
Lectura l = leerSensores();
if (xQueueSend(colaLecturas, &l, 0) != pdTRUE) {
  // la cola está llena: decidir qué hacer (descartar, contar, avisar)
}

// En la tarea que consume:
Lectura recibida;
if (xQueueReceive(colaLecturas, &recibida, portMAX_DELAY) == pdTRUE) {
  enviar(recibida);
}
```

Una cola **copia** cada elemento al entrar y al salir, así que no hay datos compartidos que proteger: cada tarea trabaja con su copia. Mantiene el orden, guarda varios elementos si el consumidor se atrasa, y `xQueueReceive` con `portMAX_DELAY` duerme a la tarea hasta que llega algo, sin gastar procesador. El último parámetro de `xQueueSend` es cuánto esperar si la cola está llena: `0` significa no esperar.

Desde una interrupción se usa `xQueueSendFromISR`, una versión especial que no puede esperar (ver [2.5](/conceptos/2-5)).

### 4. Mutex: turnarse un recurso

```cpp
SemaphoreHandle_t mutexI2C = xSemaphoreCreateMutex();

void leerSensorProtegido() {
  if (xSemaphoreTake(mutexI2C, pdMS_TO_TICKS(100)) == pdTRUE) {   // esperar hasta 100 ms
    // usar el bus I2C: nadie más puede hasta que se libere
    xSemaphoreGive(mutexI2C);
  } else {
    // no se consiguió en 100 ms: reintentar después
  }
}
```

Un **mutex** es un candado: la tarea que lo toma usa el recurso, y cualquier otra que intente tomarlo espera hasta que se devuelva. Sirve para recursos que no se pueden usar a la vez: un bus I2C o SPI compartido, una estructura de datos con varios campos, la tarjeta SD.

A diferencia de la sección crítica de [B.11](/conceptos/b-11), un mutex no deshabilita las interrupciones y permite que la tarea que espera duerma. Es para esperas de milisegundos entre tareas; la sección crítica es para copiar unos bytes compartidos con una interrupción.

### 5. El tamaño del stack

Cada tarea tiene su propio stack, del tamaño que se pide al crearla (en el ESP32, en bytes). Si se queda corto, el ESP32 lo detecta y se reinicia con `A stack overflow in task ...`. Las tareas que usan `HTTPClient`, TLS o `printf` con flotantes necesitan bastante: 8 KB es un punto de partida razonable para comunicación, y más si se usa HTTPS.

```cpp
UBaseType_t libre = uxTaskGetStackHighWaterMark(nullptr);   // bytes que nunca se usaron
```

Medilo en las pruebas, en la peor situación (con errores de red, reintentos), y dejá un margen.

### 6. Reglas para un sistema con tareas

- **Pocas tareas**: una por cosa que necesite bloquear (comunicación, BLE). El control y la interfaz pueden seguir en `loop()` con un scheduler cooperativo.
- **Datos entre tareas, por colas**. Recursos compartidos, con mutex. Nada de variables globales sueltas.
- **Toda tarea espera en algún momento** (`vTaskDelay`, `xQueueReceive`). Una tarea de prioridad alta que nunca espera no deja correr a las de prioridad baja, y el watchdog termina reiniciando el equipo (ver [2.6](/conceptos/2-6)).
- **Siempre en el mismo orden**: si una tarea toma dos mutex, todas las que los usan los toman en el mismo orden. Si no, pueden quedar esperándose mutuamente para siempre (*deadlock*).

## Ejemplos

### Ejemplo 1. Dos tareas y `loop()` en paralelo

```cpp dos-tareas.ino
void tareaLento(void*) {
  for (;;) {
    Serial.printf("[lento]  núcleo %d, %lu ms\n", xPortGetCoreID(), millis());
    vTaskDelay(pdMS_TO_TICKS(2000));
  }
}

void tareaRapido(void*) {
  for (;;) {
    Serial.printf("[rápido] núcleo %d, %lu ms\n", xPortGetCoreID(), millis());
    vTaskDelay(pdMS_TO_TICKS(500));
  }
}

void setup() {
  Serial.begin(115200);
  xTaskCreatePinnedToCore(tareaLento, "lento", 4096, nullptr, 1, nullptr, 0);
  xTaskCreatePinnedToCore(tareaRapido, "rapido", 4096, nullptr, 1, nullptr, 1);
}

void loop() {
  Serial.printf("[loop]   núcleo %d\n", xPortGetCoreID());
  delay(1000);   // en una tarea (y loop es una), delay solo frena a esta tarea
}
```

Las tres tareas imprimen cada una a su ritmo, sin coordinarse entre sí. `xPortGetCoreID()` muestra en qué núcleo corre cada una. `Serial` se usa desde varias tareas a la vez, así que alguna línea puede mezclarse con otra: el ejemplo 3 muestra cómo evitarlo.

### Ejemplo 2. El control produce, la comunicación envía

El patrón más útil para el controlador: `loop()` hace el control (rápido, nunca bloquea) y pone cada lectura en una cola; una tarea de comunicación las saca y las envía, tarde lo que tarde.

```cpp productor-consumidor.ino
#include <atomic>

struct Lectura {
  uint32_t momentoS;
  float temperatura;
  float humedadSuelo;
};

QueueHandle_t colaEnvios = nullptr;
std::atomic<uint32_t> descartadas{0};   // otra tarea puede leerla (ver B.11)

bool enviarAlBackend(const Lectura& l) {
  // acá iría el HTTPClient de 0.10; simulamos una red lenta
  vTaskDelay(pdMS_TO_TICKS(1500));
  Serial.printf("[comunicación] enviada lectura de %u s (%.1f C)\n",
                static_cast<unsigned>(l.momentoS), l.temperatura);
  return true;
}

void tareaComunicacion(void*) {
  Lectura l;
  for (;;) {
    if (xQueueReceive(colaEnvios, &l, portMAX_DELAY) == pdTRUE) {   // duerme hasta que haya algo
      while (!enviarAlBackend(l)) {
        vTaskDelay(pdMS_TO_TICKS(10000));                            // reintentar más tarde
      }
    }
  }
}

void setup() {
  Serial.begin(115200);
  colaEnvios = xQueueCreate(30, sizeof(Lectura));
  xTaskCreatePinnedToCore(tareaComunicacion, "comunicacion", 8192, nullptr, 1, nullptr, 0);
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 1000) {
    ultimo = millis();
    Lectura l{millis() / 1000, 24.5f, 41.0f};      // acá irían las lecturas reales
    if (xQueueSend(colaEnvios, &l, 0) != pdTRUE) {  // nunca esperar: el control no se frena
      descartadas++;
    }
    Serial.printf("[control] lectura %u encolada, en cola: %u\n", static_cast<unsigned>(l.momentoS),
                  static_cast<unsigned>(uxQueueMessagesWaiting(colaEnvios)));
  }
  // riego, ventanas, pantalla: siguen funcionando aunque el envío tarde
}
```

El control genera una lectura por segundo y el envío tarda 1,5 segundos: la cola va creciendo, y cuando se llene, las nuevas se descartan y se cuentan, pero el control nunca se detiene. En el sistema real, las lecturas se agruparían en un solo envío, o se mandaría una por minuto. La tarea de comunicación pasa casi todo el tiempo dormida en `xQueueReceive`, sin consumir procesador.

### Ejemplo 3. Un mutex para el estado compartido y para `Serial`

La pantalla (en `loop()`) y la tarea BLE (que recibe lecturas de los nodos) comparten el estado de los nodos. Un mutex protege la estructura, y otro evita que los mensajes del monitor serie se mezclen.

```cpp mutex.ino
struct EstadoNodos {
  float temperatura[4] = {};
  uint32_t actualizado[4] = {};
};

EstadoNodos estado;
SemaphoreHandle_t mutexEstado = nullptr;
SemaphoreHandle_t mutexSerial = nullptr;

void registrar(const char* texto) {
  if (xSemaphoreTake(mutexSerial, pdMS_TO_TICKS(50)) == pdTRUE) {
    Serial.println(texto);
    xSemaphoreGive(mutexSerial);
  }
}

// Tarea que simula la recepción BLE de los nodos
void tareaBle(void*) {
  uint8_t nodo = 0;
  for (;;) {
    float t = 20.0f + random(0, 100) / 10.0f;
    if (xSemaphoreTake(mutexEstado, pdMS_TO_TICKS(100)) == pdTRUE) {
      estado.temperatura[nodo] = t;            // los dos campos se actualizan juntos
      estado.actualizado[nodo] = millis();
      xSemaphoreGive(mutexEstado);
    }
    char linea[48];
    snprintf(linea, sizeof(linea), "[ble] nodo %u: %.1f C", nodo, t);
    registrar(linea);
    nodo = (nodo + 1) % 4;
    vTaskDelay(pdMS_TO_TICKS(700));
  }
}

void setup() {
  Serial.begin(115200);
  mutexEstado = xSemaphoreCreateMutex();
  mutexSerial = xSemaphoreCreateMutex();
  xTaskCreatePinnedToCore(tareaBle, "ble", 4096, nullptr, 1, nullptr, 0);
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo < 3000) return;
  ultimo = millis();

  EstadoNodos copia;
  if (xSemaphoreTake(mutexEstado, pdMS_TO_TICKS(100)) == pdTRUE) {
    copia = estado;                            // copiar rápido y soltar el mutex
    xSemaphoreGive(mutexEstado);
  } else {
    return;
  }

  char linea[64];
  snprintf(linea, sizeof(linea), "[pantalla] %.1f %.1f %.1f %.1f C",
           copia.temperatura[0], copia.temperatura[1], copia.temperatura[2], copia.temperatura[3]);
  registrar(linea);
  // dibujar con la copia, sin tener el mutex tomado
}
```

`loop()` toma el mutex solo el tiempo de copiar el estado, y dibuja con la copia: así la tarea BLE nunca espera a la pantalla. Cada `xSemaphoreTake` tiene un tiempo máximo y se chequea el resultado, en lugar de esperar para siempre. El mutex de `Serial` hace que cada línea salga completa.

## Errores comunes

### Compartir variables entre tareas sin protección

```cpp
// Mal: dos tareas leen y escriben la misma estructura
Lectura ultima;   // tarea A escribe, tarea B lee: puede leer la mitad de una y la mitad de otra

// Bien: una cola si es un flujo de datos, o un mutex si es un estado compartido
```

### Una tarea que nunca espera

```cpp
// Mal: con prioridad alta, no deja correr a nadie de prioridad menor
void tarea(void*) {
  for (;;) {
    if (hayAlgo) procesar();   // gira sin parar
  }
}

// Bien: esperar en una cola, o al menos ceder con vTaskDelay
void tarea(void*) {
  for (;;) {
    if (xQueueReceive(cola, &dato, portMAX_DELAY) == pdTRUE) procesar(dato);
  }
}
```

### Stack chico

Empezá con valores generosos (4 KB para tareas simples, 8 KB o más para red, 12 a 16 KB con HTTPS), medí con `uxTaskGetStackHighWaterMark` en el peor caso, y ajustá dejando margen.

### Tomar dos mutex en distinto orden

```cpp
// Mal
// Tarea A: toma mutexI2C, después mutexEstado
// Tarea B: toma mutexEstado, después mutexI2C
// Si cada una toma el primero, las dos esperan para siempre el segundo.

// Bien: todas las tareas toman primero mutexI2C y después mutexEstado.
```

### Una función de tarea que retorna

```cpp
// Mal: al retornar, el ESP32 aborta
void tarea(void*) {
  hacerAlgoUnaVez();
}

// Bien
void tarea(void*) {
  hacerAlgoUnaVez();
  vTaskDelete(nullptr);   // la tarea se borra a sí misma
}
```

## Ejercicio

Este controlador envía cada lectura al backend dentro de `loop()`, y cuando la red está lenta, la pantalla deja de responder varios segundos. Reestructuralo con una cola y una tarea de comunicación, de forma que `loop()` nunca espere a la red.

```cpp bloqueante.ino
void loop() {
  actualizarPantalla();
  controlarRiego();

  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 60000) {
    ultimo = millis();
    Lectura l = leerSensores();
    enviarAlBackend(l);            // HTTP: puede tardar 5 segundos o más
  }
}
```

<details>
<summary>Pista</summary>

Creá la cola y la tarea en `setup()`. En `loop()`, en lugar de `enviarAlBackend`, `xQueueSend` con espera 0. La tarea hace `xQueueReceive` con `portMAX_DELAY` y envía.

</details>

<details>
<summary>Ver solución</summary>

```cpp no-bloqueante.ino
QueueHandle_t colaEnvios = nullptr;

void tareaComunicacion(void*) {
  Lectura l;
  for (;;) {
    if (xQueueReceive(colaEnvios, &l, portMAX_DELAY) == pdTRUE) {
      if (!enviarAlBackend(l)) {
        xQueueSendToFront(colaEnvios, &l, 0);     // no perderla: vuelve al principio de la cola
        vTaskDelay(pdMS_TO_TICKS(30000));        // y esperar antes de reintentar
      }
    }
  }
}

void setup() {
  Serial.begin(115200);
  colaEnvios = xQueueCreate(60, sizeof(Lectura));   // una hora de lecturas
  xTaskCreatePinnedToCore(tareaComunicacion, "comunicacion", 8192, nullptr, 1, nullptr, 0);
}

void loop() {
  actualizarPantalla();
  controlarRiego();

  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 60000) {
    ultimo = millis();
    Lectura l = leerSensores();
    xQueueSend(colaEnvios, &l, 0);               // nunca espera; si la cola está llena, se pierde
  }
}
```

Ahora `loop()` solo copia la lectura a la cola, algo que tarda microsegundos. La tarea de comunicación puede tardar lo que haga falta, y si el envío falla, devuelve la lectura al principio de la cola y espera antes de reintentar, sin perderla. Con 60 lugares, la cola aguanta una hora sin red. La tarea va en el núcleo 0, junto al WiFi; `loop()` sigue en el 1.

</details>

## Resumen

- En el ESP32, todo corre sobre FreeRTOS: `loop()` es una tarea más, y podés crear otras con `xTaskCreatePinnedToCore`.
- Una tarea que espera (`vTaskDelay`, `xQueueReceive`) no frena a las demás. Toda tarea tiene un bucle infinito y espera en algún momento.
- Los datos entre tareas van por colas, que copian y mantienen el orden. Los recursos compartidos (bus I2C, estructuras, `Serial`) se protegen con mutex, tomándolos poco tiempo.
- Cada tarea tiene su propio stack: elegí el tamaño con margen y medilo con `uxTaskGetStackHighWaterMark`.
- Pocas tareas: una por cada cosa que bloquea (red, BLE). El resto, en `loop()` con un scheduler cooperativo.
