**PlatformIO** es un entorno para desarrollar firmware que se usa como extensión de VS Code (o desde la terminal). Compila con las mismas herramientas que el Arduino IDE y con el mismo framework de Arduino, pero organiza el proyecto de otra forma: todo lo que el proyecto necesita (placa, versión de la plataforma, librerías con sus versiones, opciones de compilación) está escrito en un archivo, **`platformio.ini`**, junto al código. Para un firmware que crece, que mantienen varias personas o que tiene más de un equipo (el nodo y el controlador), es la herramienta que más ordena el trabajo.

## Por qué te importa

En [0.13](/conceptos/0-13) viste el problema de las versiones: en el Arduino IDE, las librerías y el core se instalan por computadora, y el proyecto no dice con qué versiones se compila. Con PlatformIO eso queda en el proyecto. También resuelve otras cosas que en el IDE son incómodas: carpetas para organizar el código (ver [1.1](/conceptos/1-1) y [2.1](/conceptos/2-1)), varios entornos en un mismo proyecto (el firmware del nodo y el del controlador), pruebas que corren en la PC sin placa (ver [2.8](/conceptos/2-8)), y un monitor serie que traduce los errores del ESP32 a líneas de tu código.

## Paso a paso

### 1. La estructura de un proyecto

```text
controlador-invernadero/
├── platformio.ini      la configuración del proyecto
├── src/                el código: main.cpp y los módulos .cpp
├── include/            headers del proyecto
├── lib/                librerías propias (cada una en su carpeta)
├── test/               pruebas
└── .pio/               lo que genera PlatformIO (no se versiona)
```

No hay `.ino`: el punto de entrada es `src/main.cpp`, con su `setup()` y su `loop()`.

### 2. `platformio.ini`

```ini
[env:controlador]
platform = espressif32
board = esp32-s3-devkitc-1
framework = arduino
monitor_speed = 115200
lib_deps =
  bblanchon/ArduinoJson @ ^7.2.0
build_flags =
  -DVERSION_FIRMWARE=\"1.4.0\"
```

- `[env:nombre]`: un **entorno**. Cada uno es una forma de compilar el proyecto.
- `platform`, `board`, `framework`: el chip, la placa exacta y el framework (Arduino). Fijá la versión de la plataforma cuando el proyecto esté estable (ver [0.13](/conceptos/0-13)).
- `lib_deps`: librerías externas con su versión. PlatformIO las descarga para este proyecto.
- `build_flags`: opciones de compilación, como `-D` para definir macros (ver [B.5](/conceptos/b-5)).
- `monitor_speed`: la velocidad del monitor serie, para no tener que elegirla cada vez.

### 3. Los comandos

Desde la barra de VS Code o desde la terminal:

| Comando | Qué hace |
|---|---|
| `pio run` | compila |
| `pio run -t upload` | compila y sube a la placa |
| `pio device monitor` | abre el monitor serie |
| `pio run -e nodo -t upload` | compila y sube solo el entorno `nodo` |
| `pio test -e native` | corre las pruebas en la PC |

### 4. De un `.ino` a `main.cpp`

Un `.ino` no se puede copiar tal cual a `main.cpp`. Hay dos diferencias:

- El Arduino IDE agrega `#include <Arduino.h>` solo; en un `.cpp` hay que escribirlo.
- El IDE genera prototipos para las funciones de los `.ino`; en un `.cpp`, una función tiene que estar declarada antes de usarse (ver [B.6](/conceptos/b-6)).

```cpp
#include <Arduino.h>

void regar();             // prototipo: ahora se puede usar antes de su definición

void setup() { regar(); }
void loop() {}

void regar() { /* ... */ }
```

En la práctica, migrar es también una buena oportunidad para sacar cada responsabilidad a su propio módulo, con su header.

### 5. Librerías propias en `lib/`

El código que comparten el nodo y el controlador (el formato de las lecturas, el protocolo BLE, la lógica de control pura) puede ir como una **librería propia** en `lib/`:

```text
lib/
└── protocolo/
    ├── protocolo.h
    └── protocolo.cpp
```

PlatformIO la encuentra sola cuando algún archivo hace `#include "protocolo.h"`, y la compila para cada entorno que la use. Cada librería va en su propia subcarpeta.

### 6. Herramientas que hacen la diferencia

- **Varios entornos**: el nodo y el controlador en el mismo proyecto, cada uno con su placa y sus opciones, compartiendo `lib/`.
- **Decodificador de excepciones**: con `monitor_filters = esp32_exception_decoder`, cuando el ESP32 se reinicia por un error, el monitor muestra en qué función y en qué línea pasó, en lugar de una lista de direcciones.
- **Pruebas en la PC**: un entorno `native` compila la lógica que no depende del hardware para la computadora y la prueba en segundos (ver [2.8](/conceptos/2-8)).
- **Integración con git**: como todo está en archivos de texto, el control de versiones guarda también la configuración. La carpeta `.pio/` se excluye.

## Ejemplos

### Ejemplo 1. El proyecto mínimo

```ini platformio.ini
[env:esp32dev]
platform = espressif32
board = esp32dev
framework = arduino
monitor_speed = 115200
monitor_filters = esp32_exception_decoder
```

```cpp src/main.cpp
// nodo (ESP32 clásico)
#include <Arduino.h>

constexpr uint8_t PIN_LED = 2;

void parpadear();

void setup() {
  Serial.begin(115200);
  pinMode(PIN_LED, OUTPUT);
}

void loop() {
  parpadear();
}

void parpadear() {
  static uint32_t ultimo = 0;
  static bool encendido = false;
  if (millis() - ultimo >= 500) {
    ultimo = millis();
    encendido = !encendido;
    digitalWrite(PIN_LED, encendido ? HIGH : LOW);
  }
}
```

Con estos dos archivos, `pio run -t upload` compila, sube, y `pio device monitor` muestra la salida. El prototipo `void parpadear();` es lo único que cambia respecto del `.ino` equivalente.

### Ejemplo 2. El nodo y el controlador en un solo proyecto

El protocolo compartido va en `lib/`, y cada firmware tiene su propio `main` en una carpeta. Con `build_src_filter`, cada entorno compila solo lo suyo.

```text
invernadero/
├── platformio.ini
├── lib/
│   └── protocolo/
│       ├── protocolo.h
│       └── protocolo.cpp
└── src/
    ├── controlador/
    │   └── main.cpp
    └── nodo/
        └── main.cpp
```

```ini platformio.ini
[platformio]
default_envs = controlador

[env]
platform = espressif32
framework = arduino
monitor_speed = 115200
monitor_filters = esp32_exception_decoder
lib_deps =
  bblanchon/ArduinoJson @ ^7.2.0

[env:controlador]
board = esp32-s3-devkitc-1
build_src_filter = +<controlador/>
build_flags = -DROL_CONTROLADOR

[env:nodo]
board = esp32dev
build_src_filter = +<nodo/>
build_flags = -DROL_NODO
```

```cpp lib/protocolo/protocolo.h
#pragma once
#include <Arduino.h>

namespace protocolo {

struct Lectura {
  float temperatura;
  uint8_t humedadSuelo;
};

constexpr size_t TAMANO = 3;

void codificar(const Lectura& l, uint8_t trama[TAMANO]);
bool decodificar(const uint8_t* trama, size_t largo, Lectura& l);

}  // namespace protocolo
```

```cpp src/nodo/main.cpp
#include <Arduino.h>
#include "protocolo.h"

void setup() {
  Serial.begin(115200);
  uint8_t trama[protocolo::TAMANO];
  protocolo::codificar({24.5f, 41}, trama);
  Serial.printf("trama: %02X %02X %02X\n", trama[0], trama[1], trama[2]);
}

void loop() {}
```

La sección `[env]` tiene lo común; cada entorno agrega su placa y su carpeta. `pio run -e nodo -t upload` sube el firmware del nodo, `pio run -e controlador -t upload` el del controlador. Un cambio en el protocolo se hace una vez en `lib/` y lo reciben los dos, que es justo lo que evita que el nodo y el controlador dejen de entenderse.

### Ejemplo 3. Un entorno para probar en la PC

La lógica de control pura (como `decidirRiego` de [1.1](/conceptos/1-1)) no depende del hardware, así que se puede compilar para la PC y probar con el framework de pruebas Unity, que viene con PlatformIO.

```text
invernadero/
├── lib/
│   └── control/
│       ├── control.h        sin #include <Arduino.h>
│       └── control.cpp
└── test/
    └── test_control/
        └── test_main.cpp
```

```ini platformio.ini
[env:native]
platform = native
test_framework = unity
build_flags = -std=c++17
```

```cpp lib/control/control.h
#pragma once
#include <cstdint>

namespace control {

enum class AccionRiego : uint8_t { Ninguna, Encender, Apagar };

AccionRiego decidirRiego(float humedad, bool tanqueConAgua, bool regando,
                         float minima, float maxima);

}  // namespace control
```

```cpp test/test_control/test_main.cpp
#include <unity.h>
#include "control.h"

using control::AccionRiego;
using control::decidirRiego;

void setUp() {}
void tearDown() {}

void test_suelo_seco_enciende() {
  TEST_ASSERT_TRUE(decidirRiego(20.0f, true, false, 35.0f, 55.0f) == AccionRiego::Encender);
}

void test_tanque_vacio_nunca_enciende() {
  TEST_ASSERT_TRUE(decidirRiego(20.0f, false, false, 35.0f, 55.0f) == AccionRiego::Ninguna);
}

void test_tanque_vacio_apaga_si_regaba() {
  TEST_ASSERT_TRUE(decidirRiego(40.0f, false, true, 35.0f, 55.0f) == AccionRiego::Apagar);
}

int main() {
  UNITY_BEGIN();
  RUN_TEST(test_suelo_seco_enciende);
  RUN_TEST(test_tanque_vacio_nunca_enciende);
  RUN_TEST(test_tanque_vacio_apaga_si_regaba);
  return UNITY_END();
}
```

`pio test -e native` compila `control` y las pruebas para la computadora y las corre en segundos, sin placa conectada. Para que funcione, `control.h` y `control.cpp` no pueden incluir `Arduino.h` ni usar nada del hardware: es la separación de [1.1](/conceptos/1-1) puesta a prueba. El entorno `native` necesita un compilador de C++ instalado en la PC. El tema completo está en [2.8](/conceptos/2-8).

## Errores comunes

### Copiar un `.ino` a `main.cpp` sin prototipos

```cpp
// Mal: regar() se usa antes de declararse
#include <Arduino.h>
void setup() { regar(); }
void regar() { /* ... */ }

// Bien
#include <Arduino.h>
void regar();
void setup() { regar(); }
void regar() { /* ... */ }
```

### Librerías propias sueltas en `lib/`

```text
Mal:   lib/protocolo.h, lib/protocolo.cpp
Bien:  lib/protocolo/protocolo.h, lib/protocolo/protocolo.cpp
```

PlatformIO trata cada subcarpeta de `lib/` como una librería. Archivos sueltos no se encuentran.

### No fijar la plataforma

Sin versión en `platform`, PlatformIO usa la última instalada, y un día el proyecto compila con otro core sin que nadie lo haya decidido. Cuando el proyecto esté estable, fijala: `platform = espressif32 @ 6.9.0` (y revisá qué core trae; ver [0.13](/conceptos/0-13)).

### Versionar `.pio/`

La carpeta `.pio/` tiene cientos de MB de archivos generados. Va en el `.gitignore`; lo que se versiona es `platformio.ini` y el código.

## Ejercicio

Tenés este sketch del Arduino IDE para el nodo sensor. Migralo a un proyecto PlatformIO con un entorno para un ESP32 común, ArduinoJson 7 como dependencia y el decodificador de excepciones activado, y corregí lo que hace falta para que compile como `.cpp`.

```cpp nodo.ino
void setup() {
  Serial.begin(115200);
  enviarLectura(leerTemperatura());
}

void loop() {}

float leerTemperatura() {
  return 24.5f;
}

void enviarLectura(float t) {
  Serial.printf("temperatura: %.1f\n", t);
}
```

<summary>Pista</summary>

Hacen falta dos archivos: `platformio.ini` y `src/main.cpp`. En el `.cpp`, falta un include y faltan dos prototipos.

</details>

<details>
<summary>Ver solución</summary>

```ini platformio.ini
[env:nodo]
platform = espressif32
board = esp32dev
framework = arduino
monitor_speed = 115200
monitor_filters = esp32_exception_decoder
lib_deps =
  bblanchon/ArduinoJson @ ^7.2.0
```

```cpp src/main.cpp
#include <Arduino.h>

float leerTemperatura();
void enviarLectura(float t);

void setup() {
  Serial.begin(115200);
  enviarLectura(leerTemperatura());
}

void loop() {}

  return 24.5f;
}

  Serial.printf("temperatura: %.1f\n", t);
```

En el `.ino`, el IDE agregaba `#include <Arduino.h>` y generaba los prototipos de `leerTemperatura` y `enviarLectura`. En el `.cpp` hay que escribirlos. El paso siguiente natural sería mover cada función a su módulo (`sensores`, `envio`) con su header en `include/` o como librería en `lib/`.

## Resumen

- PlatformIO guarda en `platformio.ini` la placa, la plataforma, las librerías con versión y las opciones de cada proyecto.
- El código va en `src/` (con `main.cpp`), los headers en `include/` y las librerías propias en `lib/`, cada una en su carpeta.
- Al migrar un `.ino`: agregar `#include <Arduino.h>` y los prototipos de las funciones.
- Varios entornos permiten tener el nodo y el controlador en un proyecto, compartiendo código.
- `esp32_exception_decoder` traduce los errores a líneas de código, y el entorno `native` permite probar la lógica en la PC.
