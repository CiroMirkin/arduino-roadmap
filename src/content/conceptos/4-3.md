La **API de ingesta** es la puerta por la que entran los datos de los equipos al backend: las lecturas de los controladores, los eventos de riego, las alarmas. Tiene requisitos distintos a los de una API para una app: la usan cientos de equipos que reintentan cuando falla la red (así que recibe **duplicados**), envían **lotes** acumulados durante un corte, tienen relojes que no siempre son confiables, y no se pueden actualizar todos a la vez. Diseñarla bien es lo que hace que los datos del invernadero sean completos y correctos.

## Por qué te importa

En [3.5](/conceptos/3-5) viste el lado del equipo: cada lectura lleva un identificador único, y el equipo reintenta hasta que el backend confirma. Esta lección es el lado del backend: cómo recibir eso de forma que los reintentos nunca dupliquen datos, que un dato malo no trabe a los buenos, y que la API pueda cambiar sin dejar afuera a los equipos con firmware viejo.

Los errores acá se ven en los datos: gráficos con picos de consumo de agua que nunca existieron (duplicados), huecos de horas (un lote rechazado entero por una lectura mala), o lecturas fechadas en 1970.

## Paso a paso

### 1. El contrato

El contrato de una API es lo que se promete: qué se envía, qué se responde y qué significa cada respuesta. Para la ingesta de lecturas:

```text
POST /api/v1/lecturas
Authorization: Bearer <clave del equipo>        (ver 3.4)
Content-Type: application/json

{
  "lecturas": [
    { "id": "inv2-ctrl-00000123", "momento": "2026-10-05T14:30:00Z", "temp": 24.5, "suelo": 41 },
    { "id": "inv2-ctrl-00000124", "momento": "2026-10-05T14:31:00Z", "temp": 24.7, "suelo": 40 }
  ]
}
```

La respuesta dice qué pasó con cada lectura:

```json
{ "aceptadas": ["inv2-ctrl-00000124"], "duplicadas": ["inv2-ctrl-00000123"], "rechazadas": [] }
```

El equipo no envía su organización ni su invernadero: el backend los deduce de la clave (ver [4.1](/conceptos/4-1)).

### 2. Validar cada elemento por separado

Un lote es una lista de elementos independientes. Si uno es inválido (falta el `id`, la humedad es 180 %, la fecha es del año 1970), se **rechaza ese elemento**, no el lote entero. Rechazar todo haría que el equipo reintentara el lote completo para siempre, y las lecturas buenas nunca entrarían. Los rechazados se informan en la respuesta y se registran, porque suelen indicar un sensor dañado o un bug de firmware (ver [6.3](/conceptos/6-3)).

### 3. Duplicados: aceptados en silencio

Un elemento con un `id` que ya existe para ese dispositivo es un **reintento**, no un error. Se informa como `duplicada` y no se guarda de nuevo. La restricción de unicidad va sobre el par `(dispositivo_id, id_envio)`, porque el identificador es único solo dentro del equipo que lo generó.

Para el equipo, `aceptada` y `duplicada` significan lo mismo: el dato está guardado y puede sacarlo de su cola.

### 4. Dos momentos

Cada lectura guarda dos horas:

- `momento`: cuándo midió el equipo. Es la hora que importa para los gráficos, sobre todo para lecturas acumuladas durante un corte de red.
- `recibido`: cuándo llegó al servidor. Siempre confiable, porque la pone el backend.

Un equipo sin reloj sincronizado (recién arrancado, sin acceso a un servidor de hora) puede mandar fechas absurdas. La API rechaza momentos imposibles (anteriores a la instalación del sistema o varios minutos en el futuro), y comparar `momento` con `recibido` permite detectar equipos con el reloj desfasado. Los supuestos falsos sobre el tiempo se ven en [7.1](/conceptos/7-1).

### 5. Guardar el lote de una vez

Insertar 50 lecturas con 50 consultas separadas es lento. PostgreSQL puede recibir arreglos y convertirlos en filas con `unnest`, así todo el lote entra en una sola consulta, y `ON CONFLICT ... DO NOTHING RETURNING` devuelve solo las filas que realmente se insertaron: las que no aparecen eran duplicadas.

### 6. Versionar desde el primer día

Un sitio web y su backend se actualizan juntos. Los equipos en el campo no: puede haber firmware de hace dos años funcionando. Por eso la ruta lleva una versión (`/api/v1/...`). Cuando el formato tenga que cambiar de forma incompatible, se crea la `v2`, y la `v1` sigue funcionando hasta que no quede ningún equipo que la use (la versión de firmware que envía cada equipo, ver [2.7](/conceptos/2-7), dice cuándo).

## Ejemplos

### Ejemplo 1. Validar un elemento del lote

Una función pura que revisa una lectura y devuelve los valores limpios, o el motivo del rechazo.

```js validar-lectura.js
const INICIO_DEL_SISTEMA = Date.parse("2025-01-01T00:00:00Z");
const TOLERANCIA_FUTURO_MS = 5 * 60 * 1000;   // relojes un poco adelantados

function validarLectura(l, ahoraMs = Date.now()) {
  if (typeof l !== "object" || l === null) return { error: "no es un objeto" };

  if (typeof l.id !== "string" || !/^[A-Za-z0-9-]{1,40}$/.test(l.id)) {
    return { error: "id inválido" };
  }

  const momentoMs = Date.parse(l.momento);
  if (Number.isNaN(momentoMs)) return { error: "momento inválido", id: l.id };
  if (momentoMs < INICIO_DEL_SISTEMA || momentoMs > ahoraMs + TOLERANCIA_FUTURO_MS) {
    return { error: "momento fuera de rango", id: l.id };
  }

  if (typeof l.temp !== "number" || l.temp < -30 || l.temp > 70) {
    return { error: "temperatura fuera de rango", id: l.id };
  }
  if (!Number.isInteger(l.suelo) || l.suelo < 0 || l.suelo > 100) {
    return { error: "humedad fuera de rango", id: l.id };
  }

  return {
    valor: { id: l.id, momento: new Date(momentoMs).toISOString(), temp: l.temp, suelo: l.suelo },
  };
}

module.exports = { validarLectura };

// validarLectura({ id: "inv2-ctrl-1", momento: "2026-10-05T14:30:00Z", temp: 24.5, suelo: 41 })
//   -> { valor: { ... } }
// validarLectura({ id: "inv2-ctrl-2", momento: "1970-01-01T00:00:00Z", temp: 24.5, suelo: 41 })
//   -> { error: "momento fuera de rango", id: "inv2-ctrl-2" }
```

La validación chequea tipos y rangos, y el `id` se limita a un formato y un largo razonables antes de llegar a la base de datos. `ahoraMs` es un parámetro con valor por defecto: en las pruebas se le pasa una hora fija, la misma idea del reloj falso de [2.8](/conceptos/2-8).

### Ejemplo 2. La ruta de ingesta

La ruta valida cada lectura, inserta las válidas en una sola consulta y responde qué pasó con cada una.

```sql lecturas-v1.sql
CREATE TABLE lecturas (
  organizacion_id  BIGINT NOT NULL,
  dispositivo_id   BIGINT NOT NULL,
  id_envio         TEXT NOT NULL,
  momento          TIMESTAMPTZ NOT NULL,
  recibido         TIMESTAMPTZ NOT NULL DEFAULT now(),
  temperatura      NUMERIC(4,1),
  humedad_suelo    SMALLINT,
  PRIMARY KEY (dispositivo_id, id_envio),
  FOREIGN KEY (organizacion_id, dispositivo_id) REFERENCES dispositivos (organizacion_id, id)
);
```

```js ingesta.js
const express = require("express");
const { autenticarEquipo } = require("./autenticacion");   // 3.4: deja req.equipo
const { validarLectura } = require("./validar-lectura");

const router = express.Router();
const MAXIMO_POR_LOTE = 200;

router.post("/api/v1/lecturas", express.json({ limit: "64kb" }), autenticarEquipo, async (req, res) => {
  const entrada = req.body && req.body.lecturas;
  if (!Array.isArray(entrada) || entrada.length === 0 || entrada.length > MAXIMO_POR_LOTE) {
    return res.status(400).json({ error: `se esperan entre 1 y ${MAXIMO_POR_LOTE} lecturas` });
  }

  const validas = [];
  const rechazadas = [];
  for (const l of entrada) {
    const r = validarLectura(l);
    if (r.error) rechazadas.push({ id: r.id || null, motivo: r.error });
    else validas.push(r.valor);
  }

  let aceptadas = [];
  if (validas.length > 0) {
    const { rows } = await req.db.query(
      `INSERT INTO lecturas (organizacion_id, dispositivo_id, id_envio, momento, temperatura, humedad_suelo)
       SELECT $1, $2, t.id, t.momento, t.temp, t.suelo
         FROM unnest($3::text[], $4::timestamptz[], $5::numeric[], $6::smallint[])
              AS t(id, momento, temp, suelo)
       ON CONFLICT (dispositivo_id, id_envio) DO NOTHING
       RETURNING id_envio`,
      [
        req.equipo.organizacion_id,
        req.equipo.id,
        validas.map((v) => v.id),
        validas.map((v) => v.momento),
        validas.map((v) => v.temp),
        validas.map((v) => v.suelo),
      ]
    );
    aceptadas = rows.map((r) => r.id_envio);
  }

  const setAceptadas = new Set(aceptadas);
  const duplicadas = validas.map((v) => v.id).filter((id) => !setAceptadas.has(id));

  if (rechazadas.length > 0) {
    console.warn(JSON.stringify({ evento: "lecturas_rechazadas", dispositivo: req.equipo.id, rechazadas }));
  }
  res.status(200).json({ aceptadas, duplicadas, rechazadas });
});

module.exports = router;
```

Todo el lote entra en una consulta: `unnest` convierte los arreglos en filas, y `RETURNING` devuelve solo las insertadas, así que las que faltan en `aceptadas` eran duplicadas. La organización y el dispositivo salen de la autenticación. `express.json({ limit })` y el máximo de elementos protegen al servidor de cuerpos gigantes (ver [4.4](/conceptos/4-4)). La respuesta es siempre 200 con el detalle; el equipo saca de su cola todo lo que figure en cualquiera de las tres listas. Si dos lecturas del mismo lote tuvieran el mismo `id`, PostgreSQL insertaría la primera e ignoraría la segunda, que quedaría como duplicada: el resultado sigue siendo correcto.

### Ejemplo 3. Idempotencia para órdenes desde la app

Las lecturas tienen un identificador natural. Otras operaciones no: por ejemplo, el operario aprieta "regar 2 minutos" en la app, la conexión del celular falla, y la app reintenta. Para eso se usa un encabezado `Idempotency-Key`: la app genera una clave al apretar el botón, y el backend guarda la respuesta de cada clave para devolverla igual si se repite.

```sql idempotencia.sql
CREATE TABLE claves_idempotencia (
  organizacion_id  BIGINT NOT NULL,
  clave            TEXT NOT NULL,
  respuesta        JSONB NOT NULL,
  creado           TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (organizacion_id, clave)
);
```

```js idempotencia.js
// Envuelve una acción: si la clave ya se usó, devuelve la misma respuesta sin repetir la acción
async function conIdempotencia(req, res, accion) {
  const clave = req.get("Idempotency-Key");
  if (!clave || clave.length > 64) {
    return res.status(400).json({ error: "falta Idempotency-Key" });
  }

  const cliente = await req.db.connect();
  try {
    await cliente.query("BEGIN");
    // Reservar la clave; si otro pedido con la misma clave está en curso, este espera
    const reserva = await cliente.query(
      `INSERT INTO claves_idempotencia (organizacion_id, clave, respuesta)
       VALUES ($1, $2, '{}'::jsonb)
       ON CONFLICT (organizacion_id, clave) DO NOTHING
       RETURNING clave`,
      [req.usuario.organizacion_id, clave]
    );

    if (reserva.rowCount === 0) {                      // ya se procesó: repetir la respuesta
      const { rows } = await cliente.query(
        "SELECT respuesta FROM claves_idempotencia WHERE organizacion_id = $1 AND clave = $2",
        [req.usuario.organizacion_id, clave]
      );
      await cliente.query("COMMIT");
      return res.status(200).json(rows[0].respuesta);
    }

    const respuesta = await accion(cliente);           // la acción real, una sola vez
    await cliente.query(
      "UPDATE claves_idempotencia SET respuesta = $3 WHERE organizacion_id = $1 AND clave = $2",
      [req.usuario.organizacion_id, clave, JSON.stringify(respuesta)]
    );
    await cliente.query("COMMIT");
    return res.status(201).json(respuesta);
  } catch (error) {
    await cliente.query("ROLLBACK");                   // la clave se libera: se puede reintentar
    throw error;
  } finally {
    cliente.release();
  }
}

// Uso en la ruta de riego manual (con requierePermiso("riego.accionar"), ver 4.2)

//     const { rows } = await db.query(
//       "INSERT INTO comandos (organizacion_id, invernadero_id, tipo, segundos) VALUES ($1, $2, 'regar', $3) RETURNING id",
//       [req.usuario.organizacion_id, req.params.id, req.body.segundos]);
//     return { comando: rows[0].id };
//   }));

module.exports = { conIdempotencia };
```

La reserva de la clave y la acción ocurren en la misma transacción: si la acción falla, el `ROLLBACK` libera la clave y el reintento puede hacerla. Si llega el mismo pedido dos veces casi al mismo tiempo, el segundo `INSERT` espera a que el primero termine (por la clave primaria) y después encuentra la clave ya usada. Las claves viejas se borran con una tarea periódica (por ejemplo, las de más de un día). Las transacciones se ven en [5.2](/conceptos/5-2).

## Errores comunes

### Rechazar el lote entero por un elemento

Un 400 para todo el lote hace que el equipo lo reintente para siempre. Validá elemento por elemento y respondé el detalle.

### Tratar los duplicados como errores

```js
// Mal: un reintento recibe 409 o 500, y el equipo no sabe si sacar la lectura de la cola
INSERT INTO lecturas ... ;   -- sin ON CONFLICT: falla por clave duplicada

// Bien
INSERT INTO lecturas ... ON CONFLICT (dispositivo_id, id_envio) DO NOTHING RETURNING id_envio;
```

### Tomar la organización del cuerpo

Un campo `"organizacionId"` en el JSON del equipo no se usa para nada que importe: la organización sale de la clave (ver [3.4](/conceptos/3-4) y [4.1](/conceptos/4-1)).

### Confiar ciegamente en el reloj del equipo

Sin validar el momento, una lectura de 1970 o de 2099 rompe los gráficos y los cálculos diarios. Validá el rango y guardá también la hora de recepción.

### Una consulta por elemento

Cincuenta `INSERT` por lote, con cientos de equipos, multiplican la carga de la base. Insertá el lote en una consulta.

### Cambiar el formato sin versionar

Cambiar un campo de la `v1` deja sin servicio a todos los equipos con firmware anterior. Los cambios incompatibles van a una versión nueva.

router.post("/api/v1/eventos-riego", express.json({ limit: "4kb" }), autenticarEquipo, async (req, res) => {

  if (typeof id !== "string" || !/^[A-Za-z0-9-]{1,40}$/.test(id)) {

  const momentoMs = Date.parse(momento);

    return res.status(400).json({ error: "litros inválidos" });

  );

});

## Resumen

- La API de ingesta recibe lotes de equipos que reintentan: tiene que tolerar duplicados y datos malos sin trabarse.
- Validá cada elemento por separado, guardá los válidos y respondé qué pasó con cada uno: aceptado, duplicado o rechazado.
- Idempotencia con el identificador del equipo: clave única `(dispositivo_id, id_envio)` y `ON CONFLICT DO NOTHING`. Para órdenes sin identificador natural, `Idempotency-Key`.
- Guardá el momento del equipo y la hora de recepción, y rechazá momentos imposibles.
- Insertá cada lote en una consulta, y versioná la API desde el primer día.
