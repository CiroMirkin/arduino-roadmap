La **arquitectura hexagonal** (también llamada *puertos y adaptadores*, y muy parecida a la *Clean Architecture*) organiza una aplicación en dos zonas: un **centro** con las reglas del negocio, que no sabe nada de HTTP, de bases de datos ni de librerías; y unos **adaptadores** alrededor, que conectan ese centro con el mundo. El centro define lo que necesita como **puertos** ("guardar una orden de riego", "saber la hora"), y cada adaptador implementa uno ("con PostgreSQL", "con el reloj del sistema"). Es la misma idea que separar el firmware en aplicación, servicios y drivers (ver [2.1](/conceptos/2-1)), aplicada al backend.

## Por qué te importa

En el firmware ya viste el beneficio: la lógica de riego, separada de los pines y de los sensores, se prueba en la computadora con dobles de prueba (ver [2.8](/conceptos/2-8)). En el backend pasa lo mismo cuando las reglas crecen. Si la decisión de si se puede regar una zona (permiso, cupo de agua del día, si ya hay un riego en curso, si el tanque está vacío) está mezclada dentro de una ruta de Express con cinco consultas SQL, para probarla hace falta levantar el servidor y una base de datos. Y la misma regla, cuando aparece en otro lugar (una tarea programada, un comando de la pantalla del controlador), se copia.

## Cómo funciona

Hay tres partes:

1. El **dominio** y los **casos de uso**: funciones u objetos con las reglas. "Programar un riego" recibe los datos ya limpios, consulta lo que necesita a través de puertos, decide y devuelve un resultado.
2. Los **puertos**: lo que el dominio necesita del exterior, descripto en sus propios términos (`riegosDelDia(zonaId)`, `ahora()`, `enviarOrden(controlador, orden)`), sin mencionar SQL ni HTTP.
3. Los **adaptadores**: del lado de entrada, la ruta de Express, una tarea programada o un mensaje MQTT, que traducen y llaman al caso de uso; del lado de salida, el repositorio de PostgreSQL, el cliente MQTT o el reloj, que implementan los puertos.

La regla que lo sostiene: **las dependencias apuntan hacia adentro**. Los adaptadores conocen al dominio; el dominio no conoce a ningún adaptador. Quien arma todo (el `index.js` que arranca el servidor) crea los adaptadores y se los pasa al caso de uso.

## Ejemplo

El caso de uso de programar un riego manual, con sus puertos recibidos como parámetros:

```js dominio/programar-riego.js
// Sin require de express ni de pg: solo reglas.
const CUPO_DIARIO_LITROS = 2000;
const CAUDAL_L_POR_S = 0.5;

async function programarRiego({ zonaId, segundos }, { riegos, tanque, reloj, controladores }) {
  if (await riegos.hayUnoEnCurso(zonaId)) {
    return { ok: false, motivo: "ya hay un riego en curso en la zona" };
  }
  if (await tanque.estaVacio(zonaId)) {
    return { ok: false, motivo: "tanque vacío" };
  }
  const usados = await riegos.litrosDelDia(zonaId, reloj.ahora());
  if (usados + segundos * CAUDAL_L_POR_S > CUPO_DIARIO_LITROS) {
    return { ok: false, motivo: "supera el cupo diario de agua" };
  }
  const orden = await riegos.crear({ zonaId, segundos, momento: reloj.ahora() });
  await controladores.enviarOrden(zonaId, orden);
  return { ok: true, orden };
}

module.exports = { programarRiego };
```

```js adaptadores/http-riego.js
const { programarRiego } = require("../dominio/programar-riego");

function rutaRiego(puertos) {
  return async (req, res) => {
    // permisos (4.2) y validación (6.3) ya pasaron en los middlewares
    const r = await programarRiego(
      { zonaId: req.zona.id, segundos: req.body.segundos },
      puertos
    );
    if (!r.ok) return res.status(409).json({ error: r.motivo });
    res.status(202).json({ orden: r.orden.id });
  };
}

module.exports = { rutaRiego };
```

```js dominio/programar-riego.test.js
const test = require("node:test");
const assert = require("node:assert");
const { programarRiego } = require("./programar-riego");

function puertosFalsos({ usados = 0, enCurso = false, vacio = false } = {}) {
  const enviadas = [];
  return {
    enviadas,
    riegos: {
      hayUnoEnCurso: async () => enCurso,
      litrosDelDia: async () => usados,
      crear: async (datos) => ({ id: 1, ...datos }),
    },
    tanque: { estaVacio: async () => vacio },
    reloj: { ahora: () => new Date("2026-10-05T14:00:00Z") },
    controladores: { enviarOrden: async (zona, orden) => enviadas.push(orden) },
  };
}

test("rechaza si supera el cupo diario", async () => {
  const p = puertosFalsos({ usados: 1990 });
  const r = await programarRiego({ zonaId: 4, segundos: 60 }, p);   // 30 litros más
  assert.strictEqual(r.ok, false);
  assert.strictEqual(p.enviadas.length, 0);
});

test("programa y envía la orden si todo está bien", async () => {
  const p = puertosFalsos();
  const r = await programarRiego({ zonaId: 4, segundos: 60 }, p);
  assert.strictEqual(r.ok, true);
  assert.strictEqual(p.enviadas.length, 1);
});
```

Las pruebas corren en milisegundos, sin servidor ni base. La ruta de Express queda en cinco líneas: traduce el pedido y la respuesta. Si mañana la misma orden llega desde la pantalla del controlador por MQTT, se escribe otro adaptador de entrada y el caso de uso no cambia. Un detalle: las dos consultas que leen y la que crea no están en una transacción, así que dos pedidos simultáneos podrían pasar el chequeo del cupo; el adaptador de PostgreSQL tendría que resolverlo (ver [5.2](/conceptos/5-2)).

## Cuándo sí y cuándo no

Conviene cuando:

- hay reglas de negocio con varias condiciones que vale la pena probar una por una,
- la misma regla se usa desde varias entradas (HTTP, tareas programadas, mensajes),
- es probable que cambie una pieza de infraestructura (la base, la cola de mensajes, el proveedor de notificaciones).

No conviene cuando:

- la mayor parte del código es leer y guardar formularios (CRUD) sin reglas: las capas agregan archivos sin beneficio,
- el equipo es chico y el sistema nuevo: se puede empezar simple y extraer el dominio del módulo que lo necesite cuando aparezcan las reglas.

## Resumen

- El centro tiene las reglas y no conoce HTTP, SQL ni librerías; los adaptadores lo conectan con el mundo.
- El dominio define puertos con sus propios términos; los adaptadores los implementan.
- Las dependencias apuntan hacia adentro: el dominio no importa ningún adaptador.
- El beneficio principal: probar las reglas sin infraestructura y reusarlas desde varias entradas.
- Es la misma idea que las capas del firmware; se adopta de a partes, donde hay reglas.
