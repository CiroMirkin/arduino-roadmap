El backend del invernadero recibe lecturas y envía órdenes a equipos que están en el campo. Tiene que poder responder dos preguntas en cada petición: **¿quién es este equipo?** y **¿a qué organización e invernadero pertenece?** Sin eso, cualquiera que conozca la URL puede enviar lecturas falsas o pedir la configuración de otro cliente. La **autenticación de dispositivos** resuelve la primera pregunta con un secreto que solo tiene ese equipo; el backend lo verifica y, a partir de ahí, sabe todo lo demás.

## Por qué te importa

Con varias organizaciones en el mismo backend (ver [4.1](/conceptos/4-1)), un error de autenticación no es un problema de un equipo: es que un productor puede ver o modificar los invernaderos de otro. Y los equipos están físicamente al alcance de cualquiera: un controlador se puede desarmar y leer su memoria. El diseño tiene que suponer que **alguna clave se va a filtrar** y que el daño quede limitado a ese equipo.

## Cómo funciona

**Una clave por equipo.** Cada controlador tiene su propia clave larga y aleatoria (por ejemplo, 32 bytes en hexadecimal). La envía en cada petición, sobre HTTPS, en un encabezado:

```text
Authorization: Bearer 5f3c9a...e81b
```

El backend busca qué equipo tiene esa clave y, de ahí, su organización e invernadero. La alternativa de una clave compartida por organización es más simple de instalar, pero si se filtra una vez, compromete a todos los equipos de esa organización.

**El backend guarda hashes, no claves.** Como con las contraseñas, el backend guarda un hash de cada clave. Si roban la base de datos, no obtienen claves utilizables.

**Aprovisionamiento.** La clave tiene que llegar al equipo de forma segura. Opciones comunes: generarla al fabricar o instalar el equipo y grabarla en la NVS (ver [0.11](/conceptos/0-11)), o que el equipo nuevo se registre con un **código de alta** de un solo uso (impreso en una etiqueta o en un QR) y reciba su clave definitiva del backend.

**Revocación y rotación.** Si un equipo se pierde o se sospecha que su clave se filtró, se **revoca** en el backend: deja de funcionar al instante, sin afectar a los demás. **Rotar** es cambiar la clave periódicamente: el backend entrega una nueva al equipo, acepta las dos durante un período de transición, y después invalida la vieja.

**Alternativas más fuertes.** Con **TLS mutuo**, cada equipo tiene un certificado propio y el servidor lo verifica durante la conexión; la clave privada nunca viaja. Con **tokens de corta duración** (por ejemplo, JWT), el equipo usa su secreto para pedir un token que vence en una hora, y el token es lo que viaja en cada petición. Los dos agregan complejidad, a cambio de más seguridad.

## Ejemplo

Del lado del equipo, la clave se lee de la NVS (nunca escrita en el código) y se agrega a cada petición:

```cpp autenticacion.ino
#include <WiFi.h>
#include <HTTPClient.h>
#include <Preferences.h>

char claveEquipo[65];   // 32 bytes en hexadecimal + '\0'

bool cargarClave() {
  Preferences prefs;
  prefs.begin("equipo", true);
  size_t n = prefs.getString("clave", claveEquipo, sizeof(claveEquipo));
  prefs.end();
  return n == 64;   // sin clave válida, el equipo no está dado de alta
}

int enviarConAutenticacion(const char* url, const char* cuerpo) {
  char encabezado[80];
  snprintf(encabezado, sizeof(encabezado), "Bearer %s", claveEquipo);

  HTTPClient http;
  http.begin(url);   // en producción: HTTPS con verificación del certificado (ver 0.10)
  http.setTimeout(5000);
  http.addHeader("Content-Type", "application/json");
  http.addHeader("Authorization", encabezado);
  int codigo = http.POST(cuerpo);
  http.end();
  return codigo;   // 401: la clave fue revocada o es incorrecta
}

void setup() {
  Serial.begin(115200);
  if (!cargarClave()) {
    Serial.println("equipo sin dar de alta: no hay clave en la NVS");
  }
}

void loop() {}
```

Del lado del backend (Node.js con Express), un *middleware* verifica la clave en cada petición y deja a mano el equipo y su organización:

```js autenticacion.js
const crypto = require("crypto");

function hashClave(clave) {
  return crypto.createHash("sha256").update(clave).digest("hex");
}

async function autenticarEquipo(req, res, next) {
  const encabezado = req.get("Authorization") || "";
  const [tipo, clave] = encabezado.split(" ");
  if (tipo !== "Bearer" || !clave) {
    return res.status(401).json({ error: "falta la clave del equipo" });
  }

  const { rows } = await req.db.query(
    `SELECT id, organizacion_id, invernadero_id
       FROM dispositivos
      WHERE clave_hash = $1 AND revocado = false`,
    [hashClave(clave)]
  );
  if (rows.length === 0) {
    return res.status(401).json({ error: "clave inválida o revocada" });
  }

  req.equipo = rows[0];   // a partir de acá, cada consulta filtra por req.equipo.organizacion_id
  next();
}

module.exports = { autenticarEquipo, hashClave };
```

Las claves son largas y aleatorias, así que un hash SHA-256 alcanza (para contraseñas elegidas por personas haría falta un algoritmo lento, como bcrypt). La organización y el invernadero salen de la base de datos, **nunca** de lo que el equipo dice en el cuerpo del mensaje: un equipo no puede declarar que pertenece a otra organización. El filtro por organización se ve en [4.1](/conceptos/4-1).

## Cuándo sí y cuándo no

- **Clave por equipo**: siempre. Es el mínimo razonable, y la base para revocar equipos sin afectar a los demás.
- **Clave compartida por organización**: solo en un prototipo, nunca en equipos instalados.
- **Rotación periódica**: conviene en cuanto hay muchos equipos o equipos que llevan años instalados.
- **TLS mutuo o tokens de corta duración**: cuando la seguridad es crítica o hay requisitos de un cliente; agregan complejidad en el aprovisionamiento.
- Cualquiera de estas opciones **sin HTTPS** no sirve: la clave viajaría en texto plano.

## Resumen

- Cada equipo tiene su propia clave larga y aleatoria, guardada en la NVS, y la envía en cada petición sobre HTTPS.
- El backend guarda un hash de cada clave, y deduce la organización y el invernadero de la base de datos, no de lo que dice el equipo.
- Una clave por equipo permite revocar solo el equipo comprometido.
- El aprovisionamiento (cómo llega la clave) y la rotación (cómo se cambia) son parte del diseño.
- TLS mutuo y tokens de corta duración dan más seguridad a cambio de más complejidad.
