Un sketch de Arduino no tiene una función `main()` como un programa de C++ común. El framework arranca el chip, llama una vez a `setup()` y después llama a `loop()` una y otra vez, para siempre. Todo lo que hace el dispositivo tiene que entrar en ese ciclo. `delay()` detiene el ciclo; `millis()` permite medir el tiempo sin detenerlo, y es la base para que el controlador haga muchas cosas a la vez.

## Por qué te importa

El primer sketch que todos escriben hace parpadear un LED con `delay(1000)`. Funciona, y lleva a escribir así todo lo demás: regar es `encenderBomba(); delay(30000); apagarBomba();`. Pero durante esos 30 segundos el controlador del invernadero no lee la temperatura, no atiende el botón de emergencia y no actualiza la pantalla. Si en ese medio minuto la temperatura sube a 40 °C, nadie abre las ventanas.

`millis()` resuelve eso: en lugar de esperar, el programa pregunta en cada vuelta si ya pasó el tiempo. Cada vuelta de `loop()` dura microsegundos, así que el controlador atiende todo casi al mismo tiempo.

## Paso a paso

### 1. Qué pasa antes de `setup()` y después de `loop()`

Cuando el ESP32 arranca, el core de Arduino inicializa el hardware y después hace algo equivalente a esto:

```cpp
void main() {        // escrito por el framework, no por vos
  setup();
  for (;;) {
    loop();
  }
}
```

`setup()` es el lugar para configurar: pines, `Serial.begin()`, inicializar sensores. `loop()` se ejecuta miles de veces por segundo, y cada vez que termina, vuelve a empezar. Las variables locales de `loop()` se crean de nuevo en cada vuelta; lo que tiene que recordarse entre vueltas va en variables globales o `static` (ver [B.7](/conceptos/b-7)).

En el ESP32, `loop()` corre dentro de una tarea de FreeRTOS. Mientras tanto, otras tareas manejan el WiFi y el BLE. Eso se ve en [2.4](/conceptos/2-4).

### 2. `delay()` congela tu código

```cpp
void loop() {
  digitalWrite(PIN_BOMBA, HIGH);
  delay(30000);                    // 30 segundos sin hacer nada más
  digitalWrite(PIN_BOMBA, LOW);
  delay(300000);                   // 5 minutos sin hacer nada más
}
```

Durante un `delay`, la línea siguiente no se ejecuta. En el ESP32 el sistema sigue atendiendo el WiFi y el BLE en sus propias tareas, pero tu `loop()` queda detenido. Para un sketch que hace una sola cosa no importa; para un controlador que tiene que vigilar varias, es un problema.

### 3. `millis()`: la hora desde el arranque

```cpp
uint32_t ahora = millis();   // milisegundos desde que arrancó el equipo
```

`millis()` devuelve cuántos milisegundos pasaron desde el arranque, como un `unsigned long` de 32 bits. Llamarlo no detiene nada. Con eso se puede medir cuánto tiempo pasó desde un momento guardado:

```cpp
uint32_t inicio = millis();
// ... más tarde ...
uint32_t transcurrido = millis() - inicio;
```

A los 4.294.967.295 ms (unos 49,7 días) el contador da la vuelta a 0. Por eso siempre se usa un tipo sin signo de 32 bits y siempre se mide con una resta: `millis() - inicio` da el tiempo correcto aunque el contador haya pasado por cero en el medio, porque los enteros sin signo también dan la vuelta en la resta (ver [B.1](/conceptos/b-1)).

### 4. El patrón: preguntar en lugar de esperar

```cpp
constexpr uint32_t INTERVALO_MS = 1000;
uint32_t ultimo = 0;

void loop() {
  if (millis() - ultimo >= INTERVALO_MS) {
    ultimo = millis();
    // lo que hay que hacer cada segundo
  }
  // el resto del loop sigue corriendo
}
```

En cada vuelta, `loop()` pregunta: ¿pasó al menos un segundo desde la última vez? Casi siempre la respuesta es no y sigue de largo. Cuando es sí, hace la tarea y anota el momento. Ninguna parte del código espera.

### 5. Varias tareas con distintos tiempos

Con una variable `ultimo` por tarea, cada una corre a su propio ritmo:

```cpp
void loop() {
  static uint32_t ultimaLectura = 0;
  static uint32_t ultimaPantalla = 0;

  if (millis() - ultimaLectura >= 2000) {
    ultimaLectura = millis();
    leerSensores();
  }
  if (millis() - ultimaPantalla >= 500) {
    ultimaPantalla = millis();
    actualizarPantalla();
  }
  atenderBoton();   // en cada vuelta
}
```

Esto se llama a veces *multitarea cooperativa*: cada tarea hace su parte rápido y devuelve el control. Funciona mientras ninguna tarea bloquee.

### 6. Duraciones: algo que empieza y termina

Para algo que dura un tiempo, como un riego de 30 segundos, se guarda cuándo empezó y se pregunta en cada vuelta si ya terminó:

```cpp
bool regando = false;
uint32_t inicioRiego = 0;

void empezarRiego() {
  digitalWrite(PIN_BOMBA, HIGH);
  regando = true;
  inicioRiego = millis();
}

void actualizarRiego() {
  if (regando && millis() - inicioRiego >= 30000) {
    digitalWrite(PIN_BOMBA, LOW);
    regando = false;
  }
}
```

`empezarRiego()` vuelve enseguida. `actualizarRiego()` se llama en cada vuelta de `loop()` y apaga la bomba cuando corresponde. Mientras tanto, el resto del controlador sigue trabajando.

## Ejemplos

### Ejemplo 1. Parpadear sin `delay`

El LED de un nodo parpadea mientras su botón sigue respondiendo al instante.

```cpp parpadeo.ino
// nodo (ESP32 clásico)
constexpr uint8_t PIN_LED = 2;
constexpr uint8_t PIN_BOTON = 27;
constexpr uint32_t PARPADEO_MS = 500;

void setup() {
  Serial.begin(115200);
  pinMode(PIN_LED, OUTPUT);
  pinMode(PIN_BOTON, INPUT_PULLUP);
}

void loop() {
  static uint32_t ultimoCambio = 0;
  static bool encendido = false;

  if (millis() - ultimoCambio >= PARPADEO_MS) {
    ultimoCambio = millis();
    encendido = !encendido;
    digitalWrite(PIN_LED, encendido ? HIGH : LOW);
  }

  if (digitalRead(PIN_BOTON) == LOW) {
    Serial.println("botón presionado");   // responde aunque el LED esté a mitad de ciclo
  }
}
```

Probá la versión con `delay(500)` y presioná el botón rápido: la mayoría de las pulsaciones se pierden. Con `millis()`, ninguna. (El botón imprime muchas veces mientras lo mantenés presionado; cómo detectar una sola pulsación se ve en [0.3](/conceptos/0-3).)

### Ejemplo 2. El ciclo del controlador

Lectura de sensores cada 2 segundos, pantalla cada 500 ms, envío al backend cada minuto, y control de ventilación con cada lectura nueva.

```cpp controlador.ino
constexpr uint32_t LECTURA_MS = 2000;
constexpr uint32_t PANTALLA_MS = 500;
constexpr uint32_t ENVIO_MS = 60000;

float temperatura = 0.0f;
int humedadSuelo = 0;

void leerSensores() {
  temperatura = 20.0f + (millis() / 1000 % 15);   // simulado: sube y baja
  humedadSuelo = 40;
}

void controlarVentilacion() {
  Serial.println(temperatura > 30.0f ? "ventanas: abiertas" : "ventanas: cerradas");
}

void actualizarPantalla() {
  // dibujar en la pantalla; acá, nada
}

void enviarAlBackend() {
  Serial.printf("enviando %.1f C, %d%%\n", temperatura, humedadSuelo);
}

void setup() {
  Serial.begin(115200);
}

void loop() {
  static uint32_t ultimaLectura = 0;
  static uint32_t ultimaPantalla = 0;
  static uint32_t ultimoEnvio = 0;
  uint32_t ahora = millis();

  if (ahora - ultimaLectura >= LECTURA_MS) {
    ultimaLectura = ahora;
    leerSensores();
    controlarVentilacion();
  }
  if (ahora - ultimaPantalla >= PANTALLA_MS) {
    ultimaPantalla = ahora;
    actualizarPantalla();
  }
  if (ahora - ultimoEnvio >= ENVIO_MS) {
    ultimoEnvio = ahora;
    enviarAlBackend();
  }
}
```

`ahora` se lee una sola vez por vuelta, así todas las comparaciones usan el mismo instante. Cada tarea es una función corta, y `loop()` solo decide cuándo llamar a cada una. Cuando este patrón crece, conviene ordenarlo en clases o en tareas de FreeRTOS, como se ve en [2.1](/conceptos/2-1) y [2.3](/conceptos/2-3).

### Ejemplo 3. Una clase `Temporizador` y un riego por tiempo

El patrón del `if` con `millis()` se repite tanto que conviene encapsularlo. Con una clase chica, el riego programado (30 segundos cada 5 minutos) queda claro y sin bloquear.

```cpp riego-temporizado.ino
class Temporizador {
public:
  explicit Temporizador(uint32_t intervaloMs) : _intervaloMs(intervaloMs) {}

  // true una vez cada intervalo
  bool listo() {
    if (millis() - _ultimo >= _intervaloMs) {
      _ultimo += _intervaloMs;            // sin deriva acumulada
      if (millis() - _ultimo >= _intervaloMs) {
        _ultimo = millis();               // si se atrasó mucho, no recuperar de golpe
      }
      return true;
    }
    return false;
  }

  void reiniciar() { _ultimo = millis(); }

private:
  uint32_t _intervaloMs;
  uint32_t _ultimo = 0;
};

constexpr uint8_t PIN_BOMBA = 4;
constexpr uint32_t DURACION_RIEGO_MS = 30UL * 1000UL;

Temporizador cadaCincoMinutos(5UL * 60UL * 1000UL);
bool regando = false;
uint32_t inicioRiego = 0;

void setup() {
  Serial.begin(115200);
  pinMode(PIN_BOMBA, OUTPUT);
  digitalWrite(PIN_BOMBA, LOW);
}

void loop() {
  if (!regando && cadaCincoMinutos.listo()) {
    digitalWrite(PIN_BOMBA, HIGH);
    regando = true;
    inicioRiego = millis();
    Serial.println("riego: inicio");
  }

  if (regando && millis() - inicioRiego >= DURACION_RIEGO_MS) {
    digitalWrite(PIN_BOMBA, LOW);
    regando = false;
    Serial.println("riego: fin");
  }

  // acá siguen el resto de las tareas: sensores, pantalla, botones
}
```

`_ultimo += _intervaloMs` mantiene el ritmo exacto aunque `loop()` llegue unos milisegundos tarde a cada chequeo: el siguiente intervalo se cuenta desde cuando *tocaba*, no desde cuando se detectó. El segundo `if` evita un caso raro: si `loop()` estuvo bloqueado varios intervalos, el temporizador no dispara varias veces seguidas para ponerse al día.

## Errores comunes

### `delay` dentro de `loop()` en código que vigila otras cosas

```cpp
// Mal
void loop() {
  leerSensores();
  delay(2000);
}

// Bien
void loop() {
  static uint32_t ultima = 0;
  if (millis() - ultima >= 2000) {
    ultima = millis();
    leerSensores();
  }
}
```

`delay` está bien en `setup()` para esperar a que un sensor arranque, o en pruebas rápidas. En la lógica del controlador, no.

### Comparar con una suma

```cpp
// Mal: falla cuando millis() da la vuelta
if (millis() >= ultimo + intervalo) { /* ... */ }

// Bien
if (millis() - ultimo >= intervalo) { /* ... */ }
```

El error aparece recién a los 49,7 días de funcionamiento continuo, y por eso nunca se ve en las pruebas.

### Guardar `millis()` en un tipo equivocado

```cpp
// Mal
int ultimo = millis();          // con signo: la resta se rompe al desbordar
float ultimoF = millis();       // pierde precisión con valores grandes

// Bien
uint32_t ultimo = millis();
```

### Bloquear con un `while` que espera

```cpp
// Mal: es un delay disfrazado
while (millis() - inicio < 30000) { }

// Bien: preguntar en cada vuelta de loop() y seguir de largo
if (millis() - inicio >= 30000) { terminarRiego(); }
```

## Ejercicio

Este sketch riega 10 segundos cada 5 minutos y tiene un botón para detener el riego. El botón casi nunca funciona. Reescribilo con `millis()` para que el botón responda siempre, incluso a la mitad de un riego.

```cpp riego-bloqueante.ino
constexpr uint8_t PIN_BOMBA = 4;
constexpr uint8_t PIN_DETENER = 16;

void setup() {
  pinMode(PIN_BOMBA, OUTPUT);
  pinMode(PIN_DETENER, INPUT_PULLUP);
}

void loop() {
  if (digitalRead(PIN_DETENER) == LOW) {
    digitalWrite(PIN_BOMBA, LOW);
  }
  digitalWrite(PIN_BOMBA, HIGH);
  delay(10000);
  digitalWrite(PIN_BOMBA, LOW);
  delay(300000);
}
```

<details>
<summary>Pista</summary>

Hacen falta dos cosas guardadas entre vueltas: si está regando, y cuándo empezó el riego (o el último riego). El botón se lee en cada vuelta, fuera de cualquier espera.

</details>

<details>
<summary>Ver solución</summary>

```cpp riego-no-bloqueante.ino
constexpr uint8_t PIN_BOMBA = 4;
constexpr uint8_t PIN_DETENER = 16;
constexpr uint32_t DURACION_MS = 10UL * 1000UL;
constexpr uint32_t PERIODO_MS = 5UL * 60UL * 1000UL;

bool regando = false;
uint32_t inicioRiego = 0;
uint32_t ultimoRiego = 0;

void setup() {
  pinMode(PIN_BOMBA, OUTPUT);
  digitalWrite(PIN_BOMBA, LOW);
  pinMode(PIN_DETENER, INPUT_PULLUP);
}

void loop() {
  uint32_t ahora = millis();

  if (!regando && ahora - ultimoRiego >= PERIODO_MS) {
    digitalWrite(PIN_BOMBA, HIGH);
    regando = true;
    inicioRiego = ahora;
    ultimoRiego = ahora;
  }

  if (regando && ahora - inicioRiego >= DURACION_MS) {
    digitalWrite(PIN_BOMBA, LOW);
    regando = false;
  }

  if (regando && digitalRead(PIN_DETENER) == LOW) {
    digitalWrite(PIN_BOMBA, LOW);
    regando = false;
  }
}
```

En la versión original, el botón se leía una sola vez cada 310 segundos, en el instante entre el fin de un `delay` y el principio del siguiente. Ahora `loop()` da miles de vueltas por segundo y lee el botón en todas. El primer riego empieza a los 5 minutos del arranque; si querés que empiece enseguida, inicializá `ultimoRiego` con `-PERIODO_MS`, que en un `uint32_t` da la vuelta al valor correcto.

</details>

## Resumen

- El framework llama a `setup()` una vez y a `loop()` para siempre. Lo que tiene que recordarse entre vueltas va en variables globales o `static`.
- `delay()` congela tu `loop()`: mientras espera, no se atiende nada más.
- `millis()` da los milisegundos desde el arranque, en un `uint32_t` que da la vuelta a los 49,7 días.
- El patrón no bloqueante: `if (millis() - ultimo >= intervalo) { ultimo = millis(); ... }`. Siempre con resta.
- Para algo que dura un tiempo, guardá cuándo empezó y preguntá en cada vuelta si ya terminó.
