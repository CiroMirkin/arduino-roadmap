Un firmware que funciona en el banco de pruebas no está terminado: le falta decidir **qué hacer cuando algo sale mal**. Un sensor deja de responder, la red se cae, la flash se llena, una tarea se cuelga. El manejo de errores en firmware tiene tres partes: **informar** el error (con valores de retorno, porque en Arduino no se usan excepciones), **reaccionar** de forma definida de antemano (reintentar, degradar el servicio, pasar a un estado seguro) y, como última red, el **watchdog**: un temporizador del hardware que reinicia el chip si el programa deja de dar señales de vida.

## Por qué te importa

El controlador del invernadero maneja agua y temperatura de plantas vivas, sin nadie mirando la mayor parte del tiempo. Un error mal manejado no se ve como un mensaje en una pantalla: se ve como una bomba que quedó encendida toda la noche, unas ventanas que no cerraron durante una helada, o un equipo colgado que dejó de controlar todo durante un fin de semana.

La pregunta de diseño para cada pieza es: **si esto falla, ¿cuál es el estado seguro?** Para la bomba, apagada. Para las ventanas, depende de la estación. Para el envío al backend, guardar y reintentar. Tener esas respuestas escritas en el código, y un watchdog que garantice que el código sigue corriendo, es lo que permite dejar el equipo solo.

## Paso a paso

### 1. Tres clases de problemas

| Clase | Ejemplos | Respuesta |
|---|---|---|
| Errores esperables | sensor desconectado, red caída, servidor con error, tanque vacío | detectarlos y reaccionar de forma definida |
| Bugs | índice fuera de rango, puntero nulo, división por cero | evitarlos con diseño y pruebas; si ocurren, el chip se reinicia |
| Cuelgues | una espera sin tiempo máximo, un deadlock, un bucle infinito | el watchdog los convierte en reinicios |

Esta lección se ocupa sobre todo de la primera y la tercera.

### 2. Informar errores sin excepciones

En el firmware de Arduino no se usan excepciones de C++: el código las tiene que propagar a mano. Las formas habituales:

```cpp
bool leer(float& valor);                      // true si salió bien; el valor, por referencia

enum class ResultadoEnvio : uint8_t { Ok, SinRed, Rechazado, ErrorServidor };
ResultadoEnvio enviar(const Lectura& l);      // varios tipos de error distintos

[[nodiscard]] bool guardarConfig(const Config& c);   // el compilador avisa si se ignora el resultado
```

`[[nodiscard]]` le pide al compilador que advierta cuando alguien llama a la función y no usa lo que devuelve. Ponelo en toda función cuyo error no debería ignorarse.

### 3. Reaccionar: reintentar, degradar, estado seguro, avisar

Para cada error esperable, una respuesta decidida de antemano:

- **Reintentar**, con un límite y esperando entre intentos (ver [3.5](/conceptos/3-5)): sirve para errores pasajeros, como un envío fallido.
- **Degradar**: seguir funcionando con menos. Si se pierde el sensor de suelo, regar por horario; si se cae la red, guardar las lecturas localmente.
- **Estado seguro**: si no hay forma de seguir con seguridad, llevar los actuadores a la posición menos peligrosa. La bomba apagada casi siempre es la opción segura.
- **Avisar**: una alarma en la pantalla y en el backend, para que una persona se entere.

Un detalle importante: una falla **momentánea** no debería disparar todo eso. Un sensor que falla una lectura de cada cien es normal; uno que falla diez seguidas no. Contar las fallas consecutivas antes de reaccionar evita alarmas falsas.

### 4. El watchdog

El watchdog es un temporizador del hardware que cuenta hacia atrás. El programa tiene que **alimentarlo** (reiniciar la cuenta) periódicamente. Si pasa el tiempo configurado sin que lo alimenten, el watchdog asume que el programa se colgó y reinicia el chip.

El ESP32 tiene varios. El que se usa en el código es el **watchdog de tareas** (*Task Watchdog*, TWDT): vigila una lista de tareas, y cada una tiene que alimentarlo dentro del plazo (5 segundos por defecto en el core de Arduino). Para la tarea de `loop()`, el core tiene funciones propias:

```cpp
void setup() {
  enableLoopWDT();       // vigilar loop(): si una vuelta tarda más del plazo, reinicio
}
```

El core alimenta este watchdog automáticamente al terminar cada vuelta de `loop()`. Así, mientras `loop()` siga dando vueltas, no pasa nada; si se cuelga dentro de una vuelta, el chip se reinicia. Para tareas propias de FreeRTOS:

```cpp
#include <esp_task_wdt.h>

void tareaComunicacion(void*) {
  esp_task_wdt_add(nullptr);          // vigilar esta tarea
  for (;;) {
    // ... una vuelta de trabajo, con tiempos máximos en todo lo que espera ...
    esp_task_wdt_reset();             // "sigo viva": un solo lugar por vuelta
  }
}
```

La regla de oro: **alimentar el watchdog en un solo lugar**, al completar una vuelta de trabajo. Si se alimenta dentro de cada bucle de espera, una espera infinita sigue alimentándolo y el cuelgue nunca se detecta.

### 5. Saber por qué se reinició

Al arrancar, `esp_reset_reason()` dice por qué se reinició el chip:

| Valor | Significado |
|---|---|
| `ESP_RST_POWERON` | se encendió (o volvió la luz) |
| `ESP_RST_SW` | reinicio por software (`ESP.restart()`) |
| `ESP_RST_PANIC` | error grave: excepción, `abort`, puntero inválido |
| `ESP_RST_TASK_WDT` / `ESP_RST_INT_WDT` / `ESP_RST_WDT` | algún watchdog |
| `ESP_RST_BROWNOUT` | el voltaje bajó demasiado (fuente débil, bomba arrancando) |
| `ESP_RST_DEEPSLEEP` | despertó de un deep sleep |

Informar la causa al backend en cada arranque convierte "a veces se reinicia" en "se reinicia por watchdog los días de mucho viento", que ya es una pista. Los `BROWNOUT` son muy comunes cuando la bomba y el ESP32 comparten una fuente chica.

### 6. Arrancar en un estado seguro

Después de un reinicio, el controlador no sabe qué estaba haciendo. Por eso `setup()` lleva **todos los actuadores a su estado seguro primero**, antes de cualquier otra cosa, y después reconstruye el estado leyendo sensores y fines de carrera. Si los reinicios se repiten (un *bucle de reinicios*), conviene detectarlo y arrancar en un **modo seguro**, con funciones mínimas, en lugar de repetir el mismo error cada pocos segundos.

## Ejemplos

### Ejemplo 1. Errores como valores, y un comportamiento degradado

La lectura del sensor de suelo devuelve un resultado con el motivo del error. El control cuenta las fallas seguidas y, a partir de cinco, deja de regar por humedad y pasa a riego por horario.

```cpp errores-sensor.ino
enum class ResultadoLectura : uint8_t { Ok, SinRespuesta, FueraDeRango };

[[nodiscard]] ResultadoLectura leerHumedad(float& porcentaje) {
  uint32_t mv = analogReadMilliVolts(2);
  if (mv < 100) return ResultadoLectura::SinRespuesta;          // cable cortado
  if (mv > 3000) return ResultadoLectura::FueraDeRango;         // en corto o dañado
  porcentaje = constrain((2600.0f - mv) / 14.5f, 0.0f, 100.0f);
  return ResultadoLectura::Ok;
}

const char* texto(ResultadoLectura r) {
  switch (r) {
    case ResultadoLectura::Ok:           return "ok";
    case ResultadoLectura::SinRespuesta: return "sin respuesta";
    case ResultadoLectura::FueraDeRango: return "fuera de rango";
  }
  return "?";
}

constexpr int FALLAS_PARA_DEGRADAR = 5;
int fallasSeguidas = 0;
bool modoDegradado = false;

void controlarRiego() {
  float humedad;
  ResultadoLectura r = leerHumedad(humedad);

  if (r == ResultadoLectura::Ok) {
    fallasSeguidas = 0;
    if (modoDegradado) {
      modoDegradado = false;
      Serial.println("sensor recuperado: vuelve el riego por humedad");
    }
    Serial.printf("humedad %.0f%%\n", humedad);   // acá: decidir por humedad
    return;
  }

  fallasSeguidas++;
  Serial.printf("lectura fallida (%s), %d seguidas\n", texto(r), fallasSeguidas);
  if (!modoDegradado && fallasSeguidas >= FALLAS_PARA_DEGRADAR) {
    modoDegradado = true;
    Serial.println("ALARMA: sensor de suelo fuera de servicio, riego por horario");
    // acá: activar la alarma (pantalla y backend)
  }
  if (modoDegradado) {
    // acá: regar por horario (ver la estrategia de 1.6)
  }
}

void setup() {
  Serial.begin(115200);
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 5000) {
    ultimo = millis();
    controlarRiego();
  }
}
```

`[[nodiscard]]` hace que el compilador advierta si alguien escribe `leerHumedad(h);` sin mirar el resultado. Distinguir `SinRespuesta` de `FueraDeRango` ayuda a quien va a revisar el equipo: uno sugiere un cable cortado, el otro un sensor en corto. Al recuperarse el sensor, el sistema vuelve solo al modo normal.

### Ejemplo 2. El watchdog de `loop()` y la causa del reinicio

Este sketch activa el watchdog de `loop()`, informa la causa del último reinicio, y simula un cuelgue a los 20 segundos para ver el watchdog en acción.

```cpp watchdog.ino
const char* causaReinicio(esp_reset_reason_t r) {
  switch (r) {
    case ESP_RST_POWERON:  return "encendido";
    case ESP_RST_SW:       return "reinicio por software";
    case ESP_RST_PANIC:    return "error grave (panic)";
    case ESP_RST_TASK_WDT: return "watchdog de tareas";
    case ESP_RST_INT_WDT:  return "watchdog de interrupciones";
    case ESP_RST_WDT:      return "otro watchdog";
    case ESP_RST_BROWNOUT: return "caída de voltaje";
    case ESP_RST_DEEPSLEEP:return "despertar de deep sleep";
    default:               return "otra";
  }
}

void setup() {
  Serial.begin(115200);
  digitalWrite(4, HIGH);                 // primero: actuadores en estado seguro
  pinMode(4, OUTPUT);

  Serial.printf("arranque, causa: %s\n", causaReinicio(esp_reset_reason()));
  enableLoopWDT();                        // si una vuelta de loop() se cuelga, reinicio
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 1000) {
    ultimo = millis();
    Serial.printf("vivo: %lu s\n", millis() / 1000);
  }

  if (millis() > 20000) {
    Serial.println("simulando un cuelgue...");
    while (true) { }                      // nunca termina la vuelta: el watchdog actúa
  }
}
```

A los 20 segundos el `while (true)` impide que `loop()` termine la vuelta, nadie alimenta el watchdog, y unos segundos después el chip se reinicia. En el arranque siguiente aparece "watchdog de tareas" como causa. Fijate en que `setup()` pone la bomba en su estado seguro antes que cualquier otra cosa.

### Ejemplo 3. Detectar un bucle de reinicios y arrancar en modo seguro

Si el controlador se reinicia por un error una y otra vez en poco tiempo, cada arranque vuelve a encender cosas y a fallar. Un contador en memoria que sobrevive a los reinicios (pero no a un corte de luz) permite detectarlo y arrancar en modo seguro.

```cpp modo-seguro.ino
RTC_NOINIT_ATTR uint32_t reiniciosSeguidos;   // no se borra en un reinicio por software o watchdog
RTC_NOINIT_ATTR uint32_t marcaValida;          // para saber si el contador tiene un valor real

constexpr uint32_t MARCA = 0xC0FFEE42;
constexpr uint32_t LIMITE_REINICIOS = 3;
constexpr uint32_t TIEMPO_ESTABLE_MS = 5UL * 60UL * 1000UL;

bool modoSeguro = false;

bool fueReinicioPorFalla(esp_reset_reason_t r) {
  return r == ESP_RST_PANIC || r == ESP_RST_TASK_WDT || r == ESP_RST_INT_WDT || r == ESP_RST_WDT;
}

void setup() {
  Serial.begin(115200);
  digitalWrite(4, HIGH);                     // bomba apagada antes que nada
  pinMode(4, OUTPUT);

  esp_reset_reason_t causa = esp_reset_reason();
  if (marcaValida != MARCA || causa == ESP_RST_POWERON) {
    marcaValida = MARCA;                       // primer arranque o vuelta de la luz
    reiniciosSeguidos = 0;
  }

  if (fueReinicioPorFalla(causa)) {
    reiniciosSeguidos++;
  }

  if (reiniciosSeguidos >= LIMITE_REINICIOS) {
    modoSeguro = true;
    Serial.printf("MODO SEGURO: %u reinicios por falla seguidos\n",
                  static_cast<unsigned>(reiniciosSeguidos));
    // en modo seguro: sin riego automático, sin la función sospechosa,
    // pantalla con el aviso, y un intento de informar al backend
  } else {
    Serial.printf("arranque normal (%u reinicios por falla seguidos)\n",
                  static_cast<unsigned>(reiniciosSeguidos));
  }

  enableLoopWDT();
}

void loop() {
  // Si el equipo funcionó bien un buen rato, el contador vuelve a cero
  static bool estable = false;
  if (!estable && millis() > TIEMPO_ESTABLE_MS) {
    estable = true;
    reiniciosSeguidos = 0;
    Serial.println("funcionamiento estable: contador de reinicios en cero");
  }

  if (modoSeguro) {
    // solo lo mínimo: mostrar el estado, esperar al operario
    return;
  }
  // control normal...
}
```

`RTC_NOINIT_ATTR` ubica la variable en una memoria que el arranque no inicializa: conserva su valor en un reinicio por software o por watchdog, pero tiene basura después de un corte de luz. Por eso la "marca" mágica: si no coincide, el contador no es confiable y se pone en cero. Tres reinicios por falla sin cinco minutos estables en el medio activan el modo seguro, que se queda hasta que alguien intervenga o se corte la luz.

## Errores comunes

### Ignorar los valores de retorno

```cpp
// Mal
prefs.putFloat("umbral", nuevo);      // ¿se guardó?
leerHumedad(h);                       // ¿h tiene un valor válido?

// Bien
if (prefs.putFloat("umbral", nuevo) == 0) { /* avisar */ }
if (leerHumedad(h) != ResultadoLectura::Ok) { /* reaccionar */ }
```

### Fallar "abierto"

```cpp
// Mal: si el sensor falla, h queda en 0 y el control riega sin parar
float h = 0;
leerHumedad(h);
if (h < 35) regar();

// Bien: sin lectura válida, no se riega por humedad
float h;
if (leerHumedad(h) == ResultadoLectura::Ok && h < 35) regar();
```

Ante la duda, la falla tiene que llevar al estado seguro.

### Alimentar el watchdog en todas partes

```cpp
// Mal: una espera infinita sigue alimentando al watchdog
while (!respuestaRecibida()) {
  esp_task_wdt_reset();
}

// Bien: un tiempo máximo en la espera, y el watchdog se alimenta una vez por vuelta
uint32_t inicio = millis();
while (!respuestaRecibida() && millis() - inicio < 3000) {
  vTaskDelay(pdMS_TO_TICKS(10));
}
```

### No poner los actuadores en estado seguro al arrancar

Si `setup()` configura WiFi, pantalla y sensores antes de apagar la bomba, después de un reinicio la bomba puede quedar encendida varios segundos (o para siempre, si algo falla antes). Los actuadores, primero.

### Reiniciar como respuesta a todo

`ESP.restart()` cada vez que algo falla esconde el problema, interrumpe el control y, si la causa persiste, genera un bucle de reinicios. Reiniciar es la última opción, no la primera.

## Ejercicio

Este código del controlador tiene tres problemas de manejo de errores. Encontralos y corregilos.

```cpp riego-fragil.ino
float leerHumedad() {
  uint32_t mv = analogReadMilliVolts(2);
  return (2600.0f - mv) / 14.5f;         // si el sensor falla, devuelve cualquier cosa
}

bool enviarEstado();                      // true si el backend respondió

void setup() {
  WiFi.begin("invernadero", "clave");
  conectarPantalla();
  enableLoopWDT();
  pinMode(4, OUTPUT);                    // bomba
}

void loop() {
  if (leerHumedad() < 35.0f) digitalWrite(4, LOW);
  else digitalWrite(4, HIGH);

  while (!enviarEstado()) {
    esp_task_wdt_reset();                 // para que el watchdog no reinicie
  }
}
```

```cpp riego-robusto.ino
[[nodiscard]] bool leerHumedad(float& porcentaje) {
  uint32_t mv = analogReadMilliVolts(2);
  if (mv < 100 || mv > 3000) return false;              // sensor desconectado o en corto
  porcentaje = constrain((2600.0f - mv) / 14.5f, 0.0f, 100.0f);
  return true;
}

void setup() {
  digitalWrite(4, HIGH);                               // 1. bomba apagada, antes que nada
  pinMode(4, OUTPUT);
  WiFi.begin("invernadero", "clave");
  conectarPantalla();
  enableLoopWDT();
}

void loop() {
  float h;
  bool regar = leerHumedad(h) && h < 35.0f;             // 2. sin lectura válida, no regar
  digitalWrite(4, regar ? LOW : HIGH);

  static uint32_t ultimoEnvio = 0;
  if (millis() - ultimoEnvio >= 60000) {                // 3. un intento por minuto, sin esperar
    ultimoEnvio = millis();
    if (!enviarEstado()) {
      // queda pendiente para el próximo intento (o en la cola de 0.10)
    }
  }
}
```

El primer problema: si el cable del sensor se cortaba, `mv` era casi 0 y la "humedad" daba 179 %, o con el sensor en corto, un número negativo que encendía la bomba. Ahora la lectura informa si es válida, y sin lectura válida no se riega. El segundo: la bomba se configuraba al final de `setup()`, después del WiFi y la pantalla, así que tras un reinicio quedaba en un estado indefinido mientras tanto. El tercero: el `while` esperaba al backend para siempre, alimentando al watchdog: si la red se caía, el controlador quedaba trabado ahí, sin regar ni detectar el cuelgue. Ahora se intenta una vez por minuto y `loop()` nunca espera; el envío real debería tener sus propios tiempos máximos (ver [0.10](/conceptos/0-10)).

## Resumen

- Para cada error esperable, una respuesta definida: reintentar, degradar, ir al estado seguro y avisar. Contá fallas seguidas antes de reaccionar.
- Sin excepciones, los errores se informan con valores de retorno; `[[nodiscard]]` evita que se ignoren.
- Ante la duda, la falla lleva al estado seguro: sin lectura válida, la bomba no se enciende.
- El watchdog reinicia el chip si una tarea vigilada deja de alimentarlo. Se alimenta en un solo lugar, al completar una vuelta.
- Al arrancar: actuadores en estado seguro primero, informar `esp_reset_reason()`, y detectar bucles de reinicios para entrar en modo seguro.
