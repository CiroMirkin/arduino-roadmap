**Domain-Driven Design** (diseño guiado por el dominio) es un conjunto de ideas para sistemas donde lo difícil son las **reglas del negocio**, no la tecnología. Propone que el código hable el mismo idioma que los expertos del negocio (el **lenguaje ubicuo**), que un sistema grande se divida en **contextos delimitados** donde cada palabra tiene un solo significado, y que las reglas que tienen que cumplirse siempre vivan dentro de **agregados** que las protegen. Es más una forma de pensar el modelo que una estructura de carpetas.

## Por qué te importa

Hoy el sistema del invernadero tiene pocas reglas. Pero el negocio va a pedir más: cupos de agua por invernadero, cultivos con necesidades distintas por etapa, turnos de riego que no se superpongan para no bajar la presión, abonos por cantidad de equipos. Cuando eso pasa, aparecen dos problemas típicos. El código usa palabras que no son las del productor ("registro", "item", "entidad"), y cada conversación necesita traducción. Y la misma palabra significa cosas distintas en distintas partes ("dispositivo" para monitoreo y para facturación), así que el modelo se vuelve una mezcla que nadie entiende del todo.

## Cómo funciona

*Lenguaje ubicuo.* Las clases, funciones y tablas usan las palabras del negocio, con el significado que le da el productor. Si el agrónomo dice "ciclo de riego" y "almácigo", el código también. Cuando aparece una palabra nueva en una charla, es una pista de un concepto que falta en el modelo.

*Contextos delimitados.* Un sistema grande no tiene un único modelo. Monitoreo (lecturas, alarmas), riego (zonas, ciclos, cupos) y facturación (abonos, planes) son contextos distintos, cada uno con su modelo y su lenguaje. Se comunican por interfaces explícitas, compartiendo identificadores, no tablas.

*Objetos de valor.* Conceptos definidos por su valor, sin identidad, que validan lo que contienen: una `Humedad` entre 0 y 100, un `Caudal` en litros por segundo. Una vez creados, no cambian.

*Entidades y agregados.* Una entidad tiene identidad (la zona 4 sigue siendo la zona 4 aunque cambie su nombre). Un agregado es un grupo de entidades que se modifica como una unidad, a través de una raíz, para que las reglas que involucran a todas se cumplan siempre. Se lee y se guarda entero, en una transacción (ver [5.2](/conceptos/5-2)).

*Eventos de dominio.* Algo que pasó y le importa al negocio: "riego terminado", "cupo agotado". Otros contextos reaccionan a ellos sin que el agregado los conozca.

## Ejemplo

Un objeto de valor y un agregado para el cupo de agua del invernadero:

```js riego/humedad.js
class Humedad {
  constructor(porcentaje) {
    if (typeof porcentaje !== "number" || porcentaje < 0 || porcentaje > 100) {
      throw new RangeError("la humedad va de 0 a 100");
    }
    this.porcentaje = porcentaje;
    Object.freeze(this);
  }
  estaPorDebajoDe(otra) {
    return this.porcentaje < otra.porcentaje;
  }
}

module.exports = { Humedad };
```

```js riego/invernadero.js
// Raíz del agregado: toda modificación de riegos pasa por acá.
class Invernadero {
  constructor({ id, cupoDiarioLitros, zonas, litrosUsadosHoy }) {
    this.id = id;
    this.cupoDiarioLitros = cupoDiarioLitros;
    this.zonas = zonas;               // [{ id, riegoEnCurso: bool }]
    this.litrosUsadosHoy = litrosUsadosHoy;
    this.eventos = [];
  }

  iniciarRiego(zonaId, litros) {
    const zona = this.zonas.find((z) => z.id === zonaId);
    if (!zona) throw new Error("la zona no es de este invernadero");
    if (zona.riegoEnCurso) throw new Error("ya hay un riego en curso en la zona");
    if (this.litrosUsadosHoy + litros > this.cupoDiarioLitros) {
      this.eventos.push({ tipo: "cupo_agotado", invernadero: this.id });
      throw new Error("supera el cupo diario del invernadero");
    }
    zona.riegoEnCurso = true;
    this.litrosUsadosHoy += litros;
    this.eventos.push({ tipo: "riego_iniciado", zona: zonaId, litros });
  }
}

module.exports = { Invernadero };
```

El repositorio carga el invernadero con sus zonas y lo usado en el día, llama a `iniciarRiego`, y guarda todo junto en una transacción (con `SELECT ... FOR UPDATE` sobre el invernadero, para que dos riegos simultáneos no pasen el chequeo a la vez). Las reglas que involucran a varias zonas viven en un solo lugar, con los nombres que usa el productor. Los eventos acumulados se publican después de guardar: el contexto de notificaciones avisa del cupo agotado sin que el agregado sepa que existe.

## Cuándo sí y cuándo no

Conviene cuando:

- el valor del sistema está en reglas de negocio complejas que cambian seguido,
- hay expertos del negocio con quienes hablar y un modelo que refinar con ellos,
- el sistema es grande y distintos equipos trabajan en distintas partes.

No conviene, o solo en parte, cuando:

- el sistema es mayormente CRUD y reportes: los agregados y eventos agregan complejidad sin reglas que proteger,
- el equipo es de una o dos personas: el lenguaje ubicuo y los objetos de valor son baratos y útiles siempre; los contextos delimitados y los eventos, cuando el tamaño lo pida.

## Resumen

- DDD es para sistemas donde lo difícil son las reglas del negocio.
- El código usa el lenguaje de los expertos, con un solo significado por contexto.
- Los contextos delimitados separan modelos que usan las mismas palabras con sentidos distintos.
- Los objetos de valor validan y no cambian; los agregados protegen reglas que involucran a varias entidades y se guardan enteros.
- Lo barato (lenguaje y objetos de valor) sirve siempre; lo demás, cuando el dominio lo justifica.
