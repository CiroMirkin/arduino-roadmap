**CQRS** (*Command Query Responsibility Segregation*, separación de responsabilidades entre comandos y consultas) propone usar **un modelo para escribir** y **otro para leer**. Los comandos ("reconocer alarma", "guardar lecturas") pasan por el modelo de escritura, normalizado y con todas las reglas. Las consultas ("el tablero de la organización") leen de un modelo de lectura con la forma exacta que necesita cada pantalla, calculado de antemano. Los dos se sincronizan, normalmente con algo de atraso.

## Por qué te importa

Leer y escribir tienen necesidades opuestas. Para escribir, el modelo normalizado de [5.1](/conceptos/5-1) es ideal: cada dato en un solo lugar, restricciones que garantizan que lo guardado sea válido. Para leer, ese mismo modelo obliga a juntar varias tablas y agregar miles de filas cada vez que alguien abre el tablero. En el sistema del invernadero, las lecturas se escriben de a una por minuto por equipo, y el tablero se consulta muchas veces más de lo que cambia. Cuando los índices (ver [4.5](/conceptos/4-5)) ya no alcanzan para que el tablero sea rápido, separar los modelos es el paso siguiente.

## Cómo funciona

*El lado de escritura* recibe comandos, aplica las reglas (permisos, validaciones, invariantes) y guarda en las tablas normalizadas. No está pensado para responder consultas de pantallas.

*El lado de lectura* tiene una o más **proyecciones**: tablas o vistas con datos ya combinados y agregados. Una por pantalla, si hace falta. Pueden estar en la misma base, en una réplica o en otro almacén (Redis, un motor de búsqueda).

*La sincronización* mantiene las proyecciones al día. Opciones de menor a mayor complejidad: una vista materializada que se refresca cada minuto; actualizar la proyección en la misma transacción que el comando; o publicar eventos cuando algo cambia y que un proceso aparte actualice las proyecciones (ver [8.4](/conceptos/8-4)). Salvo la segunda, el lado de lectura queda un poco atrasado: consistencia eventual (ver [5.3](/conceptos/5-3)).

No hace falta llevarlo al extremo: la forma más común y útil es la misma base, con algunas vistas materializadas o tablas resumen para las pantallas más pesadas.

## Ejemplo

Un resumen por invernadero para el tablero, como vista materializada en PostgreSQL:

```sql resumen-invernaderos.sql
CREATE MATERIALIZED VIEW resumen_invernaderos AS
SELECT i.organizacion_id,
       i.id                                      AS invernadero_id,
       i.nombre,
       ult.momento                               AS ultima_lectura,
       ult.temperatura                           AS temperatura_actual,
       hoy.humedad_promedio,
       coalesce(al.abiertas, 0)                  AS alarmas_abiertas
  FROM invernaderos i
  LEFT JOIN LATERAL (
         SELECT l.momento, l.temperatura
           FROM lecturas l
           JOIN dispositivos d ON d.id = l.dispositivo_id
          WHERE d.invernadero_id = i.id
          ORDER BY l.momento DESC
          LIMIT 1) ult ON true
  LEFT JOIN LATERAL (
         SELECT round(avg(l.humedad_suelo), 1) AS humedad_promedio
           FROM lecturas l
           JOIN dispositivos d ON d.id = l.dispositivo_id
          WHERE d.invernadero_id = i.id
            AND l.momento >= date_trunc('day', now())) hoy ON true
  LEFT JOIN LATERAL (
         SELECT count(*) AS abiertas
           FROM alarmas a
          WHERE a.invernadero_id = i.id AND a.reconocida IS NULL) al ON true;

-- Necesario para refrescar sin bloquear las lecturas del tablero
CREATE UNIQUE INDEX ON resumen_invernaderos (invernadero_id);
CREATE INDEX ON resumen_invernaderos (organizacion_id);
```

```js refrescar-resumen.js
// Tarea periódica, cada minuto
async function refrescarResumen(db) {
  await db.query("REFRESH MATERIALIZED VIEW CONCURRENTLY resumen_invernaderos");
}

// El tablero: una consulta simple sobre la proyección
async function tablero(db, organizacionId) {
  const { rows } = await db.query(
    "SELECT * FROM resumen_invernaderos WHERE organizacion_id = $1 ORDER BY nombre",
    [organizacionId]
  );
  return rows;
}

module.exports = { refrescarResumen, tablero };
```

El trabajo pesado se hace una vez por minuto, no una vez por cada usuario que abre el tablero. `CONCURRENTLY` permite que el tablero siga leyendo mientras se refresca (y por eso exige el índice único). Los comandos siguen escribiendo en las tablas normales, sin saber que la vista existe. El atraso de hasta un minuto es aceptable para un tablero; para la alarma que el usuario acaba de reconocer, la app la marca como reconocida con la respuesta del comando, sin esperar el refresco. Ojo con dos cosas: el "día" de `date_trunc` es el del servidor, y en un sistema real se usaría la zona de cada organización (ver [7.1](/conceptos/7-1)); y una vista materializada no aplica la seguridad a nivel de fila de las tablas, así que el filtro por organización de la consulta es obligatorio (ver [4.1](/conceptos/4-1)).

## Cuándo sí y cuándo no

Conviene cuando:

- las lecturas superan por mucho a las escrituras y algunas pantallas necesitan datos combinados o agregados,
- ya se probaron los índices y las consultas siguen siendo lentas,
- distintas pantallas necesitan formas muy distintas de los mismos datos.

No conviene cuando:

- las consultas son simples y rápidas con buenos índices,
- los usuarios necesitan ver siempre el dato exacto de este instante, y no se puede manejar un atraso,
- se plantea con bases distintas, colas y eventos desde el día uno: es la versión más cara, para cuando las más simples no alcancen.

## Resumen

- CQRS separa el modelo que recibe comandos (normalizado, con reglas) del que responde consultas (con la forma de cada pantalla).
- Las proyecciones se calculan de antemano y se mantienen sincronizadas, normalmente con algo de atraso.
- La versión más simple: vistas materializadas o tablas resumen en la misma base.
- El atraso es consistencia eventual; lo que el usuario acaba de hacer se muestra sin esperar la proyección.
- Se usa cuando los índices ya no alcanzan, no como punto de partida.
