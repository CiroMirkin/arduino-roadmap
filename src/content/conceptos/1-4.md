En [B.2](/conceptos/b-2), [B.3](/conceptos/b-3) y [B.7](/conceptos/b-7) viste las herramientas: guardas de inclusión, la división entre `.h` y `.cpp`, `extern` y `static`. Esta lección es sobre cómo usarlas para **organizar** un firmware en módulos. Tres ideas: cada módulo vive en su propio **namespace**, su header expone **solo lo necesario**, y todo lo demás queda **interno** al `.cpp`.

## Por qué te importa

Un firmware chico tiene pocos nombres y no choca nada. Cuando el controlador del invernadero tiene riego, ventilación, pantalla, sensores, BLE y reporte, aparecen varias funciones `actualizar()`, varias variables `estado`, varias constantes `INTERVALO_MS`. Y las librerías traen sus propios nombres: una variable global `config` puede chocar con algo de una librería que ni sabías que existía.

El otro problema es el acoplamiento. Si `riego.h` expone todas sus variables con `extern`, cualquier archivo puede modificar el estado del riego, y cuando la bomba se enciende sola, el culpable puede estar en cualquier parte del proyecto. Un módulo que expone poco se puede cambiar por dentro sin miedo.

## Paso a paso

### 1. Namespaces

Un **namespace** agrupa nombres bajo un prefijo:

```cpp
namespace riego {
  void actualizar();
  bool activo();
}

namespace ventilacion {
  void actualizar();
  bool ventanasAbiertas();
}

riego::actualizar();          // no choca con ventilacion::actualizar()
ventilacion::actualizar();
```

`riego::actualizar` y `ventilacion::actualizar` son funciones distintas. El `::` es el operador de resolución de ámbito, que se ve completo en [1.8](/conceptos/1-8).

Un namespace se puede abrir en varios archivos: el `.h` declara dentro de `namespace riego { ... }` y el `.cpp` define dentro del mismo namespace. También se pueden anidar: `namespace invernadero::riego { ... }` (C++17).

### 2. El header es la interfaz

El header de un módulo responde una pregunta: **¿qué necesitan los demás para usar este módulo?** Nada más.

```cpp riego.h
#pragma once
#include "tipos.h"

namespace riego {

void begin();
void actualizar(const Lectura& lectura);
bool activo();
uint32_t litrosHoy();

}  // namespace riego
```

No aparecen el pin de la válvula, los umbrales internos ni las variables de estado. Quien usa el módulo no puede depender de ellos, así que se pueden cambiar sin tocar nada afuera. Además, como el header cambia poco, los archivos que lo incluyen no se recompilan cada vez que se toca el interior del módulo.

### 3. Lo interno, en un namespace sin nombre

```cpp riego.cpp
#include "riego.h"
#include "config.h"

namespace {   // sin nombre: solo visible en este archivo

constexpr uint8_t PIN_VALVULA = 26;
bool regando = false;
uint32_t pulsosHoy = 0;

void abrirValvula()  { digitalWrite(PIN_VALVULA, LOW);  regando = true; }
void cerrarValvula() { digitalWrite(PIN_VALVULA, HIGH); regando = false; }

}  // namespace

namespace riego {

void begin() {
  digitalWrite(PIN_VALVULA, HIGH);
  pinMode(PIN_VALVULA, OUTPUT);
}

void actualizar(const Lectura& lectura) {
  if (!regando && lectura.humedadSuelo < HUMEDAD_MINIMA) abrirValvula();
  else if (regando && lectura.humedadSuelo > HUMEDAD_MAXIMA) cerrarValvula();
}

bool activo() { return regando; }
uint32_t litrosHoy() { return pulsosHoy / 450; }

}  // namespace riego
```

Un **namespace sin nombre** hace lo mismo que `static` fuera de una clase (ver [B.7](/conceptos/b-7)): todo lo que contiene es visible solo en este archivo. Se puede usar para variables, funciones, constantes y tipos, todos a la vez, y es la forma habitual en C++ moderno de marcar lo interno.

### 4. Estado compartido sin `extern` por todos lados

Cuando otro módulo necesita un dato, hay dos opciones:

```cpp
// Opción A: exponer la variable
extern bool regando;          // cualquiera puede leerla... y escribirla

// Opción B: exponer una función de lectura
namespace riego { bool activo(); }   // se puede leer; cambiarla solo desde riego
```

La opción B mantiene el control: el estado del riego solo cambia dentro del módulo de riego, por sus reglas. `extern` queda para casos puntuales, como una configuración que de verdad comparten todos, y aun así suele ir como `const` o detrás de funciones.

### 5. `using`: en los `.cpp`, no en los headers

```cpp
// En un .cpp: aceptable, el efecto queda en este archivo
using invernadero::Lectura;

// En un header: nunca
using namespace std;   // afecta a todos los que incluyan el header
```

`using namespace` trae todos los nombres de un namespace al alcance actual. En un header, eso le pasa a todos los archivos que lo incluyan, sin que lo pidan, y puede causar choques imposibles de rastrear. En un `.cpp` el efecto es local, aunque igual conviene traer solo los nombres que usás (`using std::min;`).

### 6. Cómo nombrar

Una convención simple: un namespace por módulo, con el mismo nombre que el archivo (`riego.h`, `riego.cpp`, `namespace riego`). Para un proyecto que comparte código entre el nodo y el controlador, un namespace de proyecto alrededor (`invernadero::riego`) evita choques con librerías. Evitá nombres que ya usan librerías comunes: `WiFi`, `Serial`, `BLE`.

## Ejemplos

### Ejemplo 1. Dos módulos con los mismos nombres

```cpp namespaces.ino
namespace riego {
  bool activo = false;
  void actualizar(float humedad) {
    if (!activo && humedad < 35.0f) activo = true;
    else if (activo && humedad > 55.0f) activo = false;
  }
}

namespace ventilacion {
  bool activo = false;
  void actualizar(float temperatura) {
    if (!activo && temperatura > 30.0f) activo = true;
    else if (activo && temperatura < 27.0f) activo = false;
  }
}

void setup() {
  Serial.begin(115200);
  riego::actualizar(30.0f);
  ventilacion::actualizar(25.0f);
  Serial.printf("riego %d, ventilación %d\n", riego::activo, ventilacion::activo);   // 1, 0
}

void loop() {}
```

Los dos módulos usan `activo` y `actualizar` sin chocar. En un proyecto real cada namespace estaría en su archivo, y las variables `activo` serían internas, como en el ejemplo 2.

### Ejemplo 2. Un módulo de alarmas con su interfaz

El módulo de alarmas recibe eventos de otros módulos (temperatura extrema, tanque vacío, nodo sin noticias), recuerda cuáles están activas y las expone para la pantalla y el reporte. Su interfaz es chica; su estado, interno.

```cpp alarmas.h
#pragma once
#include <Arduino.h>

namespace alarmas {

enum class Tipo : uint8_t { TemperaturaAlta, TemperaturaBaja, TanqueVacio, NodoSinNoticias, Cantidad };

void activar(Tipo tipo);
void desactivar(Tipo tipo);
bool activa(Tipo tipo);
bool hayAlguna();
const char* nombre(Tipo tipo);

}  // namespace alarmas
```

```cpp alarmas.cpp
#include "alarmas.h"

namespace {

constexpr size_t CANTIDAD = static_cast<size_t>(alarmas::Tipo::Cantidad);
bool activas[CANTIDAD] = {};

size_t indice(alarmas::Tipo t) { return static_cast<size_t>(t); }

}  // namespace

namespace alarmas {

void activar(Tipo tipo) {
  if (!activas[indice(tipo)]) {
    activas[indice(tipo)] = true;
    Serial.printf("ALARMA: %s\n", nombre(tipo));
  }
}

void desactivar(Tipo tipo) { activas[indice(tipo)] = false; }

bool activa(Tipo tipo) { return activas[indice(tipo)]; }

bool hayAlguna() {
  for (bool a : activas) if (a) return true;
  return false;
}

const char* nombre(Tipo tipo) {
  switch (tipo) {
    case Tipo::TemperaturaAlta: return "temperatura alta";
    case Tipo::TemperaturaBaja: return "temperatura baja";
    case Tipo::TanqueVacio:     return "tanque vacío";
    case Tipo::NodoSinNoticias: return "nodo sin noticias";
    case Tipo::Cantidad:        break;
  }
  return "?";
}

}  // namespace alarmas
```

```cpp controlador.ino
#include "alarmas.h"

void setup() {
  Serial.begin(115200);
  alarmas::activar(alarmas::Tipo::TanqueVacio);
  Serial.println(alarmas::hayAlguna() ? "hay alarmas" : "todo ok");
}

void loop() {}
```

El arreglo `activas` es interno: nadie puede marcar una alarma sin pasar por `activar`, que además la registra en el monitor serie. El valor `Cantidad` al final del enum es un truco común para saber cuántos valores tiene (ver [B.10](/conceptos/b-10)). Si mañana las alarmas se guardan en NVS para sobrevivir a un reinicio, cambia solo `alarmas.cpp`.

### Ejemplo 3. El proyecto con un namespace general

El nodo y el controlador comparten código (el formato de las lecturas, el protocolo BLE). Todo el código propio va dentro de `invernadero`, con un namespace por módulo.

```cpp invernadero/tipos.h
#pragma once
#include <Arduino.h>

namespace invernadero {

struct Lectura {
  float temperatura;
  float humedadAire;
  float humedadSuelo;
};

}  // namespace invernadero
```

```cpp invernadero/protocolo.h
#pragma once
#include "tipos.h"

namespace invernadero::protocolo {

constexpr size_t TAMANO_TRAMA = 6;

void codificar(const Lectura& l, uint8_t trama[TAMANO_TRAMA]);
bool decodificar(const uint8_t* trama, size_t largo, Lectura& l);

}  // namespace invernadero::protocolo
```

```cpp controlador.ino
#include "invernadero/protocolo.h"

using invernadero::Lectura;                 // en el .ino: traer solo lo que se usa
namespace protocolo = invernadero::protocolo;   // un alias corto

void setup() {
  Serial.begin(115200);
  Lectura l{24.5f, 68.0f, 41.0f};
  uint8_t trama[protocolo::TAMANO_TRAMA];
  protocolo::codificar(l, trama);
}

void loop() {}
```

`namespace protocolo = invernadero::protocolo;` crea un alias para no escribir el nombre largo cada vez. El `using` y el alias están en el `.ino`, no en los headers, así no afectan a nadie más. El nombre `protocolo` dentro de `invernadero` no puede chocar con un `protocolo` de alguna librería.

## Errores comunes

### `using namespace` en un header

```cpp
// Mal: utilidades.h
#pragma once
#include <algorithm>
using namespace std;

// Bien: calificar en el header, y en todo caso usar using en los .cpp
#pragma once
#include <algorithm>
inline float limitar(float v, float lo, float hi) { return std::min(std::max(v, lo), hi); }
```

### Exponer todo el estado con `extern`

```cpp
// Mal: riego.h
extern bool regando;
extern uint32_t inicioRiegoMs;
extern float humedadObjetivo;

// Bien: riego.h
namespace riego {
  bool activo();
  void fijarObjetivo(float humedad);   // con validación adentro
}
```

### Detalles internos sin marcar como internos

```cpp
// Mal: riego.cpp, función auxiliar global
bool superoTiempoMaximo() { /* ... */ }   // choca con otra del mismo nombre en otro archivo

// Bien
namespace {
bool superoTiempoMaximo() { /* ... */ }
}
```

### Un namespace que repite el prefijo en cada nombre

```cpp
// Mal: el namespace ya da el contexto
namespace riego { void riegoActualizar(); bool riegoActivo(); }
riego::riegoActualizar();

// Bien
namespace riego { void actualizar(); bool activo(); }
riego::actualizar();
```

Es el mismo razonamiento que con `enum class` (ver [B.10](/conceptos/b-10)): el prefijo manual sobra cuando el lenguaje ya da el contexto.

## Ejercicio

El controlador tiene dos archivos escritos por personas distintas, y el build falla con `multiple definition of 'estado'` y `multiple definition of 'actualizar()'`. Además, `pantalla.cpp` declara `extern int estado;` y a veces muestra el estado del módulo equivocado. Reorganizá los dos módulos para que compilen, cada uno con una interfaz chica, y que la pantalla pueda pedir el estado de cada uno sin ambigüedad.

```cpp riego.cpp
int estado = 0;   // 0 = quieto, 1 = regando
void actualizar() { /* ... */ }
```

```cpp ventilacion.cpp
int estado = 0;   // 0 = cerrado, 1 = abriendo, 2 = abierto
void actualizar() { /* ... */ }
```

```cpp riego.cpp
#include <Arduino.h>
#include "riego.h"

namespace {
riego::Estado estadoActual = riego::Estado::Quieto;

namespace riego {
void actualizar() { /* ... modifica estadoActual ... */ }
Estado estado() { return estadoActual; }
}
```

```cpp ventilacion.h
#pragma once

```

```cpp ventilacion.cpp
namespace ventilacion {
void actualizar() { /* ... */ }
Estado estado() { return estadoActual; }
}
```

En `pantalla.cpp`, el `extern int estado;` se reemplaza por `#include "riego.h"` y `#include "ventilacion.h"`, y se consulta `riego::estado()` o `ventilacion::estado()`. Ya no hay forma de confundirlos: son tipos distintos, y comparar el estado de la ventilación con `riego::Estado::Regando` no compila. Y ningún otro archivo puede modificar el estado de un módulo.

## Resumen

- Un namespace por módulo evita choques de nombres entre módulos y con librerías: `riego::actualizar()`, `ventilacion::actualizar()`.
- El header expone solo lo que otros necesitan; los detalles quedan en el `.cpp`.
- Lo interno de un `.cpp` va en un namespace sin nombre (o con `static`).
- Para compartir estado, mejor funciones de consulta que variables `extern`: el estado cambia solo dentro de su módulo.
- `using namespace` nunca en un header; en los `.cpp`, preferí traer solo los nombres que usás.
