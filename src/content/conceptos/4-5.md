Las tablas del backend del invernadero no crecen igual. Las de organizaciones, invernaderos y usuarios tienen pocas filas y cambian poco. La de **lecturas** crece todo el tiempo: un controlador que envía una lectura por minuto genera más de medio millón de filas por año, y con muchos invernaderos se llega a cientos de millones. Para que las consultas sigan siendo rápidas hacen falta **índices** bien elegidos, y para que los datos viejos se puedan borrar o archivar sin frenar todo, conviene **particionar** la tabla por fecha.

## Por qué te importa

Con pocas filas, cualquier consulta es rápida, y por eso estos problemas no aparecen en las pruebas. Aparecen meses después de instalar los equipos: el gráfico de la última semana tarda diez segundos en cargar, la ingesta empieza a responder lento y los equipos acumulan pendientes, y borrar los datos de hace dos años bloquea la base durante horas.

Elegir índices no es agregar uno por columna: es mirar qué consultas hace realmente el sistema y diseñar los índices para ellas. Y el particionado es una decisión que cuesta mucho cambiar con la tabla llena: conviene tomarla temprano.

## Paso a paso

### 1. Qué hace la base sin índice

Sin un índice útil, para responder "las lecturas del dispositivo 17 de ayer", PostgreSQL recorre **toda la tabla** (un *seq scan*) y se queda con las filas que cumplen la condición. Con cien millones de filas, eso tarda.

Un **índice** es una estructura aparte, ordenada por una o más columnas (normalmente un árbol B), que permite ir directo a las filas buscadas, como el índice alfabético de un libro.

### 2. Índices compuestos y el orden de las columnas

Un índice puede tener varias columnas, y el **orden importa**: el índice está ordenado por la primera, dentro de ella por la segunda, y así. Sirve para consultas que filtran por un **prefijo** de sus columnas:

```sql
CREATE INDEX lecturas_disp_momento ON lecturas (organizacion_id, dispositivo_id, momento);
```

| Condición | ¿Usa bien el índice? |
|---|---|
| `organizacion_id = 3 AND dispositivo_id = 17 AND momento >= ...` | sí: prefijo completo, rango al final |
| `organizacion_id = 3 AND dispositivo_id = 17` | sí: prefijo |
| `organizacion_id = 3` | sí, aunque recorre todos sus dispositivos |
| `dispositivo_id = 17` | no bien: falta la primera columna |
| `momento >= ...` | no: es la última columna |

La regla práctica: **primero las columnas que se comparan por igualdad, al final la del rango** (normalmente la fecha). En un sistema multi-tenant, `organizacion_id` casi siempre va primero, porque toda consulta filtra por ella (ver [4.1](/conceptos/4-1)).

### 3. `EXPLAIN ANALYZE`: ver qué hace la consulta

Antes de agregar un índice, hay que ver qué está haciendo la consulta:

```sql
EXPLAIN ANALYZE
SELECT momento, temperatura FROM lecturas
 WHERE organizacion_id = 3 AND dispositivo_id = 17
   AND momento >= now() - interval '1 day';
```

La salida muestra el plan: `Seq Scan` (recorrió toda la tabla) o `Index Scan` (usó un índice), cuántas filas revisó y cuánto tardó. Es la única forma de saber si un índice se usa de verdad.

### 4. Condiciones que impiden usar el índice

Un índice sobre `momento` está ordenado por `momento`. Si la consulta aplica una función a la columna (`date(momento) = '2026-10-05'`, `extract(hour from momento) = 6`), el índice no sirve, porque los valores calculados no están ordenados en él. La solución habitual es reescribir la condición como un rango sobre la columna original:

```sql
-- No usa el índice sobre momento
WHERE date(momento) = '2026-10-05'

-- Usa el índice
WHERE momento >= '2026-10-05' AND momento < '2026-10-06'
```

### 5. El costo de cada índice

Cada índice se actualiza en **cada inserción**. En la tabla de lecturas, que recibe escrituras todo el tiempo, cinco índices hacen la ingesta notablemente más lenta que dos. Además, ocupan espacio, a veces tanto como la tabla. Se crean los índices que usan las consultas reales, se verifican con `EXPLAIN ANALYZE`, y se borran los que no se usan (PostgreSQL lleva estadísticas de uso de cada índice).

### 6. Particionado por tiempo

**Particionar** una tabla es dividirla en varias tablas más chicas (las **particiones**) que desde afuera se ven como una sola. Para lecturas, lo natural es una partición por mes:

```sql
CREATE TABLE lecturas (...) PARTITION BY RANGE (momento);
CREATE TABLE lecturas_2026_10 PARTITION OF lecturas
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

Ventajas:

- Una consulta por fechas solo revisa las particiones de ese rango (*partition pruning*).
- Borrar los datos de un mes viejo es `DROP TABLE lecturas_2024_10`: inmediato, en lugar de un `DELETE` de millones de filas que tarda horas y deja la tabla fragmentada.
- Cada partición tiene sus propios índices, más chicos.

Dos condiciones: las particiones tienen que **existir antes** de que lleguen datos para ese período (una inserción sin partición falla), y toda restricción de unicidad tiene que **incluir la columna de particionado**.

## Ejemplos

### Ejemplo 1. El efecto de un índice, con `EXPLAIN ANALYZE`

Primero la consulta sin índice, después con uno compuesto. Se puede probar en una base de prueba con datos generados.

```sql indice.sql
-- Datos de prueba: 100 dispositivos, una lectura por minuto durante 30 días (~4,3 millones de filas).
-- En una base de prueba, con la tabla de lecturas sin las claves foráneas (o con esos dispositivos cargados).
INSERT INTO lecturas (organizacion_id, dispositivo_id, id_envio, momento, temperatura, humedad_suelo)
SELECT (d % 10) + 1, d, 'prueba-' || d || '-' || m,
       now() - (m || ' minutes')::interval, 20 + random() * 10, (random() * 100)::int
  FROM generate_series(1, 100) AS d, generate_series(1, 43200) AS m;

ANALYZE lecturas;   -- actualizar las estadísticas que usa el planificador

EXPLAIN ANALYZE
SELECT momento, temperatura FROM lecturas
 WHERE organizacion_id = 8 AND dispositivo_id = 17
   AND momento >= now() - interval '1 day';
-- Seq Scan on lecturas ... rows=1440 ... (recorrió millones de filas)

CREATE INDEX lecturas_org_disp_momento ON lecturas (organizacion_id, dispositivo_id, momento);

EXPLAIN ANALYZE
SELECT momento, temperatura FROM lecturas
 WHERE organizacion_id = 8 AND dispositivo_id = 17
   AND momento >= now() - interval '1 day';
-- Index Scan using lecturas_org_disp_momento ... rows=1440 ... (fue directo)
```

Las dos consultas devuelven las mismas 1440 filas; lo que cambia es cuántas tuvo que revisar la base para encontrarlas. En una tabla de este tamaño, la diferencia suele ser de cientos de milisegundos a uno o dos. Los tiempos exactos dependen del servidor; lo que hay que mirar es `Seq Scan` contra `Index Scan` y las filas revisadas.

### Ejemplo 2. Índices pensados para las consultas reales

El backend hace, sobre todo, tres consultas a la tabla de lecturas. Cada índice responde a una de ellas.

```sql indices-lecturas.sql
-- Consulta 1: gráfico de un dispositivo en un rango de fechas
--   WHERE organizacion_id = $1 AND dispositivo_id = $2 AND momento >= $3 AND momento < $4
CREATE INDEX lecturas_org_disp_momento ON lecturas (organizacion_id, dispositivo_id, momento);

-- Consulta 2: última lectura de cada dispositivo de una organización (tablero)
--   SELECT DISTINCT ON (dispositivo_id) ... WHERE organizacion_id = $1
--   ORDER BY dispositivo_id, momento DESC
-- La resuelve el mismo índice 1: mismo prefijo y mismo orden

-- Consulta 3: ingesta, detectar duplicados por (dispositivo_id, id_envio)
-- La resuelve la clave primaria, que ya es un índice (ver 4.3)
```

```sql consultas.sql
-- Tablero: última lectura de cada dispositivo de la organización 3
SELECT DISTINCT ON (dispositivo_id) dispositivo_id, momento, temperatura, humedad_suelo
  FROM lecturas
 WHERE organizacion_id = 3
   AND momento >= now() - interval '1 hour'      -- acota la búsqueda a lo reciente
 ORDER BY dispositivo_id, momento DESC;

-- Promedio diario de un dispositivo en un mes, con rangos y no con date(momento) en el WHERE
SELECT date_trunc('day', momento) AS dia, avg(temperatura) AS promedio
  FROM lecturas
 WHERE organizacion_id = 3 AND dispositivo_id = 17
   AND momento >= '2026-09-01' AND momento < '2026-10-01'
 GROUP BY dia
 ORDER BY dia;
```

Con dos índices (el compuesto y la clave primaria) se cubren las tres consultas principales, y la ingesta solo mantiene esos dos. En la segunda consulta, `date_trunc` se usa en el `SELECT` y el `GROUP BY`, que no afectan al índice; el filtro del `WHERE` es un rango sobre `momento`. `DISTINCT ON` es una extensión de PostgreSQL que se queda con la primera fila de cada grupo, según el `ORDER BY`.

### Ejemplo 3. La tabla de lecturas particionada por mes

La tabla se define particionada desde el principio. Una tarea programada crea las particiones de los meses siguientes y elimina las que superan el período de retención.

```sql lecturas-particionada.sql
CREATE TABLE lecturas (
  organizacion_id  BIGINT NOT NULL,
  dispositivo_id   BIGINT NOT NULL,
  id_envio         TEXT NOT NULL,
  momento          TIMESTAMPTZ NOT NULL,
  recibido         TIMESTAMPTZ NOT NULL DEFAULT now(),
  temperatura      NUMERIC(4,1),
  humedad_suelo    SMALLINT,
  -- en una tabla particionada, la clave tiene que incluir la columna de particionado
  PRIMARY KEY (dispositivo_id, id_envio, momento)
) PARTITION BY RANGE (momento);

CREATE INDEX lecturas_org_disp_momento ON lecturas (organizacion_id, dispositivo_id, momento);
-- (el índice se crea automáticamente en cada partición)

CREATE TABLE lecturas_2026_10 PARTITION OF lecturas FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE lecturas_2026_11 PARTITION OF lecturas FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
```

```js mantener-particiones.js
// Se ejecuta una vez por día (por ejemplo, con un cron del servidor)
async function mantenerParticiones(db, { mesesAdelante = 2, mesesRetencion = 24 } = {}) {
  const hoy = new Date();

  for (let i = 0; i <= mesesAdelante; i++) {
    const inicio = new Date(Date.UTC(hoy.getUTCFullYear(), hoy.getUTCMonth() + i, 1));
    const fin = new Date(Date.UTC(hoy.getUTCFullYear(), hoy.getUTCMonth() + i + 1, 1));
    const nombre = `lecturas_${inicio.getUTCFullYear()}_${String(inicio.getUTCMonth() + 1).padStart(2, "0")}`;
    await db.query(
      `CREATE TABLE IF NOT EXISTS ${nombre} PARTITION OF lecturas
         FOR VALUES FROM ('${inicio.toISOString()}') TO ('${fin.toISOString()}')`
    );
  }

  const limite = new Date(Date.UTC(hoy.getUTCFullYear(), hoy.getUTCMonth() - mesesRetencion, 1));
  const nombreViejo = `lecturas_${limite.getUTCFullYear()}_${String(limite.getUTCMonth() + 1).padStart(2, "0")}`;
  await db.query(`DROP TABLE IF EXISTS ${nombreViejo}`);   // borra un mes entero, al instante
}

module.exports = { mantenerParticiones };
```

La clave primaria pasó de `(dispositivo_id, id_envio)` a `(dispositivo_id, id_envio, momento)`, porque PostgreSQL exige que la unicidad incluya la columna de particionado. La idempotencia de [4.3](/conceptos/4-3) se mantiene: un reintento trae el mismo `id_envio` **y** el mismo `momento`, así que sigue chocando con la clave. Las particiones se crean con dos meses de anticipación, para que una inserción nunca falle por falta de partición. Los nombres de las tablas se arman con fechas calculadas en el código, nunca con datos que vengan de un pedido, porque no se pueden pasar como parámetros de la consulta. Antes de borrar particiones viejas, lo habitual es guardar un resumen (promedios diarios) en una tabla aparte.

## Errores comunes

### Un índice por columna "por las dudas"

Índices sueltos en `organizacion_id`, `dispositivo_id` y `momento` ocupan espacio, frenan la ingesta y sirven peor que un único índice compuesto pensado para la consulta. Diseñá los índices a partir de las consultas.

### El orden equivocado en un índice compuesto

```sql
-- Mal: el rango primero
CREATE INDEX ON lecturas (momento, organizacion_id, dispositivo_id);

-- Bien: igualdades primero, rango al final
CREATE INDEX ON lecturas (organizacion_id, dispositivo_id, momento);
```

### Funciones sobre la columna indexada

`WHERE date(momento) = ...` o `WHERE momento::date = ...` no usan el índice sobre `momento`. Usá rangos.

### No mirar `EXPLAIN ANALYZE`

Crear un índice y suponer que se usa. A veces el planificador decide no usarlo (por estadísticas viejas, por el tipo de dato, por una condición mal escrita). Verificalo.

### Olvidar crear las particiones futuras

Si el primer día del mes no existe la partición de ese mes, todas las inserciones fallan. Crealas con anticipación, con una tarea automática y una alarma si falla.

## Ejercicio

La app tiene estas tres consultas lentas. Proponé los índices necesarios (la menor cantidad posible) y corregí la consulta que no puede usar ningún índice tal como está escrita.

```sql consultas-lentas.sql
-- A: eventos de riego de un invernadero en la última semana
SELECT * FROM eventos_riego
 WHERE organizacion_id = $1 AND invernadero_id = $2 AND momento >= now() - interval '7 days';

-- B: alarmas activas de una organización
SELECT * FROM alarmas WHERE organizacion_id = $1 AND activa = true;

-- C: eventos de riego de una organización en un día
SELECT * FROM eventos_riego
 WHERE organizacion_id = $1 AND date(momento) = $2;
```

<details>
<summary>Pista</summary>

A y C son sobre la misma tabla: ¿un índice puede servir para las dos? Para C, pensá en cómo escribir el día como un rango.

</details>

<details>
<summary>Ver solución</summary>

```sql indices.sql
-- Para A: igualdades (organización, invernadero) y rango (momento) al final
CREATE INDEX eventos_org_inv_momento ON eventos_riego (organizacion_id, invernadero_id, momento);

-- Para C: organización y rango de momento
CREATE INDEX eventos_org_momento ON eventos_riego (organizacion_id, momento);

-- Para B: índice parcial, solo sobre las alarmas activas (pocas filas)
CREATE INDEX alarmas_activas_org ON alarmas (organizacion_id) WHERE activa = true;
```

```sql consulta-c-corregida.sql
SELECT * FROM eventos_riego
 WHERE organizacion_id = $1
   AND momento >= $2::date
   AND momento <  $2::date + interval '1 day';
```

La consulta C aplicaba `date()` a `momento`, así que ningún índice sobre `momento` servía; escrita como rango, usa `eventos_org_momento`. A y C no pueden compartir un índice, porque C no filtra por invernadero y A sí: en `(organizacion_id, invernadero_id, momento)`, sin la segunda columna, el rango de fechas no se aprovecha. Para B, un **índice parcial** (con `WHERE`) solo incluye las filas activas, que son pocas, así que es chico y rápido de mantener. Después de crearlos, verificá con `EXPLAIN ANALYZE` que cada consulta los use.

## Resumen

- Sin un índice útil, la base recorre toda la tabla. Un índice ordenado permite ir directo a las filas.
- En un índice compuesto, primero las columnas con igualdad y al final la del rango. En multi-tenant, casi siempre empieza por `organizacion_id`.
- `EXPLAIN ANALYZE` muestra si una consulta usa el índice. Funciones sobre la columna lo impiden: usá rangos.
- Cada índice frena las escrituras y ocupa espacio: creá los que usan las consultas reales.
- Particionar por mes permite consultas por fecha más rápidas y borrar meses enteros al instante. Las particiones se crean con anticipación, y la clave única incluye la fecha.
