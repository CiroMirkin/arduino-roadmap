Cuando los datos viven en **un solo lugar** (una base de datos, una transacción), es posible que todos vean siempre el mismo valor: eso es **consistencia fuerte**. Cuando viven en **varios lugares** que se comunican por una red que puede fallar (el backend y los controladores, una base principal y sus réplicas), eso deja de ser posible sin sacrificar algo. La alternativa habitual es la **consistencia eventual**: durante un tiempo, distintos lugares pueden tener valores distintos, pero si dejan de llegar cambios, todos terminan **convergiendo** al mismo valor.

## Por qué te importa

El sistema del invernadero ya es distribuido, aunque no lo parezca: la configuración de riego vive en el backend y en cada controlador. Si internet se corta tres horas, el controlador no puede preguntar el umbral vigente, y aun así tiene que seguir regando. No hay forma de que el backend y el controlador estén siempre de acuerdo y que, al mismo tiempo, el controlador siga funcionando sin red. Hay que elegir, y para un sistema que maneja plantas vivas, la elección es clara: el controlador sigue funcionando con lo que tiene, y se pone al día cuando puede.

Entender esto evita dos errores: diseñar como si la red nunca fallara (y que el controlador deje de regar ante un corte), y no tener un mecanismo para que los datos converjan (y que el controlador quede con una configuración vieja para siempre).

## Cómo funciona

**El dilema de la partición.** Cuando una red se parte en dos (el controlador sin internet), cada lado puede o bien seguir funcionando con lo que sabe (**disponibilidad**), o bien negarse a actuar hasta poder confirmar con el otro lado (**consistencia**). No se puede tener las dos durante la partición. A esto se lo conoce como el teorema CAP (ver [9.4](/conceptos/9-4)). El controlador elige disponibilidad; un sistema bancario, para una transferencia, elegiría consistencia.

**Convergencia con versiones.** Para que los datos converjan sin ambigüedad, cada cambio tiene un **número de versión** que crece. El controlador recuerda qué versión de la configuración tiene; al reconectarse, la informa, y el backend le envía la vigente solo si es más nueva. No importa cuántos cambios hubo durante el corte: el controlador recibe el último.

**Quién manda.** Si un dato se puede modificar en los dos lados (por ejemplo, el operario ajusta el umbral en la pantalla del controlador mientras está sin red, y alguien lo cambia en la app), hay un conflicto. Opciones: definir un único lugar donde se modifica (lo más simple), "la última escritura gana" según la hora (riesgoso con relojes desfasados, ver [7.1](/conceptos/7-1)), o guardar los dos cambios y que una persona decida.

**Réplicas y "leer lo que escribí".** Cuando el backend crece, es común tener réplicas de la base para las consultas de lectura. Las réplicas reciben los cambios con un pequeño atraso. Para que un usuario no deje de ver un cambio que acaba de hacer, lo que el usuario acaba de escribir se lee de la base principal, y las réplicas se usan para el resto (tableros, reportes).

## Ejemplo

Sincronización de la configuración entre el backend y el controlador con números de versión. El backend guarda la configuración con historial (ver [5.1](/conceptos/5-1)), y su `id` creciente sirve como versión.

```js config-equipos.js
// GET /api/v1/config?version=17  (con autenticarEquipo, ver 3.4)
router.get("/api/v1/config", autenticarEquipo, async (req, res) => {
  const versionDelEquipo = Number(req.query.version) || 0;

  const { rows } = await req.db.query(
    `SELECT id::integer AS version,                 -- pg devuelve BIGINT y NUMERIC como texto:
            humedad_minima::float8 AS humedad_minima, -- se convierten para que el JSON lleve números
            humedad_maxima::float8 AS humedad_maxima,
            riego_maximo_s
       FROM config_riego
      WHERE organizacion_id = $1 AND zona_id = $2
      ORDER BY id DESC
      LIMIT 1`,
    [req.equipo.organizacion_id, req.equipo.zona_id]   // zona_id: agregarlo a lo que carga autenticarEquipo (3.4)
  );
  if (rows.length === 0) return res.status(404).json({ error: "zona sin configuración" });

  if (rows[0].version <= versionDelEquipo) {
    return res.status(304).end();          // el equipo ya tiene la vigente (o una igual)
  }
  res.json(rows[0]);                        // la vigente, con su versión
});
```

```cpp sync-config.ino
#include <HTTPClient.h>
#include <ArduinoJson.h>
#include <Preferences.h>

struct ConfigRiego {
  uint32_t version;
  float humedadMinima;
  float humedadMaxima;
  uint32_t riegoMaximoS;
};

ConfigRiego config = {0, 35.0f, 55.0f, 300};   // valores seguros hasta la primera sincronización

// Llamar cada pocos minutos desde la tarea de comunicación (ver 2.4 y 3.1)
void sincronizarConfig() {
  char url[96];
  snprintf(url, sizeof(url), "http://192.168.0.10:3000/api/v1/config?version=%lu",
           static_cast<unsigned long>(config.version));

  HTTPClient http;
  http.begin(url);
  http.setTimeout(5000);
  http.addHeader("Authorization", "Bearer ...");   // la clave del equipo (ver 3.4)
  int codigo = http.GET();

  if (codigo == 200) {
    JsonDocument doc;
    if (!deserializeJson(doc, http.getString())) {
      ConfigRiego nueva{doc["version"] | 0u, doc["humedad_minima"] | config.humedadMinima,
                        doc["humedad_maxima"] | config.humedadMaxima,
                        doc["riego_maximo_s"] | config.riegoMaximoS};
      bool valida = nueva.version > config.version && nueva.humedadMinima < nueva.humedadMaxima;
      if (valida) {
        config = nueva;
        Preferences prefs;                               // guardar para sobrevivir a reinicios (0.11)
        prefs.begin("config", false);
        prefs.putBytes("riego", &config, sizeof(config));
        prefs.end();
      }
    }
  }
  // 304: ya estaba al día. Error o sin red: seguir con la que hay.
  http.end();
}
```

Un detalle que rompe la sincronización si se pasa por alto: la librería `pg` de Node devuelve las columnas `BIGINT` y `NUMERIC` como texto (para no perder precisión), así que sin las conversiones del `SELECT` el JSON llevaría `"version":"17"`, y el controlador, que espera un número, ignoraría la configuración. El controlador siempre tiene una configuración para trabajar: la última que recibió, guardada en la flash. Mientras no hay red, la usa; cuando vuelve, pregunta con su versión y recibe la vigente si cambió. Si en el medio hubo diez cambios, solo recibe el último. La configuración se modifica en un solo lugar (la app, a través del backend), así que no hay conflictos que resolver. Para que el cambio llegue antes, el backend puede avisar por MQTT (ver [3.2](/conceptos/3-2)) que hay una versión nueva, y el controlador la pide en ese momento.

## Cuándo sí y cuándo no

La consistencia eventual es la opción correcta cuando:

- una parte del sistema tiene que seguir funcionando aunque se corte la comunicación (los controladores),
- un atraso de segundos o minutos en ver un cambio es aceptable (tableros, reportes, réplicas),
- hay un mecanismo claro para converger (versiones, un único lugar de escritura).

Hace falta consistencia fuerte (transacciones en un solo lugar, ver [5.2](/conceptos/5-2)) cuando:

- dos operaciones no pueden contradecirse nunca (descontar un cupo, asignar un recurso único),
- un valor desactualizado causa un daño que no se puede deshacer.

En la práctica, un mismo sistema tiene las dos: el cupo de agua se controla con una transacción en el backend, y la configuración de los controladores se sincroniza de forma eventual.

## Resumen

- Con datos en varios lugares unidos por una red que falla, no se puede tener a la vez acuerdo permanente y funcionamiento durante los cortes.
- Consistencia eventual: los lugares pueden diferir por un tiempo, pero convergen cuando dejan de llegar cambios.
- Los controladores eligen seguir funcionando con lo último que saben, y se ponen al día al reconectarse.
- Las versiones crecientes hacen que la convergencia sea simple; un único lugar de escritura evita conflictos.
- Lo que el usuario acaba de escribir se lee de la base principal; las réplicas, para el resto.
