`volatile` le dice al compilador que una variable puede cambiar por fuera del flujo normal del código: desde una interrupción, desde otra tarea o desde el hardware. Con esa marca, el compilador lee y escribe la variable en memoria cada vez que el código la usa, en lugar de guardar una copia en un registro. `volatile` resuelve ese problema y nada más: no hace atómicas las operaciones ni evita que dos partes del programa se pisen. Para eso hacen falta otras herramientas, que también se ven en esta lección.

## Por qué te importa

El controlador del invernadero tiene código que no corre en el `loop()`: interrupciones que cuentan los pulsos del caudalímetro o detectan el botón de emergencia, y callbacks de BLE que corren en otra tarea cuando llega un dato de un nodo. Todos se comunican con `loop()` a través de variables compartidas.

El compilador optimiza mirando una función por vez. Si dentro de un bucle nada modifica una variable, asume que no cambia y la lee una sola vez. Así, un `while (!presionado)` puede quedar colgado para siempre aunque el botón se presione. Y aunque la variable sea `volatile`, una interrupción que llega en el momento justo puede hacer que se pierdan pulsos del caudalímetro o que la pantalla muestre una temperatura de un nodo con la humedad de otro. Estos bugs aparecen una vez cada muchas horas y no se pueden reproducir a voluntad.

## Paso a paso

### 1. Lo que hace el optimizador

```cpp
bool listo = false;   // la pone en true una interrupción

void esperar() {
  while (!listo) { }
}
```

El Arduino IDE compila con optimizaciones activadas. El compilador mira `esperar()` y razona así: dentro del `while` nadie modifica `listo`, así que su valor no puede cambiar mientras dura el bucle. Lee `listo` una vez y, si es `false`, genera un bucle infinito que ni siquiera vuelve a leerla.

El razonamiento es correcto para código normal. El compilador no sabe que existe una interrupción que puede cambiar la variable en cualquier momento.

### 2. `volatile`: leer siempre de memoria

```cpp
volatile bool listo = false;
```

Con `volatile`, cada `!listo` del bucle lee la variable de la memoria. Cuando la interrupción la pone en `true`, el bucle lo ve en la vuelta siguiente.

Una variable necesita `volatile` cuando:

- la escribe una interrupción y la lee el resto del programa (o al revés),
- la escribe un callback que corre en otra tarea de FreeRTOS, como los de BLE o WiFi, y la lee `loop()`,
- representa un registro de hardware. Esto lo resuelven las librerías y el core; en tu código casi no aparece.

### 3. Lo que `volatile` no hace

```cpp
volatile uint32_t pulsos = 0;

void IRAM_ATTR alPulso() { pulsos++; }   // interrupción

void loop() {
  pulsos++;                              // ¿y si la interrupción llega acá en el medio?
}
```

`pulsos++` son tres pasos: leer `pulsos`, sumarle uno y escribir el resultado. Si la interrupción ocurre después de que `loop()` leyó (digamos, 100) y antes de que escriba, la interrupción escribe 101, y después `loop()` escribe su 101. Hubo dos incrementos y el contador subió uno. A esto se lo llama *condición de carrera*.

`volatile` no lo evita: solo garantiza que cada lectura y escritura vaya a memoria, no que nadie se meta entre ellas. Lo mismo pasa al leer un dato de varias partes, como un `struct` o un `uint64_t`: la interrupción puede cambiar la mitad mientras leés la otra mitad.

En el ESP32, leer o escribir un entero de 32 bits alineado es una sola operación, así que una bandera `bool` o un contador que **solo escribe una de las partes** está bien con `volatile`. Todo lo demás necesita protección.

### 4. Secciones críticas

Una *sección crítica* es un bloque de código durante el cual no puede correr nada que toque los datos compartidos. En el ESP32 se usan con un *spinlock*:

```cpp
portMUX_TYPE candado = portMUX_INITIALIZER_UNLOCKED;
volatile uint32_t pulsos = 0;

void IRAM_ATTR alPulso() {
  portENTER_CRITICAL_ISR(&candado);
  pulsos++;
  portEXIT_CRITICAL_ISR(&candado);
}

uint32_t leerYReiniciar() {
  portENTER_CRITICAL(&candado);
  uint32_t n = pulsos;
  pulsos = 0;
  portEXIT_CRITICAL(&candado);
  return n;
}
```

Entre `portENTER_CRITICAL` y `portEXIT_CRITICAL`, las interrupciones están deshabilitadas en ese núcleo, y el otro núcleo del ESP32 espera si intenta entrar con el mismo candado. Dentro de una interrupción se usan las versiones con `_ISR`. La sección crítica tiene que ser cortísima: solo copiar o modificar los datos, nunca `Serial.print`, ni `delay`, ni nada que tarde.

En ejemplos de Arduino vas a ver `noInterrupts()` e `interrupts()`. En el ESP32 solo afectan al núcleo donde corren y no protegen contra una tarea del otro núcleo, así que para datos compartidos con callbacks de BLE o WiFi son más seguros los spinlocks.

### 5. `std::atomic` para contadores y banderas

```cpp
#include <atomic>

std::atomic<uint32_t> lecturasRecibidas{0};

void alRecibirLectura() {        // callback de BLE, en otra tarea
  lecturasRecibidas++;           // incremento atómico: no se pierde ninguno
}

void loop() {
  uint32_t n = lecturasRecibidas.exchange(0);   // leer y poner en cero, en un solo paso
}
```

`std::atomic` es la herramienta de C++ moderno para variables compartidas entre tareas. Cada operación (`++`, `exchange`, `load`, `store`) es indivisible, y además el compilador no la optimiza de forma insegura, así que no hace falta `volatile`. En el ESP32 funciona bien para enteros de hasta 32 bits. Para un `struct` completo, la sección crítica sigue siendo la opción.

### 6. Resumen de cuándo usar cada cosa

| Situación | Herramienta |
|---|---|
| Una bandera o un contador que escribe una parte y lee la otra | `volatile` |
| Leer y modificar desde los dos lados (`++` en ambos, leer y reiniciar) | sección crítica o `std::atomic` |
| Un `struct` o un dato de más de 32 bits compartido | sección crítica para copiarlo entero |
| Variables que solo usa `loop()` | nada: no son compartidas |

## Ejemplos

### Ejemplo 1. Una bandera desde una interrupción

El botón de emergencia del tablero dispara una interrupción. La interrupción solo levanta una bandera; el trabajo de verdad lo hace `loop()`.

```cpp emergencia.ino
constexpr uint8_t PIN_EMERGENCIA = 4;
constexpr uint8_t PIN_BOMBA = 26;

volatile bool emergencia = false;

void IRAM_ATTR alPresionarEmergencia() {
  emergencia = true;              // solo escribe: volatile alcanza
}

void setup() {
  Serial.begin(115200);
  pinMode(PIN_BOMBA, OUTPUT);
  pinMode(PIN_EMERGENCIA, INPUT_PULLUP);
  attachInterrupt(digitalPinToInterrupt(PIN_EMERGENCIA), alPresionarEmergencia, FALLING);
}

void loop() {
  if (emergencia) {
    emergencia = false;
    digitalWrite(PIN_BOMBA, LOW);
    Serial.println("parada de emergencia");
  }
  // resto del control...
}
```

La interrupción solo escribe `true` y `loop()` solo lee y escribe `false`. Si la interrupción llega justo entre la lectura y el `emergencia = false`, se pierde ese segundo aviso, pero la bomba igual se apaga por el primero, así que acá no importa. `IRAM_ATTR` pone la función en una memoria que siempre está disponible, como se explica en [0.8](/conceptos/0-8).

### Ejemplo 2. Leer y reiniciar un contador sin perder pulsos

El caudalímetro de la bomba genera 450 pulsos por litro. Cada 10 segundos, el controlador suma los litros de ese período al total del día y reinicia el contador.

```cpp caudal.ino
constexpr uint8_t PIN_CAUDALIMETRO = 33;
constexpr float PULSOS_POR_LITRO = 450.0f;

portMUX_TYPE candadoPulsos = portMUX_INITIALIZER_UNLOCKED;
volatile uint32_t pulsos = 0;
float litrosHoy = 0.0f;

void IRAM_ATTR alPulso() {
  portENTER_CRITICAL_ISR(&candadoPulsos);
  pulsos++;
  portEXIT_CRITICAL_ISR(&candadoPulsos);
}

uint32_t tomarPulsos() {
  portENTER_CRITICAL(&candadoPulsos);
  uint32_t n = pulsos;
  pulsos = 0;
  portEXIT_CRITICAL(&candadoPulsos);
  return n;
}

void setup() {
  Serial.begin(115200);
  pinMode(PIN_CAUDALIMETRO, INPUT_PULLUP);
  attachInterrupt(digitalPinToInterrupt(PIN_CAUDALIMETRO), alPulso, FALLING);
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 10000) {
    ultimo = millis();
    uint32_t n = tomarPulsos();                 // dentro del candado: solo copiar
    float litros = n / PULSOS_POR_LITRO;        // fuera del candado: el resto
    litrosHoy += litros;
    Serial.printf("%.2f L en 10 s, %.1f L hoy\n", litros, litrosHoy);
  }
}
```

Sin el candado en `tomarPulsos`, un pulso que llega entre la copia y el `pulsos = 0` se pierde. A 450 pulsos por litro un pulso es poco, pero al mes son litros que no aparecen en los registros. El cálculo y el `printf` quedan fuera de la sección crítica para que dure lo menos posible.

### Ejemplo 3. Un `struct` que llega por BLE

Cuando un nodo envía una lectura, el callback de BLE la guarda en una variable compartida. `loop()` la toma para mostrarla y para el control. Una `Lectura` tiene varios campos, así que copiarla no es una operación única.

```cpp lectura-compartida.ino
struct Lectura {
  float temperatura;
  float humedadAire;
  float humedadSuelo;
  uint8_t nodo;
};

portMUX_TYPE candadoLectura = portMUX_INITIALIZER_UNLOCKED;
Lectura ultimaLectura = {};             // protegida por el candado
volatile bool hayLecturaNueva = false;

// Lo llama la librería BLE, en su propia tarea
void alRecibirDeNodo(const Lectura& recibida) {
  portENTER_CRITICAL(&candadoLectura);
  ultimaLectura = recibida;             // copia completa, sin interrupciones
  hayLecturaNueva = true;
  portEXIT_CRITICAL(&candadoLectura);
}

bool tomarLectura(Lectura& destino) {
  bool habia;
  portENTER_CRITICAL(&candadoLectura);
  habia = hayLecturaNueva;
  if (habia) {
    destino = ultimaLectura;
    hayLecturaNueva = false;
  }
  portEXIT_CRITICAL(&candadoLectura);
  return habia;
}

void setup() {
  Serial.begin(115200);
}

void loop() {
  Lectura l;
  if (tomarLectura(l)) {
    Serial.printf("nodo %d: %.1f C, suelo %.0f%%\n", l.nodo, l.temperatura, l.humedadSuelo);
  }
}
```

Sin el candado, `loop()` podría copiar la `temperatura` de una lectura y la `humedadSuelo` de la siguiente, si el callback escribe en el medio. Con el candado, la copia es completa o no ocurre. `ultimaLectura` no necesita `volatile` porque solo se accede dentro de secciones críticas, que ya impiden que el compilador reordene o guarde copias de esos accesos. `hayLecturaNueva` tampoco lo necesitaría por la misma razón, pero el `volatile` deja claro que la variable es compartida. Cuando hay que pasar muchos datos entre tareas, FreeRTOS tiene colas, que se ven en [2.4](/conceptos/2-4).

## Errores comunes

### Una bandera sin `volatile`

```cpp
// Mal
bool datoListo = false;          // la escribe una interrupción

// Bien
volatile bool datoListo = false;
```

Puede funcionar en una prueba y fallar al cambiar una línea en otro lugar, porque el optimizador decide distinto según el código que rodea al bucle.

### Creer que `volatile` protege `++`

```cpp
// Mal: incrementos desde la interrupción y desde loop()
volatile uint32_t eventos = 0;
void IRAM_ATTR alEvento() { eventos++; }
void loop() { if (algo()) eventos++; }

// Bien
std::atomic<uint32_t> eventos{0};
void IRAM_ATTR alEvento() { eventos++; }
void loop() { if (algo()) eventos++; }
```

### Leer y reiniciar en dos pasos

```cpp
// Mal
uint32_t n = pulsos;
pulsos = 0;              // un pulso que llegó en el medio se pierde

// Bien
portENTER_CRITICAL(&candado);
uint32_t n = pulsos;
pulsos = 0;
portEXIT_CRITICAL(&candado);
```

### Hacer trabajo pesado dentro de la sección crítica

```cpp
// Mal: las interrupciones quedan deshabilitadas mientras se imprime
portENTER_CRITICAL(&candado);
Serial.printf("pulsos: %u\n", static_cast<unsigned>(pulsos));
pulsos = 0;
portEXIT_CRITICAL(&candado);

// Bien: copiar adentro, trabajar afuera
portENTER_CRITICAL(&candado);
uint32_t n = pulsos;
pulsos = 0;
portEXIT_CRITICAL(&candado);
Serial.printf("pulsos: %u\n", static_cast<unsigned>(n));
```

Una sección crítica larga hace que se pierdan interrupciones, y si dura demasiado, el *watchdog* del ESP32 reinicia el equipo (ver [2.6](/conceptos/2-6)).

## Ejercicio

El controlador mide el caudal de riego cada segundo. Durante las pruebas, la medición a veces da 0 aunque el agua está pasando, y el total diario sale un poco menor que lo que marca el medidor del tanque. Encontrá los dos problemas y corregilos.

void IRAM_ATTR alPulso() {

}

void setup() {

  }

```

portMUX_TYPE candado = portMUX_INITIALIZER_UNLOCKED;
volatile uint32_t pulsos = 0;

```

Sin `volatile`, el compilador puede reutilizar un valor de `pulsos` leído antes en lugar de leer el que dejó la interrupción, y por eso a veces aparecía 0. Sin la sección crítica, los pulsos que llegan entre la lectura y el `pulsos = 0` se pierden, y el total diario queda corto.

## Resumen

- `volatile` obliga al compilador a leer y escribir la variable en memoria en cada acceso. Hace falta en toda variable que modifica una interrupción u otra tarea.
- `volatile` no hace atómicas las operaciones: `++`, leer y reiniciar, o copiar un `struct` pueden ser interrumpidos en el medio.
- Para esos casos: una sección crítica (`portENTER_CRITICAL` con un `portMUX_TYPE` en el ESP32) o `std::atomic` para enteros.
- Dentro de una sección crítica, solo copiar o modificar datos. El trabajo pesado, afuera.
- Una bandera que escribe solo una de las partes está bien con `volatile` solo.
