Un **modelo relacional** organiza los datos en **tablas** con columnas de tipo definido, cada fila identificada por una **clave primaria**, y relaciones entre tablas expresadas con **claves foráneas**. Diseñarlo bien es decidir qué tablas existen, qué columnas tiene cada una, qué tipo es cada columna, qué reglas tienen que cumplir los datos (restricciones), y cómo va a cambiar el modelo con el tiempo (migraciones). En [4.1](/conceptos/4-1) viste la parte multi-tenant; esta lección es sobre el resto del modelado.

## Por qué te importa

El modelo de datos es la parte del backend que más cuesta cambiar: el código se reescribe en una tarde, pero millones de filas guardadas con un diseño equivocado se arrastran durante años. Una lista guardada como texto con comas, una fecha sin zona horaria, una columna sin restricciones que se llenó de valores imposibles: cada una de esas decisiones se paga en cada consulta y cada reporte.

Además, el sistema del invernadero no se puede apagar para cambiar el modelo: los equipos envían datos todo el tiempo. Cambiar una tabla con la base en uso exige hacerlo en pasos seguros.

## Paso a paso

### 1. Entidades, claves y relaciones

Cada "cosa" del dominio con identidad propia es una tabla: organizaciones, invernaderos, zonas de riego, cultivos, dispositivos, lecturas. Cada tabla tiene una **clave primaria** que identifica cada fila sin ambigüedad, y las relaciones se expresan con claves foráneas:

- **Uno a muchos**: un invernadero tiene muchas zonas. La tabla `zonas` tiene una columna `invernadero_id`.
- **Muchos a muchos**: una zona puede tener varios cultivos, y un cultivo estar en varias zonas. Hace falta una **tabla intermedia** (`zonas_cultivos`) con las dos claves, y puede tener datos propios de la relación, como la fecha de siembra.

### 2. Un dato, un lugar (normalización)

**Normalizar** es evitar que el mismo dato esté repetido en varios lugares, porque las copias terminan desincronizándose. Si el nombre del cultivo está escrito en cada zona, cambiarlo exige actualizar todas las filas, y alguna queda vieja. Con una tabla `cultivos` y una referencia, el nombre está en un solo lugar.

La normalización tiene excepciones razonables: el `organizacion_id` en la tabla de lecturas (ver [4.1](/conceptos/4-1)) es una copia deliberada para filtrar e indexar rápido. La diferencia es que es una decisión consciente, controlada por el backend, no un descuido.

### 3. Elegir los tipos

| Dato | Tipo en PostgreSQL | Por qué |
|---|---|---|
| identificadores | `BIGINT` / `BIGSERIAL` (o `UUID`) | 64 bits: no se agotan |
| momentos | `TIMESTAMPTZ` | instante absoluto, sin ambigüedad de zona horaria |
| fechas sin hora (fecha de siembra) | `DATE` | |
| mediciones de sensores | `REAL` o `NUMERIC(p,s)` | `NUMERIC` si importa la precisión exacta |
| cantidades exactas (litros facturados, dinero) | `NUMERIC(p,s)` | sin errores de redondeo de punto flotante |
| textos | `TEXT` | sin límite artificial; los largos se validan con `CHECK` |
| conjuntos cerrados (rol, tipo de equipo) | `TEXT` con `CHECK` o una tabla de referencia | |
| datos variables y poco consultados | `JSONB` | flexible, pero sin las garantías de las columnas |

Una regla sobre `JSONB`: es útil para datos cuya forma varía (el diagnóstico de un equipo, ver [4.7](/conceptos/4-7)), pero no reemplaza a las columnas. Lo que se filtra, se relaciona o se valida va en columnas.

### 4. Restricciones: la base como última defensa

Las restricciones hacen que la base de datos rechace datos inválidos, vengan de donde vengan:

- `NOT NULL`: el dato es obligatorio.
- `UNIQUE`: no puede repetirse.
- `CHECK (condición)`: una regla sobre los valores de la fila (`humedad_minima < humedad_maxima`).
- `REFERENCES`: la fila referenciada tiene que existir.

El código del backend valida para dar mensajes claros (ver [6.3](/conceptos/6-3)); las restricciones garantizan que, aunque haya un bug, un script manual o una ruta olvidada, lo guardado sea válido.

### 5. Historial en lugar de sobrescribir

Para algunos datos, el valor anterior importa. Si la configuración de riego de una zona se sobrescribe, nadie puede responder "¿con qué umbral se regaba el mes pasado, cuando se secaron las plantas?". Guardar cada versión (con quién la cambió y cuándo) y marcar cuál está vigente resuelve eso con poco costo, porque la configuración cambia pocas veces.

### 6. Migraciones

El modelo cambia con el tiempo, y esos cambios se escriben como **migraciones**: archivos numerados con el SQL de cada cambio, que se aplican en orden y quedan versionados con el código. Así todas las bases (desarrollo, pruebas, producción) tienen exactamente el mismo modelo.

Con la base en uso, los cambios se hacen en pasos que nunca rompen lo que está corriendo. Para agregar una columna obligatoria, por ejemplo: **expandir** (agregarla permitiendo nulos), completar los datos, actualizar el código, y recién después **contraer** (agregar `NOT NULL`, borrar lo viejo). Lo mismo para renombrar o cambiar el tipo de una columna.

## Ejemplos

### Ejemplo 1. Zonas, cultivos y la relación entre ellos

```sql zonas-cultivos.sql
CREATE TABLE zonas (
  id               BIGSERIAL PRIMARY KEY,
  organizacion_id  BIGINT NOT NULL,
  invernadero_id   BIGINT NOT NULL,
  nombre           TEXT NOT NULL CHECK (length(nombre) BETWEEN 1 AND 60),
  superficie_m2    NUMERIC(8,2) CHECK (superficie_m2 > 0),
  FOREIGN KEY (organizacion_id, invernadero_id) REFERENCES invernaderos (organizacion_id, id),
  UNIQUE (invernadero_id, nombre),          -- no dos zonas con el mismo nombre en un invernadero
  UNIQUE (organizacion_id, id)
);

CREATE TABLE cultivos (
  id      BIGSERIAL PRIMARY KEY,
  nombre  TEXT NOT NULL UNIQUE               -- catálogo común: "tomate perita", "lechuga mantecosa"
);

CREATE TABLE zonas_cultivos (
  zona_id         BIGINT NOT NULL REFERENCES zonas(id) ON DELETE CASCADE,
  cultivo_id      BIGINT NOT NULL REFERENCES cultivos(id),
  fecha_siembra   DATE NOT NULL,
  fecha_cosecha   DATE,
  PRIMARY KEY (zona_id, cultivo_id, fecha_siembra),
  CHECK (fecha_cosecha IS NULL OR fecha_cosecha >= fecha_siembra)
);

-- ¿Qué zonas de la organización 3 tienen tomate sembrado y sin cosechar?
SELECT z.nombre AS zona, c.nombre AS cultivo, zc.fecha_siembra
  FROM zonas z
  JOIN zonas_cultivos zc ON zc.zona_id = z.id
  JOIN cultivos c ON c.id = zc.cultivo_id
 WHERE z.organizacion_id = 3
   AND c.nombre LIKE 'tomate%'
   AND zc.fecha_cosecha IS NULL;
```

La tabla intermedia guarda datos que no son ni de la zona ni del cultivo, sino de la relación: cuándo se sembró y cuándo se cosechó. La clave primaria incluye la fecha de siembra, así la misma zona puede tener tomate en varias temporadas. `ON DELETE CASCADE` hace que, si se borra una zona, se borren sus relaciones con cultivos; el catálogo de cultivos no se toca. Las restricciones garantizan nombres no vacíos, superficies positivas y cosechas posteriores a la siembra.

### Ejemplo 2. Configuración de riego con historial

Cada cambio de configuración es una fila nueva; la vigente es la más reciente de cada zona.

```sql config-riego.sql
CREATE TABLE config_riego (
  id               BIGSERIAL PRIMARY KEY,
  organizacion_id  BIGINT NOT NULL,
  zona_id          BIGINT NOT NULL,
  humedad_minima   NUMERIC(4,1) NOT NULL,
  humedad_maxima   NUMERIC(4,1) NOT NULL,
  riego_maximo_s   INTEGER NOT NULL,
  creado_por       BIGINT NOT NULL REFERENCES usuarios(id),
  creado           TIMESTAMPTZ NOT NULL DEFAULT now(),
  FOREIGN KEY (organizacion_id, zona_id) REFERENCES zonas (organizacion_id, id),
  CHECK (humedad_minima >= 5 AND humedad_maxima <= 95 AND humedad_minima < humedad_maxima),
  CHECK (riego_maximo_s BETWEEN 10 AND 1800)
);

CREATE INDEX config_riego_zona_creado ON config_riego (zona_id, creado DESC);

-- Configuración vigente de una zona
SELECT humedad_minima, humedad_maxima, riego_maximo_s, creado
  FROM config_riego
 WHERE organizacion_id = $1 AND zona_id = $2
 ORDER BY creado DESC
 LIMIT 1;

-- ¿Qué configuración regía el 15 de septiembre?
SELECT humedad_minima, humedad_maxima, creado_por, creado
  FROM config_riego
 WHERE organizacion_id = $1 AND zona_id = $2 AND creado <= '2026-09-15'
 ORDER BY creado DESC
 LIMIT 1;
```

Nunca se hace `UPDATE` sobre la configuración: cada cambio es un `INSERT`. Así queda el historial completo, con quién hizo cada cambio, y la pregunta "¿qué umbral se usaba cuando pasó tal cosa?" tiene respuesta. Las mismas reglas que valida el controlador (ver [0.11](/conceptos/0-11)) están como `CHECK` en la base: un valor absurdo no puede guardarse ni por error. El índice hace que buscar la vigente sea instantáneo.

### Ejemplo 3. Una migración en pasos seguros

Los dispositivos tienen que pasar a pertenecer a una zona (no solo a un invernadero). La tabla tiene miles de filas y la ingesta la consulta en cada pedido.

```sql 0007_dispositivos_zona_expandir.sql
-- Paso 1 (expandir): columna nueva, permitiendo nulos. No rompe nada de lo que corre.
ALTER TABLE dispositivos ADD COLUMN zona_id BIGINT;

-- Paso 2: completar los valores existentes (por ejemplo, la primera zona de cada invernadero)
UPDATE dispositivos d
   SET zona_id = (SELECT z.id FROM zonas z
                   WHERE z.invernadero_id = d.invernadero_id
                   ORDER BY z.id LIMIT 1)
 WHERE d.zona_id IS NULL;
```

```text
Paso 3: desplegar el backend nuevo, que completa zona_id al dar de alta un dispositivo
        y lo usa en las consultas. El backend viejo sigue funcionando, porque ignora la columna.
```

```sql 0008_dispositivos_zona_contraer.sql
-- Paso 4 (contraer): cuando todo el código nuevo está en producción y no quedan nulos
ALTER TABLE dispositivos
  ADD CONSTRAINT dispositivos_zona_fk FOREIGN KEY (organizacion_id, zona_id)
      REFERENCES zonas (organizacion_id, id) NOT VALID;
ALTER TABLE dispositivos VALIDATE CONSTRAINT dispositivos_zona_fk;
ALTER TABLE dispositivos ALTER COLUMN zona_id SET NOT NULL;
```

Cada migración es un archivo numerado que se aplica una vez, en orden, en todas las bases (herramientas como `node-pg-migrate` o `knex` llevan el registro de cuáles ya se aplicaron). En ningún momento el sistema está roto: entre los pasos, el código viejo y el nuevo funcionan con la tabla como está. `NOT VALID` agrega la clave foránea sin revisar todas las filas existentes en el momento (lo que bloquearía la tabla más tiempo), y `VALIDATE CONSTRAINT` las revisa después, con un bloqueo más liviano.

## Errores comunes

### Listas dentro de un texto

```sql
-- Mal
cultivos TEXT   -- "tomate,lechuga"

-- Bien: una tabla intermedia (ejemplo 1)
```

### Fechas sin zona horaria

```sql
-- Mal: ¿14:30 de qué zona? ¿Antes o después del cambio de horario?
momento TIMESTAMP

-- Bien
momento TIMESTAMPTZ
```

Más sobre los supuestos falsos con el tiempo en [7.1](/conceptos/7-1).

### Tablas sin restricciones

Confiar en que "el código ya valida" deja la base abierta a cualquier camino que no pase por ese código. Las reglas importantes van también como `NOT NULL`, `CHECK`, `UNIQUE` y claves foráneas.

### `JSONB` para todo

Guardar la configuración, las relaciones o los datos que se filtran dentro de un `JSONB` pierde los tipos, las restricciones y las claves foráneas. `JSONB` es para lo realmente variable.

### Cambios destructivos con la base en uso

Renombrar o borrar una columna en un solo paso rompe el código que la usa mientras se despliega el nuevo. Expandir, migrar los datos, cambiar el código, y recién después contraer.

```sql alarmas.sql
CREATE TABLE alarmas (
  id                BIGSERIAL PRIMARY KEY,
  organizacion_id   BIGINT NOT NULL,
  invernadero_id    BIGINT NOT NULL,
  tipo              TEXT NOT NULL CHECK (tipo IN
                      ('temperatura_alta', 'temperatura_baja', 'tanque_vacio', 'equipo_sin_noticias')),
  activada          TIMESTAMPTZ NOT NULL DEFAULT now(),
  reconocida        TIMESTAMPTZ,              -- nulo = sin reconocer
  reconocida_por    BIGINT REFERENCES usuarios(id),
  FOREIGN KEY (organizacion_id, invernadero_id) REFERENCES invernaderos (organizacion_id, id),
  -- reconocida y reconocida_por van juntas
  CHECK ((reconocida IS NULL) = (reconocida_por IS NULL))
);

CREATE INDEX alarmas_activas_org ON alarmas (organizacion_id) WHERE reconocida IS NULL;
```

Los problemas del modelo original:

- **El invernadero y el usuario por nombre**: si cambian de nombre, las alarmas viejas quedan apuntando a nada, y nada impide un nombre inexistente. Ahora son claves foráneas.
- **`tipo` libre**: "temperatura alta" y "Temp. alta" son lo mismo para una persona y distintos para una consulta. Ahora es un conjunto cerrado con `CHECK`, con nombres estables.
- **`TIMESTAMP` sin zona**: pasa a `TIMESTAMPTZ`.
- **`reconocida` como texto "si"/"no"**: admite "Sí", "SI", "s"... Se reemplaza por el momento en que se reconoció (nulo si no), que además da la información de cuándo.
- **Nada obligatorio**: ahora lo esencial es `NOT NULL`, y el `CHECK` final impide una alarma "reconocida" sin saber por quién, o al revés.
- **Sin organización**: falta `organizacion_id` para el aislamiento de [4.1](/conceptos/4-1).

El índice parcial acelera la consulta más frecuente: las alarmas sin reconocer de una organización.

</details>

## Resumen

- Cada entidad es una tabla con clave primaria; las relaciones van con claves foráneas, y las de muchos a muchos con una tabla intermedia.
- Normalizar: cada dato en un solo lugar. Las copias deliberadas (como `organizacion_id` en las lecturas) son decisiones conscientes.
- Elegí bien los tipos: `TIMESTAMPTZ` para momentos, `NUMERIC` para cantidades exactas, `JSONB` solo para lo variable.
- Las restricciones (`NOT NULL`, `CHECK`, `UNIQUE`, `REFERENCES`) hacen que la base rechace datos inválidos venga de donde venga.
- Guardá historial cuando el valor anterior importa, y cambiá el modelo con migraciones en pasos seguros: expandir, migrar, contraer.
