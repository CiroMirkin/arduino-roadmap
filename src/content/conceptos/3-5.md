Cuando el controlador envía datos por una red que falla, tiene que decidir tres cosas: **qué errores reintentar** (los pasajeros, no los que indican un pedido mal armado), **cuánto esperar entre intentos** (cada vez más, con algo de azar, hasta un máximo: *backoff exponencial con jitter*) y **cómo evitar duplicados** cuando un envío llegó pero la respuesta se perdió. Lo último se resuelve con **idempotencia**: diseñar el envío para que repetirlo tenga el mismo efecto que hacerlo una vez.

## Por qué te importa

En [0.10](/conceptos/0-10), [2.4](/conceptos/2-4) y [3.1](/conceptos/3-1) el controlador ya guarda las lecturas que no pudo enviar y las reintenta. Hacerlo mal tiene consecuencias concretas. Reintentar sin espera ni máximo, durante una caída del backend, multiplica la carga justo cuando el servidor intenta recuperarse; con cien equipos, el backend puede no levantarse nunca. Reintentar errores que no son pasajeros llena la cola con datos que nunca van a entrar.

Y el problema más sutil: si el backend guardó una lectura pero la respuesta no llegó, el controlador la reenvía, y el registro de riego queda con dos riegos donde hubo uno. En el backend de varias organizaciones, un duplicado puede significar un consumo de agua facturado dos veces.

## Paso a paso

### 1. Qué errores se reintentan

| Resultado | ¿Reintentar? | Por qué |
|---|---|---|
| 2xx | no: éxito | |
| negativo (sin conexión, tiempo agotado) | sí | problema pasajero de red |
| 5xx (error del servidor) | sí | el servidor puede recuperarse |
| 429 (demasiadas peticiones) | sí, respetando lo que pida el servidor | el backend está limitando (ver [4.4](/conceptos/4-4)) |
| 4xx (salvo 429) | no | el pedido tiene un problema; repetirlo da el mismo error |

Un 4xx se registra (con el cuerpo de la respuesta, que suele explicar el problema) y el dato se descarta o se guarda aparte para revisarlo.

### 2. Backoff exponencial

Entre un intento fallido y el siguiente, la espera **se duplica**, hasta un máximo:

```text
intento:  1    2    3    4     5     6     7 ...
espera:   2 s  4 s  8 s  16 s  32 s  60 s  60 s ...   (máximo 60 s)
```

Ante un corte breve, el reintento llega rápido. Ante un corte largo, los intentos se espacian y el equipo no gasta energía ni castiga a la red. Cuando un envío sale bien, la espera vuelve al mínimo.

### 3. Jitter: un poco de azar

Si el backend se cae, todos los controladores empiezan a fallar al mismo tiempo, y con el mismo backoff, todos reintentan en el mismo segundo: 2 s después, 4 s después, 8 s después. Cuando el backend se recupera, recibe todos los pedidos juntos y puede volver a caerse. Es el problema de la **manada** (*thundering herd*).

La solución es agregar una parte aleatoria a cada espera. Una forma simple y efectiva: esperar un tiempo al azar entre la mitad y el total de la espera calculada.

```cpp
uint32_t espera = base * (1u << intento);            // exponencial
if (espera > maximo) espera = maximo;
espera = espera / 2 + esp_random() % (espera / 2 + 1);   // entre 50 % y 100 %
```

`esp_random()` es el generador de números aleatorios por hardware del ESP32.

### 4. Respetar lo que pide el servidor

Cuando el backend está sobrecargado, puede responder `429` o `503` con un encabezado `Retry-After: 30`, que significa "volvé a intentar en 30 segundos". Si llega, el equipo usa esa espera en lugar de la propia: el servidor sabe mejor que nadie cuándo va a poder atender.

### 5. El problema de los duplicados

```text
equipo ──POST lectura──► backend   (la guarda)
equipo ◄──── 201 ─────── backend   (la respuesta se pierde)
equipo: "no hubo respuesta, reintento"
equipo ──POST lectura──► backend   (¿la guarda otra vez?)
```

Desde el equipo, "no llegó" y "llegó pero no volvió la respuesta" son indistinguibles. Cualquier sistema que reintenta va a enviar duplicados de vez en cuando. No se puede evitar desde el equipo; hay que diseñar el envío para que los duplicados no hagan daño.

### 6. Idempotencia con un identificador único

Una operación es **idempotente** si hacerla varias veces tiene el mismo efecto que hacerla una vez. Para que el envío de lecturas lo sea, cada lectura lleva un **identificador único** generado en el equipo, y el backend guarda ese identificador con una restricción de unicidad: si llega uno que ya existe, responde éxito sin guardar nada nuevo.

Un identificador práctico: el identificador del equipo más un número de secuencia que crece con cada lectura (guardado en NVS cada tanto para no repetirlo después de un reinicio), o un valor aleatorio de 64 bits. Del lado del backend, una restricción `UNIQUE` en la base de datos hace el resto (ver [4.3](/conceptos/4-3)).

## Ejemplos

### Ejemplo 1. Una clase para el backoff

La política de esperas en una clase chica y pura, que se puede probar sin red.

```cpp backoff.ino
class Backoff {
public:
  Backoff(uint32_t minimoMs, uint32_t maximoMs) : _minimoMs(minimoMs), _maximoMs(maximoMs) {}

  // Llamar después de un fallo: devuelve cuánto esperar antes del próximo intento
  uint32_t siguienteEspera() {
    uint32_t espera = _minimoMs;
    for (uint32_t i = 0; i < _fallos && espera < _maximoMs; i++) espera *= 2;
    if (espera > _maximoMs) espera = _maximoMs;
    _fallos++;
    return espera / 2 + esp_random() % (espera / 2 + 1);   // jitter: entre 50 % y 100 %
  }

  void exito() { _fallos = 0; }
  uint32_t fallosSeguidos() const { return _fallos; }

private:
  uint32_t _minimoMs;
  uint32_t _maximoMs;
  uint32_t _fallos = 0;
};

void setup() {
  Serial.begin(115200);
  Backoff backoff(2000, 60000);
  for (int i = 0; i < 8; i++) {
    Serial.printf("fallo %d: esperar %u ms\n", i + 1, static_cast<unsigned>(backoff.siguienteEspera()));
  }
  backoff.exito();
  Serial.printf("tras un éxito: esperar %u ms\n", static_cast<unsigned>(backoff.siguienteEspera()));
}

void loop() {}
```

La salida muestra esperas de alrededor de 1-2 s, 2-4 s, 4-8 s... hasta quedar entre 30 y 60 s, y después de un éxito vuelve al principio. El bucle que duplica se detiene al llegar al máximo, así que nunca desborda aunque haya miles de fallos seguidos. Con `esp_random()` reemplazado por una función inyectada, esta clase se prueba en la PC como en [2.8](/conceptos/2-8).

### Ejemplo 2. Enviar, clasificar el resultado y reintentar

La tarea de comunicación intenta enviar la primera lectura pendiente. Según el resultado, la saca de la cola, la descarta o programa el próximo intento.

```cpp reintentos.ino
#include <WiFi.h>
#include <HTTPClient.h>

// Backoff: la clase del ejemplo 1

enum class ResultadoEnvio : uint8_t { Ok, Reintentar, Descartar };

ResultadoEnvio enviar(const char* cuerpo, uint32_t& retryAfterMs) {
  retryAfterMs = 0;
  HTTPClient http;
  http.begin("http://192.168.0.10:3000/api/invernaderos/2/lecturas");
  http.setConnectTimeout(3000);
  http.setTimeout(5000);
  http.addHeader("Content-Type", "application/json");
  const char* encabezados[] = {"Retry-After"};
  http.collectHeaders(encabezados, 1);

  int codigo = http.POST(cuerpo);
  ResultadoEnvio r;
  if (codigo >= 200 && codigo < 300) {
    r = ResultadoEnvio::Ok;
  } else if (codigo < 0 || codigo >= 500 || codigo == 429) {
    r = ResultadoEnvio::Reintentar;
    long segundos = http.header("Retry-After").toInt();   // 0 si no vino
    if (segundos > 0 && segundos <= 3600) retryAfterMs = static_cast<uint32_t>(segundos) * 1000;
  } else {
    Serial.printf("rechazado (%d): %s\n", codigo, http.getString().c_str());
    r = ResultadoEnvio::Descartar;
  }
  http.end();
  return r;
}

Backoff backoff(2000, 60000);
uint32_t proximoIntentoMs = 0;

void intentarEnvio() {
  if (static_cast<int32_t>(millis() - proximoIntentoMs) < 0) return;   // todavía no
  const char* lectura = "{\"id\":\"inv2-ctrl-000123\",\"temp\":24.5}";   // la primera pendiente

  uint32_t retryAfter;
  switch (enviar(lectura, retryAfter)) {
    case ResultadoEnvio::Ok:
      backoff.exito();
      // sacar la lectura de la cola
      break;
    case ResultadoEnvio::Descartar:
      backoff.exito();          // el problema no es la red: no frenar a las siguientes
      // sacar la lectura de la cola y guardarla aparte para revisar
      break;
    case ResultadoEnvio::Reintentar: {
      uint32_t espera = retryAfter ? retryAfter : backoff.siguienteEspera();
      proximoIntentoMs = millis() + espera;
      Serial.printf("reintento en %u ms\n", static_cast<unsigned>(espera));
      break;
    }
  }
}

void setup() {
  Serial.begin(115200);
  WiFi.begin("invernadero", "clave-del-wifi");
}

void loop() {
  if (WiFi.status() == WL_CONNECTED) intentarEnvio();
}
```

`static_cast<int32_t>(millis() - proximoIntentoMs) < 0` compara dos momentos de forma segura aunque `millis()` dé la vuelta: la resta sin signo convertida a con signo dice si `proximoIntentoMs` está en el futuro. Un `Retry-After` del servidor tiene prioridad sobre el backoff propio. El descarte de un 4xx reinicia el backoff, porque el problema era del dato, no de la red. La lectura ya lleva un `id`, que es lo que hace seguros los reintentos (ejemplo 3).

### Ejemplo 3. Lecturas idempotentes, de punta a punta

Del lado del equipo, cada lectura recibe un identificador único: el identificador del equipo y un número de secuencia que nunca se repite, ni siquiera después de un reinicio.

```cpp identificador.ino
#include <Preferences.h>

constexpr const char* ID_EQUIPO = "inv2-ctrl";
constexpr uint32_t BLOQUE = 100;          // se guarda en NVS cada 100 lecturas

uint32_t secuencia = 0;
uint32_t limiteReservado = 0;

void iniciarSecuencia() {
  Preferences prefs;
  prefs.begin("envios", false);
  // Al arrancar, saltar al siguiente bloque: nunca se repite un número ya usado
  secuencia = prefs.getUInt("reservado", 0);
  limiteReservado = secuencia + BLOQUE;
  prefs.putUInt("reservado", limiteReservado);
  prefs.end();
}

void nuevoId(char* salida, size_t tam) {
  if (secuencia >= limiteReservado) {     // se terminó el bloque: reservar otro
    limiteReservado += BLOQUE;
    Preferences prefs;
    prefs.begin("envios", false);
    prefs.putUInt("reservado", limiteReservado);
    prefs.end();
  }
  snprintf(salida, tam, "%s-%08lu", ID_EQUIPO, static_cast<unsigned long>(secuencia++));
}

void setup() {
  Serial.begin(115200);
  iniciarSecuencia();
  for (int i = 0; i < 3; i++) {
    char id[32];
    nuevoId(id, sizeof(id));
    Serial.println(id);    // inv2-ctrl-00000000, inv2-ctrl-00000001, ...
  }
}

void loop() {}
```

En lugar de escribir la NVS con cada lectura (ver [0.11](/conceptos/0-11)), se reserva un bloque de 100 números y se guarda solo el límite. Si el equipo se reinicia, salta al bloque siguiente: puede quedar un hueco en la numeración, pero nunca un número repetido.

Del lado del backend, la tabla tiene una restricción de unicidad sobre el identificador, y la inserción ignora los repetidos:

```sql lecturas.sql
CREATE TABLE lecturas (
  id_envio        TEXT PRIMARY KEY,          -- el identificador generado por el equipo
  dispositivo_id  INTEGER NOT NULL REFERENCES dispositivos(id),
  momento         TIMESTAMPTZ NOT NULL,
  temperatura     NUMERIC(4,1),
  humedad_suelo   SMALLINT
);
```

```js ingesta.js
// Ruta Express: POST /api/invernaderos/:id/lecturas (con el middleware de 3.4)
async function recibirLectura(req, res) {
  const { id, temp, suelo, momento } = req.body;
  // validar tipos y rangos antes de esto (ver 6.3)
  await req.db.query(
    `INSERT INTO lecturas (id_envio, dispositivo_id, momento, temperatura, humedad_suelo)
     VALUES ($1, $2, $3, $4, $5)
     ON CONFLICT (id_envio) DO NOTHING`,
    [id, req.equipo.id, momento, temp, suelo]
  );
  res.status(201).json({ ok: true });   // nueva o repetida, la respuesta es la misma
}
```

`ON CONFLICT ... DO NOTHING` hace que una lectura repetida no genere un error ni una fila nueva. El backend responde lo mismo en los dos casos: para el equipo, lo importante es que la lectura está guardada. Con esto, reintentar es siempre seguro. El diseño completo de la ingesta se ve en [4.3](/conceptos/4-3).

## Errores comunes

### Reintentar los 4xx

```cpp
// Mal: un JSON mal armado se reintenta para siempre y bloquea la cola
if (codigo != 200) reintentar();

// Bien: solo errores pasajeros
if (codigo < 0 || codigo >= 500 || codigo == 429) reintentar();
else if (codigo >= 400) descartarYRegistrar();
```

### Reintentos sin espera, sin máximo o sin jitter

Reintentar cada segundo durante una caída, o con esperas que crecen sin límite (una espera de días no sirve), o todos los equipos al mismo tiempo. Backoff exponencial, con máximo y con jitter.

### Reintentar sin idempotencia

Sin un identificador único por envío, cada reintento después de una respuesta perdida es un duplicado. El identificador lo genera el equipo, una sola vez por lectura, y viaja en todos los intentos.

### Generar el identificador en cada intento

```cpp
// Mal: cada reintento tiene un id nuevo, y el backend no detecta el duplicado
void intentar() { nuevoId(id, sizeof(id)); enviar(lectura, id); }

// Bien: el id se genera al crear la lectura y se guarda con ella en la cola
```

### Reintentar bloqueando el control

```cpp
// Mal
while (!enviar(lectura)) delay(backoff.siguienteEspera());

// Bien: programar el próximo intento y volver; la tarea de comunicación lo retoma (ejemplo 2)
```

## Ejercicio

Este código envía los eventos de riego al backend. El registro del backend muestra eventos duplicados, y durante una caída del servidor, cuando volvió, todos los controladores lo tumbaron otra vez. Además, un evento con un formato que el backend rechaza quedó trabando la cola durante días. Corregilo describiendo los cambios y escribiendo la nueva lógica de reintento.

```cpp eventos-riego.ino
void enviarEventos() {
  while (hayEventos()) {

      quitarPrimerEvento();
    } else {
      delay(5000);
    }
  }
}
```

<summary>Ver solución</summary>

```cpp eventos-riego.ino
// Backoff: la clase del ejemplo 1
Backoff backoff(2000, 120000);
uint32_t proximoIntentoMs = 0;

// El id se genera una sola vez, al registrar el evento, y se guarda con él
struct Evento {
  char id[32];
  char tipo[16];
  float litros;
};

void actualizarEnvios() {                                   // llamar seguido; nunca bloquea
  if (!hayEventos()) return;
  if (static_cast<int32_t>(millis() - proximoIntentoMs) < 0) return;

  const Evento& e = primerEvento();
  char cuerpo[128];
  snprintf(cuerpo, sizeof(cuerpo), "{\"id\":\"%s\",\"tipo\":\"%s\",\"litros\":%.1f}",
           e.id, e.tipo, e.litros);
  int codigo = post(cuerpo);

  if (codigo >= 200 && codigo < 300) {
    quitarPrimerEvento();
    backoff.exito();
  } else if (codigo < 0 || codigo >= 500 || codigo == 429) {
    proximoIntentoMs = millis() + backoff.siguienteEspera();   // pasajero: reintentar más tarde
  } else {
    guardarParaRevisar(e, codigo);                            // 4xx: el reintento no lo arregla
    quitarPrimerEvento();
    backoff.exito();
  }
}
```

Los duplicados venían de reintentar sin identificador: ahora cada evento lleva un `id` generado al crearlo, y el backend los ignora con `ON CONFLICT DO NOTHING`. La avalancha al volver el servidor venía de que todos esperaban exactamente 5 segundos: ahora la espera crece hasta 2 minutos y tiene jitter. El evento trabado era un 4xx que se reintentaba para siempre: ahora se guarda aparte y la cola sigue. Y el `while` con `delay` bloqueaba la tarea entera: ahora la función programa el próximo intento y vuelve.

</details>

## Resumen

- Se reintentan los errores pasajeros (sin conexión, 5xx, 429); los 4xx se registran y se descartan.
- Backoff exponencial: la espera se duplica en cada fallo, hasta un máximo, y vuelve al mínimo con el primer éxito.
- Jitter: una parte aleatoria en cada espera evita que todos los equipos reintenten a la vez. `Retry-After` del servidor tiene prioridad.
- Un envío sin respuesta puede haber llegado: los reintentos generan duplicados.
- Idempotencia: cada dato lleva un identificador único generado una vez en el equipo, y el backend ignora los repetidos (`UNIQUE` y `ON CONFLICT DO NOTHING`).
