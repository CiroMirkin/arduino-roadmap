En [B.9](/conceptos/b-9) viste la herencia: una clase derivada **es un** tipo de la base. La **composición** es otra forma de construir clases: una clase **tiene** otros objetos como miembros y les delega parte del trabajo. Una zona de riego tiene una válvula, un sensor de suelo y un temporizador. La recomendación de "composición por sobre herencia" dice que, cuando las dos sirven, conviene la composición: es más flexible, más fácil de cambiar y, en firmware, más simple de razonar.

## Por qué te importa

La tentación con la herencia es usarla para reutilizar código: "la bomba hace lo mismo que el relé, así que hereda de `Rele`". Funciona hasta que algo cambia. Una bomba con caudalímetro hereda de la bomba; una bomba con caudalímetro y alarma hereda de esa; aparece una bomba con alarma pero sin caudalímetro y no tiene dónde ubicarse. Y el día que una bomba se controla con un MOSFET en lugar de un relé, toda la jerarquía está mal.

Con composición, cada pieza es independiente y se combinan como bloques. Una zona de riego se arma con la válvula, el sensor y el temporizador que correspondan; si el hardware cambia, se cambia una pieza. Los objetos compuestos además viven dentro del objeto que los contiene, sin `new` ni punteros, lo que en un microcontrolador es una ventaja.

## Paso a paso

### 1. "Es un" o "tiene un"

Antes de heredar, probá la frase en voz alta:

| Frase | ¿Suena bien? | Relación |
|---|---|---|
| Un sensor analógico **es un** sensor de temperatura | sí | herencia de una interfaz |
| Una bomba **es un** relé | no: la bomba **tiene** (o usa) un relé | composición |
| Una zona de riego **es una** válvula | no: **tiene** una válvula | composición |
| Un controlador **es un** cliente BLE | no: **tiene** una conexión BLE | composición |

Si la frase con "es un" suena forzada, es composición.

### 2. Composición: objetos como miembros

```cpp
class Rele {
public:
  explicit Rele(uint8_t pin, bool activoEnBajo = true) : _pin(pin), _activoEnBajo(activoEnBajo) {}
  void begin()    { pinMode(_pin, OUTPUT); apagar(); }
  void encender() { digitalWrite(_pin, _activoEnBajo ? LOW : HIGH); _encendido = true; }
  void apagar()   { digitalWrite(_pin, _activoEnBajo ? HIGH : LOW); _encendido = false; }
  bool encendido() const { return _encendido; }
private:
  uint8_t _pin;
  bool _activoEnBajo;
  bool _encendido = false;
};

class Bomba {
public:
  explicit Bomba(uint8_t pinRele) : _rele(pinRele) {}
  void begin() { _rele.begin(); }
  void encender() {
    if (_rele.encendido()) return;
    _rele.encender();
    _arranques++;
  }
  void apagar() { _rele.apagar(); }
  uint32_t arranques() const { return _arranques; }
private:
  Rele _rele;                  // la bomba TIENE un relé
  uint32_t _arranques = 0;
};
```

`Bomba` guarda un `Rele` como miembro y le **delega** el encendido. Desde afuera, la bomba ofrece lo que tiene sentido para una bomba (`encender`, `apagar`, `arranques`); cómo maneja su relé es un detalle interno. El relé se construye en la lista de inicialización (`: _rele(pinRele)`) y vive dentro de la bomba: no hay `new` ni punteros.

### 3. El problema de las jerarquías

```text
Rele
└── Bomba
    └── BombaConCaudalimetro
        └── BombaConCaudalimetroYAlarma
```

Cada combinación nueva de características pide una clase nueva en la jerarquía. Con dos características opcionales (caudalímetro, alarma) ya hay cuatro combinaciones; con tres, ocho. Y todas quedan atadas a `Rele`.

Con composición, las características son piezas que se agregan:

```cpp
class Bomba {
  Rele _rele;
  Caudalimetro* _caudalimetro = nullptr;   // opcional
  bool _alarmaSinFlujo = false;            // una opción, no una subclase
};
```

### 4. Composición con interfaces

Cuando una pieza puede ser de distintos tipos, se combina composición con una interfaz (herencia de interfaz, ver [B.9](/conceptos/b-9)). La bomba no tiene "un relé": tiene "algo que se enciende y se apaga".

```cpp
class Interruptor {
public:
  virtual void encender() = 0;
  virtual void apagar() = 0;
  virtual ~Interruptor() = default;
};

class InterruptorRele : public Interruptor { /* digitalWrite */ };
class InterruptorMosfet : public Interruptor { /* ledcWrite al 100 % o 0 % */ };

class Bomba {
public:
  explicit Bomba(Interruptor& interruptor) : _interruptor(interruptor) {}
  void encender() { _interruptor.encender(); }
  void apagar()   { _interruptor.apagar(); }
private:
  Interruptor& _interruptor;
};
```

La herencia quedó donde tiene sentido (un relé **es un** interruptor), y la bomba **tiene** un interruptor, sin saber de qué tipo. Que la bomba reciba su interruptor desde afuera, en lugar de crearlo ella, se llama **inyección de dependencias**, y es lo que permite usar un interruptor simulado para probar.

### 5. Ventajas en firmware

- **Memoria predecible**: los objetos compuestos por valor viven dentro del objeto que los contiene. Un `ZonaRiego` global con sus piezas ocupa memoria estática, sin heap (ver [B.8](/conceptos/b-8)).
- **Sin costo de `virtual`** cuando no hace falta variar el tipo: componer un `Rele` por valor no necesita vtables.
- **Inicialización clara**: el constructor arma todas las piezas, y `begin()` las inicializa en orden.

### 6. Cuándo sí heredar

- **Interfaces** con varias implementaciones intercambiables: sensores, interruptores, destinos de reporte.
- **Callbacks** que exige una librería (`BLEServerCallbacks`).
- Una relación "es un" genuina, donde la derivada se puede usar en cualquier lugar donde se usa la base sin sorpresas.

Si la única razón para heredar es no volver a escribir dos métodos, componé.

## Ejemplos

### Ejemplo 1. La misma bomba, con herencia y con composición

```cpp bomba-herencia.ino
// Con herencia: la bomba "es un" relé
class Rele {
public:
  explicit Rele(uint8_t pin) : _pin(pin) {}
  void begin()    { pinMode(_pin, OUTPUT); apagar(); }
  void encender() { digitalWrite(_pin, LOW); }
  void apagar()   { digitalWrite(_pin, HIGH); }
protected:
  uint8_t _pin;
};

class BombaHeredada : public Rele {
public:
  using Rele::Rele;   // reutiliza el constructor del relé
};

BombaHeredada bombaH(26);

void setup() {
  bombaH.begin();
  bombaH.encender();
  // bombaH también expone todo lo que el relé tenga, ahora y en el futuro,
  // y cambiar el relé por otra cosa obliga a cambiar la jerarquía.
}

void loop() {}
```

```cpp bomba-composicion.ino
// Con composición: la bomba "tiene un" relé
class Rele {
public:
  explicit Rele(uint8_t pin) : _pin(pin) {}
  void begin()    { pinMode(_pin, OUTPUT); apagar(); }
  void encender() { digitalWrite(_pin, LOW); _encendido = true; }
  void apagar()   { digitalWrite(_pin, HIGH); _encendido = false; }
  bool encendido() const { return _encendido; }
private:
  uint8_t _pin;
  bool _encendido = false;
};

class Bomba {
public:
  Bomba(uint8_t pinRele, uint32_t maximoMs) : _rele(pinRele), _maximoMs(maximoMs) {}
  void begin() { _rele.begin(); }

  void encender() {
    if (_rele.encendido()) return;
    _rele.encender();
    _inicioMs = millis();
  }
  void apagar() { _rele.apagar(); }

  void actualizar() {   // regla propia de la bomba: nunca más del tiempo máximo
    if (_rele.encendido() && millis() - _inicioMs >= _maximoMs) apagar();
  }

private:
  Rele _rele;
  uint32_t _maximoMs;
  uint32_t _inicioMs = 0;
};

Bomba bomba(26, 10UL * 60UL * 1000UL);

void setup() {
  bomba.begin();
  bomba.encender();
}

void loop() {
  bomba.actualizar();
}
```

En la versión con composición, nadie puede encender el relé de la bomba salteándose el tiempo máximo, porque el relé es privado. La bomba agrega reglas propias en lugar de heredar una interfaz ajena.

### Ejemplo 2. Una zona de riego armada con piezas

Cada cantero del invernadero es una zona: una válvula (un relé), un sensor de suelo y sus propios umbrales. El controlador tiene un arreglo de zonas.

```cpp zonas.ino
class Rele {
public:
  explicit Rele(uint8_t pin) : _pin(pin) {}
  void begin()    { pinMode(_pin, OUTPUT); apagar(); }
  void encender() { digitalWrite(_pin, LOW); _encendido = true; }
  void apagar()   { digitalWrite(_pin, HIGH); _encendido = false; }
  bool encendido() const { return _encendido; }
private:
  uint8_t _pin;
  bool _encendido = false;
};

class SensorSuelo {
public:
  SensorSuelo(uint8_t pin, uint32_t mvSeco, uint32_t mvMojado)
    : _pin(pin), _mvSeco(mvSeco), _mvMojado(mvMojado) {}
  float leerPorcentaje() const {
    uint32_t mv = analogReadMilliVolts(_pin);
    float f = (static_cast<float>(_mvSeco) - mv) / (static_cast<float>(_mvSeco) - _mvMojado);
    return constrain(f * 100.0f, 0.0f, 100.0f);
  }
private:
  uint8_t _pin;
  uint32_t _mvSeco;
  uint32_t _mvMojado;
};

class ZonaRiego {
public:
  ZonaRiego(const char* nombre, uint8_t pinValvula, SensorSuelo sensor, float minima, float maxima)
    : _nombre(nombre), _valvula(pinValvula), _sensor(sensor), _minima(minima), _maxima(maxima) {}

  void begin() { _valvula.begin(); }

  void actualizar() {
    float h = _sensor.leerPorcentaje();
    if (!_valvula.encendido() && h < _minima) {
      _valvula.encender();
      Serial.printf("%s: riego ON (%.0f%%)\n", _nombre, h);
    } else if (_valvula.encendido() && h > _maxima) {
      _valvula.apagar();
      Serial.printf("%s: riego OFF (%.0f%%)\n", _nombre, h);
    }
  }

  bool regando() const { return _valvula.encendido(); }

private:
  const char* _nombre;
  Rele _valvula;
  SensorSuelo _sensor;
  float _minima;
  float _maxima;
};

ZonaRiego zonas[] = {
  {"tomates", 26, SensorSuelo(32, 2600, 1150), 35.0f, 55.0f},
  {"lechugas", 25, SensorSuelo(33, 2550, 1180), 45.0f, 65.0f},
};

void setup() {
  Serial.begin(115200);
  for (ZonaRiego& z : zonas) z.begin();
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo < 5000) return;
  ultimo = millis();
  for (ZonaRiego& z : zonas) z.actualizar();
}
```

Agregar una zona es agregar una línea al arreglo, con sus pines, su calibración y sus umbrales. La válvula y el sensor son privados: la única forma de regar es a través de la regla de la zona. Todo vive en memoria estática, sin `new`. Para que la decisión se pueda probar aparte, se extraería como en [1.1](/conceptos/1-1).

### Ejemplo 3. Inyectar las piezas para poder probar

El control de clima recibe por referencia un sensor y un actuador, a través de interfaces. En el invernadero recibe los reales; en el banco de pruebas, unos simulados, y el código del control es el mismo.

```cpp clima-inyectado.ino
class SensorTemperatura {
public:
  virtual float celsius() = 0;
  virtual ~SensorTemperatura() = default;
};

class Ventanas {
public:
  virtual void abrir() = 0;
  virtual void cerrar() = 0;
  virtual bool abiertas() const = 0;
  virtual ~Ventanas() = default;
};

class ControlClima {
public:
  ControlClima(SensorTemperatura& sensor, Ventanas& ventanas) : _sensor(sensor), _ventanas(ventanas) {}

  void actualizar() {
    float t = _sensor.celsius();
    if (!_ventanas.abiertas() && t > 30.0f) _ventanas.abrir();
    else if (_ventanas.abiertas() && t < 27.0f) _ventanas.cerrar();
  }

private:
  SensorTemperatura& _sensor;
  Ventanas& _ventanas;
};

// --- Piezas simuladas para el banco de pruebas ---

class SensorGuionado : public SensorTemperatura {
public:
  float celsius() override {
    static const float valores[] = {25, 28, 31, 32, 29, 26, 24};
    float v = valores[_i];
    _i = (_i + 1) % 7;
    return v;
  }
private:
  size_t _i = 0;
};

class VentanasDeMentira : public Ventanas {
public:
  void abrir() override  { _abiertas = true;  Serial.println("  -> abrir"); }
  void cerrar() override { _abiertas = false; Serial.println("  -> cerrar"); }
  bool abiertas() const override { return _abiertas; }
private:
  bool _abiertas = false;
};

SensorGuionado sensorPrueba;
VentanasDeMentira ventanasPrueba;
ControlClima clima(sensorPrueba, ventanasPrueba);

void setup() {
  Serial.begin(115200);
  delay(500);
  for (int i = 0; i < 7; i++) {
    Serial.printf("paso %d\n", i);
    clima.actualizar();
  }
  // abre al pasar de 30 (paso 2) y cierra al bajar de 27 (paso 5)
}

void loop() {}
```

`ControlClima` no crea su sensor ni sus ventanas: los recibe. Esa es toda la diferencia que permite probarlo con un guion de temperaturas y ver exactamente cuándo abre y cuándo cierra, sin esperar a que haga calor de verdad. En el firmware real, se le pasan una implementación de `SensorTemperatura` con el SHT31 y una de `Ventanas` con el servo.

## Errores comunes

### Heredar para reutilizar código

```cpp
// Mal: la zona no "es un" relé
class ZonaRiego : public Rele { /* ... */ };

// Bien
class ZonaRiego {
  Rele _valvula;
  // ...
};
```

### Exponer las piezas compuestas

```cpp
// Mal: cualquiera puede abrir la válvula sin pasar por las reglas de la zona
class ZonaRiego {
public:
  Rele valvula;
};

// Bien: operaciones de la zona; las piezas, privadas
class ZonaRiego {
public:
  void regar();
  void detener();
private:
  Rele _valvula;
};
```

### Referencias a piezas que no viven lo suficiente

```cpp
// Mal: el sensor es local de setup() y desaparece al salir
ControlClima* clima;
void setup() {
  SensorSht31 sensor;
  clima = new ControlClima(sensor, ventanas);   // referencia colgante
}

// Bien: las piezas viven al menos tanto como quien las referencia
SensorSht31 sensor;
ControlClima clima(sensor, ventanas);
```

Cuando una clase guarda una referencia, el objeto referenciado tiene que vivir más (ver [B.2](/conceptos/b-2)). En firmware, la forma más simple es que todos sean globales.

### Jerarquías profundas

Más de dos niveles de herencia en un firmware casi siempre indican que se está usando herencia para combinar características. Rediseñá con composición: cada característica, una pieza.

## Ejercicio

Este es el diseño actual de las bombas del invernadero. Aparece un pedido nuevo: una bomba con alarma de "funcionamiento en seco" pero **sin** caudalímetro (usa un sensor de presión). Explicá por qué la jerarquía no lo admite bien, y rediseñala con composición.

```cpp jerarquia.ino
class Rele { /* encender, apagar */ };
class Bomba : public Rele { /* cuenta arranques */ };
class BombaConCaudalimetro : public Bomba { /* mide litros */ };
class BombaConCaudalimetroYAlarma : public BombaConCaudalimetro { /* alarma si no hay flujo */ };
```

<details>
<summary>Pista</summary>

La alarma necesita saber "si hay flujo", no necesariamente de un caudalímetro. Pensá en una interfaz chica para eso, y en una bomba que tiene un interruptor y, opcionalmente, un detector de flujo.

</details>

<details>
<summary>Ver solución</summary>

La alarma quedó atada al caudalímetro por la jerarquía: para una bomba con alarma y sensor de presión habría que crear `BombaConPresion`, después `BombaConPresionYAlarma`, duplicando la lógica de la alarma. Y todas heredan de `Rele`, así que ninguna puede usar un MOSFET.

```cpp bombas-compuestas.ino
class Interruptor {
public:
  virtual void encender() = 0;
  virtual void apagar() = 0;
  virtual ~Interruptor() = default;
};

class DetectorFlujo {
public:
  virtual bool hayFlujo() = 0;
  virtual ~DetectorFlujo() = default;
};

// Implementaciones: InterruptorRele, InterruptorMosfet,
// FlujoPorCaudalimetro, FlujoPorPresion...

class Bomba {
public:
  Bomba(Interruptor& interruptor, DetectorFlujo* flujo = nullptr)
    : _interruptor(interruptor), _flujo(flujo) {}

  void encender() {
    if (_encendida || _alarmaSeco) return;
    _interruptor.encender();
    _encendida = true;
    _inicioMs = millis();
    _arranques++;
  }

  void apagar() {
    _interruptor.apagar();
    _encendida = false;
  }

  void actualizar() {
    if (!_encendida || _flujo == nullptr) return;          // sin detector, no hay alarma
    if (millis() - _inicioMs > 5000 && !_flujo->hayFlujo()) {
      apagar();
      _alarmaSeco = true;
    }
  }

  bool alarmaSeco() const { return _alarmaSeco; }
  uint32_t arranques() const { return _arranques; }

private:
  Interruptor& _interruptor;
  DetectorFlujo* _flujo;       // puntero: puede no haber detector (ver B.2)
  bool _encendida = false;
  bool _alarmaSeco = false;
  uint32_t _inicioMs = 0;
  uint32_t _arranques = 0;
};
```

Ahora cualquier combinación es una línea: `Bomba b1(rele26);` (sin alarma), `Bomba b2(rele25, &caudalimetro);`, `Bomba b3(mosfet14, &sensorPresion);`. La lógica de la alarma está una sola vez, y funciona con cualquier detector de flujo.

</details>

## Resumen

- Herencia es "es un"; composición es "tiene un". Si la frase con "es un" suena forzada, componé.
- Con composición, una clase guarda otros objetos como miembros, les delega trabajo y los mantiene privados.
- Las jerarquías para combinar características crecen sin control; con composición, cada característica es una pieza.
- Combiná composición con interfaces cuando una pieza puede variar, y recibí las piezas desde afuera para poder probar con piezas simuladas.
- La herencia queda para interfaces y callbacks de librerías.
