**Sharding** es repartir los datos de una aplicación entre **varios servidores de base de datos**, cada uno con una parte (un *shard*). Una **clave de sharding** decide en qué servidor vive cada fila: por ejemplo, todas las filas de la organización 17 van al shard 2. Así, la capacidad total (disco, memoria, escrituras por segundo) crece agregando servidores. Es la última herramienta de la lista, porque complica casi todo lo demás: consultas que cruzan shards, transacciones, migraciones y operación.

## Por qué te importa

Con un modelo bien indexado (ver [4.5](/conceptos/4-5)), la tabla de lecturas particionada por mes y un servidor de base razonable, PostgreSQL atiende a muchísimos equipos. Es probable que el sistema del invernadero nunca necesite sharding. Pero conviene saber qué es, por qué se deja para el final, y qué decisiones de hoy lo facilitan si algún día hace falta: la principal, que casi todos los datos tienen un `organizacion_id`, que es la clave de sharding natural de un sistema multi-organización (ver [4.1](/conceptos/4-1)).

## Cómo funciona

*El orden habitual antes de llegar acá:* índices y consultas mejores; un servidor más grande; particionado por tiempo y archivar lo viejo; réplicas de lectura para los reportes (ver [5.3](/conceptos/5-3)); un caché para lo más consultado (ver [5.4](/conceptos/5-4)). El sharding se justifica cuando las **escrituras** o el **tamaño** superan lo que puede un solo servidor, porque las réplicas ayudan con las lecturas pero no con eso.

*La clave de sharding* tiene que cumplir dos cosas: que las consultas frecuentes incluyan la clave (para ir a un solo shard), y que reparta bien la carga. En un sistema multi-organización, `organizacion_id` cumple la primera casi siempre. La segunda depende: una organización enorme puede llenar un shard sola.

*El ruteo.* Algo tiene que saber en qué shard está cada organización: una tabla de ruteo (organización → shard), o una función de hash. La tabla es más flexible: permite mover una organización a otro shard.

*Lo que se complica:* consultas que cruzan organizaciones (reportes internos, estadísticas globales), transacciones entre shards (no hay), cambios de esquema (se aplican en todos los shards), y mover organizaciones entre shards sin cortar el servicio.

*Herramientas.* Extensiones como **Citus** hacen sharding dentro de PostgreSQL: las tablas se distribuyen por una columna y las consultas se rutean solas. Simplifican mucho, pero no eliminan las limitaciones de fondo.

## Ejemplo

Un ruteo manual por organización: cada organización tiene asignado un shard, y el backend elige el pool de conexiones según la organización del pedido.

```js shards.js
const { Pool } = require("pg");

// Un pool por servidor de base de datos
const pools = {
  a: new Pool({ connectionString: process.env.DB_SHARD_A }),
  b: new Pool({ connectionString: process.env.DB_SHARD_B }),
};

// Base global, chica: cuentas, organizaciones y en qué shard está cada una
const global = new Pool({ connectionString: process.env.DB_GLOBAL });

const cache = new Map();   // organizacion_id -> shard (cambia muy rara vez)

async function shardDe(organizacionId) {
  if (!cache.has(organizacionId)) {
    const { rows } = await global.query(
      "SELECT shard FROM organizaciones WHERE id = $1", [organizacionId]);
    if (rows.length === 0) throw new Error("organización inexistente");
    cache.set(organizacionId, rows[0].shard);
  }
  return pools[cache.get(organizacionId)];
}

// Middleware: después de autenticar, req.db apunta al shard de la organización
async function elegirShard(req, res, next) {
  const organizacionId = req.usuario?.organizacion_id ?? req.equipo?.organizacion_id;
  req.db = await shardDe(organizacionId);
  next();
}

// Un reporte global tiene que consultar todos los shards y combinar
async function lecturasDeHoyEnTotal() {
  const partes = await Promise.all(Object.values(pools).map((p) =>
    p.query("SELECT count(*)::bigint AS n FROM lecturas WHERE momento >= date_trunc('day', now())")));
  return partes.reduce((total, r) => total + Number(r.rows[0].n), 0);
}

module.exports = { elegirShard, lecturasDeHoyEnTotal };
```

El resto del backend no cambia: sigue usando `req.db` como en [4.1](/conceptos/4-1), y como cada consulta ya filtra por organización, va a un solo shard. La autenticación de los equipos busca la clave en la base global (o en todos los shards) antes de saber el shard. El reporte global muestra el costo: hay que preguntar a todos los shards y sumar en la aplicación. Mover una organización de un shard a otro implica copiar sus datos, cambiar la fila de ruteo y vaciar el caché en todas las instancias, sin perder las lecturas que llegan mientras tanto.

## Cuándo sí y cuándo no

Conviene cuando:

- las escrituras o el volumen de datos superan lo que puede un servidor, aun después de índices, particionado, archivado y un servidor más grande,
- hay una clave natural que casi todas las consultas incluyen (como la organización).

No conviene cuando:

- el problema son las lecturas: réplicas y caché son mucho más simples,
- el problema es una consulta lenta: casi siempre se arregla con índices o con un modelo de lectura (ver [8.3](/conceptos/8-3)),
- se hace "por las dudas": cada consulta global, migración y transacción se vuelve más difícil para siempre.

## Resumen

- Sharding reparte los datos entre varios servidores según una clave; el particionado los divide dentro de uno.
- Se justifica cuando las escrituras o el tamaño superan un servidor, después de agotar lo más simple.
- En un sistema multi-organización, la clave natural es `organizacion_id`.
- Las consultas que cruzan shards, las transacciones y las migraciones se vuelven más difíciles.
- Herramientas como Citus lo simplifican, sin eliminar sus límites.
