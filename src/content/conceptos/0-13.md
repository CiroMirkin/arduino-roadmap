Casi ningún firmware se escribe solo con el lenguaje: usa el **core** (el soporte de Arduino para el ESP32, con `WiFi`, `Preferences`, `ledcAttach`...) y **librerías** de terceros (sensores, JSON, pantallas). Todas tienen **versiones**, y una versión mayor nueva puede cambiar la forma de usarlas. Saber qué versiones usa tu proyecto, y fijarlas, es lo que hace que el firmware que compila hoy siga compilando dentro de un año, y que compile igual en la computadora de otra persona.

## Por qué te importa

El firmware del invernadero depende de varias piezas externas: el core de Arduino-ESP32, la librería BLE, ArduinoJson para hablar con el backend, una librería para la pantalla táctil. Si alguien actualiza el core "para probar", los ejemplos de PWM dejan de compilar porque la API cambió (ver [0.5](/conceptos/0-5)). Si otra persona instala ArduinoJson desde cero, recibe la versión 7 y el código escrito para la 6 da errores.

Estos errores parecen errores de tu código, y se pierde tiempo buscando en el lugar equivocado. Con las versiones anotadas y fijadas, el problema directamente no aparece.

## Paso a paso

### 1. Dónde viven el core y las librerías

En el Arduino IDE:

- El **core** se instala desde *Herramientas → Placa → Gestor de placas*. Para el ESP32 es el paquete *esp32* de Espressif, con su número de versión (por ejemplo, 3.x).
- Las **librerías** se instalan desde el *Gestor de librerías* y quedan en la carpeta `Arduino/libraries` de tus documentos. También se pueden agregar como `.zip`.

Las dos cosas se instalan **por computadora**, no por proyecto. Todos tus sketches usan la misma versión de cada librería, y otra persona que abre tu proyecto usa la que tenga instalada ella.

### 2. El versionado semántico

La mayoría de las librerías numeran sus versiones como `MAYOR.MENOR.PARCHE`:

| Cambia | Ejemplo | Significa |
|---|---|---|
| PARCHE | 7.2.0 → 7.2.1 | correcciones; tu código sigue igual |
| MENOR | 7.2.1 → 7.3.0 | funciones nuevas, compatibles |
| MAYOR | 6.21.3 → 7.0.0 | cambios incompatibles: puede romper tu código |

Actualizar un parche es seguro casi siempre. Antes de pasar a una versión mayor, leé las notas de la versión (*changelog* o *release notes*) y la guía de migración, si existe.

### 3. Casos reales de cambios mayores

- **Arduino-ESP32 2.x → 3.x**: cambió la API de PWM (`ledcSetup` → `ledcAttach`), la de algunos temporizadores, y partes de la librería BLE. Muchos ejemplos de internet son de la 2.x.
- **ArduinoJson 6 → 7**: `StaticJsonDocument<N>` y `DynamicJsonDocument` se reemplazaron por un único `JsonDocument` que crece solo.

Cuando un ejemplo no compila y el error menciona una función que "no existe", lo primero es preguntarse para qué versión se escribió.

### 4. Saber qué versión se está compilando

Muchas librerías definen macros con su versión, y el core del ESP32 también:

```cpp
#include <ArduinoJson.h>

void setup() {
  Serial.begin(115200);
  Serial.printf("core Arduino-ESP32 %d.%d.%d\n",
                ESP_ARDUINO_VERSION_MAJOR, ESP_ARDUINO_VERSION_MINOR, ESP_ARDUINO_VERSION_PATCH);
  Serial.printf("ArduinoJson %s\n", ARDUINOJSON_VERSION);
}
```

Con esas macros se puede elegir código según la versión (compilación condicional, ver [B.2](/conceptos/b-2)), o frenar la compilación con un mensaje claro si la versión no es la esperada:

```cpp
static_assert(ARDUINOJSON_VERSION_MAJOR == 7, "Este proyecto necesita ArduinoJson 7.x");
```

`static_assert` se evalúa al compilar: si la condición es falsa, la compilación se detiene con ese mensaje, en lugar de con cincuenta errores confusos.

### 5. Conflictos entre librerías

```text
Multiple libraries were found for "SD.h"
  Used: .../esp32/libraries/SD
  Not used: .../Arduino/libraries/SD
```

Si dos librerías instaladas tienen un archivo con el mismo nombre, el IDE elige una. El mensaje dice cuál. Pasa mucho cuando se instala una librería genérica que el core del ESP32 ya trae, o cuando hay una copia instalada desde el gestor y otra desde un `.zip`. La solución es borrar la que sobra.

### 6. PlatformIO: versiones por proyecto

PlatformIO es una alternativa al Arduino IDE (como extensión de VS Code) que resuelve el problema de raíz: cada proyecto declara en `platformio.ini` qué plataforma y qué librerías usa, con sus versiones, y PlatformIO las descarga para ese proyecto. Dos personas que abren el proyecto compilan exactamente con lo mismo.

```ini
[env:controlador]
platform = espressif32 @ 6.9.0
board = esp32-s3-devkitc-1
framework = arduino
lib_deps =
  bblanchon/ArduinoJson @ ^7.2.0
```

`^7.2.0` acepta desde la 7.2.0 hasta antes de la 8.0.0: recibe correcciones sin arriesgar cambios incompatibles. Para una versión exacta, se escribe sin el `^`. Más sobre PlatformIO en [1.7](/conceptos/1-7).

## Ejemplos

### Ejemplo 1. Informar las versiones al arrancar

El controlador imprime al arrancar con qué versiones fue compilado. Cuando alguien reporta un problema, es lo primero que se mira.

```cpp versiones.ino
#include <ArduinoJson.h>

constexpr const char* VERSION_FIRMWARE = "1.4.0";

void setup() {
  Serial.begin(115200);
  delay(500);
  Serial.printf("firmware del controlador %s\n", VERSION_FIRMWARE);
  Serial.printf("compilado el %s a las %s\n", __DATE__, __TIME__);
  Serial.printf("core Arduino-ESP32 %d.%d.%d\n",
                ESP_ARDUINO_VERSION_MAJOR, ESP_ARDUINO_VERSION_MINOR, ESP_ARDUINO_VERSION_PATCH);
  Serial.printf("ArduinoJson %s\n", ARDUINOJSON_VERSION);
}

void loop() {}
```

`__DATE__` y `__TIME__` son macros que el compilador reemplaza por la fecha y hora de compilación. La versión del firmware conviene enviarla también al backend, para saber qué versión corre en cada invernadero.

### Ejemplo 2. Código que compila con el core 2.x y con el 3.x

Mientras un proyecto migra de versión, puede convenir que compile con las dos. La diferencia de PWM se resuelve en un solo lugar.

```cpp pwm-compatible.ino
constexpr uint8_t PIN_LUCES = 25;
constexpr uint32_t FRECUENCIA = 2000;
constexpr uint8_t BITS = 10;

#if ESP_ARDUINO_VERSION_MAJOR >= 3
  bool iniciarPwm()             { return ledcAttach(PIN_LUCES, FRECUENCIA, BITS); }
  void escribirPwm(uint32_t v)  { ledcWrite(PIN_LUCES, v); }
#else
  constexpr uint8_t CANAL = 0;
  bool iniciarPwm() {
    ledcSetup(CANAL, FRECUENCIA, BITS);
    ledcAttachPin(PIN_LUCES, CANAL);
    return true;
  }
  void escribirPwm(uint32_t v)  { ledcWrite(CANAL, v); }
#endif

void setup() {
  Serial.begin(115200);
  if (!iniciarPwm()) Serial.println("error de PWM");
  escribirPwm(512);
}

void loop() {}
```

El resto del programa usa `iniciarPwm` y `escribirPwm`, sin saber qué versión del core hay debajo. Cuando ya nadie use la 2.x, se borra la rama vieja y listo. Esconder una dependencia externa detrás de funciones propias es la misma idea de las capas de [2.1](/conceptos/2-1).

### Ejemplo 3. Un proyecto con versiones fijas para el nodo y el controlador

El proyecto del invernadero tiene dos firmwares que comparten código. Con PlatformIO, un solo `platformio.ini` define los dos entornos con sus versiones, y un `static_assert` frena la compilación si alguien usa otra versión mayor de ArduinoJson.

```ini platformio.ini
[platformio]
default_envs = controlador

[env]
platform = espressif32 @ 6.9.0
framework = arduino
monitor_speed = 115200
lib_deps =
  bblanchon/ArduinoJson @ ^7.2.0

[env:controlador]
board = esp32-s3-devkitc-1
board_build.arduino.memory_type = qio_opi
build_flags = -DROL_CONTROLADOR

[env:nodo]
board = esp32dev
build_flags = -DROL_NODO
```

```cpp versiones-requeridas.h
#pragma once
#include <Arduino.h>
#include <ArduinoJson.h>

static_assert(ARDUINOJSON_VERSION_MAJOR == 7,
              "Este proyecto usa la API de ArduinoJson 7 (JsonDocument). "
              "Instalá la versión 7.x.");

static_assert(ESP_ARDUINO_VERSION_MAJOR >= 2,
              "Este proyecto necesita el core Arduino-ESP32 2.x o posterior.");
```

La sección `[env]` tiene lo común; cada entorno agrega su placa y sus opciones. `board_build.arduino.memory_type = qio_opi` es el equivalente de elegir la PSRAM OPI en el menú del IDE (ver [0.2](/conceptos/0-2)). Fijar la versión de la plataforma (`espressif32 @ 6.9.0`) fija también la versión del core que trae, y conviene revisar cuál es: durante mucho tiempo la plataforma oficial `espressif32` de PlatformIO trajo el core 2.x, y el 3.x se usaba a través de la plataforma de la comunidad *pioarduino*. El header con los `static_assert` protege incluso a quien compile con el Arduino IDE en lugar de PlatformIO.

## Errores comunes

### No anotar las versiones

Un proyecto sin las versiones de su core y sus librerías anotadas (en un `platformio.ini`, o al menos en el README) es difícil de recompilar dentro de un año. Anotalas desde el primer día.

### Actualizar todo sin leer

```text
Mal:   "Actualizar todo" en el gestor de librerías el día antes de instalar el equipo
Bien:  actualizar una cosa por vez, leer las notas de las versiones mayores, compilar y probar
```

### Copiar ejemplos de otra versión

Si un ejemplo usa `ledcSetup`, `StaticJsonDocument` o funciones que tu compilador no conoce, probablemente es de otra versión. Buscá el ejemplo equivalente en la documentación de la versión que tenés.

### Dos copias de la misma librería

Una librería instalada desde el gestor y otra copia desde un `.zip`, o una librería genérica que pisa a la del core, producen el mensaje `Multiple libraries were found` y comportamientos raros. Dejá una sola.

## Ejercicio

Un compañero clona el proyecto del controlador, instala las librerías desde el gestor y al compilar recibe:

```text
error: 'DynamicJsonDocument' was not declared in this scope
```

Vos tenés ArduinoJson 6.21 y el proyecto compila. Explicá qué pasó, y proponé dos cambios en el proyecto para que no vuelva a pasar: uno que dé un mensaje claro y otro que fije la versión.

<details>
<summary>Pista</summary>

El gestor de librerías instala la última versión disponible. Pensá en `static_assert` con la macro de versión, y en `lib_deps` de PlatformIO.

</details>

<details>
<summary>Ver solución</summary>

El compañero instaló la última versión de ArduinoJson, la 7, donde `DynamicJsonDocument` ya no existe (se reemplazó por `JsonDocument`). El proyecto está escrito para la 6 y nada lo indicaba.

Mensaje claro, en un header que incluyan todos los archivos que usan ArduinoJson:

```cpp versiones-requeridas.h
#pragma once
#include <ArduinoJson.h>

static_assert(ARDUINOJSON_VERSION_MAJOR == 6,
              "Este proyecto usa ArduinoJson 6.x (DynamicJsonDocument). "
              "Con la 7.x no compila: instalá la 6.21 o migrá el código.");
```

Versión fijada, si el proyecto usa PlatformIO:

```ini platformio.ini
lib_deps =
  bblanchon/ArduinoJson @ ^6.21.3
```

Con el `static_assert`, el error deja de ser un `not declared` confuso y pasa a explicar qué hacer. Con `lib_deps`, el problema no aparece: PlatformIO descarga la versión 6 para este proyecto, sin importar qué haya instalado en la computadora. A mediano plazo conviene migrar a la 7, siguiendo la guía de migración de la librería, y cambiar los dos archivos en el mismo cambio.

</details>

## Resumen

- El core y las librerías tienen versiones, y en el Arduino IDE se instalan por computadora, no por proyecto.
- Versionado semántico: un cambio del primer número (MAYOR) puede romper tu código; leé las notas antes de actualizar.
- Muchas librerías definen macros con su versión: sirven para informar, para compilación condicional y para `static_assert`.
- `Multiple libraries were found` indica dos librerías con el mismo header: dejá una sola.
- PlatformIO fija plataforma y librerías por proyecto en `platformio.ini`. Con `^` se aceptan correcciones sin cambios incompatibles.
