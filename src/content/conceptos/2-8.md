Probar firmware en la placa es lento: compilar, subir, reproducir la situación (vaciar el tanque, calentar el sensor, esperar cinco minutos) y mirar el monitor serie. Pero la mayoría de los bugs no están en el hardware: están en la **lógica** (una condición mal escrita, una transición olvidada, un caso borde en un parser). Esa lógica, si está separada del hardware, se puede compilar y **probar en la PC**, con cientos de casos en segundos. Esta lección muestra cómo diseñar el código para que eso sea posible, y cómo escribir las pruebas con PlatformIO y Unity.

## Por qué te importa

El controlador del invernadero tiene reglas que no se pueden equivocar: la bomba se apaga si se vacía el tanque, el riego respeta el tiempo máximo, la alarma suena después de dos minutos de calor extremo. Verificar todo eso a mano después de cada cambio es imposible, así que en la práctica no se verifica, y los bugs aparecen en el campo.

Con pruebas automáticas, cada regla importante queda escrita como un caso que se verifica solo. Si un cambio rompe el corte por tanque vacío, la prueba falla en la PC antes de subir el firmware a ningún equipo. Y el diseño que hace falta para poder probar (lógica pura, hardware detrás de interfaces) es el mismo que viene apareciendo desde [1.1](/conceptos/1-1): las pruebas son la recompensa de esa separación.

## Paso a paso

### 1. Qué se prueba en la PC y qué en la placa

| En la PC (rápido, automático) | En la placa (más lento, a veces manual) |
|---|---|
| decisiones de control (riego, ventilación, alarmas) | que los drivers hablen bien con cada sensor |
| transiciones de las máquinas de estados | tiempos reales, interrupciones, PWM |
| codificar y decodificar tramas y mensajes | que el BLE y el WiFi conecten |
| parsers (comandos, respuestas del backend) | consumo de memoria y de batería |
| filtros, conversiones, calibraciones | la pantalla |

La regla: todo lo que es "recibir datos y devolver un resultado" va a la PC. Lo que depende de que el hardware se comporte de cierta forma, a la placa.

### 2. Diseñar para poder probar

Para compilar algo en la PC, no puede incluir `Arduino.h` ni llamar a `digitalWrite`, `analogRead` o `millis`. Eso se logra con dos técnicas que ya viste:

- **Funciones puras** que reciben todo lo que necesitan como parámetros (`decidirRiego` en [1.1](/conceptos/1-1), `siguiente` en [2.2](/conceptos/2-2)).
- **Interfaces** para lo que la lógica necesita del mundo (un sensor, un relé, un reloj), recibidas desde afuera (ver la inyección de dependencias en [1.2](/conceptos/1-2)). En el firmware se le pasan las implementaciones reales; en las pruebas, unas falsas.

### 3. El tiempo también es una dependencia

La lógica que usa `millis()` directamente no se puede probar sin esperar. La solución es pedir la hora a una interfaz:

```cpp
class Reloj {
public:
  virtual uint32_t ahoraMs() const = 0;
  virtual ~Reloj() = default;
};

// En el firmware
class RelojArduino : public Reloj {
public:
  uint32_t ahoraMs() const override { return millis(); }
};

// En las pruebas
class RelojFalso : public Reloj {
public:
  uint32_t ahoraMs() const override { return _ms; }
  void avanzar(uint32_t ms) { _ms += ms; }
private:
  uint32_t _ms = 0;
};
```

Con un reloj falso, la prueba "pasa cinco minutos" en una línea: `reloj.avanzar(5 * 60 * 1000);`.

### 4. Dobles de prueba

Un **doble de prueba** (*fake*) es una implementación simple de una interfaz, hecha para las pruebas:

- Uno de **entrada** devuelve lo que la prueba le indica (un sensor que dice "humedad 20 %").
- Uno de **salida** recuerda lo que le pidieron (un relé que anota si está encendido y cuántas veces lo encendieron).

La prueba arma la situación con los dobles de entrada, ejecuta la lógica y revisa los dobles de salida.

### 5. Unity con PlatformIO

PlatformIO incluye **Unity**, un framework de pruebas simple para C. Con un entorno `native` en `platformio.ini` (ver [1.7](/conceptos/1-7)), las pruebas se compilan para la PC:

```ini
[env:native]
platform = native
test_framework = unity
build_flags = -std=c++17
```

Cada prueba es una función, y las verificaciones son macros:

```cpp
TEST_ASSERT_TRUE(condicion);
TEST_ASSERT_EQUAL(esperado, obtenido);                 // enteros
TEST_ASSERT_FLOAT_WITHIN(0.01f, esperado, obtenido);   // flotantes, con tolerancia
TEST_ASSERT_EQUAL_UINT8_ARRAY(esperado, obtenido, n);  // arreglos de bytes
```

`pio test -e native` compila y corre todo, y muestra qué pasó y qué falló. El entorno `native` necesita un compilador de C++ en la PC (por ejemplo, MinGW en Windows o el de Xcode en macOS).

### 6. Qué hace buena a una prueba

- **Un comportamiento por prueba**, con un nombre que lo describe: `test_tanque_vacio_apaga_la_bomba`.
- **Casos borde y casos negativos**: el valor justo en el umbral, la trama corrupta, el evento que no debería hacer nada. Ahí están los bugs.
- **Comportamiento, no implementación**: verificar que la bomba se apaga, no qué variable interna cambió. Así las pruebas sobreviven a las refactorizaciones.
- **Rápidas y sin hardware**: cientos de pruebas en segundos invitan a correrlas siempre.

## Ejemplos

### Ejemplo 1. Probar la codificación de la trama BLE

El protocolo entre el nodo y el controlador (ver [0.9](/conceptos/0-9)) es código puro: el mejor candidato para empezar. La prueba verifica que codificar y decodificar devuelve lo mismo, y que una trama inválida se rechaza.

```cpp lib/protocolo/protocolo.h
#pragma once
#include <cstddef>
#include <cstdint>

namespace protocolo {

struct Lectura {
  float temperatura;        // °C, se transmite en décimas
  uint8_t humedadSuelo;     // %
};

constexpr size_t TAMANO = 3;

void codificar(const Lectura& l, uint8_t trama[TAMANO]);
bool decodificar(const uint8_t* trama, size_t largo, Lectura& l);

}  // namespace protocolo
```

```cpp lib/protocolo/protocolo.cpp
#include "protocolo.h"
#include <cmath>

namespace protocolo {

void codificar(const Lectura& l, uint8_t trama[TAMANO]) {
  int16_t decimas = static_cast<int16_t>(std::lround(l.temperatura * 10.0f));
  uint16_t bits = static_cast<uint16_t>(decimas);
  trama[0] = static_cast<uint8_t>(bits & 0xFF);
  trama[1] = static_cast<uint8_t>(bits >> 8);
  trama[2] = l.humedadSuelo;
}

bool decodificar(const uint8_t* trama, size_t largo, Lectura& l) {
  if (trama == nullptr || largo != TAMANO) return false;
  if (trama[2] > 100) return false;                         // humedad imposible
  uint16_t bits = static_cast<uint16_t>(trama[0] | (trama[1] << 8));
  l.temperatura = static_cast<int16_t>(bits) / 10.0f;
  l.humedadSuelo = trama[2];
  return true;
}

}  // namespace protocolo
```

```cpp test/test_protocolo/test_main.cpp
#include <unity.h>
#include "protocolo.h"

using namespace protocolo;   // en un archivo de pruebas, aceptable

void setUp() {}
void tearDown() {}

void test_ida_y_vuelta_conserva_los_valores() {
  uint8_t trama[TAMANO];
  codificar({24.5f, 41}, trama);
  Lectura l{};
  TEST_ASSERT_TRUE(decodificar(trama, TAMANO, l));
  TEST_ASSERT_FLOAT_WITHIN(0.05f, 24.5f, l.temperatura);
  TEST_ASSERT_EQUAL(41, l.humedadSuelo);
}

void test_temperatura_bajo_cero() {
  uint8_t trama[TAMANO];
  codificar({-3.2f, 70}, trama);
  Lectura l{};
  TEST_ASSERT_TRUE(decodificar(trama, TAMANO, l));
  TEST_ASSERT_FLOAT_WITHIN(0.05f, -3.2f, l.temperatura);
}

void test_formato_en_bytes() {
  uint8_t trama[TAMANO];
  codificar({24.5f, 41}, trama);
  const uint8_t esperado[TAMANO] = {245, 0, 41};   // 245 décimas, little-endian
  TEST_ASSERT_EQUAL_UINT8_ARRAY(esperado, trama, TAMANO);
}

void test_rechaza_largo_incorrecto() {
  const uint8_t corta[2] = {245, 0};
  Lectura l{};
  TEST_ASSERT_FALSE(decodificar(corta, 2, l));
}

void test_rechaza_humedad_imposible() {
  const uint8_t trama[TAMANO] = {245, 0, 180};
  Lectura l{};
  TEST_ASSERT_FALSE(decodificar(trama, TAMANO, l));
}

int main() {
  UNITY_BEGIN();
  RUN_TEST(test_ida_y_vuelta_conserva_los_valores);
  RUN_TEST(test_temperatura_bajo_cero);
  RUN_TEST(test_formato_en_bytes);
  RUN_TEST(test_rechaza_largo_incorrecto);
  RUN_TEST(test_rechaza_humedad_imposible);
  return UNITY_END();
}
```

`protocolo.h` y `protocolo.cpp` solo incluyen cabeceras de C++ estándar, así que compilan en la PC y en el ESP32 por igual. `test_formato_en_bytes` fija el formato exacto: si alguien cambia el orden de los bytes, el nodo y el controlador dejarían de entenderse, y esta prueba lo detecta. Las dos últimas pruebas son casos negativos, donde suelen estar los bugs.

### Ejemplo 2. Probar el ciclo de riego con un reloj falso

El ciclo de riego de [2.2](/conceptos/2-2), reescrito para recibir el reloj y para devolver si la bomba debe estar encendida en lugar de tocar el pin.

```cpp lib/control/ciclo_riego.h
#pragma once
#include <cstdint>
#include "reloj.h"     // la interfaz Reloj del paso 3

enum class EstadoRiego : uint8_t { Esperando, Regando, Absorbiendo, Bloqueado };

struct EntradasRiego {
  float humedadSuelo;
  bool tanqueConAgua;
};

class CicloRiego {
public:
  CicloRiego(const Reloj& reloj, uint32_t riegoMs, uint32_t absorcionMs)
    : _reloj(reloj), _riegoMs(riegoMs), _absorcionMs(absorcionMs), _desdeMs(reloj.ahoraMs()) {}

  void actualizar(const EntradasRiego& in) {
    uint32_t t = _reloj.ahoraMs() - _desdeMs;
    switch (_estado) {
      case EstadoRiego::Esperando:
        if (!in.tanqueConAgua) cambiarA(EstadoRiego::Bloqueado);
        else if (in.humedadSuelo < 35.0f) cambiarA(EstadoRiego::Regando);
        break;
      case EstadoRiego::Regando:
        if (!in.tanqueConAgua) cambiarA(EstadoRiego::Bloqueado);
        else if (t >= _riegoMs) cambiarA(EstadoRiego::Absorbiendo);
        break;
      case EstadoRiego::Absorbiendo:
        if (t >= _absorcionMs) cambiarA(EstadoRiego::Esperando);
        break;
      case EstadoRiego::Bloqueado:
        if (in.tanqueConAgua) cambiarA(EstadoRiego::Esperando);
        break;
    }
  }

  EstadoRiego estado() const { return _estado; }
  bool bombaEncendida() const { return _estado == EstadoRiego::Regando; }

private:
  void cambiarA(EstadoRiego e) { _estado = e; _desdeMs = _reloj.ahoraMs(); }

  const Reloj& _reloj;
  uint32_t _riegoMs, _absorcionMs;
  EstadoRiego _estado = EstadoRiego::Esperando;
  uint32_t _desdeMs;
};
```

```cpp test/test_ciclo_riego/test_main.cpp
#include <unity.h>
#include "ciclo_riego.h"

class RelojFalso : public Reloj {
public:
  uint32_t ahoraMs() const override { return _ms; }
  void avanzar(uint32_t ms) { _ms += ms; }
private:
  uint32_t _ms = 1000;
};

constexpr uint32_t RIEGO = 3 * 60 * 1000;
constexpr uint32_t ABSORCION = 5 * 60 * 1000;
const EntradasRiego SECO{20.0f, true};
const EntradasRiego HUMEDO{60.0f, true};
const EntradasRiego SIN_AGUA{20.0f, false};

void setUp() {}
void tearDown() {}

void test_suelo_seco_empieza_a_regar() {
  RelojFalso reloj;
  CicloRiego ciclo(reloj, RIEGO, ABSORCION);
  ciclo.actualizar(SECO);
  TEST_ASSERT_TRUE(ciclo.bombaEncendida());
}

void test_riega_el_tiempo_configurado_y_pasa_a_absorber() {
  RelojFalso reloj;
  CicloRiego ciclo(reloj, RIEGO, ABSORCION);
  ciclo.actualizar(SECO);
  reloj.avanzar(RIEGO - 1);
  ciclo.actualizar(SECO);
  TEST_ASSERT_TRUE(ciclo.bombaEncendida());          // todavía no
  reloj.avanzar(1);
  ciclo.actualizar(SECO);
  TEST_ASSERT_FALSE(ciclo.bombaEncendida());
  TEST_ASSERT_TRUE(ciclo.estado() == EstadoRiego::Absorbiendo);
}

void test_no_vuelve_a_regar_durante_la_absorcion() {
  RelojFalso reloj;
  CicloRiego ciclo(reloj, RIEGO, ABSORCION);
  ciclo.actualizar(SECO);
  reloj.avanzar(RIEGO);
  ciclo.actualizar(SECO);
  reloj.avanzar(ABSORCION / 2);
  ciclo.actualizar(SECO);                            // el sensor todavía marca seco
  TEST_ASSERT_FALSE(ciclo.bombaEncendida());
}

void test_tanque_vacio_corta_el_riego_en_curso() {
  RelojFalso reloj;
  CicloRiego ciclo(reloj, RIEGO, ABSORCION);
  ciclo.actualizar(SECO);
  reloj.avanzar(10000);
  ciclo.actualizar(SIN_AGUA);
  TEST_ASSERT_FALSE(ciclo.bombaEncendida());
  TEST_ASSERT_TRUE(ciclo.estado() == EstadoRiego::Bloqueado);
}

void test_suelo_humedo_no_riega() {
  RelojFalso reloj;
  CicloRiego ciclo(reloj, RIEGO, ABSORCION);
  ciclo.actualizar(HUMEDO);
  TEST_ASSERT_FALSE(ciclo.bombaEncendida());
}

int main() {
  UNITY_BEGIN();
  RUN_TEST(test_suelo_seco_empieza_a_regar);
  RUN_TEST(test_riega_el_tiempo_configurado_y_pasa_a_absorber);
  RUN_TEST(test_no_vuelve_a_regar_durante_la_absorcion);
  RUN_TEST(test_tanque_vacio_corta_el_riego_en_curso);
  RUN_TEST(test_suelo_humedo_no_riega);
  return UNITY_END();
}
```

Ocho minutos de funcionamiento del ciclo se prueban en milisegundos. `test_riega_el_tiempo_configurado_y_pasa_a_absorber` verifica el límite exacto: un milisegundo antes sigue regando, justo en el tiempo deja de hacerlo. En el firmware, `CicloRiego` recibe un `RelojArduino`, y `loop()` usa `bombaEncendida()` para manejar el relé.

### Ejemplo 3. Un relé falso para verificar las acciones

Cuando la lógica actúa a través de una interfaz (como el `Interruptor` de [1.2](/conceptos/1-2)), un doble de salida registra lo que se le pidió, y la prueba lo revisa.

```cpp test/test_bomba/test_main.cpp
#include <unity.h>
#include <cstdint>

class Interruptor {
public:
  virtual void encender() = 0;
  virtual void apagar() = 0;
  virtual ~Interruptor() = default;
};

// La clase bajo prueba: una bomba con tiempo máximo
class Bomba {
public:
  Bomba(Interruptor& i, uint32_t maximoMs) : _i(i), _maximoMs(maximoMs) {}
  void encender(uint32_t ahoraMs) {
    if (_encendida) return;
    _i.encender();
    _encendida = true;
    _inicioMs = ahoraMs;
  }
  void apagar() { _i.apagar(); _encendida = false; }
  void actualizar(uint32_t ahoraMs) {
    if (_encendida && ahoraMs - _inicioMs >= _maximoMs) apagar();
  }
private:
  Interruptor& _i;
  uint32_t _maximoMs;
  bool _encendida = false;
  uint32_t _inicioMs = 0;
};

// Doble de salida: recuerda lo que le pidieron
class InterruptorFalso : public Interruptor {
public:
  void encender() override { encendido = true; encendidos++; }
  void apagar() override { encendido = false; }
  bool encendido = false;
  int encendidos = 0;
};

void setUp() {}
void tearDown() {}

void test_se_apaga_al_llegar_al_maximo() {
  InterruptorFalso rele;
  Bomba bomba(rele, 60000);
  bomba.encender(0);
  bomba.actualizar(59999);
  TEST_ASSERT_TRUE(rele.encendido);
  bomba.actualizar(60000);
  TEST_ASSERT_FALSE(rele.encendido);
}

void test_encender_dos_veces_no_reinicia_el_tiempo() {
  InterruptorFalso rele;
  Bomba bomba(rele, 60000);
  bomba.encender(0);
  bomba.encender(50000);           // segundo pedido: se ignora
  bomba.actualizar(60000);
  TEST_ASSERT_FALSE(rele.encendido);
  TEST_ASSERT_EQUAL(1, rele.encendidos);
}

void test_funciona_cuando_millis_da_la_vuelta() {
  InterruptorFalso rele;
  Bomba bomba(rele, 60000);
  bomba.encender(4294960000u);     // poco antes del desborde de 32 bits
  bomba.actualizar(30000);          // ya dio la vuelta: pasaron 37.296 ms
  TEST_ASSERT_TRUE(rele.encendido);
  bomba.actualizar(60000);          // pasaron 67.296 ms
  TEST_ASSERT_FALSE(rele.encendido);
}

int main() {
  UNITY_BEGIN();
  RUN_TEST(test_se_apaga_al_llegar_al_maximo);
  RUN_TEST(test_encender_dos_veces_no_reinicia_el_tiempo);
  RUN_TEST(test_funciona_cuando_millis_da_la_vuelta);
  return UNITY_END();
}
```

La tercera prueba verifica algo imposible de comprobar a mano: el comportamiento cuando `millis()` da la vuelta a los 49,7 días (ver [0.1](/conceptos/0-1)). Acá la bomba recibe la hora como parámetro, otra forma válida de inyectar el tiempo. Por simplicidad, todo está en el archivo de prueba; en el proyecto real, `Bomba` e `Interruptor` estarían en `lib/`.

## Errores comunes

### Lógica que incluye `Arduino.h`

```cpp
// Mal: lib/control/control.h
#include <Arduino.h>
bool debeRegar(float h) { return h < 35.0f; }   // no compila en la PC

// Bien
#include <cstdint>
bool debeRegar(float h);
```

Si un archivo de lógica necesita `Arduino.h`, es señal de que tiene una dependencia del hardware que conviene sacar.

### Pruebas que dependen del tiempo real

```cpp
// Mal
ciclo.actualizar(SECO);
std::this_thread::sleep_for(std::chrono::minutes(3));   // pruebas lentas e inestables

// Bien
reloj.avanzar(3 * 60 * 1000);
```

### Probar solo el caso feliz

Si las pruebas solo verifican que "con suelo seco riega", no detectan el bug del tanque vacío. Los casos importantes son los bordes (justo en el umbral, justo en el tiempo) y las situaciones de falla.

### Probar detalles internos

```cpp
// Mal: verifica cómo está hecho por dentro
TEST_ASSERT_EQUAL(3, ciclo._contadorInterno);

// Bien: verifica lo que se observa desde afuera
TEST_ASSERT_FALSE(ciclo.bombaEncendida());
```

Las pruebas de comportamiento siguen pasando aunque se reescriba el interior; las de detalles internos se rompen con cada cambio.

### Querer probar todo en la PC

Un driver que habla I2C o una conexión BLE no se prueban con dobles que imitan el bus: el esfuerzo es grande y las pruebas no dicen si funciona con el hardware real. Mantené esas piezas delgadas y probalas en la placa.

## Ejercicio

Esta clase controla la luz de cultivo: la enciende si hay poca luz natural entre las 6 y las 20 horas, y nunca más de 14 horas por día. Tal como está no se puede probar en la PC. Rediseñala para que se pueda, y escribí dos pruebas: que no enciende de noche aunque esté oscuro, y que se apaga al llegar a las 14 horas.

```cpp luz-cultivo.ino
class LuzCultivo {
public:
  void actualizar() {
    int lux = analogRead(34);
    int hora = horaActual();                   // del reloj del sistema
    bool debeEncender = lux < 800 && hora >= 6 && hora < 20 && _minutosHoy < 14 * 60;
    digitalWrite(25, debeEncender ? HIGH : LOW);
    if (debeEncender && millis() - _ultimoMinuto >= 60000) {
      _ultimoMinuto = millis();
      _minutosHoy++;
    }
  }
private:
  uint32_t _ultimoMinuto = 0;
  uint32_t _minutosHoy = 0;
};
```

```cpp lib/control/luz_cultivo.h
#pragma once
#include <cstdint>

class LuzCultivo {
public:
  // Devuelve si la luz debe estar encendida. No toca hardware.
  bool actualizar(int lux, int hora, uint32_t ahoraMs) {
    bool debeEncender = lux < 800 && hora >= 6 && hora < 20 && _minutosHoy < 14 * 60;
    if (debeEncender && ahoraMs - _ultimoMinuto >= 60000) {
      _ultimoMinuto = ahoraMs;
      _minutosHoy++;
    }
    return debeEncender;
  }
  void nuevoDia() { _minutosHoy = 0; }
private:
  uint32_t _ultimoMinuto = 0;
  uint32_t _minutosHoy = 0;
};
```

```cpp test/test_luz/test_main.cpp
#include <unity.h>
#include "luz_cultivo.h"

void setUp() {}
void tearDown() {}

void test_no_enciende_de_noche_aunque_este_oscuro() {
  LuzCultivo luz;
  TEST_ASSERT_FALSE(luz.actualizar(100, 23, 0));
  TEST_ASSERT_FALSE(luz.actualizar(100, 4, 0));
}

void test_se_apaga_a_las_14_horas_de_uso() {
  LuzCultivo luz;
  uint32_t t = 0;
  for (int minuto = 0; minuto < 14 * 60; minuto++) {
    t += 60000;
    TEST_ASSERT_TRUE(luz.actualizar(100, 10, t));
  }
  t += 60000;
  TEST_ASSERT_FALSE(luz.actualizar(100, 10, t));   // ya cumplió las 14 horas
}

int main() {
  UNITY_BEGIN();
  RUN_TEST(test_no_enciende_de_noche_aunque_este_oscuro);
  RUN_TEST(test_se_apaga_a_las_14_horas_de_uso);
  return UNITY_END();
}
```

```cpp src/main.cpp (fragmento)
LuzCultivo luz;
void loop() {
  bool encender = luz.actualizar(analogRead(34), horaActual(), millis());
  digitalWrite(25, encender ? HIGH : LOW);
}
```

La lógica ya no lee pines ni el reloj: todo entra como parámetro, y la decisión sale como valor de retorno. En el firmware, `loop()` hace la lectura y maneja el pin. La segunda prueba simula 14 horas de funcionamiento en unos milisegundos. Faltaba además algo que el diseño original escondía: nadie reiniciaba `_minutosHoy` a la medianoche. Ahora hay un `nuevoDia()` explícito, y se podría agregar una prueba para eso.

## Resumen

- La mayoría de los bugs están en la lógica, y la lógica separada del hardware se prueba en la PC, en segundos.
- Para poder probar: funciones puras y dependencias (sensores, actuadores, reloj) detrás de interfaces que se reciben desde afuera.
- El tiempo es una dependencia más: un reloj falso permite probar minutos u horas de funcionamiento al instante.
- Los dobles de prueba fijan entradas y registran salidas. Con Unity y `pio test -e native`, las pruebas corren sin placa.
- Probá comportamientos, casos borde y fallas. Los drivers y las conexiones, en la placa.
