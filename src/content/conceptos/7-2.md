Todo programa que habla por una red tiene supuestos sobre ella, y la mayoría son falsos: que un mensaje enviado llega, que llega una sola vez, que llega en orden, que responde rápido, que si hay WiFi hay internet, que la dirección del servidor no cambia. A principios de los 90 alguien los juntó en una lista que se volvió clásica, las **falacias de la computación distribuida**, y treinta años después siguen siendo la causa de la mayoría de los datos duplicados, perdidos o desordenados entre los equipos y el backend. Muchas lecciones anteriores son, en el fondo, defensas contra estos supuestos.

## Por qué te importa

Los controladores del invernadero están en el campo, con WiFi de un router doméstico, a veces detrás de un enlace por radio o un módem celular. La red va a fallar todos los días de formas distintas. Si el código supone que no, el resultado no es un error visible: son lecturas duplicadas que inflan el consumo de agua, huecos en los gráficos, órdenes de riego que se ejecutan dos veces, o un controlador que se queda esperando una respuesta mientras la bomba sigue prendida.

## Cómo funciona

Estos son los supuestos falsos y la defensa de cada uno en el sistema del invernadero.

*"Si lo mandé, llegó."* Un pedido puede perderse a la ida, o llegar y perderse la respuesta. Desde el equipo, los dos casos se ven igual: un tiempo agotado. La única respuesta correcta es reintentar, y eso lleva al siguiente.

*"Llega una sola vez."* Si se reintenta lo que pudo haber llegado, el backend recibe duplicados. La defensa es la **idempotencia**: cada lectura y cada orden lleva un identificador, y repetirla no cambia nada (ver [3.5](/conceptos/3-5) y [4.3](/conceptos/4-3)).

*"Llega en orden."* Con reintentos, colas y lotes, una lectura vieja puede llegar después de una nueva. Los datos llevan su propio momento de medición, y las configuraciones, un número de versión (ver [5.3](/conceptos/5-3)). Nada se ordena por el momento de llegada.

*"La red responde rápido."* Un pedido puede tardar un minuto. Todo pedido tiene un tiempo máximo (`setConnectTimeout`, `setTimeout`), y la comunicación va en una tarea aparte, para que una red lenta nunca frene el control del riego (ver [2.4](/conceptos/2-4)).

*"Si hay WiFi, hay internet."* `WiFi.status() == WL_CONNECTED` dice que el equipo habla con el router. El router puede estar sin internet, o el backend caído. El estado que importa es "¿cuándo fue la última vez que el backend respondió?".

*"La dirección del servidor no cambia."* Una IP fija en el firmware se rompe el día que se cambia de servidor o de proveedor. En producción, un nombre (`api.ejemplo.com`) resuelto por DNS, y la URL guardada en la configuración, no compilada.

*"La red es segura."* En el WiFi del invernadero puede haber cualquiera. HTTPS con verificación del certificado (ver [0.10](/conceptos/0-10)) y una clave por equipo (ver [3.4](/conceptos/3-4)).

*"El ancho de banda sobra."* Un módem celular puede cobrar por megabyte, y un enlace débil apenas pasa unos kilobytes por segundo. Lotes, mensajes chicos y nada de mandar lo que no cambió.

## Ejemplo

El controlador muestra en pantalla el estado de la conexión. Mirar solo el WiFi daría "conectado" aunque el backend lleve una hora sin responder; por eso el estado se basa en la última respuesta real del backend.

```cpp enlace.ino
#include <WiFi.h>
#include <HTTPClient.h>

enum class EstadoEnlace : uint8_t { SinWifi, SinBackend, Ok };

constexpr uint32_t SIN_BACKEND_TRAS_MS = 5UL * 60UL * 1000UL;   // 5 minutos sin respuestas

uint32_t ultimaRespuestaMs = 0;
bool huboRespuesta = false;

// Llamar después de cada pedido al backend, con el código que devolvió HTTPClient.
void registrarResultado(int codigo) {
  if (codigo > 0) {             // cualquier respuesta HTTP, aunque sea un error: el backend está
    ultimaRespuestaMs = millis();
    huboRespuesta = true;
  }
  // codigo < 0: sin conexión o tiempo agotado. No se sabe qué pasó con el pedido.
}

EstadoEnlace estadoEnlace() {
  if (WiFi.status() != WL_CONNECTED) return EstadoEnlace::SinWifi;
  if (!huboRespuesta || millis() - ultimaRespuestaMs > SIN_BACKEND_TRAS_MS) {
    return EstadoEnlace::SinBackend;
  }
  return EstadoEnlace::Ok;
}

const char* textoEnlace(EstadoEnlace e) {
  switch (e) {
    case EstadoEnlace::SinWifi:    return "sin WiFi";
    case EstadoEnlace::SinBackend: return "WiFi sin servidor";
    case EstadoEnlace::Ok:         return "conectado";
  }
  return "?";
}

void setup() {
  Serial.begin(115200);
  WiFi.begin("red", "clave");   // en el equipo real, desde la NVS (ver 6.1)
}

void loop() {
  static uint32_t ultimoPedido = 0;
  if (millis() - ultimoPedido >= 30000) {
    ultimoPedido = millis();
    if (WiFi.status() == WL_CONNECTED) {
      HTTPClient http;
      http.begin("http://192.168.0.10:3000/api/v1/salud");
      http.setConnectTimeout(3000);
      http.setTimeout(5000);
      registrarResultado(http.GET());
      http.end();
    }
    Serial.printf("enlace: %s\n", textoEnlace(estadoEnlace()));
  }
}
```

La distinción le sirve al operario: "sin WiFi" es un problema del router o de la señal, en el invernadero; "WiFi sin servidor" es un problema de internet o del backend, y no se arregla reiniciando el controlador. En el sistema real, `registrarResultado` se llama desde la tarea de comunicación con el resultado de cada envío de lecturas, y no hace falta un pedido aparte. El pedido de este ejemplo bloquea `loop()` hasta 8 segundos; en el controlador va en su propia tarea (ver [2.4](/conceptos/2-4) y [3.1](/conceptos/3-1)).

## Cuándo sí y cuándo no

Estos supuestos se pueden ignorar en un prototipo en tu escritorio, con el backend en la misma red y un solo equipo. Para cualquier equipo instalado, hay que asumir siempre que:

- cada pedido puede no llegar, llegar dos veces o llegar tarde;
- cada pedido necesita un tiempo máximo y un plan para cuando no hay respuesta;
- el equipo tiene que seguir funcionando sin red (ver [5.3](/conceptos/5-3));
- el orden y la hora de los datos los dicen los datos, no la red.

La idempotencia no es opcional en cuanto hay reintentos, y sin reintentos se pierden datos: en la práctica, siempre hace falta.

## Resumen

- Un pedido sin respuesta tiene resultado desconocido: pudo llegar o no.
- Reintentar es obligatorio, y eso genera duplicados: idempotencia con identificadores.
- La red no conserva el orden: los datos llevan su momento y las configuraciones, su versión.
- Todo pedido tiene un tiempo máximo y va en una tarea que no frena el control.
- WiFi conectado no significa backend alcanzable: el estado real es la última respuesta recibida.
