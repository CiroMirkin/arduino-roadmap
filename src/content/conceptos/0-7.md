**I2C** y **SPI** son los dos buses más usados para conectar sensores, memorias y pantallas al ESP32. Los dos son *sincrónicos*: el ESP32 (el *maestro*) genera una señal de reloj y los dispositivos leen o escriben un bit en cada pulso. I2C usa solo dos cables compartidos por todos los dispositivos, que se distinguen por su **dirección**. SPI usa cuatro cables y es mucho más rápido, pero cada dispositivo necesita su propia línea de **chip select**.

## Por qué te importa

En el controlador del invernadero conviven varios dispositivos: un sensor de temperatura y humedad por I2C, otro igual en el otro extremo del invernadero, una tarjeta microSD por SPI para guardar el historial, y la pantalla táctil, que usa los dos. Elegir el bus correcto para cada uno, y conectarlo bien, define si todo funciona junto.

Los problemas típicos son silenciosos: un sensor que no aparece porque al bus le faltan resistencias de pull-up, dos sensores iguales con la misma dirección de los que solo responde uno, una tarjeta SD que falla porque otro dispositivo SPI tiene su chip select flotando. Entender cómo funciona cada bus permite diagnosticarlos en minutos.

## Paso a paso

### 1. Qué tienen en común

Los dos buses tienen un **maestro** (el ESP32), que inicia todas las comunicaciones, y uno o más **esclavos** (los sensores), que responden. El maestro genera el reloj, así que no hace falta acordar una velocidad exacta como en UART (ver [0.6](/conceptos/0-6)): el esclavo lee cada bit cuando el reloj se lo indica.

Casi todos los dispositivos funcionan con **registros**: posiciones de memoria internas con un número. Para leer la temperatura, el maestro le dice al sensor "dame el registro tal" (o le manda un comando), y el sensor responde con unos bytes. La hoja de datos del sensor dice qué registros o comandos tiene y qué significa cada byte.

### 2. I2C: dos cables y direcciones

```text
            3,3 V
             │  │
            4,7k 4,7k     (resistencias de pull-up)
             │  │
ESP32 SDA ───┴──┼──────── SDA sensor A ──── SDA sensor B
ESP32 SCL ──────┴──────── SCL sensor A ──── SCL sensor B
GND ───────────────────── GND ──────────── GND
```

- **SDA** lleva los datos y **SCL** el reloj. Todos los dispositivos se conectan a los mismos dos cables.
- Cada dispositivo tiene una **dirección** de 7 bits (de 0x08 a 0x77). El maestro empieza cada mensaje con la dirección, y solo responde el dispositivo que la tiene.
- Las líneas necesitan **resistencias de pull-up** (típicamente 4,7 kΩ a 3,3 V). Los dispositivos solo pueden llevar la línea a `LOW`; el pull-up la devuelve a `HIGH`. Muchos módulos ya las traen soldadas.
- Velocidad: 100 kHz (estándar) o 400 kHz (rápida).

```cpp
#include <Wire.h>

void setup() {
  Wire.begin(21, 22);        // SDA, SCL (en el ESP32 clásico, 21 y 22 son los de siempre)
  Wire.setClock(400000);     // 400 kHz
}
```

### 3. Leer y escribir por I2C

```cpp
// Enviar un comando de 2 bytes al dispositivo 0x44
Wire.beginTransmission(0x44);
Wire.write(0x24);
Wire.write(0x00);
uint8_t error = Wire.endTransmission();   // 0 = ok; otro valor = nadie respondió o falló

// Pedir 6 bytes al dispositivo 0x44
uint8_t recibidos = Wire.requestFrom(0x44, 6);
for (uint8_t i = 0; i < recibidos; i++) {
  uint8_t b = Wire.read();
}
```

`endTransmission` devuelve 0 si el dispositivo confirmó la recepción. `requestFrom` devuelve cuántos bytes llegaron realmente. Chequeá los dos: son la forma de enterarte de que un sensor se desconectó.

### 4. SPI: cuatro cables y chip select

```text
ESP32 SCK  ─────┬──────────── SCK  tarjeta SD
ESP32 MOSI ─────┼──┬───────── MOSI tarjeta SD
ESP32 MISO ─────┼──┼──┬────── MISO tarjeta SD
ESP32 CS_SD ────┼──┼──┼────── CS   tarjeta SD
                │  │  │
                └──┴──┴────── SCK, MOSI, MISO de otro dispositivo
ESP32 CS_OTRO ─────────────── CS del otro dispositivo
```

- **SCK**: reloj. **MOSI** (*Master Out, Slave In*): datos del ESP32 al dispositivo. **MISO** (*Master In, Slave Out*): datos del dispositivo al ESP32. Se envía y se recibe al mismo tiempo.
- **CS** (*chip select*): uno por dispositivo. En reposo está en `HIGH`; el maestro lo baja a `LOW` para hablar con ese dispositivo, y los demás ignoran el bus.
- Velocidad: de 1 a decenas de MHz. Por eso las pantallas y las tarjetas SD usan SPI.
- Hay cuatro **modos** (0 a 3), según en qué flanco del reloj se leen los bits. La hoja de datos dice cuál usar; las librerías lo configuran solas.

```cpp
#include <SPI.h>

SPI.begin(18, 19, 23, 5);   // SCK, MISO, MOSI, CS (pines VSPI del ESP32 clásico)
```

### 5. Cuál usar

| | I2C | SPI |
|---|---|---|
| Cables | 2 (más GND y alimentación) | 3 compartidos + 1 CS por dispositivo |
| Cómo se elige el dispositivo | dirección | chip select |
| Velocidad | 100 a 400 kHz | 1 a 80 MHz |
| Distancia | corta: decenas de cm, hasta 1 m con cuidado | corta: decenas de cm |
| Típico para | sensores, relojes, expansores de pines | pantallas, tarjetas SD, memorias, ADC rápidos |

Para sensores que se leen cada pocos segundos, I2C alcanza y ahorra pines. Para mover mucha información (una imagen, un archivo), SPI.

### 6. Librerías o registros

Para casi todos los sensores comunes hay librerías que esconden los registros: `begin()`, `readTemperature()` y listo. Usarlas está bien, y para dispositivos complejos (una tarjeta SD, una pantalla) es lo razonable. Saber leer un dispositivo directamente, como en el ejemplo 2, sirve cuando no hay librería, cuando la librería bloquea demasiado, o para entender qué falla.

## Ejemplos

### Ejemplo 1. El escáner I2C

La primera prueba con cualquier dispositivo I2C: recorrer todas las direcciones y ver quién responde.

```cpp escaner-i2c.ino
#include <Wire.h>

void setup() {
  Serial.begin(115200);
  delay(1000);
  Wire.begin(21, 22);

  int encontrados = 0;
  for (uint8_t direccion = 0x08; direccion <= 0x77; direccion++) {
    Wire.beginTransmission(direccion);
    if (Wire.endTransmission() == 0) {
      Serial.printf("dispositivo en 0x%02X\n", direccion);
      encontrados++;
    }
  }
  Serial.printf("%d dispositivos encontrados\n", encontrados);
}

void loop() {}
```

Si no aparece nada: revisá alimentación, SDA y SCL (¿invertidos? ¿en otros pines?) y pull-ups. Si aparece una dirección distinta a la esperada, puede que el pin de dirección del módulo esté configurado de otra forma.

### Ejemplo 2. Un sensor de temperatura y humedad por I2C, sin librería

El SHT31 es un sensor de temperatura y humedad común, en la dirección 0x44. Para medir, se le envía el comando `0x24 0x00`, se espera unos 15 ms y se leen 6 bytes: temperatura (2 bytes + CRC) y humedad (2 bytes + CRC). Cada par de bytes viene con un **CRC**, una verificación más robusta que un checksum simple.

```cpp sht31.ino
#include <Wire.h>

class Sht31 {
public:
  explicit Sht31(uint8_t direccion = 0x44) : _direccion(direccion) {}

  // Inicia una medición. No espera.
  bool pedirMedicion() {
    Wire.beginTransmission(_direccion);
    Wire.write(0x24);
    Wire.write(0x00);
    _pedido = (Wire.endTransmission() == 0);
    _momentoPedido = millis();
    return _pedido;
  }

  // Llamar en cada vuelta de loop(). True cuando hay una medición nueva y válida.
  bool actualizar() {
    if (!_pedido || millis() - _momentoPedido < 20) return false;
    _pedido = false;

    uint8_t b[6];
    if (Wire.requestFrom(_direccion, static_cast<uint8_t>(6)) != 6) return false;
    for (uint8_t& x : b) x = Wire.read();

    if (crc8(b, 2) != b[2] || crc8(b + 3, 2) != b[5]) return false;   // datos alterados

    uint16_t crudoT = (b[0] << 8) | b[1];
    uint16_t crudoH = (b[3] << 8) | b[4];
    _temperatura = -45.0f + 175.0f * crudoT / 65535.0f;
    _humedad = 100.0f * crudoH / 65535.0f;
    return true;
  }

  float temperatura() const { return _temperatura; }
  float humedad() const { return _humedad; }

private:
  // CRC-8 del SHT31: polinomio 0x31, valor inicial 0xFF
  static uint8_t crc8(const uint8_t* datos, size_t largo) {
    uint8_t crc = 0xFF;
    for (size_t i = 0; i < largo; i++) {
      crc ^= datos[i];
      for (int bit = 0; bit < 8; bit++) {
        crc = (crc & 0x80) ? static_cast<uint8_t>((crc << 1) ^ 0x31) : static_cast<uint8_t>(crc << 1);
      }
    }
    return crc;
  }

  uint8_t _direccion;
  bool _pedido = false;
  uint32_t _momentoPedido = 0;
  float _temperatura = 0.0f;
  float _humedad = 0.0f;
};

Sht31 sensor;

void setup() {
  Serial.begin(115200);
  Wire.begin(21, 22);
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 2000) {
    ultimo = millis();
    if (!sensor.pedirMedicion()) Serial.println("el sensor no responde");
  }
  if (sensor.actualizar()) {
    Serial.printf("%.2f C, %.1f %%HR\n", sensor.temperatura(), sensor.humedad());
  }
}
```

El patrón "pedir y después leer" es el mismo del sensor de CO₂ de [0.6](/conceptos/0-6): el sensor tarda en medir, y en ese tiempo el controlador sigue trabajando en lugar de esperar con un `delay(15)`. Las fórmulas de conversión y el CRC salen de la hoja de datos. Si el CRC no coincide, la lectura se descarta en lugar de mostrar un valor corrupto.

### Ejemplo 3. Guardar el historial en una tarjeta microSD

El controlador guarda una línea por minuto en un archivo CSV en una tarjeta microSD conectada por SPI. Si la tarjeta no está o falla, el controlador sigue funcionando y reintenta más tarde.

```cpp registro-sd.ino
#include <SPI.h>
#include <SD.h>

constexpr uint8_t PIN_SD_CS = 5;

bool sdLista = false;

bool iniciarSd() {
  sdLista = SD.begin(PIN_SD_CS);
  if (sdLista && !SD.exists("/registro.csv")) {
    File f = SD.open("/registro.csv", FILE_WRITE);
    if (f) {
      f.println("segundos,temperatura,humedad");
      f.close();
    }
  }
  return sdLista;
}

bool registrar(float temperatura, float humedad) {
  if (!sdLista && !iniciarSd()) return false;

  File f = SD.open("/registro.csv", FILE_APPEND);
  if (!f) {
    sdLista = false;          // la tarjeta se sacó o falló: reintentar la próxima vez
    return false;
  }
  char linea[48];
  snprintf(linea, sizeof(linea), "%lu,%.2f,%.1f",
           static_cast<unsigned long>(millis() / 1000), temperatura, humedad);
  f.println(linea);
  f.close();                  // cerrar asegura que los datos queden escritos
  return true;
}

void setup() {
  Serial.begin(115200);
  SPI.begin(18, 19, 23, PIN_SD_CS);
  Serial.println(iniciarSd() ? "SD lista" : "sin tarjeta SD");
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 60000) {
    ultimo = millis();
    if (!registrar(24.5f, 68.0f)) {     // acá irían las lecturas reales
      Serial.println("no se pudo registrar");
    }
  }
}
```

La librería `SD` maneja todo el protocolo SPI de la tarjeta y el sistema de archivos FAT. El código solo se ocupa de qué hacer si la tarjeta falta: marcarla como no lista y reintentar en el próximo registro, en lugar de reiniciar o quedarse esperando. Cerrar el archivo después de cada línea es más lento que dejarlo abierto, pero si se corta la luz, se pierde como mucho una línea.

## Errores comunes

### Bus I2C sin pull-ups

Si usás un sensor suelto (sin módulo) o un módulo sin resistencias, el bus no funciona o funciona a medias. Agregá 4,7 kΩ de SDA a 3,3 V y de SCL a 3,3 V. Los pull-ups internos del ESP32 son demasiado débiles para I2C salvo en distancias muy cortas.

### Cables I2C largos

I2C fue diseñado para conexiones dentro de una misma placa. Con un metro de cable empiezan los errores; con varios metros, no funciona. Para un sensor en la otra punta del invernadero, conviene un nodo propio con BLE (ver [0.9](/conceptos/0-9)), un sensor con salida RS-485, o un extensor de bus I2C.

### Dos dispositivos con la misma dirección

```cpp
// Mal: los dos sensores en 0x44, responde uno solo (o ninguno bien)
Sht31 sensorNorte(0x44);
Sht31 sensorSur(0x44);

// Bien: el pin ADDR del segundo, a 3,3 V, lo pasa a 0x45
Sht31 sensorNorte(0x44);
Sht31 sensorSur(0x45);
```

Si el sensor no tiene pin de dirección, hace falta un multiplexor I2C o un segundo bus (el ESP32 tiene dos: `Wire` y `Wire1`).

### Un CS que queda flotando

```cpp
// Mal: el CS de un dispositivo que no se usa en este momento queda sin configurar
SPI.begin(18, 19, 23);

// Bien: todos los CS como salida y en HIGH antes de empezar
pinMode(PIN_SD_CS, OUTPUT);
digitalWrite(PIN_SD_CS, HIGH);
pinMode(PIN_OTRO_CS, OUTPUT);
digitalWrite(PIN_OTRO_CS, HIGH);
```

Un CS flotando puede quedar en `LOW`: ese dispositivo cree que le hablan a él y responde al mismo tiempo que el otro.

### No chequear si el dispositivo respondió

```cpp
// Mal
Wire.requestFrom(0x44, 6);
uint8_t a = Wire.read();   // si no llegó nada, devuelve -1 convertido a 255

// Bien
if (Wire.requestFrom(0x44, 6) == 6) { /* leer */ }
```

## Ejercicio

El controlador tiene dos sensores SHT31: uno en la zona norte y otro en la sur. Los dos están conectados al mismo bus I2C, y el escáner muestra un solo dispositivo en 0x44. Explicá qué cambio de hardware hace falta, y escribí el código para leer los dos con la clase `Sht31` del ejemplo 2, mostrando la diferencia de temperatura entre las dos zonas.

<details>
<summary>Pista</summary>

El SHT31 tiene un pin ADDR: conectado a GND, la dirección es 0x44; conectado a 3,3 V, es 0x45. La clase ya recibe la dirección en el constructor.

</details>

<details>
<summary>Ver solución</summary>

En el sensor de la zona sur, el pin ADDR se conecta a 3,3 V (en muchos módulos hay que cortar o soldar un puente). Con eso, el escáner muestra dos dispositivos: 0x44 y 0x45.

```cpp dos-zonas.ino
// La clase Sht31 es la del ejemplo 2

Sht31 sensorNorte(0x44);
Sht31 sensorSur(0x45);

void setup() {
  Serial.begin(115200);
  Wire.begin(21, 22);
}

void loop() {
  static uint32_t ultimo = 0;
  static bool hayNorte = false;
  static bool haySur = false;

  if (millis() - ultimo >= 2000) {
    ultimo = millis();
    sensorNorte.pedirMedicion();
    sensorSur.pedirMedicion();
  }

  if (sensorNorte.actualizar()) hayNorte = true;
  if (sensorSur.actualizar()) haySur = true;

  if (hayNorte && haySur) {
    hayNorte = false;
    haySur = false;
    float diferencia = sensorNorte.temperatura() - sensorSur.temperatura();
    Serial.printf("norte %.1f C, sur %.1f C, diferencia %.1f C\n",
                  sensorNorte.temperatura(), sensorSur.temperatura(), diferencia);
  }
}
```

Los dos sensores miden al mismo tiempo, porque cada uno recibe su comando y mide por su cuenta. Una diferencia grande y sostenida entre zonas indica que el aire no circula bien, y es un dato útil para decidir dónde poner un ventilador.

</details>

## Resumen

- I2C: dos cables compartidos (SDA y SCL), dispositivos identificados por dirección, pull-ups obligatorios, velocidad baja y distancias cortas. Ideal para sensores.
- SPI: SCK, MOSI y MISO compartidos más un CS por dispositivo, mucho más rápido. Ideal para pantallas y tarjetas SD.
- El escáner I2C es la primera herramienta de diagnóstico. Si no aparece nada, revisá cables, alimentación y pull-ups.
- Dos dispositivos I2C iguales necesitan direcciones distintas (pin ADDR) o buses distintos.
- Chequeá siempre lo que devuelven `endTransmission` y `requestFrom`, y validá los CRC cuando el dispositivo los manda.
