Una **transacción** agrupa varias operaciones sobre la base de datos para que se apliquen **todas o ninguna**: si algo falla en el medio, la base vuelve al estado anterior. El **control de concurrencia** se ocupa de otro problema: qué pasa cuando varios pedidos leen y modifican los mismos datos al mismo tiempo. Juntos, son lo que garantiza que los datos del invernadero sigan siendo correctos aunque el servidor se caiga a mitad de camino o dos personas toquen lo mismo a la vez.

## Por qué te importa

El backend atiende muchos pedidos en paralelo: equipos enviando lecturas, operarios accionando riegos, administradores cambiando la configuración. Cuando dos de ellos tocan los mismos datos, aparecen errores que no se ven en las pruebas (donde todo pasa de a uno): un cupo de agua que se pasa del límite, un cambio de configuración que desaparece, un registro de riego sin su descuento.

En lecciones anteriores ya usaste transacciones sin detenerte en ellas: en [4.1](/conceptos/4-1) para Row Level Security, en [4.3](/conceptos/4-3) para la idempotencia de las órdenes, en [4.6](/conceptos/4-6) para la cola. Esta lección explica qué garantizan y cómo usarlas para los casos de concurrencia.

## Paso a paso

### 1. Todo o nada

```sql
BEGIN;
INSERT INTO eventos_riego (zona_id, litros, ...) VALUES (...);
UPDATE cupos SET usado = usado + 15 WHERE zona_id = 7;
COMMIT;      -- las dos quedan; con ROLLBACK (o si algo falla), ninguna
```

Las propiedades que garantiza una transacción se resumen como **ACID**: **atomicidad** (todo o nada), **consistencia** (las restricciones se cumplen al terminar), **aislamiento** (otras transacciones no ven el trabajo a medio hacer) y **durabilidad** (lo confirmado sobrevive a una caída).

### 2. Transacciones desde Node

Con la librería `pg`, una transacción usa **una sola conexión** del pool para todas sus consultas: no se puede usar `pool.query` (cada llamada podría ir por otra conexión).

```js
const cliente = await pool.connect();
try {
  await cliente.query("BEGIN");
  // ... consultas con cliente.query ...
  await cliente.query("COMMIT");
} catch (error) {
  await cliente.query("ROLLBACK");
  throw error;
} finally {
  cliente.release();   // siempre devolver la conexión al pool
}
```

Este patrón se repite tanto que conviene escribirlo una vez, en una función auxiliar (ejemplo 1).

### 3. La actualización perdida

El error de concurrencia más común es **leer, decidir en el código y escribir**:

```text
pedido A: lee usado = 80
pedido B: lee usado = 80
pedido A: 80 + 15 = 95 ≤ 100 → escribe usado = 95
pedido B: 80 + 15 = 95 ≤ 100 → escribe usado = 95
resultado: se consumieron 30 litros, quedó registrado 15
```

Una transacción sola no lo evita: con el nivel de aislamiento por defecto de PostgreSQL (*read committed*), las dos transacciones pueden leer el mismo valor. Hay tres soluciones, según el caso.

### 4. Solución 1: una sola sentencia atómica

Si la decisión se puede expresar en SQL, se hace todo en una sentencia, que la base ejecuta sin que nada se intercale:

```sql
UPDATE cupos SET usado = usado + $2
 WHERE zona_id = $1 AND usado + $2 <= limite
RETURNING usado;
```

Si devuelve una fila, se consumió; si no devuelve ninguna, el cupo no alcanzaba. Es la solución más simple y más eficiente. Sirve para contadores, saldos, stocks, cupos.

### 5. Solución 2: bloquear la fila (`SELECT ... FOR UPDATE`)

Cuando la decisión es más compleja y necesita código, se lee la fila **bloqueándola**: otras transacciones que quieran bloquearla esperan hasta que esta termine.

```sql
BEGIN;
SELECT usado, limite FROM cupos WHERE zona_id = $1 FOR UPDATE;   -- los demás esperan acá
-- decidir en el código...
UPDATE cupos SET usado = ... WHERE zona_id = $1;
COMMIT;
```

Funciona siempre, a cambio de que los pedidos sobre la misma fila se hagan de a uno. Por eso la transacción tiene que ser **corta**: nada de esperar respuestas de otros servicios con la fila bloqueada.

### 6. Solución 3: bloqueo optimista con una versión

Para ediciones que hace una persona (abre un formulario, piensa, guarda), no se puede tener una fila bloqueada durante minutos. El **bloqueo optimista** agrega una columna `version` a la fila: la app la lee junto con los datos, y al guardar, la actualización exige que la versión siga siendo la misma:

```sql
UPDATE zonas SET nombre = $3, version = version + 1
 WHERE id = $1 AND version = $2;
```

Si alguien guardó en el medio, la versión cambió, la actualización no afecta ninguna fila, y el backend responde `409 Conflict`: la app le muestra al usuario los datos nuevos para que decida. Se llama "optimista" porque supone que los conflictos son raros y solo actúa cuando ocurren.

## Ejemplos

### Ejemplo 1. Una función para transacciones

```js transaccion.js
// Ejecuta trabajo(cliente) dentro de una transacción; confirma si sale bien, deshace si falla
async function enTransaccion(pool, trabajo) {
  const cliente = await pool.connect();
  try {
    await cliente.query("BEGIN");
    const resultado = await trabajo(cliente);
    await cliente.query("COMMIT");
    return resultado;
  } catch (error) {
    await cliente.query("ROLLBACK");
    throw error;
  } finally {
    cliente.release();
  }
}

module.exports = { enTransaccion };

// Uso: registrar un riego y su consumo, juntos o ninguno
// await enTransaccion(pool, async (db) => {
//   await db.query("INSERT INTO eventos_riego (...) VALUES (...)", [...]);
//   await db.query("UPDATE totales_diarios SET litros = litros + $2 WHERE zona_id = $1 AND dia = current_date", [zona, litros]);
// });
```

Cualquier excepción dentro de `trabajo` (un error de la base, una validación que falla) termina en `ROLLBACK`, y la conexión vuelve al pool en todos los casos. Las rutas solo escriben lo que hay que hacer, sin repetir el manejo de `BEGIN`, `COMMIT` y `ROLLBACK`.

### Ejemplo 2. El cupo diario de agua sin actualizaciones perdidas

Cada zona tiene un cupo diario de litros (por ejemplo, por una restricción de la cooperativa de riego). Un riego manual solo se acepta si queda cupo, y varios operarios pueden pedirlo a la vez.

```sql cupos.sql
CREATE TABLE cupos (
  organizacion_id  BIGINT NOT NULL,
  zona_id          BIGINT NOT NULL,
  dia              DATE NOT NULL,
  limite_litros    NUMERIC(8,1) NOT NULL CHECK (limite_litros >= 0),
  usado_litros     NUMERIC(8,1) NOT NULL DEFAULT 0 CHECK (usado_litros >= 0),
  PRIMARY KEY (zona_id, dia),
  CHECK (usado_litros <= limite_litros)    -- la base tampoco permite pasarse
);
```

```js riego-con-cupo.js
const { enTransaccion } = require("./transaccion");

// Devuelve { ok: true, usado } o { ok: false, motivo }
async function pedirRiego(pool, { organizacionId, zonaId, litros, usuarioId }) {
  return enTransaccion(pool, async (db) => {
    // Descontar y verificar en una sola sentencia: nadie puede intercalarse
    const { rows } = await db.query(
      `UPDATE cupos SET usado_litros = usado_litros + $3
        WHERE organizacion_id = $1 AND zona_id = $2 AND dia = current_date
          AND usado_litros + $3 <= limite_litros
       RETURNING usado_litros, limite_litros`,
      [organizacionId, zonaId, litros]
    );
    if (rows.length === 0) {
      return { ok: false, motivo: "no queda cupo suficiente (o la zona no tiene cupo hoy)" };
    }

    await db.query(
      `INSERT INTO comandos (organizacion_id, zona_id, tipo, litros, creado_por)
       VALUES ($1, $2, 'regar', $3, $4)`,
      [organizacionId, zonaId, litros, usuarioId]
    );
    return { ok: true, usado: rows[0].usado_litros, limite: rows[0].limite_litros };
  });
}

module.exports = { pedirRiego };
```

La verificación del cupo y el descuento son una sola sentencia: dos pedidos simultáneos no pueden leer el mismo valor, porque ninguno lee antes de escribir. Si el segundo no entra, el `UPDATE` no afecta ninguna fila y se responde que no hay cupo. El descuento y el comando de riego están en la misma transacción: si falla el `INSERT`, el cupo se devuelve solo. El `CHECK` de la tabla es la última red: aunque alguien escriba un `UPDATE` sin la condición, la base no deja pasarse del límite.

### Ejemplo 3. Editar la configuración sin pisar cambios ajenos

La pantalla de configuración de una zona carga los datos con su versión; al guardar, la versión tiene que coincidir.

```sql zonas-version.sql
ALTER TABLE zonas ADD COLUMN version INTEGER NOT NULL DEFAULT 1;
```

```js editar-zona.js
// GET /zonas/:id devuelve { id, nombre, superficie_m2, version }
// PUT /zonas/:id recibe { nombre, superficie_m2, version }
async function editarZona(req, res) {
  const { nombre, superficie_m2, version } = req.body;
  if (!Number.isInteger(version)) {
    return res.status(400).json({ error: "falta la versión que se editó" });
  }

  const { rows } = await req.db.query(
    `UPDATE zonas
        SET nombre = $3, superficie_m2 = $4, version = version + 1
      WHERE organizacion_id = $1 AND id = $2 AND version = $5
     RETURNING id, nombre, superficie_m2, version`,
    [req.usuario.organizacion_id, req.params.id, nombre, superficie_m2, version]
  );

  if (rows.length === 1) {
    return res.json(rows[0]);                       // guardado, con la versión nueva
  }

  // No se actualizó: o no existe (o es de otra organización), o alguien la cambió
  const actual = await req.db.query(
    "SELECT id, nombre, superficie_m2, version FROM zonas WHERE organizacion_id = $1 AND id = $2",
    [req.usuario.organizacion_id, req.params.id]
  );
  if (actual.rows.length === 0) {
    return res.status(404).json({ error: "zona no encontrada" });
  }
  return res.status(409).json({
    error: "otra persona modificó esta zona mientras la editabas",
    actual: actual.rows[0],                         // la app muestra los datos nuevos
  });
}

module.exports = { editarZona };
```

Si dos personas editan a la vez, la primera en guardar incrementa la versión; la segunda recibe un 409 con los datos actuales, y la app le muestra qué cambió para que decida si vuelve a aplicar su cambio. No hay bloqueos mientras alguien tiene el formulario abierto. En la configuración de riego, que guarda historial (ver [5.1](/conceptos/5-1)), la misma idea se aplica comparando con el identificador de la última versión vigente.

## Errores comunes

### Varias escrituras relacionadas sin transacción

```js
// Mal: si falla la segunda, queda el evento sin su descuento
await pool.query("INSERT INTO eventos_riego ...");
await pool.query("UPDATE cupos ...");

// Bien
await enTransaccion(pool, async (db) => { /* las dos */ });
```

### Leer, decidir y escribir en pasos separados

```js
// Mal: actualización perdida con pedidos simultáneos
const usado = (await db.query("SELECT usado FROM cupos ...")).rows[0].usado;
await db.query("UPDATE cupos SET usado = $1 ...", [usado + litros]);

// Bien: la cuenta en la base, en una sola sentencia
await db.query("UPDATE cupos SET usado = usado + $1 WHERE ... AND usado + $1 <= limite", [litros]);
```

### Usar `pool.query` dentro de una transacción

Cada `pool.query` puede ir por una conexión distinta: el `BEGIN` queda en una, las consultas en otras, y la transacción no agrupa nada. Dentro de una transacción, siempre el mismo `cliente`.

### Transacciones largas

Esperar una respuesta HTTP, un correo o una decisión del usuario con una transacción abierta retiene una conexión y, si hay filas bloqueadas, frena a todos los que las necesitan. Las llamadas externas van antes o después de la transacción, o a una cola (ver [4.6](/conceptos/4-6)).

### Bloquear filas en distinto orden

Si una transacción bloquea la zona 1 y después la 2, y otra la 2 y después la 1, pueden quedar esperándose mutuamente (un *deadlock*). PostgreSQL lo detecta y cancela una, pero el pedido falla. Bloqueá siempre en el mismo orden (por ejemplo, por `id` creciente), como con los mutex de [2.4](/conceptos/2-4).

## Ejercicio

Esta ruta transfiere cupo de agua de una zona a otra del mismo invernadero. Tiene dos problemas: a veces el cupo de origen queda negativo cuando se hacen dos transferencias a la vez, y una vez se cayó el servidor y el cupo desapareció de una zona sin aparecer en la otra. Corregila.

```js transferir.js
async function transferirCupo(pool, org, desde, hacia, litros) {
  const { rows } = await pool.query(
    "SELECT limite_litros, usado_litros FROM cupos WHERE organizacion_id = $1 AND zona_id = $2 AND dia = current_date",
    [org, desde]
  );
  const disponible = rows[0].limite_litros - rows[0].usado_litros;
  if (disponible < litros) throw new Error("no alcanza");

  await pool.query(
    "UPDATE cupos SET limite_litros = limite_litros - $3 WHERE organizacion_id = $1 AND zona_id = $2 AND dia = current_date",
    [org, desde, litros]
  );
  await pool.query(
    "UPDATE cupos SET limite_litros = limite_litros + $3 WHERE organizacion_id = $1 AND zona_id = $2 AND dia = current_date",
    [org, hacia, litros]
  );
}
```

```js transferir.js
const { enTransaccion } = require("./transaccion");

async function transferirCupo(pool, org, desde, hacia, litros) {
  if (!(litros > 0)) throw new Error("los litros tienen que ser positivos");
  if (desde === hacia) throw new Error("origen y destino iguales");

  return enTransaccion(pool, async (db) => {
    const origen = await db.query(
      `UPDATE cupos SET limite_litros = limite_litros - $3
        WHERE organizacion_id = $1 AND zona_id = $2 AND dia = current_date
          AND limite_litros - usado_litros >= $3
       RETURNING limite_litros`,
      [org, desde, litros]
    );
    if (origen.rowCount === 0) throw new Error("no alcanza el cupo disponible en el origen");

    const destino = await db.query(
      `UPDATE cupos SET limite_litros = limite_litros + $3
        WHERE organizacion_id = $1 AND zona_id = $2 AND dia = current_date
       RETURNING limite_litros`,
      [org, hacia, litros]
    );
    if (destino.rowCount === 0) throw new Error("la zona de destino no tiene cupo hoy");   // ROLLBACK

    return { origen: origen.rows[0].limite_litros, destino: destino.rows[0].limite_litros };
  });
}
```

El cupo negativo venía de leer el disponible y descontar en pasos separados: dos transferencias simultáneas leían el mismo disponible. Ahora la verificación está dentro del `UPDATE`, en una sola sentencia. El cupo perdido venía de que los dos `UPDATE` eran independientes: si el servidor se caía entre ellos, solo se aplicaba el primero. Ahora están en una transacción, y si el destino no existe, el error provoca un `ROLLBACK` que devuelve el cupo al origen. Dos transferencias cruzadas (A→B y B→A al mismo tiempo) podrían bloquearse mutuamente; para evitarlo, se pueden actualizar las dos zonas siempre en orden de `zona_id`.

## Resumen

- Una transacción aplica todas sus operaciones o ninguna. En Node, todas sus consultas van por el mismo cliente del pool.
- Leer, decidir en el código y escribir en pasos separados produce actualizaciones perdidas con pedidos simultáneos.
- Primera opción: hacer la verificación y la escritura en una sola sentencia (`UPDATE ... WHERE condicion RETURNING`).
- Para decisiones complejas, `SELECT ... FOR UPDATE` dentro de una transacción corta. Para ediciones de personas, bloqueo optimista con una versión y `409`.
- Transacciones cortas, sin esperas externas, y los bloqueos siempre en el mismo orden.
