Con la **herencia**, una clase toma todo lo que tiene otra y le agrega o cambia cosas. A la clase original se la llama *base* y a la nueva, *derivada*. Un objeto derivado se puede usar en cualquier lugar donde se espera uno de la base. Si un método de la base es **`virtual`**, la derivada puede redefinirlo, y la llamada ejecuta la versión que corresponde al objeto real. **`override`** le pide al compilador que verifique que esa redefinición es correcta.

## Por qué te importa

Las librerías de Arduino usan herencia para avisarte cuando pasa algo. La de BLE del ESP32 no te pide una función suelta para el evento de desconexión: te pide que crees una clase que herede de `BLEServerCallbacks` y que redefinas `onDisconnect`. Si escribís `onDisconect`, con una "n" de menos, el código compila, la librería nunca lo llama, y el nodo sensor del invernadero queda invisible después de la primera desconexión. Con `override`, ese error no compila.

Además, la herencia con métodos `virtual` permite que el controlador trabaje con "un sensor de temperatura" sin saber cuál es. Hoy es un sensor analógico; mañana, uno digital por I2C; en las pruebas, uno simulado que devuelve valores fijos. El código de control no cambia.

## Paso a paso

### 1. Heredar

```cpp
class Actuador {
public:
  explicit Actuador(uint8_t pin) : _pin(pin) {}
  void begin() { pinMode(_pin, OUTPUT); apagar(); }
  void encender() { digitalWrite(_pin, HIGH); _encendido = true; }
  void apagar()   { digitalWrite(_pin, LOW);  _encendido = false; }
  bool encendido() const { return _encendido; }

protected:
  uint8_t _pin;

private:
  bool _encendido = false;
};

class Bomba : public Actuador {
public:
  Bomba(uint8_t pin, float litrosPorMinuto)
    : Actuador(pin), _litrosPorMinuto(litrosPorMinuto) {}

  float caudal() const { return _litrosPorMinuto; }

private:
  float _litrosPorMinuto;
};

Bomba bomba(4, 12.0f);
bomba.begin();       // heredado de Actuador
bomba.encender();    // heredado
bomba.caudal();      // propio de Bomba
```

`class Bomba : public Actuador` dice que una `Bomba` es un `Actuador` con algo más. La derivada recibe todos los miembros de la base. El constructor de la derivada llama al de la base en su lista de inicialización (`: Actuador(pin)`).

`protected` es un punto intermedio entre `public` y `private`: las derivadas lo pueden usar, el resto del programa no. Los miembros `private` de la base existen dentro de la derivada, pero la derivada no puede tocarlos directamente.

### 2. Una derivada se puede usar como base

```cpp
void apagarDeEmergencia(Actuador& a) {
  a.apagar();
}

apagarDeEmergencia(bomba);   // una Bomba ES un Actuador
```

Una referencia o un puntero a la base puede apuntar a un objeto de cualquier derivada. Eso permite escribir funciones que trabajan con "cualquier actuador".

### 3. Sin `virtual`, gana el tipo de la referencia

```cpp
class Actuador {
public:
  void describir() const { Serial.println("actuador genérico"); }
};

class Bomba : public Actuador {
public:
  void describir() const { Serial.println("bomba de riego"); }
};

void mostrar(const Actuador& a) { a.describir(); }

Bomba bomba;
bomba.describir();   // "bomba de riego"
mostrar(bomba);      // "actuador genérico"
```

Sin `virtual`, el compilador decide qué método llamar al compilar, mirando el tipo de la variable. En `mostrar`, la variable es `Actuador&`, así que llama a `Actuador::describir`, aunque el objeto real sea una bomba.

### 4. Con `virtual`, gana el objeto real

```cpp
class Actuador {
public:
  virtual void describir() const { Serial.println("actuador genérico"); }
  virtual ~Actuador() = default;
};

class Bomba : public Actuador {
public:
  void describir() const override { Serial.println("bomba de riego"); }
};

mostrar(bomba);      // "bomba de riego"
```

Con `virtual`, la decisión se toma al ejecutar: cada objeto lleva un puntero oculto a una tabla con sus métodos virtuales (la *vtable*), y la llamada pasa por esa tabla. El costo es un puntero extra por objeto y una indirección por llamada, despreciable en un ESP32.

`virtual ~Actuador() = default;` es un destructor virtual. Hace falta cuando un objeto derivado puede destruirse a través de un puntero a la base (`delete punteroABase;`): sin él, solo se ejecuta el destructor de la base. Regla simple: si una clase tiene algún método `virtual`, dale un destructor `virtual`.

### 5. `override` y las funciones virtuales puras

```cpp
class SensorTemperatura {
public:
  virtual float leerCelsius() = 0;          // virtual pura: sin implementación
  virtual ~SensorTemperatura() = default;
};

class SensorAnalogico : public SensorTemperatura {
public:
  float leerCelsius() override { /* ... */ return 24.5f; }
};

// SensorTemperatura s;   // no compila: la clase es abstracta
```

El `= 0` marca una función **virtual pura**: la base no la implementa y obliga a cada derivada a hacerlo. Una clase con funciones virtuales puras es *abstracta*: no se pueden crear objetos de ese tipo, solo de sus derivadas. Se usa como **interfaz**: describe qué se puede pedir, sin decir cómo.

`override` va en cada redefinición. Si la firma no coincide exactamente con la de la base (nombre, parámetros, `const`), el compilador da error:

```cpp
class SensorRoto : public SensorTemperatura {
public:
  float leerCelcius() override;   // error: 'leerCelcius' marked 'override', but does not override
};
```

### 6. Callbacks por herencia

Muchas librerías usan exactamente este mecanismo para avisarte de eventos. La librería define una clase base con métodos virtuales vacíos, vos heredás, redefinís los que te interesan y le pasás tu objeto. Cuando ocurre el evento, la librería llama al método a través de un puntero a la base, y como es virtual, se ejecuta el tuyo.

```cpp
class MisCallbacks : public BLEServerCallbacks {
  void onConnect(BLEServer* servidor) override { /* ... */ }
  void onDisconnect(BLEServer* servidor) override { /* ... */ }
};

servidor->setCallbacks(new MisCallbacks());
```

### 7. Herencia o composición

La herencia expresa "es un": una bomba es un actuador. Si la relación es "tiene un" (el control de riego tiene una bomba y un sensor), lo que corresponde es guardar esos objetos como miembros, como en el ejemplo 3 de [B.2](/conceptos/b-2). A eso se lo llama composición, y en firmware suele ser la mejor opción por defecto, como se ve en [1.2](/conceptos/1-2). La herencia brilla en dos casos: interfaces con implementaciones intercambiables y callbacks de librerías.

## Ejemplos

### Ejemplo 1. La misma llamada, con y sin `virtual`

```cpp virtual.ino
class SinVirtual {
public:
  void nombre() const { Serial.println("base"); }
};
class DerivadaSinVirtual : public SinVirtual {
public:
  void nombre() const { Serial.println("derivada"); }
};

class ConVirtual {
public:
  virtual void nombre() const { Serial.println("base"); }
  virtual ~ConVirtual() = default;
};
class DerivadaConVirtual : public ConVirtual {
public:
  void nombre() const override { Serial.println("derivada"); }
};

void setup() {
  Serial.begin(115200);

  DerivadaSinVirtual a;
  const SinVirtual& refA = a;
  refA.nombre();   // base

  DerivadaConVirtual b;
  const ConVirtual& refB = b;
  refB.nombre();   // derivada
}

void loop() {}
```

### Ejemplo 2. Los callbacks BLE del nodo sensor

El nodo sensor es un servidor BLE. Cuando el controlador se desconecta (porque se reinició, o porque se alejó), el nodo tiene que volver a anunciarse para que lo encuentren.

```cpp nodo-ble.ino
#include <BLEDevice.h>
#include <BLEServer.h>

volatile bool controladorConectado = false;

class CallbacksServidor : public BLEServerCallbacks {
  void onConnect(BLEServer* servidor) override {
    controladorConectado = true;
  }

  void onDisconnect(BLEServer* servidor) override {
    controladorConectado = false;
    BLEDevice::startAdvertising();   // volver a anunciarse
  }
};

void setup() {
  Serial.begin(115200);
  BLEDevice::init("nodo-norte");
  BLEServer* servidor = BLEDevice::createServer();
  servidor->setCallbacks(new CallbacksServidor());   // vive todo el programa
  BLEDevice::startAdvertising();
}

void loop() {
  static bool anterior = false;
  if (controladorConectado != anterior) {
    anterior = controladorConectado;
    Serial.println(anterior ? "controlador conectado" : "controlador desconectado");
  }
}
```

La librería guarda un puntero a `BLEServerCallbacks` y, cuando hay una conexión, llama a `onConnect` a través de él. Como el método es virtual, se ejecuta el de `CallbacksServidor`. Los callbacks corren en la tarea de BLE, no en la de `loop()`, por eso hacen lo mínimo y comunican el cambio con una variable `volatile` (ver [B.11](/conceptos/b-11)). El `new` sin `delete` es una reserva "para siempre", como se explica en [B.8](/conceptos/b-8). Los detalles de BLE están en [0.9](/conceptos/0-9).

### Ejemplo 3. Una interfaz para sensores intercambiables

El controlador lee la temperatura de varios lugares del invernadero con sensores distintos. Para probar la lógica de ventilación sin hardware, también hace falta un sensor simulado. Todos se ven igual desde el control.

```cpp sensores.ino
class SensorTemperatura {
public:
  virtual bool leer() = 0;                     // true si la lectura salió bien
  virtual float celsius() const = 0;
  virtual const char* nombre() const = 0;
  virtual ~SensorTemperatura() = default;
};

// Un sensor analógico tipo TMP36
class SensorAnalogico : public SensorTemperatura {
public:
  SensorAnalogico(uint8_t pin, const char* nombre) : _pin(pin), _nombre(nombre) {}

  bool leer() override {
    int mv = analogReadMilliVolts(_pin);
    if (mv < 100 || mv > 2000) return false;   // fuera de rango: sensor desconectado
    _celsius = (mv - 500) / 10.0f;
    return true;
  }
  float celsius() const override { return _celsius; }
  const char* nombre() const override { return _nombre; }

private:
  uint8_t _pin;
  const char* _nombre;
  float _celsius = 0.0f;
};

// Un sensor simulado para probar sin hardware
class SensorSimulado : public SensorTemperatura {
public:
  SensorSimulado(float inicial, float paso) : _celsius(inicial), _paso(paso) {}

  bool leer() override {
    _celsius += _paso;                         // la temperatura sube de a poco
    return true;
  }
  float celsius() const override { return _celsius; }
  const char* nombre() const override { return "simulado"; }

private:
  float _celsius;
  float _paso;
};

SensorAnalogico sensorNorte(1, "norte");
SensorAnalogico sensorSur(2, "sur");
SensorSimulado sensorPrueba(26.0f, 0.5f);

SensorTemperatura* sensores[] = {&sensorNorte, &sensorSur, &sensorPrueba};

float temperaturaMaxima() {
  float maxima = -100.0f;
  for (SensorTemperatura* s : sensores) {
    if (!s->leer()) {
      Serial.printf("sensor %s sin lectura\n", s->nombre());
      continue;
    }
    if (s->celsius() > maxima) maxima = s->celsius();
  }
  return maxima;
}

void setup() {
  Serial.begin(115200);
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 2000) {
    ultimo = millis();
    Serial.printf("máxima: %.1f C\n", temperaturaMaxima());
  }
}
```

`temperaturaMaxima` no sabe ni le importa qué tipo de sensor tiene cada posición del arreglo: solo usa la interfaz. Agregar un sensor I2C mañana es escribir una clase nueva que herede de `SensorTemperatura`; el control no se toca. El arreglo es de punteros porque el polimorfismo funciona con punteros y referencias, nunca con copias (ver el tercer error común). El `for (SensorTemperatura* s : sensores)` recorre el arreglo elemento por elemento.

## Errores comunes

### Redefinir sin `override` y con la firma equivocada

```cpp
// Mal: compila, y la librería nunca lo llama
class Callbacks : public BLEServerCallbacks {
  void onDisconect(BLEServer* s) { BLEDevice::startAdvertising(); }
};

// Bien: con override, el error de tipeo no compila
class Callbacks : public BLEServerCallbacks {
  void onDisconnect(BLEServer* s) override { BLEDevice::startAdvertising(); }
};
```

Escribí `override` en toda redefinición, sin excepción. Lo mismo vale para un `const` que falta o sobra: `float celsius() override` no redefine `float celsius() const`.

### Olvidar `virtual` en la base

```cpp
// Mal
class SensorTemperatura {
public:
  float leerCelsius() { return 0.0f; }   // sin virtual
};

// Bien
class SensorTemperatura {
public:
  virtual float leerCelsius() = 0;
  virtual ~SensorTemperatura() = default;
};
```

Sin `virtual`, las llamadas a través de punteros a la base ejecutan siempre la versión de la base. Si además las derivadas usan `override`, el compilador te avisa, porque no hay nada virtual que redefinir.

### Pasar por valor y perder la derivada

```cpp
// Mal: se copia solo la parte de la base
void informar(SensorTemperatura s);   // ni siquiera compila si la base es abstracta
void informar(Actuador a);            // con una base concreta, compila y "corta" el objeto

// Bien
void informar(const Actuador& a);
void informar(SensorTemperatura& s);
```

Copiar un objeto derivado en una variable de la base se llama *slicing*: la copia es un objeto de la base y pierde todo lo de la derivada. Con clases polimórficas, siempre referencias o punteros.

### Base sin destructor virtual

```cpp
// Mal
class SensorTemperatura {
public:
  virtual float leerCelsius() = 0;
};
SensorTemperatura* s = new SensorI2C();
delete s;   // solo corre el destructor de la base

// Bien
class SensorTemperatura {
public:
  virtual float leerCelsius() = 0;
  virtual ~SensorTemperatura() = default;
};
```

En firmware es raro destruir sensores, pero el destructor virtual no cuesta nada y evita el problema el día que pase.

## Ejercicio

El controlador tiene una función de emergencia que apaga todos los actuadores, y cada actuador debería registrar en el monitor serie qué hizo. Pero la función siempre imprime "actuador apagado", y el ventilador nunca cierra su ventana al apagarse. Corregí las clases.

```cpp emergencia.ino
class Actuador {
public:
  void apagar() { Serial.println("actuador apagado"); }
};

class Bomba : public Actuador {
public:
  void apagar() {
    digitalWrite(4, LOW);
    Serial.println("bomba apagada");
  }
};

class Ventilador : public Actuador {
public:
  void apagar(bool cerrarVentana) {
    digitalWrite(5, LOW);
    if (cerrarVentana) digitalWrite(7, LOW);
    Serial.println("ventilador apagado");
  }
};

Bomba bomba;
Ventilador ventilador;
Actuador* actuadores[] = {&bomba, &ventilador};

void apagarTodo() {
  for (Actuador* a : actuadores) {
    a->apagar();
  }
}
```

<details>
<summary>Pista</summary>

Hay dos problemas. Uno es de la base. El otro es una firma que no coincide: si le agregás `override` a cada redefinición, el compilador te lo señala.

</details>

<details>
<summary>Ver solución</summary>

```cpp emergencia.ino
class Actuador {
public:
  virtual void apagar() = 0;
  virtual ~Actuador() = default;
};

class Bomba : public Actuador {
public:
  void apagar() override {
    digitalWrite(4, LOW);
    Serial.println("bomba apagada");
  }
};

class Ventilador : public Actuador {
public:
  void apagar() override {
    digitalWrite(5, LOW);
    digitalWrite(7, LOW);          // en una emergencia, siempre cerrar
    Serial.println("ventilador apagado");
  }
};
```

`apagar` no era `virtual`, así que `a->apagar()` llamaba siempre a `Actuador::apagar`. Además, `Ventilador::apagar(bool)` tenía un parámetro que la base no tiene, así que era otra función, que nadie llamaba. Al agregar `override`, el compilador marca ese método. La corrección fue quitar el parámetro y decidir qué hace el ventilador en una emergencia.

La base pasó a ser abstracta (`= 0`) porque un "actuador genérico" no tiene nada que apagar. Si en algún momento se agrega un actuador nuevo y alguien se olvida de implementar `apagar`, el código no compila. Los pines deberían venir del constructor, pero eso no cambia el problema.

</details>

## Resumen

- `class B : public A` hace que `B` tenga todo lo de `A` y se pueda usar donde se espera un `A`.
- Sin `virtual`, el método que se llama depende del tipo de la variable. Con `virtual`, depende del objeto real.
- `override` en cada redefinición: convierte un error de firma en un error de compilación.
- `= 0` declara una función virtual pura. Una clase con funciones virtuales puras es una interfaz y no se puede instanciar.
- El polimorfismo funciona con referencias y punteros. Pasar por valor corta el objeto.
- Las librerías como BLE usan este mecanismo para los callbacks: heredás y redefinís.
