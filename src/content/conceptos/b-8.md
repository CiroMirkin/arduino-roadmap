Un programa guarda sus datos en tres zonas de memoria. La **memoria estática** tiene las variables globales y las `static`, y vive todo el programa. El **stack** tiene las variables locales, y se libera solo cuando termina cada función. El **heap** tiene lo que se pide explícitamente con `new`, y vive hasta que alguien lo libera con `delete`. En un ESP32 con unos pocos cientos de KB de RAM, saber dónde vive cada cosa es la diferencia entre un controlador que funciona meses y uno que se reinicia cada tres días.

## Por qué te importa

En JavaScript o Python, un recolector de basura libera la memoria que ya no se usa. En C++ no existe: lo que pedís con `new` queda ocupado hasta que llames a `delete`, y si te olvidás, se pierde. Una pérdida de 64 bytes por minuto no se nota en una prueba de diez minutos; a los dos días el controlador del invernadero se queda sin memoria y se reinicia de madrugada, con la bomba encendida.

El stack tiene otro problema: es chico. En el ESP32, la tarea que ejecuta `loop()` tiene 8 KB. Un arreglo local de 4000 lecturas lo desborda, y el equipo se reinicia con un mensaje sobre un "stack canary" que no explica mucho si no sabés qué es el stack.

## Paso a paso

### 1. Las tres zonas

```cpp
uint32_t riegosHoy = 0;               // estática: existe todo el programa

void registrarLectura(float t) {
  float convertida = t * 1.8f + 32;   // stack: existe mientras dura la llamada
  static uint32_t llamadas = 0;       // estática, aunque esté dentro de una función
  llamadas++;

  float* copia = new float(t);        // heap: existe hasta el delete
  delete copia;
}
```

| Zona | Qué guarda | Cuándo se libera | Tamaño en un ESP32 |
|---|---|---|---|
| Estática | globales y `static` | nunca (al apagar) | lo que declares, fijo al compilar |
| Stack | variables locales, parámetros | al salir de la función, solo | 8 KB para la tarea de `loop()` |
| Heap | lo pedido con `new` o `malloc` | cuando llamás a `delete` o `free` | lo que queda de la RAM, unos 200 a 300 KB |

`String`, `std::vector` y muchas clases de librerías usan el heap por dentro, aunque vos no escribas `new`.

### 2. El stack: automático pero chico

Cada vez que se llama una función, sus variables locales se apilan arriba de las de la función que la llamó; al terminar, se desapilan. Es rapidísimo y no hay nada que liberar a mano.

El límite es el tamaño. En el ESP32 cada tarea de FreeRTOS tiene su propio stack de tamaño fijo (ver [2.4](/conceptos/2-4)), y la tarea del `loop()` de Arduino tiene 8 KB por defecto. Si las variables locales de la cadena de llamadas superan eso, el ESP32 lo detecta y se reinicia:

```text
***ERROR*** A stack overflow in task loopTask has been detected.
```

o bien `Stack canary watchpoint triggered (loopTask)`. La regla: en el stack, variables chicas. Un arreglo de más de unos cientos de bytes va como `static`, global, o en el heap.

### 3. El heap: `new` y `delete`

```cpp
float* temperatura = new float(24.5f);   // reserva un float y lo inicializa
Serial.println(*temperatura);
delete temperatura;                      // lo libera
temperatura = nullptr;                   // ya no apunta a nada válido

uint8_t* buffer = new uint8_t[256];      // reserva un arreglo
// ... usar buffer[0] a buffer[255] ...
delete[] buffer;                         // arreglo: delete[]
```

`new` devuelve un puntero a la memoria reservada (ver [B.2](/conceptos/b-2)). Lo reservado con `new` se libera con `delete`, y lo reservado con `new[]` con `delete[]`. Hay tres formas clásicas de equivocarse:

- **Fuga**: nunca llamar a `delete`. La memoria queda ocupada para siempre.
- **Uso después de liberar**: usar el puntero después del `delete`. Lee memoria que ya puede ser de otra cosa.
- **Doble liberación**: llamar a `delete` dos veces sobre el mismo puntero. Corrompe el heap y suele terminar en un reinicio.

### 4. Fragmentación

Aunque no haya fugas, el heap puede quedar inservible. Supongamos que el programa reserva tres bloques de 10 KB, libera el primero y el tercero, y deja el del medio. Hay 20 KB libres en total, pero en dos huecos de 10 KB. Una reserva de 15 KB falla.

Con muchas reservas y liberaciones de tamaños distintos durante días, el heap queda lleno de huecos chicos. El ESP32 permite ver las dos cosas:

```cpp
Serial.printf("heap libre: %u, bloque más grande: %u\n",
              static_cast<unsigned>(ESP.getFreeHeap()),
              static_cast<unsigned>(ESP.getMaxAllocHeap()));
```

Si el primer número es estable pero el segundo baja con los días, hay fragmentación. La causa más común en Arduino es la clase `String` en código que se ejecuta seguido, como vas a ver en [B.12](/conceptos/b-12).

### 5. Reservas "para siempre"

```cpp
void setup() {
  BLEServer* servidor = BLEDevice::createServer();
  servidor->setCallbacks(new CallbacksServidor());   // sin delete, a propósito
}
```

En firmware es normal crear con `new` objetos que tienen que vivir hasta que se apague el equipo, y no liberarlos nunca. No es una fuga: se reserva una vez, no se acumula. Muchas librerías de Arduino, como la de BLE, están diseñadas para usarse así. Lo peligroso es el mismo `new` dentro de `loop()` o de un evento que se repite.

### 6. `std::unique_ptr`: el `delete` automático

```cpp
#include <memory>

void procesar() {
  std::unique_ptr<uint8_t[]> buffer = std::make_unique<uint8_t[]>(1024);
  if (!leerDatos(buffer.get(), 1024)) {
    return;                 // el buffer se libera solo
  }
  analizar(buffer.get());
}                           // y acá también
```

`std::unique_ptr` es un objeto que guarda un puntero y llama a `delete` automáticamente cuando él mismo se destruye, en cualquier salida de la función. `make_unique` reserva y crea el `unique_ptr` en un paso, y `.get()` da el puntero común para pasarlo a funciones que lo esperan. Funciona en el ESP32 sin problemas.

A esta técnica (un objeto cuyo destructor libera el recurso) se la llama RAII, y es la forma estándar en C++ moderno de no olvidarse nunca de liberar algo.

### 7. Reglas prácticas para firmware

- Lo que vive todo el programa: global o `static`, o `new` una vez en `setup()`.
- Lo temporal y chico: variable local, en el stack.
- Lo temporal y grande: un buffer `static` que se reutiliza, o `unique_ptr` si de verdad hace falta reservarlo cada vez.
- Evitá `new` dentro de `loop()` y de los eventos frecuentes.
- Monitoreá `getFreeHeap()` y `getMaxAllocHeap()` en las pruebas largas.

## Ejemplos

### Ejemplo 1. Ver el heap antes y después

```cpp heap-basico.ino
void mostrarHeap(const char* momento) {
  Serial.printf("%-18s libre: %6u  bloque max: %6u\n", momento,
                static_cast<unsigned>(ESP.getFreeHeap()),
                static_cast<unsigned>(ESP.getMaxAllocHeap()));
}

void setup() {
  Serial.begin(115200);
  mostrarHeap("al arrancar");

  uint8_t* buffer = new uint8_t[20000];
  mostrarHeap("tras new 20000");

  delete[] buffer;
  mostrarHeap("tras delete[]");
}

void loop() {}
```

Vas a ver que el heap libre baja unos 20 KB después del `new` y vuelve después del `delete[]`. Los números exactos dependen de la placa y de qué librerías estén incluidas.

### Ejemplo 2. Tres formas de tener un buffer para cada mensaje

El controlador arma un mensaje de texto cada 10 segundos para enviar al backend. Hay tres formas de conseguir la memoria:

```cpp buffers.ino
void armarMensaje(char* destino, size_t tam) {
  snprintf(destino, tam, "{\"temperatura\":%.1f}", 24.5f);
}

// 1. Mal: pierde 256 bytes cada vez que se llama
void enviarConFuga() {
  char* mensaje = new char[256];
  armarMensaje(mensaje, 256);
  Serial.println(mensaje);
}

// 2. Bien: en el stack, se libera solo. 256 bytes es poco para 8 KB.
void enviarConStack() {
  char mensaje[256];
  armarMensaje(mensaje, sizeof(mensaje));
  Serial.println(mensaje);
}

// 3. Bien: un buffer static que se reserva una vez y se reutiliza
void enviarConStatic() {
  static char mensaje[256];
  armarMensaje(mensaje, sizeof(mensaje));
  Serial.println(mensaje);
}

void setup() {
  Serial.begin(115200);
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 10000) {
    ultimo = millis();
    enviarConFuga();   // probá con las tres y mirá ESP.getFreeHeap()
    Serial.printf("heap: %u\n", static_cast<unsigned>(ESP.getFreeHeap()));
  }
}
```

Con `enviarConFuga`, el heap libre baja 256 bytes (un poco más, por el registro interno del heap) en cada envío y nunca se recupera. Con las otras dos, queda estable. Para un buffer de 256 bytes, el stack es la opción natural. La versión `static` sirve para buffers más grandes, a cambio de ocupar esa memoria todo el tiempo y no poder usarse desde dos tareas a la vez.

### Ejemplo 3. Reservar una vez, al arrancar, según la configuración

El controlador guarda un historial de lecturas para el gráfico de la pantalla. El tamaño depende de la configuración guardada (cuántas horas mostrar), así que no se conoce al compilar. Se reserva una sola vez en `setup()` y se monitorea la memoria mientras el equipo funciona.

```cpp historial-dinamico.ino
#include <memory>

struct Lectura {
  float temperatura;
  float humedadSuelo;
};

class Historial {
public:
  bool begin(size_t capacidad) {
    _lecturas = std::make_unique<Lectura[]>(capacidad);   // una sola reserva
    _capacidad = capacidad;
    return _lecturas != nullptr;
  }

  void agregar(const Lectura& l) {
    if (_capacidad == 0) return;
    _lecturas[_siguiente] = l;
    _siguiente = (_siguiente + 1) % _capacidad;
    if (_cantidad < _capacidad) _cantidad++;
  }

  size_t cantidad() const { return _cantidad; }

private:
  std::unique_ptr<Lectura[]> _lecturas;
  size_t _capacidad = 0;
  size_t _siguiente = 0;
  size_t _cantidad = 0;
};

Historial historial;

void informarMemoria() {
  Serial.printf("heap libre %u | bloque max %u | stack loop libre %u\n",
                static_cast<unsigned>(ESP.getFreeHeap()),
                static_cast<unsigned>(ESP.getMaxAllocHeap()),
                static_cast<unsigned>(uxTaskGetStackHighWaterMark(nullptr)));
}

void setup() {
  Serial.begin(115200);
  size_t horas = 24;                        // vendría de la configuración guardada
  size_t lecturasPorHora = 60;              // una por minuto
  if (!historial.begin(horas * lecturasPorHora)) {
    Serial.println("sin memoria para el historial");
  }
  informarMemoria();
}

void loop() {
  static uint32_t ultimaLectura = 0;
  static uint32_t ultimoInforme = 0;

  if (millis() - ultimaLectura >= 60000) {
    ultimaLectura = millis();
    historial.agregar({24.5f, 41.0f});      // acá irían las lecturas reales
  }
  if (millis() - ultimoInforme >= 3600000) {
    ultimoInforme = millis();
    informarMemoria();                      // una vez por hora
  }
}
```

1440 lecturas de 8 bytes son unos 11 KB: no entrarían en el stack, y como global obligarían a fijar el tamaño al compilar. La reserva se hace una vez y nunca se libera mientras el equipo funciona, así que no fragmenta nada. Si la configuración cambia, lo más simple es reiniciar el equipo. `uxTaskGetStackHighWaterMark` devuelve cuánto stack de la tarea actual nunca se llegó a usar (en el ESP32, en bytes); si se acerca a cero, el stack está por desbordarse. Con estos tres números registrados cada hora, una prueba de una semana te dice si hay fugas o fragmentación.

Un detalle de C++: `make_unique` de arreglos inicializa los elementos en cero. Y en el ESP32, si `new` no consigue memoria, el programa aborta y el equipo se reinicia en lugar de devolver `nullptr`, así que el chequeo del `begin` es más una costumbre que una red de seguridad. Para reservas grandes que pueden fallar, el ESP-IDF tiene `heap_caps_malloc`, que sí devuelve `nullptr`.

## Errores comunes

### `new` dentro de `loop()` sin `delete`

```cpp
// Mal
void loop() {
  Lectura* l = new Lectura{leerTemperatura(), leerHumedad()};
  procesar(*l);
}

// Bien: no hace falta el heap
void loop() {
  Lectura l{leerTemperatura(), leerHumedad()};
  procesar(l);
}
```

Si el objeto se usa solo dentro de la función, va en el stack. La mayoría de los `new` en `loop()` sobran.

### Un arreglo local enorme

```cpp
// Mal: 16 KB en un stack de 8 KB
void calcularPromedioDiario() {
  float muestras[4000];
  // ...
}

// Bien: en memoria estática, fuera del stack
void calcularPromedioDiario() {
  static float muestras[4000];
  // ...
}
```

Si de verdad necesitás más stack en la tarea del loop, el core de Arduino para ESP32 tiene la macro `SET_LOOP_TASK_STACK_SIZE(16 * 1024);`, que se escribe a nivel global en el sketch. Pero casi siempre la solución correcta es sacar el arreglo del stack.

### Mezclar `new[]` con `delete`

```cpp
// Mal
uint8_t* buffer = new uint8_t[128];
delete buffer;      // comportamiento indefinido

// Bien
delete[] buffer;
// o mejor, sin delete a mano:
auto buffer2 = std::make_unique<uint8_t[]>(128);
```

### Usar un puntero después del `delete`

```cpp
// Mal
delete configuracion;
Serial.println(configuracion->umbral);   // memoria liberada

// Bien
delete configuracion;
configuracion = nullptr;                 // usarlo ahora reinicia de inmediato, en lugar de fallar de forma rara después
```

Poner el puntero en `nullptr` después de liberarlo convierte un error impredecible en uno inmediato y fácil de encontrar. Con `unique_ptr`, el problema no existe.

## Ejercicio

Esta función del controlador se llama una vez por minuto. Después de unos días en funcionamiento el equipo se reinicia, y a veces se reinicia apenas se llama, con un error de stack. Encontrá los dos problemas y corregilos.

```cpp envio.ino
struct Lectura {
  float temperatura;
  float humedadSuelo;
  uint32_t momentoMs;
};

size_t copiarUltimasLecturas(Lectura* destino, size_t maximo);
bool armarJson(const Lectura* lecturas, size_t n, char* destino, size_t tam);
bool enviar(const char* json);

bool enviarResumen() {
  Lectura ultimas[2048];
  size_t n = copiarUltimasLecturas(ultimas, 2048);

  char* json = new char[1024];
  if (!armarJson(ultimas, n, json, 1024)) {
    return false;
  }
  bool ok = enviar(json);
  delete[] json;
  return ok;
}
```

<details>
<summary>Pista</summary>

Calculá cuánto ocupa `ultimas`: cada `Lectura` tiene 12 bytes. Y recorré todos los caminos por los que se puede salir de la función.

</details>

<details>
<summary>Ver solución</summary>

```cpp envio.ino
bool enviarResumen() {
  static Lectura ultimas[2048];          // 24 KB fuera del stack
  size_t n = copiarUltimasLecturas(ultimas, 2048);

  static char json[1024];                // reservado una vez, sin new
  if (!armarJson(ultimas, n, json, sizeof(json))) {
    return false;                        // ya no hay nada que liberar
  }
  return enviar(json);
}
```

`ultimas` ocupa 2048 × 12 = 24.576 bytes, el triple del stack de la tarea del loop: ese es el reinicio inmediato. Pasarlo a `static` lo saca del stack.

El `json` reservado con `new[]` se perdía cada vez que `armarJson` fallaba, porque ese `return` no pasaba por el `delete[]`. Después de días de fallos ocasionales, el heap se agotaba. Un buffer `static` elimina el problema y además evita reservar y liberar cada minuto. Otra solución válida sería `auto json = std::make_unique<char[]>(1024);`, que se libera solo en cualquier `return`.

Los dos `static` hacen que la función no se pueda llamar desde dos tareas al mismo tiempo, porque compartirían los buffers. En el controlador se llama solo desde `loop()`, así que no es un problema.

</details>

## Resumen

- Globales y `static` viven todo el programa; las locales viven en el stack hasta que termina la función; lo pedido con `new` vive en el heap hasta el `delete`.
- El stack de la tarea de `loop()` tiene 8 KB en el ESP32: los arreglos grandes van como `static`, globales o en el heap.
- Cada `new` necesita su `delete` (y cada `new[]`, su `delete[]`) en todos los caminos de salida. `std::unique_ptr` lo hace automáticamente.
- Un `new` en `setup()` para un objeto que vive todo el programa no es una fuga. Un `new` en `loop()` sin `delete` sí.
- Si `getFreeHeap()` está estable pero `getMaxAllocHeap()` baja, el heap se está fragmentando.
