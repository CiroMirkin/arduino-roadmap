Casi todo el código que maneja tiempo da por ciertas cosas que no lo son: que el reloj del equipo tiene la hora correcta, que la hora siempre avanza, que un día tiene 24 horas, que todos los equipos y servidores están de acuerdo en qué hora es. Cada supuesto falso produce un tipo de bug conocido: lecturas fechadas en 1970, riegos que duran de más, reportes diarios con una hora de menos. Conocerlos es la defensa: medir duraciones con un reloj que solo avanza, fechar con una hora sincronizada, guardar todo en UTC, y no confiar ciegamente en la hora que manda un equipo.

## Por qué te importa

El sistema del invernadero vive del tiempo: lecturas con su momento, riegos de una duración, horarios de luces, reportes por día. Y tiene todos los ingredientes para equivocarse: equipos que se quedan sin luz y arrancan sin saber la fecha, nodos que pasan horas en deep sleep, un backend en un servidor y productores en distintas zonas horarias. Estos errores no fallan en el banco de pruebas: aparecen después de un corte de luz, el día que cambia el horario, o en el primer cliente de otro país.

## Cómo funciona

Estos son los supuestos falsos más comunes en un sistema como este, y qué hacer con cada uno.

*"El equipo sabe qué hora es."* El ESP32 no tiene batería de reloj: después de un corte de luz, `time()` arranca en 1970. Recién sabe la hora cuando la sincroniza por NTP, y para eso necesita red. Hasta entonces, cualquier fecha que genere es falsa. Los nodos a batería, ni siquiera eso: mandan la medición sin hora, y el controlador la fecha al recibirla.

*"La hora siempre avanza."* NTP corrige el reloj, y la corrección puede ser hacia atrás. Una duración calculada con `time()` puede dar negativa o enorme. Para duraciones se usa `millis()`, que solo avanza (y su vuelta a cero a los 49,7 días se maneja con la resta, ver [0.1](/conceptos/0-1)).

*"Una vez sincronizado, el reloj queda bien."* El reloj se desvía con el tiempo, y en deep sleep (ver [0.12](/conceptos/0-12)) lo lleva un oscilador interno bastante menos preciso. Se resincroniza periódicamente, por ejemplo una vez por día o al despertar cada tanto.

*"Todos los relojes coinciden."* El controlador, el backend y la base de datos tienen cada uno su reloj. Por eso cada lectura guarda dos momentos: cuándo midió el equipo y cuándo la recibió el servidor (ver [4.3](/conceptos/4-3)). Comparar los dos detecta equipos con el reloj desfasado.

*"La hora local es la hora."* Un momento se guarda en **UTC** (`TIMESTAMPTZ` en PostgreSQL), y la zona horaria se aplica al mostrar o al agrupar. Guardar "14:30" sin zona es ambiguo en cuanto hay un cliente en otro país, o un país que cambia su horario.

*"Un día tiene 24 horas."* En las zonas con horario de verano, un día al año tiene 23 horas y otro 25. Un reporte "por día" se agrupa con la zona horaria de la organización, no cortando de a 24 horas desde UTC.

## Ejemplo

El controlador sincroniza la hora en UTC, mide duraciones con `millis()`, y fecha las lecturas tomadas antes de tener hora cuando por fin la tiene.

```cpp hora.ino
#include <WiFi.h>
#include <time.h>

constexpr time_t INICIO_DEL_SISTEMA = 1735689600;   // 2025-01-01 00:00:00 UTC

struct Lectura {
  uint32_t millisMedicion;   // siempre disponible
  time_t momento;            // 0 mientras no se sepa
  float temperatura;
};

void iniciarHora() {
  // Todo en UTC: la zona horaria la aplica quien muestra los datos.
  configTzTime("UTC0", "pool.ntp.org", "time.google.com");
}

bool horaConfiable() {
  return time(nullptr) > INICIO_DEL_SISTEMA;   // antes de sincronizar, time() da 1970
}

// Completa el momento de una lectura tomada antes de tener hora.
bool fechar(Lectura& l) {
  if (l.momento != 0) return true;
  if (!horaConfiable()) return false;
  uint32_t transcurridoMs = millis() - l.millisMedicion;   // correcto aunque millis() dé la vuelta
  l.momento = time(nullptr) - static_cast<time_t>(transcurridoMs / 1000);
  return true;
}

// Formato ISO 8601 en UTC: "2026-10-05T14:30:00Z"
void formatear(time_t momento, char* destino, size_t largo) {
  struct tm utc;
  gmtime_r(&momento, &utc);
  strftime(destino, largo, "%Y-%m-%dT%H:%M:%SZ", &utc);
}

void setup() {
  Serial.begin(115200);
  WiFi.begin("red", "clave");   // en el equipo real, desde la NVS (ver 6.1)
  iniciarHora();

  Lectura l{millis(), 0, 24.5f};
  while (!fechar(l)) {          // solo para la demo: en el equipo real se reintenta en cada envío
    delay(500);
  }
  char texto[25];
  formatear(l.momento, texto, sizeof(texto));
  Serial.printf("lectura de %s: %.1f °C\n", texto, l.temperatura);
}

void loop() {}
```

En el backend, los reportes diarios se agrupan con la zona horaria de cada organización:

```sql reporte-diario.sql
-- Humedad promedio por día local, para una organización con zona 'America/Argentina/Buenos_Aires'
SELECT date_trunc('day', l.momento AT TIME ZONE o.zona_horaria) AS dia,
       round(avg(l.humedad_suelo), 1)                           AS humedad_promedio
  FROM lecturas l
  JOIN organizaciones o ON o.id = l.organizacion_id
 WHERE l.organizacion_id = $1
   AND l.momento >= now() - interval '30 days'
 GROUP BY 1
 ORDER BY 1;
```

`AT TIME ZONE` convierte el momento guardado en UTC a la hora local de la organización antes de cortar por día, así "el 5 de octubre" es el 5 de octubre del productor y no el de Greenwich. La zona horaria es una columna de `organizaciones` con un nombre de la base de zonas IANA (como `America/Argentina/Buenos_Aires`), que ya conoce los cambios de horario de cada país.

## Cuándo sí y cuándo no

Usá la hora real (sincronizada, en UTC) para:

- fechar lecturas y eventos,
- horarios ("encender las luces a las 6:00", convertido a la zona del invernadero),
- todo lo que se guarda o se compara entre equipos.

Usá `millis()` para:

- duraciones (riego, ventilación, tiempos de espera),
- intervalos entre acciones (cada cuánto medir o enviar),
- cualquier cosa que tenga que funcionar aunque no haya red.

Y desconfiá de la hora que manda un equipo: el backend rechaza momentos imposibles y guarda también la hora de recepción (ver [4.3](/conceptos/4-3) y [6.3](/conceptos/6-3)).

## Resumen

- Después de un corte de luz, el ESP32 no sabe la fecha hasta sincronizar por NTP; antes, `time()` da 1970.
- Las duraciones se miden con `millis()` y una resta; la hora real puede saltar hacia atrás.
- Las lecturas tomadas sin hora guardan su `millis()` y se fechan cuando llega la sincronización.
- Todo se guarda en UTC; la zona horaria se aplica al mostrar y al agrupar por día.
- El backend guarda la hora de medición y la de recepción, y desconfía de la primera.
