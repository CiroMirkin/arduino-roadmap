En [4.4](/conceptos/4-4) el limitador cuenta los pedidos de cada equipo en la memoria del proceso. Con varias instancias detrás de un balanceador (ver [9.1](/conceptos/9-1)), eso deja de funcionar: cada instancia cuenta solo lo que le llega, y un equipo puede hacer el límite multiplicado por la cantidad de instancias. Un **limitador distribuido** guarda los contadores en un lugar compartido y rápido, normalmente **Redis**, y los modifica con **operaciones atómicas**, para que dos instancias que cuentan a la vez no se pisen.

## Por qué te importa

El limitador protege al backend de un equipo con un bug que manda cien pedidos por segundo, y protege el inicio de sesión de quien prueba contraseñas. Si al escalar a dos instancias el límite se duplica sin que nadie lo note, la protección se debilita justo cuando el sistema creció. Y si el contador compartido se implementa con "leer, sumar, escribir", bajo carga cuenta de menos. Son errores que no aparecen en las pruebas con un solo usuario.

## Cómo funciona

*Contadores compartidos.* Todas las instancias leen y escriben el mismo contador por clave (por ejemplo, `limite:equipo:42:<minuto>`). Redis es la opción habitual: está en memoria, responde en menos de un milisegundo y expira las claves solo (ver [5.4](/conceptos/5-4)).

*Atomicidad.* `INCR` suma uno y devuelve el valor nuevo en una sola operación: no hay forma de que dos instancias lean el mismo valor. Para algoritmos que necesitan leer y decidir (como el *token bucket*), se usa un script en Lua, que Redis ejecuta entero sin intercalar otros comandos.

*Ventana fija o deslizante.* La ventana fija (un contador por minuto calendario) es la más simple, pero permite el doble del límite en el borde entre dos minutos. Una ventana deslizante o un token bucket lo suavizan, a cambio de más operaciones.

*Qué pasa si Redis falla.* Hay que decidirlo de antemano. **Fallar abierto** (dejar pasar) mantiene el servicio sin protección; **fallar cerrado** (rechazar) mantiene la protección sin servicio. Para la ingesta de lecturas, abierto, con un límite local en memoria como respaldo; para el inicio de sesión, puede convenir cerrado.

*Latencia.* Cada pedido suma una ida y vuelta a Redis. Por eso Redis va en la misma red que el backend, y la operación es una sola.

## Ejemplo

Una ventana fija con `INCR` y expiración, compartida entre instancias, con un respaldo local si Redis no responde:

```js limitador-distribuido.js
const { createClient } = require("redis");

const redis = createClient({ url: process.env.REDIS_URL });
redis.on("error", (e) => console.error(JSON.stringify({ evento: "redis_error", mensaje: e.message })));

const VENTANA_S = 60;
const respaldoLocal = new Map();   // solo si Redis falla: límite por instancia

async function contar(clave) {
  const ventana = Math.floor(Date.now() / 1000 / VENTANA_S);
  const k = `limite:${clave}:${ventana}`;
  const [n] = await redis.multi()
    .incr(k)
    .expire(k, VENTANA_S * 2)          // la clave se borra sola después de su ventana
    .exec();
  return Number(n);
}

function contarLocal(clave) {
  const ventana = Math.floor(Date.now() / 1000 / VENTANA_S);
  const k = `${clave}:${ventana}`;
  const n = (respaldoLocal.get(k) || 0) + 1;
  respaldoLocal.set(k, n);
  if (respaldoLocal.size > 10000) respaldoLocal.clear();   // que no crezca sin fin
  return n;
}

function limitePorEquipo(maximo) {
  return async (req, res, next) => {
    const clave = `equipo:${req.equipo.id}`;
    let n;
    try {
      n = await contar(clave);
    } catch {
      n = contarLocal(clave);           // fallar abierto, con un límite por instancia
    }
    if (n > maximo) {
      res.set("Retry-After", String(VENTANA_S));
      return res.status(429).json({ error: "demasiados pedidos" });
    }
    next();
  };
}

module.exports = { limitePorEquipo, redis };   // redis.connect() al arrancar la app

// router.post("/api/v1/lecturas", autenticarEquipo, limitePorEquipo(30), ingesta);
```

La clave incluye el número de ventana, así cada minuto empieza un contador nuevo y no hace falta reiniciar nada. `INCR` y `EXPIRE` van en un `MULTI`, que Redis ejecuta junto: el contador nunca queda sin expiración. Volver a poner la expiración en cada pedido no molesta, porque la clave es de una sola ventana y se descarta igual. Si Redis no responde, el limitador sigue funcionando por instancia: menos preciso, pero el backend no se queda sin servicio ni sin ninguna protección. En la práctica, `express-rate-limit` con `rate-limit-redis` hace esto ya probado; escribirlo una vez sirve para entender qué decide cada opción.

## Cuándo sí y cuándo no

Hace falta un limitador distribuido cuando:

- hay más de una instancia del backend y el límite tiene que valer para el total,
- el límite protege algo sensible (inicio de sesión, operaciones caras).

No hace falta cuando:

- hay una sola instancia: el contador en memoria de [4.4](/conceptos/4-4) alcanza,
- el límite es aproximado y tolerable por instancia (dividir el límite por la cantidad de instancias es un atajo aceptable para empezar).

## Resumen

- Con varias instancias, cada una contaría solo lo suyo: los contadores van a un lugar compartido, como Redis.
- Los contadores se modifican con operaciones atómicas (`INCR`, `MULTI`, scripts Lua), nunca con "leer, sumar, escribir".
- La ventana fija es la más simple; la deslizante y el token bucket suavizan los bordes.
- Si Redis falla, se decide por ruta: fallar abierto (con respaldo local) o cerrado.
- Con una sola instancia, el limitador en memoria alcanza.
