Un **patrón de diseño** es una solución conocida para un problema que aparece una y otra vez. No hace falta memorizar decenas: en firmware, tres resuelven la mayoría de las situaciones. La **máquina de estados** ordena un proceso que pasa por etapas. **Observer** permite que un módulo avise que algo pasó sin saber a quién le interesa. **Strategy** permite cambiar un comportamiento (por ejemplo, cómo se decide el riego) sin tocar el código que lo usa.

## Por qué te importa

Cuando el controlador del invernadero crece, aparecen tres problemas recurrentes. Un proceso con etapas (el ciclo de riego: esperar, regar, dejar que el agua se absorba, medir de nuevo) escrito con `if` anidados y banderas sueltas se vuelve imposible de seguir. Un evento que le interesa a varios (una alarma) termina con el módulo que lo detecta llamando a la pantalla, al reporte y a la sirena, y cada interesado nuevo obliga a tocarlo. Y una decisión que tiene varias variantes (regar por humedad, por horario o a mano) termina con un `if (modo == ...)` repetido en diez lugares, que se desincronizan apenas se agrega un modo.

Estos patrones tienen nombre porque el problema es tan común que vale la pena reconocerlo enseguida. Pero también es común aplicarlos donde no hacen falta: la regla es usarlos cuando el problema aparece, no antes.

## Paso a paso

### 1. Máquina de estados

Un proceso que pasa por etapas se modela con un `enum class` de estados y un `switch` que dice qué hacer en cada uno y cuándo pasar al siguiente (ver [B.10](/conceptos/b-10)):

```cpp
enum class EstadoRiego : uint8_t { Esperando, Regando, Absorbiendo };

void actualizarRiego() {
  switch (estado) {
    case EstadoRiego::Esperando:
      if (humedad() < 35.0f) { abrirValvula(); cambiarA(EstadoRiego::Regando); }
      break;
    case EstadoRiego::Regando:
      if (enEsteEstadoMs() > 60000) { cerrarValvula(); cambiarA(EstadoRiego::Absorbiendo); }
      break;
    case EstadoRiego::Absorbiendo:
      if (enEsteEstadoMs() > 300000) cambiarA(EstadoRiego::Esperando);   // medir recién después
      break;
  }
}
```

Cada estado tiene reglas claras, y en cada momento el proceso está en un solo estado. El tema completo, con transiciones, eventos y cómo reemplazar `if/else` gigantes, está en [2.2](/conceptos/2-2).

### 2. Observer: avisar sin conocer a los interesados

En Observer hay un **sujeto** (el que detecta algo) y **observadores** (los interesados). Los observadores se **suscriben** al sujeto; cuando pasa algo, el sujeto **notifica** a todos los suscriptos.

```cpp
class ObservadorAlarmas {
public:
  virtual void alActivarse(TipoAlarma tipo) = 0;
  virtual ~ObservadorAlarmas() = default;
};

class Alarmas {
public:
  bool suscribir(ObservadorAlarmas& o) {
    if (_cantidad == MAXIMO) return false;
    _observadores[_cantidad++] = &o;
    return true;
  }
  void activar(TipoAlarma tipo) {
    for (size_t i = 0; i < _cantidad; i++) _observadores[i]->alActivarse(tipo);
  }
private:
  static constexpr size_t MAXIMO = 4;
  ObservadorAlarmas* _observadores[MAXIMO] = {};
  size_t _cantidad = 0;
};
```

El módulo de alarmas no conoce a la pantalla ni a la sirena: conoce una interfaz. Agregar un interesado es crear una clase que implemente `alActivarse` y suscribirla en `setup()`. Los callbacks de BLE que viste en [B.9](/conceptos/b-9) son una forma de Observer: la librería es el sujeto, y tu clase de callbacks, el observador.

En firmware conviene un arreglo fijo de observadores (se suscriben una vez, al arrancar) en lugar de una lista que crece con `new`.

### 3. Strategy: intercambiar un comportamiento

En Strategy, una decisión que tiene variantes se define como una **interfaz**, cada variante es una **implementación**, y el código que decide usa la interfaz sin saber cuál está activa:

```cpp
class EstrategiaRiego {
public:
  virtual bool debeRegar(const Lectura& l, uint8_t hora) = 0;
  virtual const char* nombre() const = 0;
  virtual ~EstrategiaRiego() = default;
};

class RiegoPorHumedad : public EstrategiaRiego { /* compara con un umbral */ };
class RiegoPorHorario : public EstrategiaRiego { /* riega en ciertas horas */ };
class RiegoManual     : public EstrategiaRiego { /* nunca decide solo */ };
```

El control tiene un puntero a la estrategia activa y la cambia cuando cambia la configuración. Agregar un modo nuevo es agregar una clase; el control no se toca. Es composición con una interfaz, como en [1.2](/conceptos/1-2).

### 4. Cuándo no usar un patrón

Cada patrón agrega piezas: interfaces, registros, clases. Si hay un solo interesado en un evento y no va a haber más, una llamada directa es más clara que un Observer. Si hay un solo modo de riego, una función alcanza. Una buena señal para introducir el patrón es el **segundo o tercer caso**: cuando aparece el segundo interesado o el tercer modo, y el código empieza a llenarse de condiciones.

### 5. Cuidados en firmware

- **Memoria fija**: observadores y estrategias como objetos globales; el sujeto guarda punteros a ellos, en arreglos de tamaño fijo.
- **Notificaciones cortas**: un observador que tarda bloquea al sujeto y a los demás observadores. Igual que con las interrupciones, conviene anotar y procesar después.
- **Sin reentrada**: un observador no debería volver a llamar al sujeto que lo está notificando; eso puede generar notificaciones dentro de notificaciones.

## Ejemplos

### Ejemplo 1. Strategy para el modo de riego

```cpp estrategias.ino
struct Lectura {
  float humedadSuelo;
};

class EstrategiaRiego {
public:
  virtual bool debeRegar(const Lectura& l, uint8_t hora, bool regando) = 0;
  virtual const char* nombre() const = 0;
  virtual ~EstrategiaRiego() = default;
};

class RiegoPorHumedad : public EstrategiaRiego {
public:
  RiegoPorHumedad(float minima, float maxima) : _minima(minima), _maxima(maxima) {}
  bool debeRegar(const Lectura& l, uint8_t, bool regando) override {
    return regando ? l.humedadSuelo < _maxima : l.humedadSuelo < _minima;
  }
  const char* nombre() const override { return "por humedad"; }
private:
  float _minima, _maxima;
};

class RiegoPorHorario : public EstrategiaRiego {
public:
  RiegoPorHorario(uint8_t desde, uint8_t hasta) : _desde(desde), _hasta(hasta) {}
  bool debeRegar(const Lectura&, uint8_t hora, bool) override {
    return hora >= _desde && hora < _hasta;
  }
  const char* nombre() const override { return "por horario"; }
private:
  uint8_t _desde, _hasta;
};

class RiegoManual : public EstrategiaRiego {
public:
  bool debeRegar(const Lectura&, uint8_t, bool regando) override { return regando; }   // no cambia nada solo
  const char* nombre() const override { return "manual"; }
};

RiegoPorHumedad porHumedad(35.0f, 55.0f);
RiegoPorHorario porHorario(6, 7);
RiegoManual manual;

EstrategiaRiego* estrategias[] = {&porHumedad, &porHorario, &manual};
EstrategiaRiego* activa = &porHumedad;
bool regando = false;

void controlar(const Lectura& l, uint8_t hora) {
  bool nuevo = activa->debeRegar(l, hora, regando);   // el control no sabe qué estrategia es
  if (nuevo != regando) {
    regando = nuevo;
    Serial.printf("[%s] riego %s\n", activa->nombre(), regando ? "ON" : "OFF");
  }
}

void setup() {
  Serial.begin(115200);
  delay(500);
  for (EstrategiaRiego* e : estrategias) {
    activa = e;
    regando = false;
    controlar({30.0f}, 6);    // suelo seco, 6 de la mañana
  }
}

void loop() {}
```

`controlar` es igual para los tres modos. Cambiar de modo es cambiar el puntero `activa`, por ejemplo cuando el usuario elige otro modo en la pantalla. Un modo nuevo (regar según la temperatura y la hora, por ejemplo) es una clase nueva, sin tocar `controlar`.

### Ejemplo 2. Observer para las alarmas

```cpp observer-alarmas.ino
enum class TipoAlarma : uint8_t { TemperaturaAlta, TanqueVacio, NodoSinNoticias };

const char* nombre(TipoAlarma t) {
  switch (t) {
    case TipoAlarma::TemperaturaAlta: return "temperatura alta";
    case TipoAlarma::TanqueVacio:     return "tanque vacío";
    case TipoAlarma::NodoSinNoticias: return "nodo sin noticias";
  }
  return "?";
}

class ObservadorAlarmas {
public:
  virtual void alActivarse(TipoAlarma tipo) = 0;
  virtual ~ObservadorAlarmas() = default;
};

class Alarmas {
public:
  bool suscribir(ObservadorAlarmas& o) {
    if (_cantidad == MAXIMO) return false;
    _observadores[_cantidad++] = &o;
    return true;
  }

  void activar(TipoAlarma tipo) {
    if (_notificando) return;            // evita notificaciones anidadas
    _notificando = true;
    for (size_t i = 0; i < _cantidad; i++) {
      _observadores[i]->alActivarse(tipo);
    }
    _notificando = false;
  }

private:
  static constexpr size_t MAXIMO = 4;
  ObservadorAlarmas* _observadores[MAXIMO] = {};
  size_t _cantidad = 0;
  bool _notificando = false;
};

class PantallaAlarmas : public ObservadorAlarmas {
public:
  void alActivarse(TipoAlarma t) override { Serial.printf("[pantalla] mostrar: %s\n", nombre(t)); }
};

class ReporteAlarmas : public ObservadorAlarmas {
public:
  void alActivarse(TipoAlarma t) override {
    Serial.printf("[reporte] encolar evento: %s\n", nombre(t));   // a la cola de 0.10
  }
};

class Sirena : public ObservadorAlarmas {
public:
  void alActivarse(TipoAlarma t) override {
    if (t == TipoAlarma::TanqueVacio) Serial.println("[sirena] sonar");   // solo le interesa una
  }
};

Alarmas alarmas;
PantallaAlarmas pantallaAlarmas;
ReporteAlarmas reporteAlarmas;
Sirena sirena;

void setup() {
  Serial.begin(115200);
  alarmas.suscribir(pantallaAlarmas);
  alarmas.suscribir(reporteAlarmas);
  alarmas.suscribir(sirena);

  alarmas.activar(TipoAlarma::TemperaturaAlta);
  alarmas.activar(TipoAlarma::TanqueVacio);
}

void loop() {}
```

`Alarmas` no incluye ni conoce a la pantalla, al reporte ni a la sirena. Cada observador decide qué hacer con cada tipo de alarma: la sirena ignora todo menos el tanque vacío. La bandera `_notificando` protege contra un observador que, por error, active otra alarma desde dentro de `alActivarse`.

### Ejemplo 3. Los tres juntos en el ciclo de riego

El ciclo de riego es una máquina de estados. La decisión de empezar a regar la toma la estrategia activa. Y cada cambio de estado se notifica a los observadores (pantalla, reporte).

```cpp ciclo-riego.ino
struct Lectura { float humedadSuelo; };

enum class EstadoRiego : uint8_t { Esperando, Regando, Absorbiendo };

const char* nombre(EstadoRiego e) {
  switch (e) {
    case EstadoRiego::Esperando:   return "esperando";
    case EstadoRiego::Regando:     return "regando";
    case EstadoRiego::Absorbiendo: return "absorbiendo";
  }
  return "?";
}

class EstrategiaRiego {
public:
  virtual bool debeEmpezar(const Lectura& l) = 0;
  virtual ~EstrategiaRiego() = default;
};

class PorHumedad : public EstrategiaRiego {
public:
  bool debeEmpezar(const Lectura& l) override { return l.humedadSuelo < 35.0f; }
};

class ObservadorRiego {
public:
  virtual void alCambiar(EstadoRiego anterior, EstadoRiego nuevo) = 0;
  virtual ~ObservadorRiego() = default;
};

class CicloRiego {
public:
  CicloRiego(EstrategiaRiego& estrategia, uint32_t riegoMs, uint32_t absorcionMs)
    : _estrategia(&estrategia), _riegoMs(riegoMs), _absorcionMs(absorcionMs) {}

  void usarEstrategia(EstrategiaRiego& e) { _estrategia = &e; }
  bool suscribir(ObservadorRiego& o) {
    if (_cantidad == 4) return false;
    _observadores[_cantidad++] = &o;
    return true;
  }

  void actualizar(const Lectura& l) {
    uint32_t enEstado = millis() - _desdeMs;
    switch (_estado) {
      case EstadoRiego::Esperando:
        if (_estrategia->debeEmpezar(l)) cambiarA(EstadoRiego::Regando);
        break;
      case EstadoRiego::Regando:
        if (enEstado >= _riegoMs) cambiarA(EstadoRiego::Absorbiendo);
        break;
      case EstadoRiego::Absorbiendo:
        if (enEstado >= _absorcionMs) cambiarA(EstadoRiego::Esperando);
        break;
    }
  }

  EstadoRiego estado() const { return _estado; }

private:
  void cambiarA(EstadoRiego nuevo) {
    EstadoRiego anterior = _estado;
    _estado = nuevo;
    _desdeMs = millis();
    // acá se abriría o cerraría la válvula según el estado nuevo
    for (size_t i = 0; i < _cantidad; i++) _observadores[i]->alCambiar(anterior, nuevo);
  }

  EstrategiaRiego* _estrategia;
  uint32_t _riegoMs;
  uint32_t _absorcionMs;
  EstadoRiego _estado = EstadoRiego::Esperando;
  uint32_t _desdeMs = 0;
  ObservadorRiego* _observadores[4] = {};
  size_t _cantidad = 0;
};

class LogRiego : public ObservadorRiego {
public:
  void alCambiar(EstadoRiego a, EstadoRiego n) override {
    Serial.printf("%lu s: %s -> %s\n", static_cast<unsigned long>(millis() / 1000), nombre(a), nombre(n));
  }
};

PorHumedad porHumedad;
CicloRiego ciclo(porHumedad, 5000, 10000);   // tiempos cortos para probar
LogRiego logRiego;

void setup() {
  Serial.begin(115200);
  ciclo.suscribir(logRiego);
}

void loop() {
  ciclo.actualizar({30.0f});   // suelo siempre seco: el ciclo se repite
}
```

Cada patrón resuelve una parte distinta: la máquina de estados ordena el proceso en el tiempo, la estrategia decide cuándo empezar, y los observadores se enteran de los cambios sin que el ciclo los conozca. El estado "absorbiendo" evita un error clásico: medir la humedad justo al cortar el riego, antes de que el agua llegue al sensor, y volver a regar de más.

## Errores comunes

### Aplicar un patrón sin necesidad

```cpp
// Mal: una interfaz, un registro y una clase para un solo interesado que nunca va a cambiar
class ObservadorLed { /* ... */ };

// Bien: una llamada directa, hasta que aparezca el segundo interesado
void alActivarAlarma() { encenderLedRojo(); }
```

### `if` por modo repartidos por todo el código

```cpp
// Mal: cada lugar que depende del modo repite la condición
if (modo == MODO_HUMEDAD) { /* ... */ } else if (modo == MODO_HORARIO) { /* ... */ }
// ... y lo mismo en la pantalla, en el reporte, en la configuración...

// Bien: una estrategia por modo; cada lugar usa la interfaz
activa->debeRegar(lectura, hora, regando);
```

### Observadores lentos

```cpp
// Mal: el observador envía al backend dentro de la notificación
void alActivarse(TipoAlarma t) override { enviarHttpAhora(t); }   // bloquea segundos

// Bien: encolar y enviar después, desde loop()
void alActivarse(TipoAlarma t) override { cola.agregar(t); }
```

### Suscripciones con `new` en tiempo de ejecución

Crear observadores con `new` cada vez que se necesitan, y olvidar desuscribirlos, deja punteros a objetos destruidos en el sujeto. En firmware, observadores globales suscriptos una vez en `setup()`.

## Ejercicio

El controlador tiene tres modos de ventilación: por temperatura, por humedad del aire (para evitar hongos) y manual. Hoy el modo se maneja así, y alguien agregó un cuarto modo ("por temperatura y humedad") en `controlarVentilacion` pero se olvidó de la pantalla, que muestra "?" con ese modo. Rediseñalo con Strategy.

```cpp ventilacion-modos.ino
int modoVentilacion = 0;   // 0 temperatura, 1 humedad, 2 manual, 3 temperatura y humedad

void controlarVentilacion(float t, float h) {
  if (modoVentilacion == 0) { abrir(t > 30.0f); }
  else if (modoVentilacion == 1) { abrir(h > 85.0f); }
  else if (modoVentilacion == 3) { abrir(t > 30.0f || h > 85.0f); }
}

const char* nombreModo() {
  if (modoVentilacion == 0) return "temperatura";
  if (modoVentilacion == 1) return "humedad";
  if (modoVentilacion == 2) return "manual";
  return "?";
}
```

```cpp ventilacion-strategy.ino
class EstrategiaVentilacion {
public:
  // devuelve true si las ventanas deben quedar abiertas
  virtual bool decidir(float temperatura, float humedad, bool abiertas) = 0;
  virtual const char* nombre() const = 0;
  virtual ~EstrategiaVentilacion() = default;
};

class PorTemperatura : public EstrategiaVentilacion {
public:
  bool decidir(float t, float, bool abiertas) override { return abiertas ? t > 27.0f : t > 30.0f; }
  const char* nombre() const override { return "temperatura"; }
};

class PorHumedad : public EstrategiaVentilacion {
public:
  bool decidir(float, float h, bool abiertas) override { return abiertas ? h > 75.0f : h > 85.0f; }
  const char* nombre() const override { return "humedad"; }
};

class Manual : public EstrategiaVentilacion {
public:
  bool decidir(float, float, bool abiertas) override { return abiertas; }
  const char* nombre() const override { return "manual"; }
};

class PorTemperaturaYHumedad : public EstrategiaVentilacion {
public:
  bool decidir(float t, float h, bool abiertas) override {
    return _temp.decidir(t, h, abiertas) || _hum.decidir(t, h, abiertas);
  }
  const char* nombre() const override { return "temperatura y humedad"; }
private:
  PorTemperatura _temp;   // composición: reutiliza las otras dos
  PorHumedad _hum;
};

PorTemperatura porTemperatura;
EstrategiaVentilacion* modoActual = &porTemperatura;

void controlarVentilacion(float t, float h) {
  abrir(modoActual->decidir(t, h, ventanasAbiertas()));
}

const char* nombreModo() { return modoActual->nombre(); }
```

Cada modo trae su propia decisión y su propio nombre, así que es imposible agregar un modo y olvidarse del nombre: si falta `nombre()`, la clase no compila, porque es una función virtual pura. Además se agregó un margen entre abrir y cerrar en cada modo, que la versión original no tenía. El modo combinado reutiliza los otros dos por composición, en lugar de copiar sus condiciones.

## Resumen

- Máquina de estados: un `enum class` de etapas y un `switch` con las reglas de cada una. Ordena procesos en el tiempo (ver [2.2](/conceptos/2-2)).
- Observer: un sujeto notifica a los observadores suscriptos sin conocerlos. Sirve cuando varios módulos se interesan por un mismo evento.
- Strategy: una interfaz con una implementación por variante. Sirve cuando un comportamiento cambia según un modo o una configuración.
- En firmware: objetos globales, arreglos fijos de observadores, notificaciones cortas y sin reentrada.
- Introducí un patrón cuando aparece el segundo o tercer caso, no antes.
