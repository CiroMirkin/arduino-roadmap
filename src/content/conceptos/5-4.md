Una **caché** guarda una copia de un resultado que es costoso de obtener, para devolverla rápido la próxima vez. **Redis** es una base de datos en memoria, muy rápida, que se usa casi siempre para esto: el backend le pregunta "¿tenés el tablero de la organización 3?", y si lo tiene, lo devuelve en un milisegundo sin consultar PostgreSQL. La contracara es que la copia puede estar **desactualizada**, y decidir cuánto tiempo vale y cuándo se descarta es la parte difícil.

## Por qué te importa

Algunas consultas del sistema del invernadero se repiten mucho con el mismo resultado: el tablero con la última lectura de cada equipo (que muchos usuarios abren y recargan), los permisos de un usuario (que se verifican en cada pedido, ver [4.2](/conceptos/4-2)), el resumen diario de una zona. Si cada una va a la base cada vez, la base trabaja de más justo en las horas de más uso.

Una caché bien usada reduce mucho esa carga. Mal usada, muestra datos viejos donde no corresponde, o peor, mezcla datos de distintas organizaciones. Además, Redis aparece en otros lugares del backend: los contadores compartidos del rate limiting (ver [4.4](/conceptos/4-4)) y las colas (ver [4.6](/conceptos/4-6)).

## Cómo funciona

**Cache-aside**, el patrón más común:

1. Buscar en la caché.
2. Si está (*hit*), devolverlo.
3. Si no está (*miss*), consultar la base, guardar el resultado en la caché con un tiempo de vida, y devolverlo.

**Tiempo de vida (TTL).** Cada copia se guarda con una expiración (por ejemplo, 30 segundos). Al vencer, Redis la borra sola, y el siguiente pedido la vuelve a calcular. El TTL define cuán desactualizado puede estar un dato: se elige según cuánto importa que esté al día.

**Invalidación.** Cuando se sabe que un dato cambió (alguien editó la configuración de una zona), se borra su copia de la caché enseguida, en lugar de esperar al TTL. El TTL sigue siendo la red de seguridad por si alguna invalidación se olvida.

**Claves.** Las claves tienen un formato fijo que incluye todo lo que hace único al resultado, empezando por la organización: `tablero:org:3`, `config:org:3:zona:12`. Una clave sin organización es un dato compartido entre todas.

**Qué cachear.** Resultados que se piden mucho, cambian poco o toleran un pequeño atraso, y son costosos de calcular. **Qué no**: datos que tienen que estar exactos en el momento (el cupo de agua de [5.2](/conceptos/5-2)), ni resultados que dependen de cada usuario en particular sin incluirlo en la clave.

**Avalancha** (*cache stampede*). Si una clave muy pedida vence, cientos de pedidos simultáneos encuentran la caché vacía y van todos a la base a la vez. Se mitiga con TTL con algo de azar, o haciendo que solo un pedido recalcule mientras los demás esperan.

## Ejemplo

El tablero de cada organización, con cache-aside, TTL e invalidación. Con la librería `redis` de Node.

```js tablero.js
const { createClient } = require("redis");

const redis = createClient({ url: process.env.REDIS_URL });
redis.on("error", (e) => console.error(JSON.stringify({ evento: "redis_error", error: e.message })));
// await redis.connect();   // al iniciar el servidor

const TTL_TABLERO_S = 30;

function claveTablero(organizacionId) {
  return `tablero:org:${organizacionId}`;
}

async function tableroDesdeLaBase(db, organizacionId) {
  const { rows } = await db.query(
    `SELECT DISTINCT ON (dispositivo_id) dispositivo_id, momento,
            temperatura::float8 AS temperatura, humedad_suelo
       FROM lecturas
      WHERE organizacion_id = $1 AND momento >= now() - interval '1 hour'
      ORDER BY dispositivo_id, momento DESC`,
    [organizacionId]
  );
  return rows;
}

async function obtenerTablero(db, organizacionId) {
  const clave = claveTablero(organizacionId);
  try {
    const enCache = await redis.get(clave);
    if (enCache) return JSON.parse(enCache);              // hit
  } catch (e) {
    // si Redis falla, seguir sin caché: la base sigue funcionando
  }

  const datos = await tableroDesdeLaBase(db, organizacionId);   // miss
  const ttl = TTL_TABLERO_S + Math.floor(Math.random() * 10);   // algo de azar contra la avalancha
  redis.set(clave, JSON.stringify(datos), { EX: ttl }).catch(() => {});
  return datos;
}

// Al cambiar algo que afecta al tablero (por ejemplo, se revoca un equipo):
async function invalidarTablero(organizacionId) {
  await redis.del(claveTablero(organizacionId)).catch(() => {});
}

module.exports = { obtenerTablero, invalidarTablero };

// Ruta: router.get("/tablero", requierePermiso("lecturas.ver"),
//                  async (req, res) => res.json(await obtenerTablero(req.db, req.usuario.organizacion_id)));
```

La clave incluye la organización, que sale de la sesión del usuario (ver [4.1](/conceptos/4-1)), así que es imposible recibir el tablero de otra. Si Redis no responde, el backend sigue funcionando consultando la base: la caché acelera, pero no puede ser un punto de falla. Con cien usuarios recargando el tablero cada 10 segundos, la base pasa de diez consultas por segundo a una cada 30-40 segundos por organización. Las lecturas nuevas aparecen con hasta 40 segundos de atraso, aceptable para un tablero que se actualiza cada minuto.

## Cuándo sí y cuándo no

Conviene una caché cuando:

- una consulta se repite mucho con el mismo resultado (tableros, catálogos, permisos),
- el resultado tolera unos segundos o minutos de atraso,
- la consulta es costosa, o la base está cerca de su límite.

No conviene (o todavía no hace falta) cuando:

- el dato tiene que estar exacto en el momento (cupos, saldos, el estado de una alarma recién reconocida),
- la consulta ya es rápida con un buen índice (ver [4.5](/conceptos/4-5)): primero los índices, después la caché,
- el volumen es bajo: una caché agrega una pieza que mantener y una fuente de bugs de datos desactualizados.

## Resumen

- Una caché guarda copias de resultados costosos para devolverlas rápido; Redis es la opción habitual.
- Cache-aside: buscar en la caché, y si no está, calcular, guardar con un tiempo de vida y devolver.
- El TTL define cuánto atraso se acepta; la invalidación descarta una copia apenas se sabe que cambió.
- Las claves incluyen la organización: la caché respeta el mismo aislamiento que la base.
- Si Redis falla, el sistema sigue funcionando sin caché. Primero índices; caché cuando hace falta.
