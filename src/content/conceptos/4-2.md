**RBAC** (*Role-Based Access Control*, control de acceso basado en roles) es la forma más común de decidir qué puede hacer cada usuario. En lugar de asignar permisos persona por persona, se definen **roles** (admin, operario, solo lectura), cada rol tiene un conjunto de **permisos** (ver lecturas, accionar el riego, administrar usuarios), y cada usuario tiene un rol **en cada organización**. El código no pregunta "¿es admin?", sino "¿tiene el permiso `riego.accionar`?", y un solo lugar define qué permisos trae cada rol.

## Por qué te importa

En el sistema del invernadero conviven usuarios con responsabilidades distintas: el dueño de la empresa administra usuarios y configuración; el encargado del invernadero acciona el riego manual y reconoce alarmas; un asesor externo solo mira los datos. Si cualquiera puede hacer cualquier cosa, un asesor podría desactivar el riego, o un operario podría darse de alta como admin.

En [4.1](/conceptos/4-1) viste cómo evitar que una organización vea los datos de otra. RBAC es la segunda capa: **dentro** de una organización, cada usuario solo puede hacer lo que su rol permite. Las dos se verifican en el backend, en cada pedido.

## Paso a paso

### 1. Autenticación y autorización

Cada pedido pasa por dos preguntas, en orden:

1. **Autenticación**: ¿quién es? Lo resuelve la sesión del usuario (o la clave de un equipo, ver [3.4](/conceptos/3-4)). Si falla, `401`.
2. **Autorización**: ¿puede hacer esto, en esta organización? Lo resuelve RBAC. Si falla, `403`.

### 2. Roles y permisos

Un **permiso** es una acción concreta, con un nombre estable: `lecturas.ver`, `riego.accionar`, `alarmas.reconocer`, `config.editar`, `usuarios.administrar`. Un **rol** es un conjunto de permisos:

| Permiso | solo lectura | operario | admin |
|---|---|---|---|
| `lecturas.ver` | ✓ | ✓ | ✓ |
| `alarmas.reconocer` | | ✓ | ✓ |
| `riego.accionar` | | ✓ | ✓ |
| `config.editar` | | | ✓ |
| `usuarios.administrar` | | | ✓ |

El código siempre pregunta por **permisos**. Si mañana aparece el rol "agrónomo" (puede ver y editar la configuración de riego, pero no accionar ni administrar usuarios), se agrega una columna a esta tabla y ningún otro código cambia.

### 3. Membresías: el rol es por organización

Una misma persona puede pertenecer a varias organizaciones con roles distintos: admin en su empresa, solo lectura en la de un cliente al que asesora. Por eso el rol no es un campo del usuario, sino de su **membresía**:

```sql
CREATE TABLE membresias (
  usuario_id       BIGINT NOT NULL REFERENCES usuarios(id),
  organizacion_id  BIGINT NOT NULL REFERENCES organizaciones(id),
  rol              TEXT NOT NULL CHECK (rol IN ('solo_lectura', 'operario', 'admin')),
  PRIMARY KEY (usuario_id, organizacion_id)
);
```

En cada pedido, la organización activa sale de la sesión (el usuario eligió en cuál trabajar), y el rol que vale es el de esa membresía.

### 4. Verificar el permiso en cada ruta

La verificación va en un **middleware** que se pone delante de cada ruta, con el permiso que esa ruta necesita:

```js
router.post("/invernaderos/:id/riego", requierePermiso("riego.accionar"), regarAhora);
```

Así, revisar quién puede hacer qué es leer las rutas: cada una declara su permiso. Una ruta sin `requierePermiso` debería llamar la atención en una revisión.

### 5. Denegar por defecto

Si un rol no figura en la tabla, o un permiso no está asignado, la respuesta es **no**. Nunca al revés ("todo permitido salvo lo prohibido"): un permiso nuevo que alguien se olvidó de configurar tiene que quedar cerrado, no abierto.

### 6. Registrar quién hizo qué

Las acciones con efecto (accionar el riego, cambiar la configuración, dar de alta un usuario) se guardan en un **registro de auditoría**: quién, en qué organización, qué hizo y cuándo. Cuando algo sale mal ("¿quién apagó el riego el domingo?"), es la única forma de saberlo. También sirve para detectar intentos de acceso denegados.

## Ejemplos

### Ejemplo 1. Los permisos en un solo lugar

```js permisos.js
const PERMISOS_POR_ROL = {
  solo_lectura: ["lecturas.ver"],
  operario: ["lecturas.ver", "alarmas.reconocer", "riego.accionar"],
  admin: [
    "lecturas.ver", "alarmas.reconocer", "riego.accionar",
    "config.editar", "usuarios.administrar",
  ],
};

function tienePermiso(rol, permiso) {
  const permisos = PERMISOS_POR_ROL[rol];
  return Array.isArray(permisos) && permisos.includes(permiso);   // rol desconocido: no
}

module.exports = { tienePermiso, PERMISOS_POR_ROL };

// tienePermiso("operario", "riego.accionar")        -> true
// tienePermiso("solo_lectura", "riego.accionar")    -> false
// tienePermiso("inventado", "lecturas.ver")         -> false
```

Toda la política de acceso está en un objeto. Un rol que no existe no tiene ningún permiso: denegar por defecto. Esta función es pura y se prueba con una tabla de casos, igual que la lógica del firmware (ver [2.8](/conceptos/2-8)).

### Ejemplo 2. Middleware y rutas

El middleware verifica el permiso en la organización activa y registra los intentos denegados. Cada ruta declara lo que necesita.

```js autorizacion.js
const { tienePermiso } = require("./permisos");

// Supone que la autenticación ya dejó req.usuario = { id, organizacion_id, rol }
function requierePermiso(permiso) {
  return (req, res, next) => {
    if (!req.usuario) {
      return res.status(401).json({ error: "no autenticado" });
    }
    if (!tienePermiso(req.usuario.rol, permiso)) {
      console.warn(JSON.stringify({
        evento: "acceso_denegado",
        usuario: req.usuario.id,
        organizacion: req.usuario.organizacion_id,
        permiso,
        ruta: req.originalUrl,
      }));
      return res.status(403).json({ error: "no tenés permiso para esta acción" });
    }
    next();
  };
}

module.exports = { requierePermiso };
```

```js rutas-invernadero.js
const express = require("express");
const { requierePermiso } = require("./autorizacion");

const router = express.Router();

router.get("/invernaderos/:id/lecturas", requierePermiso("lecturas.ver"), verLecturas);
router.post("/invernaderos/:id/riego", requierePermiso("riego.accionar"), regarAhora);
router.post("/alarmas/:id/reconocer", requierePermiso("alarmas.reconocer"), reconocerAlarma);
router.put("/invernaderos/:id/config", requierePermiso("config.editar"), editarConfig);
router.post("/usuarios", requierePermiso("usuarios.administrar"), invitarUsuario);

module.exports = router;
```

Las rutas se leen como una tabla de acceso. El registro de accesos denegados va en formato JSON para poder buscarlo después (ver [4.7](/conceptos/4-7)). Fijate en que el permiso es sobre la organización activa: `regarAhora` además tiene que verificar que el invernadero `:id` sea de esa organización, como en [4.1](/conceptos/4-1).

### Ejemplo 3. Membresías, organización activa y auditoría

Al iniciar sesión, el usuario elige con qué organización trabajar. El backend carga su rol en esa organización desde la tabla de membresías, y las acciones con efecto quedan registradas.

```js sesion.js
// Middleware que se ejecuta después de validar la sesión (req.sesion.usuarioId)
async function cargarMembresia(req, res, next) {
  const organizacionActiva = req.sesion.organizacionActiva;   // la eligió el usuario al entrar
  const { rows } = await req.db.query(
    `SELECT organizacion_id, rol
       FROM membresias
      WHERE usuario_id = $1 AND organizacion_id = $2`,
    [req.sesion.usuarioId, organizacionActiva]
  );
  if (rows.length === 0) {
    return res.status(403).json({ error: "no pertenecés a esta organización" });
  }
  req.usuario = { id: req.sesion.usuarioId, ...rows[0] };
  next();
}

async function auditar(req, accion, detalle) {
  await req.db.query(
    `INSERT INTO auditoria (usuario_id, organizacion_id, accion, detalle, momento)
     VALUES ($1, $2, $3, $4, now())`,
    [req.usuario.id, req.usuario.organizacion_id, accion, JSON.stringify(detalle)]
  );
}

// Ejemplo de uso en una ruta con efecto
async function regarAhora(req, res) {
  const invernadero = await req.repo.invernadero(req.params.id);   // filtro por organización (4.1)
  if (!invernadero) return res.status(404).json({ error: "invernadero no encontrado" });

  const segundos = Number(req.body.segundos);
  if (!Number.isInteger(segundos) || segundos < 10 || segundos > 600) {
    return res.status(400).json({ error: "segundos entre 10 y 600" });
  }
  // encolar el comando para el controlador (por HTTP o MQTT, ver 3.2)
  await auditar(req, "riego.accionar", { invernadero: invernadero.id, segundos });
  res.status(202).json({ ok: true });
}

module.exports = { cargarMembresia, auditar, regarAhora };
```

La organización activa viene de la sesión, pero igual se verifica que el usuario tenga una membresía ahí: una sesión manipulada no da acceso a una organización ajena. `regarAhora` combina las tres capas: el permiso (en el middleware de la ruta), la pertenencia del invernadero (con el repositorio de [4.1](/conceptos/4-1)) y la validación de los datos (ver [6.3](/conceptos/6-3)). El `202 Accepted` indica que la orden se aceptó y se va a ejecutar después, cuando el controlador la reciba.

## Errores comunes

### Preguntar por roles en el código

```js
// Mal
if (req.usuario.rol === "admin" || req.usuario.rol === "operario") { /* ... */ }

// Bien
router.post("/invernaderos/:id/riego", requierePermiso("riego.accionar"), regarAhora);
```

### Confiar en la interfaz

Ocultar o deshabilitar un botón no impide el pedido: se puede enviar con cualquier herramienta HTTP. Cada ruta verifica su permiso en el backend (ver [6.2](/conceptos/6-2)).

### Permitir por defecto

```js
// Mal: un rol nuevo o mal escrito tiene acceso a todo
if (PERMISOS_POR_ROL[rol] && !PERMISOS_POR_ROL[rol].includes(permiso)) return denegar();

// Bien: sin rol conocido o sin el permiso, no
if (!tienePermiso(rol, permiso)) return denegar();
```

### Que un usuario pueda cambiar su propio rol

La ruta que modifica membresías necesita `usuarios.administrar`, y además conviene impedir que un admin se quite a sí mismo el rol si es el único admin, o que alguien eleve su propio rol. Las reglas sobre el propio usuario son un caso especial que se olvida fácil.

### Un rol global en lugar de por organización

Un campo `rol` en la tabla de usuarios hace que el admin de una organización sea admin en todas las que pertenece. El rol va en la membresía.

Cambian dos cosas: la tabla de permisos y la restricción de la base de datos que lista los roles válidos. Las rutas que ya usaban `requierePermiso` no cambian. La ruta vieja, en cambio, preguntaba `rol !== "admin"`: el agrónomo, que debería poder editar la configuración, recibiría un 403. Ese es el costo de preguntar por roles: cada rol nuevo obliga a buscar todos esos `if`. Con `requierePermiso("config.editar")`, el agrónomo entra sin tocar la ruta.

## Resumen

- Autenticación: quién sos. Autorización: qué podés hacer. Las dos, en el backend, en cada pedido.
- RBAC: los roles agrupan permisos, y el código pregunta siempre por permisos, definidos en un solo lugar.
- El rol es por organización: una tabla de membresías (usuario, organización, rol).
- Cada ruta declara su permiso con un middleware; denegar por defecto.
- Las acciones con efecto se registran en una auditoría: quién, dónde, qué y cuándo.
