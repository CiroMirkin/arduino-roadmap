**Rate limiting** (limitar la tasa de pedidos) es poner un tope a cuántos pedidos puede hacer cada cliente en un período de tiempo. Cuando un cliente lo supera, el backend responde `429 Too Many Requests` en lugar de procesar el pedido, idealmente diciendo cuándo puede volver a intentar. Protege al servidor de clientes que se portan mal (por bug o a propósito) y reparte la capacidad de forma justa entre todos.

## Por qué te importa

El peligro más común para el backend del invernadero no es un ataque: es un **bug de firmware**. Un controlador con un error que lo hace reenviar la misma lectura en un bucle, sin espera, puede generar cientos de pedidos por segundo. Multiplicado por todos los equipos con esa versión, el backend se satura y deja de atender también a los equipos sanos y a la app de los productores.

El rate limiting pone un techo a lo que cada equipo puede consumir, así un equipo roto no afecta a los demás. También protege rutas costosas (reportes, exportaciones) y la ruta de inicio de sesión contra intentos de adivinar contraseñas.

## Paso a paso

### 1. Qué se limita y por qué clave

El límite se cuenta por una **clave** que identifica al cliente:

| Tipo de pedido | Clave del límite |
|---|---|
| ingesta de un equipo | el dispositivo (de su clave, ver [3.4](/conceptos/3-4)) |
| app de un usuario | el usuario, y además la organización |
| sin autenticar (login, alta) | la dirección IP |

Para pedidos autenticados, la IP es una mala clave: todos los equipos de un invernadero suelen salir a internet por el mismo router y comparten la IP pública. Con un límite por IP, un equipo roto bloquea a sus vecinos.

### 2. Ventana fija

La forma más simple: contar los pedidos de cada clave en ventanas de tiempo fijas (por ejemplo, "como máximo 60 por minuto"), y volver a cero al empezar cada minuto. Tiene un defecto: en el borde entre dos ventanas, un cliente puede hacer 60 pedidos al final de un minuto y 60 más al principio del siguiente, 120 en pocos segundos.

### 3. Token bucket

El **balde de fichas** (*token bucket*) resuelve eso y además permite ráfagas controladas:

- Cada clave tiene un balde con una **capacidad** (por ejemplo, 20 fichas).
- El balde se **recarga** a un ritmo fijo (por ejemplo, 1 ficha por segundo), sin pasar de la capacidad.
- Cada pedido gasta una ficha. Sin fichas, `429`.

```text
capacidad 20, recarga 1/s

t=0     balde lleno (20)        llegan 20 pedidos seguidos -> pasan todos, balde en 0
t=0     llega el pedido 21      -> 429, Retry-After: 1
t=5     el balde tiene 5        -> pueden pasar 5 pedidos más
```

Es ideal para los equipos: un controlador que vuelve de un corte puede enviar un lote de pendientes de golpe (la ráfaga), pero no puede sostener más de una ficha por segundo.

### 4. La respuesta: 429 con `Retry-After`

Cuando se rechaza un pedido, la respuesta dice cuánto esperar:

```text
HTTP/1.1 429 Too Many Requests
Retry-After: 3
```

Un equipo bien escrito (ver [3.5](/conceptos/3-5)) respeta ese valor en lugar de su propio backoff. También existen encabezados estándar que informan el límite y lo que queda (`RateLimit-Limit`, `RateLimit-Remaining`), útiles para clientes que quieren ajustarse antes de chocar con el límite.

### 5. Dónde se guardan los contadores

Con un solo servidor, los contadores pueden vivir en memoria. Con varias instancias del backend detrás de un balanceador, cada una contaría solo lo suyo, y un cliente podría hacer el límite multiplicado por la cantidad de instancias. En ese caso, los contadores van a un almacén compartido y rápido, como Redis (ver [5.4](/conceptos/5-4)). El diseño de un limitador distribuido se ve en [9.2](/conceptos/9-2).

### 6. Otras protecciones que van juntas

El rate limiting controla cuántos pedidos; otras defensas controlan cuánto puede costar cada uno:

- **Tamaño máximo del cuerpo** (`express.json({ limit: "64kb" })`): un pedido de 50 MB se rechaza antes de procesarlo.
- **Máximo de elementos por lote** (ver [4.3](/conceptos/4-3)).
- **Tiempos máximos** en las consultas a la base de datos.
- **Límites más estrictos para rutas costosas**, como reportes o exportaciones.

## Ejemplos

### Ejemplo 1. Un token bucket

La lógica del balde, sin Express, para entender cómo funciona y poder probarla.

```js token-bucket.js
class TokenBucket {
  constructor(capacidad, fichasPorSegundo) {
    this.capacidad = capacidad;
    this.recarga = fichasPorSegundo;
    this.fichas = capacidad;            // empieza lleno
    this.ultimaMs = Date.now();
  }

  // Intenta gastar una ficha. Devuelve 0 si se puede, o los segundos a esperar.
  intentar(ahoraMs = Date.now()) {
    const transcurrido = Math.max(0, (ahoraMs - this.ultimaMs) / 1000);   // nunca negativo
    this.fichas = Math.min(this.capacidad, this.fichas + transcurrido * this.recarga);
    this.ultimaMs = ahoraMs;

    if (this.fichas >= 1) {
      this.fichas -= 1;
      return 0;
    }
    return Math.ceil((1 - this.fichas) / this.recarga);   // cuánto falta para la próxima ficha
  }
}

module.exports = { TokenBucket };

// const balde = new TokenBucket(20, 1);
// const t = Date.now();
// for (let i = 0; i < 22; i++) console.log(i, balde.intentar(t));
//   -> 0 para los primeros 20, después 1 (esperar 1 segundo)
```

No hace falta un temporizador que recargue fichas: cada vez que llega un pedido, se calcula cuántas se recargaron desde el anterior. `ahoraMs` es un parámetro con valor por defecto, así se prueba con tiempos fijos (ver [2.8](/conceptos/2-8)).

### Ejemplo 2. Un middleware por dispositivo

Cada dispositivo tiene su balde. El middleware va después de la autenticación, así conoce al equipo.

```js limite-dispositivos.js
const { TokenBucket } = require("./token-bucket");

function limitePorDispositivo({ capacidad, fichasPorSegundo }) {
  const baldes = new Map();   // dispositivo_id -> TokenBucket

  // Borrar cada tanto los baldes de equipos inactivos, para que el Map no crezca sin fin
  setInterval(() => {
    const limite = Date.now() - 10 * 60 * 1000;
    for (const [id, balde] of baldes) {
      if (balde.ultimaMs < limite) baldes.delete(id);
    }
  }, 60 * 1000).unref();

  return (req, res, next) => {
    const id = req.equipo.id;                       // de autenticarEquipo (3.4)
    let balde = baldes.get(id);
    if (!balde) {
      balde = new TokenBucket(capacidad, fichasPorSegundo);
      baldes.set(id, balde);
    }

    const esperar = balde.intentar();
    if (esperar > 0) {
      res.set("Retry-After", String(esperar));
      return res.status(429).json({ error: "demasiados pedidos", reintentarEnSegundos: esperar });
    }
    next();
  };
}

module.exports = { limitePorDispositivo };

// Uso: 30 pedidos de ráfaga, 1 cada 2 segundos sostenido
// router.post("/api/v1/lecturas", express.json({ limit: "64kb" }), autenticarEquipo,
//             limitePorDispositivo({ capacidad: 30, fichasPorSegundo: 0.5 }), ingesta);
```

Un controlador normal envía un lote por minuto: nunca se acerca al límite. Uno que vuelve de un corte puede vaciar su cola con una ráfaga de hasta 30 pedidos. Uno con un bug que envía sin parar queda limitado a un pedido cada 2 segundos, y recibe `Retry-After` en el resto. `.unref()` hace que el temporizador de limpieza no impida que el proceso de Node termine. Como los baldes están en memoria, esto sirve para una sola instancia del backend.

### Ejemplo 3. Límites distintos con `express-rate-limit`

Para el resto de la API, la librería `express-rate-limit` ofrece ventanas configurables, los encabezados estándar y almacenes compartidos.

```js limites.js
const rateLimit = require("express-rate-limit");

// Inicio de sesión: por IP, estricto (frena los intentos de adivinar contraseñas)
const limiteLogin = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 10,
  standardHeaders: "draft-7",
  legacyHeaders: false,
  message: { error: "demasiados intentos, probá más tarde" },
});

// App de usuarios: por usuario autenticado
const limiteApp = rateLimit({
  windowMs: 60 * 1000,
  limit: 120,
  standardHeaders: "draft-7",
  legacyHeaders: false,
  keyGenerator: (req) => `usuario:${req.usuario.id}`,
});

// Reportes costosos: por organización, muy pocos por minuto
const limiteReportes = rateLimit({
  windowMs: 60 * 1000,
  limit: 5,
  standardHeaders: "draft-7",
  legacyHeaders: false,
  keyGenerator: (req) => `org:${req.usuario.organizacion_id}`,
});

// app.post("/api/login", limiteLogin, login);
// app.use("/api/app", autenticarUsuario, limiteApp);
// app.get("/api/app/reportes/:id", limiteReportes, generarReporte);
// Con varias instancias del backend: agregar la opción store, con un almacén en Redis.

module.exports = { limiteLogin, limiteApp, limiteReportes };
```

Cada tipo de ruta tiene su límite y su clave: la IP antes de autenticar, el usuario para la app en general, y la organización para lo costoso (así una organización no puede saturar los reportes, aunque tenga muchos usuarios). `standardHeaders` agrega los encabezados de límite y `Retry-After` en las respuestas 429. Los límites de la app se ponen después de la autenticación, porque la clave depende del usuario.

## Errores comunes

### Limitar a los equipos por IP

Todos los equipos de un invernadero comparten la IP del router. Para pedidos autenticados, la clave es el equipo o la organización.

### 429 sin `Retry-After`

Sin el encabezado, el equipo reintenta con su propio backoff, sin saber cuándo el servidor va a poder atenderlo.

### Un límite único para todo

El mismo límite para el login, la ingesta y los reportes es demasiado laxo para unos y demasiado estricto para otros. Cada tipo de ruta, su límite.

### Contadores en memoria con varias instancias

Con tres instancias, cada una con sus contadores, el límite real es el triple. Con más de una instancia, un almacén compartido.

### Límites sin ráfaga para los equipos

Un límite de "1 pedido cada 2 segundos" sin capacidad de ráfaga castiga al equipo que vuelve de un corte con pendientes: tarda muchísimo en ponerse al día. El token bucket permite la ráfaga y limita el ritmo sostenido.

## Resumen

- El rate limiting pone un tope de pedidos por cliente y período, y responde `429` con `Retry-After` al superarlo.
- La clave del límite es el equipo, el usuario o la organización para pedidos autenticados; la IP solo antes de autenticar.
- El token bucket permite ráfagas (capacidad) y limita el ritmo sostenido (recarga): ideal para equipos que vuelven de un corte.
- Con varias instancias del backend, los contadores van a un almacén compartido como Redis.
- Se combina con límites de tamaño, de elementos por lote y de tiempo para las operaciones costosas.
