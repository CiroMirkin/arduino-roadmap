Cuando un solo servidor no alcanza (o cuando no se puede depender de uno solo), se corren **varias instancias** del backend y se pone delante un **balanceador de carga**: un componente que recibe todos los pedidos y los reparte entre las instancias. Para que funcione, las instancias tienen que ser **intercambiables**: ninguna puede guardar en su memoria algo que otra necesite (sesiones, contadores, colas). Todo el estado compartido vive afuera, en la base de datos o en Redis. Con eso, agregar capacidad es agregar instancias, y una instancia que se cae solo reduce la capacidad, sin dejar a nadie afuera.

## Por qué te importa

El primer motivo para tener dos instancias no suele ser la carga, sino la **disponibilidad**: con una sola, cada actualización del backend o cada falla deja a todos los equipos sin dónde mandar sus datos (y llenando sus colas, ver [3.5](/conceptos/3-5)). Con dos detrás de un balanceador, se actualiza una por vez y el servicio no se interrumpe.

El problema es que un backend escrito para una sola instancia suele tener estado escondido en memoria: sesiones, los contadores del limitador de [4.4](/conceptos/4-4), un caché, una tarea programada. Con dos instancias, todo eso se rompe de formas sutiles. Saberlo antes permite escribir el backend sin estado desde el principio, que no cuesta casi nada.

## Cómo funciona

*El balanceador* puede ser un proxy como nginx o HAProxy, o un servicio del proveedor de nube. Recibe los pedidos (y normalmente termina HTTPS) y los reparte. Las estrategias comunes: por turnos (*round robin*), a la instancia con menos conexiones abiertas, o por un hash de algo del pedido.

*Los chequeos de salud* son pedidos periódicos a una ruta como `/api/v1/salud`. Si una instancia no responde o responde con error, el balanceador deja de mandarle pedidos hasta que se recupera. La ruta de salud verifica lo que la instancia necesita para trabajar (por ejemplo, que la base responda), sin hacer nada pesado.

*Sin estado en la instancia.* Las sesiones van a la base o a Redis (o se usan tokens firmados que no necesitan guardarse). Los contadores del limitador, a Redis (ver [9.2](/conceptos/9-2)). Los archivos subidos, a un almacenamiento compartido. Las tareas programadas (refrescar resúmenes, buscar equipos callados) tienen que correr en una sola instancia, o usar un bloqueo en la base para que no se ejecuten dos veces.

*Sesiones pegajosas* (*sticky sessions*): el balanceador manda siempre al mismo usuario a la misma instancia. Disimula el estado en memoria, pero si esa instancia se cae, el usuario pierde todo igual, y la carga se reparte peor. Es un parche, no una solución.

*Escalar hacia arriba primero.* Antes de agregar instancias por carga, un servidor más grande suele ser más simple y más barato. Node usa un núcleo por proceso: en un servidor con varios núcleos, varias instancias en la misma máquina ya aprovechan más.

## Ejemplo

Un balanceador con nginx delante de dos instancias del backend, y la ruta de salud:

```nginx nginx.conf (fragmento)
upstream backend_invernadero {
    least_conn;                                  # a la instancia con menos conexiones
    server 10.0.0.11:3000 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:3000 max_fails=3 fail_timeout=10s;
    keepalive 32;
}

server {
    listen 443 ssl;
    server_name api.ejemplo.com;
    # ssl_certificate y ssl_certificate_key ...

    location /api/ {
        proxy_pass http://backend_invernadero;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_next_upstream error timeout;      # solo errores de conexión, no 5xx
    }
}
```

```js salud.js
router.get("/api/v1/salud", async (req, res) => {
  try {
    await req.db.query("SELECT 1");
    res.json({ ok: true });
  } catch {
    res.status(503).json({ ok: false, motivo: "sin base de datos" });
  }
});

// En app.js: confiar en la IP que informa el balanceador (ver 4.4)
// app.set("trust proxy", 1);
```

La versión libre de nginx marca una instancia como caída cuando fallan los pedidos reales (`max_fails`); los chequeos activos a `/api/v1/salud` los hacen nginx Plus, HAProxy y los balanceadores de los proveedores de nube. `proxy_next_upstream` reintenta en la otra instancia solo si no pudo conectarse o se agotó el tiempo: reintentar un `POST` que pudo haberse procesado es seguro únicamente porque la ingesta es idempotente (ver [4.3](/conceptos/4-3)). Detrás del balanceador, todos los pedidos llegan desde su IP: `trust proxy` hace que Express use la del cliente, que importa para el limitador y los logs.

## Cuándo sí y cuándo no

Conviene tener dos o más instancias balanceadas cuando:

- el backend tiene que seguir atendiendo durante actualizaciones y fallas,
- un servidor más grande ya no alcanza, o cuesta más que varios chicos.

Lo que conviene siempre, aunque haya una sola instancia:

- escribir el backend sin estado propio (sesiones y contadores afuera),
- tener una ruta de salud.

No hace falta mientras una sola instancia atiende con holgura y unos minutos de corte durante una actualización son aceptables: los equipos guardan sus datos y los reenvían después.

## Resumen

- Un balanceador reparte los pedidos entre varias instancias del backend y deja de usar las que fallan.
- Las instancias tienen que ser intercambiables: sesiones, contadores y archivos, afuera.
- Las tareas programadas corren una sola vez, no una por instancia.
- Los reintentos del balanceador son seguros solo con operaciones idempotentes.
- El primer motivo suele ser la disponibilidad; para la carga, primero un servidor más grande.
