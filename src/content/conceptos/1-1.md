Separar responsabilidades significa que cada parte del firmware (una clase, un archivo, una función) se ocupe de **una sola cosa**, y que esa cosa sea clara. La definición más práctica: una parte tiene una sola responsabilidad si hay **un solo motivo para cambiarla**. Si la misma clase hay que tocarla cuando cambia el sensor, cuando cambia la regla de riego y cuando cambia el backend, tiene tres responsabilidades mezcladas. Es el primer paso para que un firmware que crece siga siendo entendible.

## Por qué te importa

Casi todo firmware empieza como un solo `.ino` que lee un sensor y enciende algo. Después se agrega el WiFi, la pantalla, un segundo sensor, el envío al backend, la calibración, las alarmas. Cada cosa se agrega donde es más rápido, y a las mil líneas el archivo es un bloque donde todo toca todo.

En ese punto aparecen los problemas que motivan esta parte del roadmap. Cambiar el formato del mensaje al backend rompe el riego porque compartían una variable. Para probar una regla nueva de ventilación hay que tener el invernadero entero conectado. Cuando algo falla a las tres de la mañana, nadie sabe si mirar el código del sensor, el de la red o el del control. Separar responsabilidades no elimina los bugs, pero hace que cada uno quede en un lugar acotado.

## Paso a paso

### 1. El síntoma: una función que hace todo

```cpp
void loop() {
  int mv = analogReadMilliVolts(2);                        // leer el sensor
  float humedad = (2600.0f - mv) / 14.5f;                  // convertir
  if (humedad < 35 && WiFi.status() == WL_CONNECTED) {     // decidir (¿y por qué depende del WiFi?)
    digitalWrite(4, LOW);                                  // actuar
    HTTPClient http;                                       // informar
    http.begin("http://.../riego");
    http.POST("{\"evento\":\"inicio\"}");
    http.end();
    pantalla.drawUTF8(0, 10, "Regando");                   // mostrar
  }
}
```

Seis cosas distintas en diez líneas. Y ya hay un bug escondido: el riego depende de que haya WiFi, porque el envío quedó metido dentro de la decisión.

### 2. Qué es una responsabilidad

Una forma práctica de encontrarlas es preguntarse **qué podría cambiar**, y **quién** pediría ese cambio:

| Si cambia... | Lo pide... | Responsabilidad |
|---|---|---|
| el modelo de sensor de humedad | quien arma el hardware | leer sensores |
| la regla de cuándo regar | quien cultiva | decidir |
| el módulo de relés | quien arma el hardware | manejar actuadores |
| el diseño de la pantalla | quien usa el equipo | mostrar |
| la API del backend | quien desarrolla el backend | comunicar |

Cada fila es un módulo candidato. Cuando dos cosas cambian siempre juntas y por el mismo motivo, probablemente son la misma responsabilidad.

### 3. Separar la decisión del hardware

La separación más valiosa es entre **lo que decide** y **lo que toca el mundo físico**. La decisión de riego no necesita saber de qué pin sale la lectura ni cómo se enciende la bomba: recibe datos y devuelve una decisión.

```cpp
struct Lectura {
  float humedadSuelo;
  bool tanqueConAgua;
};

enum class AccionRiego : uint8_t { Ninguna, Encender, Apagar };

AccionRiego decidirRiego(const Lectura& l, bool regando, float minima, float maxima) {
  if (!l.tanqueConAgua) return regando ? AccionRiego::Apagar : AccionRiego::Ninguna;
  if (!regando && l.humedadSuelo < minima) return AccionRiego::Encender;
  if (regando && l.humedadSuelo > maxima) return AccionRiego::Apagar;
  return AccionRiego::Ninguna;
}
```

Esta función no llama a `analogRead` ni a `digitalWrite`. Se puede probar llamándola con lecturas inventadas, en la placa o incluso en la PC (ver [2.8](/conceptos/2-8)). Si mañana el sensor cambia por uno I2C, esta función no se toca.

### 4. Interfaces chicas entre módulos

Los módulos se comunican mejor con **datos simples** que llamándose entre sí por todos lados. El módulo de sensores produce una `Lectura`; el de control la recibe y produce una decisión; el de actuadores aplica la decisión. Ninguno necesita conocer cómo funcionan los otros por dentro.

```text
Sensores ──Lectura──► Control ──Decisión──► Actuadores
              │                    │
              └──────► Reporte ◄───┘
```

Si el módulo de pantalla necesita mostrar la humedad, recibe la `Lectura`; no le pregunta al sensor.

### 5. `loop()` como coordinador

Con los módulos separados, `loop()` se vuelve un resumen del sistema:

```cpp
void loop() {
  sensores.actualizar();
  if (sensores.hayLecturaNueva()) {
    Lectura l = sensores.ultima();
    AccionRiego accion = decidirRiego(l, riego.activo(), config.minima, config.maxima);
    riego.aplicar(accion);
    pantalla.mostrar(l, riego.activo());
    reporte.registrar(l, accion);
  }
  reporte.actualizar();   // envía cuando puede, sin bloquear
}
```

Quien lee esto entiende en diez segundos qué hace el controlador. Para saber *cómo* lo hace cada parte, abre el archivo de esa parte.

### 6. Cuánto dividir

Dividir también tiene un costo: más archivos, más nombres, más saltos para seguir el código. Algunas señales de que dividiste de más: clases de una sola línea que solo llaman a otra, o tener que abrir cinco archivos para entender una acción simple. Algunas señales de que dividiste de menos: no podés describir qué hace una clase sin usar "y" ("lee los sensores *y* decide *y* envía"), o un cambio chico obliga a tocar muchas partes no relacionadas. El objetivo es que cada pieza tenga una idea clara, no que sea lo más chica posible.

## Ejemplos

### Ejemplo 1. De una función mezclada a tres funciones

La versión del paso 1, separada en lectura, decisión y acción, sin cambiar todavía la estructura de archivos:

```cpp riego-separado.ino
constexpr uint8_t PIN_SUELO = 2;    // el sensor de respaldo (ver 0.2)
constexpr uint8_t PIN_BOMBA = 4;    // relé activo en bajo

struct Lectura {
  float humedadSuelo;
};

Lectura leerSensores() {
  uint32_t mv = analogReadMilliVolts(PIN_SUELO);
  float humedad = (2600.0f - mv) / (2600.0f - 1150.0f) * 100.0f;
  return {constrain(humedad, 0.0f, 100.0f)};
}

bool debeRegar(const Lectura& l, bool regando) {
  if (!regando) return l.humedadSuelo < 35.0f;
  return l.humedadSuelo < 55.0f;                 // seguir hasta llegar al 55 %
}

void aplicarBomba(bool encender) {
  digitalWrite(PIN_BOMBA, encender ? LOW : HIGH);
}

bool regando = false;

void setup() {
  Serial.begin(115200);
  digitalWrite(PIN_BOMBA, HIGH);
  pinMode(PIN_BOMBA, OUTPUT);
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo < 2000) return;
  ultimo = millis();

  Lectura l = leerSensores();
  bool nuevo = debeRegar(l, regando);
  if (nuevo != regando) {
    regando = nuevo;
    aplicarBomba(regando);
    Serial.printf("humedad %.0f%%: %s\n", l.humedadSuelo, regando ? "riego ON" : "riego OFF");
  }
}
```

El cambio parece chico, pero ya permite cosas nuevas: probar `debeRegar` con valores inventados, cambiar el sensor tocando solo `leerSensores`, o reemplazar el relé por un MOSFET tocando solo `aplicarBomba`. Y el riego ya no depende del WiFi.

### Ejemplo 2. Probar la decisión sin hardware

Como `decidirRiego` del paso 3 es una función pura, se puede verificar con una tabla de casos al arrancar la placa, sin sensor ni bomba conectados.

```cpp prueba-decision.ino
struct Lectura {
  float humedadSuelo;
  bool tanqueConAgua;
};

enum class AccionRiego : uint8_t { Ninguna, Encender, Apagar };

AccionRiego decidirRiego(const Lectura& l, bool regando, float minima, float maxima) {
  if (!l.tanqueConAgua) return regando ? AccionRiego::Apagar : AccionRiego::Ninguna;
  if (!regando && l.humedadSuelo < minima) return AccionRiego::Encender;
  if (regando && l.humedadSuelo > maxima) return AccionRiego::Apagar;
  return AccionRiego::Ninguna;
}

struct Caso {
  const char* descripcion;
  Lectura lectura;
  bool regando;
  AccionRiego esperada;
};

const Caso CASOS[] = {
  {"seco, sin regar -> encender",       {20.0f, true},  false, AccionRiego::Encender},
  {"húmedo, sin regar -> nada",         {50.0f, true},  false, AccionRiego::Ninguna},
  {"regando, todavía seco -> nada",     {40.0f, true},  true,  AccionRiego::Ninguna},
  {"regando, ya húmedo -> apagar",      {60.0f, true},  true,  AccionRiego::Apagar},
  {"seco pero tanque vacío -> nada",    {20.0f, false}, false, AccionRiego::Ninguna},
  {"regando y se vacía el tanque -> apagar", {40.0f, false}, true, AccionRiego::Apagar},
};

void setup() {
  Serial.begin(115200);
  delay(500);
  int fallos = 0;
  for (const Caso& c : CASOS) {
    AccionRiego obtenida = decidirRiego(c.lectura, c.regando, 35.0f, 55.0f);
    bool ok = (obtenida == c.esperada);
    if (!ok) fallos++;
    Serial.printf("[%s] %s\n", ok ? " OK " : "FALLA", c.descripcion);
  }
  Serial.printf("%d fallos\n", fallos);
}

void loop() {}
```

Cada caso es una situación del invernadero escrita como datos. Si mañana alguien cambia la regla y rompe el caso del tanque vacío, esta prueba lo muestra en segundos. Con la lógica mezclada con `analogRead` y `digitalWrite`, probar ese caso exigiría vaciar el tanque de verdad. En [2.8](/conceptos/2-8) se ve cómo correr pruebas así en la PC.

### Ejemplo 3. El controlador organizado en módulos

Con las responsabilidades del paso 2, el proyecto del controlador queda así:

```text
controlador/
├── controlador.ino      coordina: setup() y loop()
├── config.h             pines, tiempos y valores por defecto
├── tipos.h              Lectura, AccionRiego, AccionVentilacion: los datos que viajan
├── sensores.h / .cpp    lee y filtra los sensores; produce una Lectura
├── control.h / .cpp     decide riego y ventilación; funciones puras
├── actuadores.h / .cpp  bomba, ventanas, ventilador; aplica decisiones
├── pantalla.h / .cpp    dibuja el estado
└── reporte.h / .cpp     cola de envíos y comunicación con el backend
```

```cpp tipos.h
#pragma once
#include <Arduino.h>

struct Lectura {
  float temperatura;
  float humedadAire;
  float humedadSuelo;
  bool tanqueConAgua;
  uint32_t momentoMs;
};

enum class AccionRiego : uint8_t { Ninguna, Encender, Apagar };
enum class AccionVentanas : uint8_t { Ninguna, Abrir, Cerrar };
```

```cpp control.h
#pragma once
#include "tipos.h"

struct ConfigControl {
  float humedadMinima;
  float humedadMaxima;
  float abrirSobreC;
  float cerrarBajoC;
};

AccionRiego decidirRiego(const Lectura& l, bool regando, const ConfigControl& c);
AccionVentanas decidirVentanas(const Lectura& l, bool abiertas, const ConfigControl& c);
```

```cpp controlador.ino
#include "config.h"
#include "tipos.h"
#include "sensores.h"
#include "control.h"
#include "actuadores.h"
#include "pantalla.h"
#include "reporte.h"

Sensores sensores;
Actuadores actuadores;
Pantalla pantalla;
Reporte reporte;
ConfigControl config = CONFIG_CONTROL_POR_DEFECTO;

void setup() {
  Serial.begin(115200);
  sensores.begin();
  actuadores.begin();
  pantalla.begin();
  reporte.begin();
}

void loop() {
  sensores.actualizar();

  if (sensores.hayLecturaNueva()) {
    const Lectura l = sensores.ultima();
    actuadores.aplicar(decidirRiego(l, actuadores.regando(), config));
    actuadores.aplicar(decidirVentanas(l, actuadores.ventanasAbiertas(), config));
    pantalla.mostrar(l, actuadores.estado());
    reporte.registrar(l, actuadores.estado());
  }

  actuadores.actualizar();   // tiempos máximos de riego, movimiento de ventanas
  pantalla.actualizar();     // los botones ▲ ▼ OK
  reporte.actualizar();      // envía pendientes cuando hay red
}
```

`tipos.h` es el vocabulario común: lo incluyen todos, y no depende de ningún otro. `control` no incluye nada de hardware. `controlador.ino` no tiene lógica propia: solo pasa datos de un módulo a otro. Cada archivo responde a un solo motivo de cambio de la tabla del paso 2. Cómo organizar estos módulos en capas (aplicación, servicios, drivers) se ve en [2.1](/conceptos/2-1).

## Errores comunes

### La clase que hace todo, con otro nombre

```cpp
// Mal: un "Manager" o "Sistema" que concentra todo
class SistemaInvernadero {
  void leerSensores();
  void decidirRiego();
  void moverVentanas();
  void dibujarPantalla();
  void enviarAlBackend();
  void guardarConfig();
};
```

Pasar el `.ino` gigante a una clase gigante no separa nada. Si para describir la clase necesitás muchos "y", dividila.

### Dividir por tipo técnico en lugar de por responsabilidad

```text
Mal:   enums.h, structs.h, funciones.cpp, variables.cpp
Bien:  sensores, control, actuadores, pantalla, reporte
```

Agrupar "todos los enums" o "todas las variables" junta cosas que cambian por motivos distintos y separa cosas que cambian juntas.

### Lógica de negocio dentro de un callback de hardware

```cpp
// Mal: la decisión de riego escondida en la interrupción del caudalímetro
void IRAM_ATTR alPulso() {
  pulsos++;
  if (pulsos > LIMITE) digitalWrite(PIN_BOMBA, HIGH);
}
```

El callback anota el evento; la decisión se toma en el módulo de control, donde se puede leer y probar (ver [0.8](/conceptos/0-8)).

### Módulos que se llaman en círculo

Si `pantalla` llama a `reporte`, `reporte` llama a `control` y `control` llama a `pantalla`, no hay módulos separados: hay un solo bloque repartido en archivos. Los datos tienen que fluir en una dirección, como en el diagrama del paso 4.

## Ejercicio

Esta función de la ventilación mezcla varias responsabilidades. Identificalas, y reescribila separando la decisión en una función pura que se pueda probar sin hardware.

```cpp ventilacion-mezclada.ino
void manejarVentilacion() {
  Wire.beginTransmission(0x44);
  Wire.write(0x24); Wire.write(0x00);
  Wire.endTransmission();
  delay(20);
  Wire.requestFrom(0x44, 6);
  uint16_t crudo = (Wire.read() << 8) | Wire.read();
  float t = -45.0f + 175.0f * crudo / 65535.0f;

  if (t > 30.0f && !ventanasAbiertas) {
    ledcWrite(PIN_SERVO, 4915);
    ventanasAbiertas = true;

    ventanasAbiertas = false;

  }
}
```

## Resumen

- Una parte del firmware tiene una sola responsabilidad si tiene un solo motivo para cambiar.
- Encontrá las responsabilidades preguntando qué podría cambiar y quién lo pediría: sensores, reglas, actuadores, pantalla, comunicación.
- La separación más valiosa es entre decidir (funciones puras, que se prueban sin hardware) y tocar el mundo físico.
- Los módulos se comunican con datos simples (`Lectura`, decisiones), y los datos fluyen en una dirección.
- `loop()` coordina: cada línea le pide algo a un módulo. Dividí hasta que cada pieza tenga una idea clara, no más.
