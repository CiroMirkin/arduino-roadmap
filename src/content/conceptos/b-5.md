Antes de compilar tu código, un programa llamado **preprocesador** lo recorre y trabaja solo con texto. Las líneas que empiezan con `#` son instrucciones para él: `#include` pega el contenido de otro archivo, `#define` reemplaza un nombre por un texto y `#if` decide qué partes del código llegan al compilador. Para declarar constantes, C++ moderno tiene una alternativa mejor: `constexpr`.

## Por qué te importa

Casi todo firmware de Arduino que vas a leer tiene un `config.h` lleno de `#define`: pines, tiempos, umbrales. Funciona, pero el preprocesador no sabe nada de C++. No chequea tipos, no respeta alcances y reemplaza el nombre en cualquier lugar donde aparezca, incluso adentro de las librerías que incluís después.

En el controlador del invernadero eso produce errores difíciles de leer. Un `;` de más en un `#define` genera un error de compilación en una línea que se ve perfecta. Una macro sin paréntesis calcula mal el tiempo de riego sin ningún aviso. Y un `#define` con un nombre común choca con un nombre igual dentro de una librería, y el error aparece en un archivo que nunca tocaste.

## Paso a paso

### 1. Las tres etapas: preprocesar, compilar y enlazar

Cuando apretás "Verificar" en el Arduino IDE pasan tres cosas, en orden:

1. El **preprocesador** procesa cada `.cpp` (y cada `.ino`): resuelve los `#include`, reemplaza las macros y descarta lo que esté dentro de un `#if` falso. El resultado es un único texto largo por archivo.
2. El **compilador** convierte ese texto en código máquina. Acá se chequean los tipos y la sintaxis.
3. El **linker** une los archivos compilados en un solo programa. Esto se explica en la próxima lección, [B.6](/conceptos/b-6).

Esta lección trata la primera etapa. Lo importante es que el preprocesador termina antes de que el compilador empiece, así que el compilador nunca ve tus `#define`: ve el texto ya reemplazado.

### 2. `#include` pega un archivo

```cpp
#include <WiFi.h>        // busca en las carpetas de librerías y del sistema
#include "config.h"      // busca primero en la carpeta de tu proyecto
```

`#include` copia el contenido completo del archivo en esa línea. Si `config.h` tiene 40 líneas, es como si las hubieras escrito ahí. Por convención, `<...>` se usa para librerías y `"..."` para los archivos de tu proyecto.

### 3. `#define` reemplaza texto

```cpp
#define PIN_BOMBA 26
#define INTERVALO_RIEGO_MS 60000

pinMode(PIN_BOMBA, OUTPUT);   // el compilador ve: pinMode(26, OUTPUT);
```

Todo lo que está después del nombre, hasta el final de la línea, es el texto de reemplazo. Sin tipos, sin chequeos: el preprocesador busca el nombre y lo cambia.

También hay macros con parámetros, que parecen funciones pero siguen siendo reemplazo de texto:

```cpp
#define CUADRADO(x) x * x

int a = CUADRADO(5);       // 5 * 5 = 25, bien
int b = CUADRADO(2 + 3);   // 2 + 3 * 2 + 3 = 11, mal
```

Se pueden "arreglar" con paréntesis (`((x) * (x))`), pero queda otro problema: el argumento se evalúa dos veces. `CUADRADO(leerSensor())` lee el sensor dos veces y puede multiplicar dos lecturas distintas.

### 4. `constexpr`: constantes de verdad

```cpp
constexpr uint8_t PIN_BOMBA = 26;
constexpr uint32_t INTERVALO_RIEGO_MS = 60UL * 1000UL;

constexpr float celsiusAFahrenheit(float c) {
  return c * 9.0f / 5.0f + 32.0f;
}
```

`constexpr` significa que el valor se conoce al compilar. Para el programa final es tan barato como un `#define`: no ocupa RAM extra y el compilador lo reemplaza donde se usa. La diferencia es que lo maneja el compilador, no el preprocesador:

- Tiene tipo. `PIN_BOMBA` es un `uint8_t`, y si lo usás donde no corresponde, el compilador te avisa.
- Respeta alcances. Una constante dentro de una clase o un `namespace` no choca con otra del mismo nombre en otra parte.
- Una función `constexpr` evalúa su argumento una vez, como cualquier función, y si los argumentos son constantes, el resultado se calcula al compilar.

> También existe `const`. `const int x = leerSensor();` es una variable que no cambia después de inicializarse, pero su valor se conoce recién al ejecutar. `constexpr` exige que el valor se conozca al compilar. Para pines, tiempos y umbrales fijos, usá `constexpr`.

### 5. Compilación condicional: lo que solo el preprocesador puede hacer

```cpp
#define MODO_DEPURACION 1

#if MODO_DEPURACION
  Serial.println("leyendo sensores...");
#endif
```

Si `MODO_DEPURACION` vale 0, la línea del `Serial.println` ni siquiera llega al compilador: el programa queda más chico y más rápido. Esto no se puede hacer con `constexpr`, porque decide qué texto se compila. Los usos típicos son activar logs, elegir código según la placa y adaptarse a distintas versiones de una librería:

```cpp
#if defined(CONFIG_IDF_TARGET_ESP32C3)
  // código solo para los nodos hechos con un ESP32-C3
#elif defined(CONFIG_IDF_TARGET_ESP32)
  // código para el ESP32 clásico
#endif
```

### 6. Guardas de inclusión y `#pragma once`

Si dos headers incluyen `lectura.h`, y tu `.cpp` incluye los dos, el contenido de `lectura.h` se pega dos veces en el mismo archivo. Si ahí se declara un `struct`, el compilador ve la misma declaración dos veces y falla con `redefinition of 'struct Lectura'`.

Las guardas evitan eso:

```cpp lectura.h
#ifndef LECTURA_H
#define LECTURA_H

struct Lectura {
  float temperatura;
  float humedadSuelo;
};

#endif
```

La primera vez, `LECTURA_H` no está definido, así que se pega todo y se define `LECTURA_H`. La segunda vez ya está definido y el preprocesador saltea hasta el `#endif`.

`#pragma once` hace lo mismo en una línea:

```cpp lectura.h
#pragma once

struct Lectura {
  float temperatura;
  float humedadSuelo;
};
```

No es parte del estándar de C++, pero lo soportan GCC (el compilador del ESP32), Clang y MSVC. Para archivos nuevos es más simple y evita el error de copiar un header y olvidarse de cambiar el nombre de la guarda. Las guardas `#ifndef` siguen siendo válidas en el código que ya existe.

## Ejemplos

### Ejemplo 1. El mismo cálculo con macro y con `constexpr`

```cpp macro-vs-constexpr.ino
#define MARGEN_MACRO 10 + 5
constexpr int MARGEN = 10 + 5;

void setup() {
  Serial.begin(115200);
  Serial.println(MARGEN_MACRO * 2);   // 20: se expande a 10 + 5 * 2
  Serial.println(MARGEN * 2);         // 30
}

void loop() {}
```

El `#define` pega el texto `10 + 5` y la multiplicación se aplica solo al 5. La constante `constexpr` ya vale 15 antes de multiplicarse.

### Ejemplo 2. El `config.h` del controlador

Un archivo de configuración con `constexpr`, incluido desde dos archivos distintos sin problemas gracias a `#pragma once`.

```cpp config.h
#pragma once
#include <Arduino.h>

// Pines
constexpr uint8_t PIN_BOMBA = 26;
constexpr uint8_t PIN_VENTILADOR = 27;
constexpr uint8_t PIN_SENSOR_SUELO = 34;

// Tiempos
constexpr uint32_t INTERVALO_LECTURA_MS = 5UL * 1000UL;
constexpr uint32_t RIEGO_MAXIMO_MS = 3UL * 60UL * 1000UL;

// Umbrales
constexpr float TEMPERATURA_VENTILAR_C = 30.0f;
constexpr int HUMEDAD_MINIMA_PORCENTAJE = 35;
```

```cpp riego.cpp
#include "config.h"

void iniciarRiego() {
  pinMode(PIN_BOMBA, OUTPUT);
  digitalWrite(PIN_BOMBA, LOW);
}
```

```cpp ventilacion.cpp
#include "config.h"

bool hayQueVentilar(float temperatura) {
  return temperatura >= TEMPERATURA_VENTILAR_C;
}
```

La `UL` en `5UL * 1000UL` hace que la multiplicación se haga como `unsigned long`, así no se desborda aunque la placa tenga `int` de 16 bits (los sufijos se explican en [B.1](/conceptos/b-1)). Es una costumbre útil para cualquier tiempo en milisegundos.

¿Por qué las constantes `constexpr` en un header no dan "definición múltiple" si se incluyen desde dos `.cpp`? Porque una variable `constexpr` a nivel de archivo tiene enlace interno: cada `.cpp` tiene su propia copia, y el compilador las resuelve como valores fijos. Lo vas a entender mejor después de [B.6](/conceptos/b-6).

### Ejemplo 3. Un firmware para todos los nodos y logs que se pueden apagar

Hay cuatro nodos sensores con el mismo firmware. Cada uno necesita un identificador distinto, y durante el desarrollo querés logs detallados que en producción no deberían ocupar espacio ni tiempo.

```cpp nodo.ino
// Valores por defecto: se pueden cambiar desde afuera, sin tocar el código
#ifndef NODO_ID
#define NODO_ID 1
#endif

#ifndef MODO_DEPURACION
#define MODO_DEPURACION 0
#endif

#if MODO_DEPURACION
  #define LOG(...) Serial.printf(__VA_ARGS__)
#else
  #define LOG(...) do {} while (0)
#endif

constexpr uint8_t ID_NODO = NODO_ID;   // a partir de acá, una constante con tipo

void setup() {
  Serial.begin(115200);
  LOG("nodo %d iniciando\n", ID_NODO);
}

void loop() {
  float temperatura = 24.5f;   // acá iría la lectura real
  LOG("nodo %d: %.1f C\n", ID_NODO, temperatura);
  delay(5000);
}
```

Con PlatformIO, cada nodo se compila con sus propios valores desde `platformio.ini`, sin editar el código:

```ini platformio.ini
[env:nodo1]
platform = espressif32
board = esp32dev
framework = arduino
build_flags = -DNODO_ID=1 -DMODO_DEPURACION=1

[env:nodo2]
platform = espressif32
board = esp32dev
framework = arduino
build_flags = -DNODO_ID=2
```

`-DNODO_ID=2` equivale a escribir `#define NODO_ID 2` antes de la primera línea. El `#ifndef` da un valor por defecto si no se pasó ninguno. Este es uno de los usos legítimos de las macros: `LOG` tiene que desaparecer por completo del programa cuando la depuración está apagada, y eso solo lo puede hacer el preprocesador. El `do {} while (0)` hace que `LOG(...);` siga siendo una instrucción válida aunque la macro esté vacía. Apenas el valor entra al código, se pasa a una constante `constexpr` con tipo.

## Errores comunes

### Macro sin paréntesis

```cpp
// Mal
#define ESPERA_MS 60 * 1000
uint32_t ciclos = 3600000 / ESPERA_MS;   // 3600000 / 60 * 1000 = 60000000

// Bien
constexpr uint32_t ESPERA_MS = 60UL * 1000UL;
uint32_t ciclos = 3600000UL / ESPERA_MS;  // 60
```

Si por algún motivo necesitás la macro, envolvé el reemplazo completo entre paréntesis: `#define ESPERA_MS (60UL * 1000UL)`.

### Punto y coma al final de un `#define`

```cpp
// Mal
#define PIN_VENTILADOR 27;
pinMode(PIN_VENTILADOR, OUTPUT);   // queda pinMode(27;, OUTPUT);

// Bien
constexpr uint8_t PIN_VENTILADOR = 27;
```

El error de compilación apunta a la línea donde se usa, no a la del `#define`, y eso confunde. Con `constexpr` el `;` va donde corresponde.

### Una macro que choca con una librería

```cpp
// Mal
#define ERROR 2
#include "libreria_actuadores.h"   // adentro tiene: enum class Resultado { OK, ERROR };
// el preprocesador convierte esa línea en: enum class Resultado { OK, 2 };

// Bien
constexpr int CODIGO_ERROR = 2;
#include "libreria_actuadores.h"
```

El `#define` reemplaza el nombre en todo el texto que viene después, incluidas las librerías. El error aparece dentro de un archivo que no escribiste. Las constantes `constexpr` no tienen este problema: el nombre `ERROR` dentro del `enum class` es otro nombre en otro alcance.

### Un header sin guardas

```cpp
// Mal: lectura.h sin #pragma once, incluido desde nodo.h y desde controlador.cpp
struct Lectura { float temperatura; };
// error: redefinition of 'struct Lectura'

// Bien
#pragma once
struct Lectura { float temperatura; };
```

Poné `#pragma once` como primera línea de todo header que escribas, aunque hoy lo incluya un solo archivo.

## Ejercicio

Este es el `config.h` de un nodo sensor. El nodo usa `VECES_POR_HORA` para reservar lugar para las lecturas de una hora, y debería valer 12, pero vale un número absurdo. Además, el archivo no compila apenas se usa `PIN_LED`. Encontrá los dos problemas y reescribí el archivo con `constexpr`.

```cpp config.h
#define PIN_LED 2;
#define MINUTOS_ENTRE_LECTURAS 5
#define INTERVALO_US MINUTOS_ENTRE_LECTURAS * 60 * 1000000ULL
#define VECES_POR_HORA 3600000000ULL / INTERVALO_US
```

<details>
<summary>Pista</summary>

Expandí `VECES_POR_HORA` a mano, reemplazando cada macro por su texto. Después mirá el `;` del primer `#define`.

</details>

<details>
<summary>Ver solución</summary>

```cpp config.h
#pragma once
#include <Arduino.h>

constexpr uint8_t PIN_LED = 2;
constexpr uint64_t MINUTOS_ENTRE_LECTURAS = 5;
constexpr uint64_t INTERVALO_US = MINUTOS_ENTRE_LECTURAS * 60ULL * 1000000ULL;
constexpr uint64_t VECES_POR_HORA = 3600000000ULL / INTERVALO_US;   // 12
```

`VECES_POR_HORA` se expande a `3600000000ULL / 5 * 60 * 1000000ULL`. La división se hace primero: 3600000000 / 5 es 720000000, y eso multiplicado por 60 y por un millón da 43.200.000.000.000.000. Con `constexpr`, `INTERVALO_US` ya vale 300000000 antes de usarse en la división, y `VECES_POR_HORA` vale 12.

El `;` en `#define PIN_LED 2;` es el que impide compilar: `pinMode(PIN_LED, OUTPUT)` se convierte en `pinMode(2;, OUTPUT)`.

Los microsegundos van en `uint64_t` porque `esp_sleep_enable_timer_wakeup` recibe un `uint64_t`, y porque 5 minutos en microsegundos (300 millones) entra en 32 bits, pero un par de horas ya no.

</details>

## Resumen

- El preprocesador trabaja con texto antes de que compile el compilador: `#include` pega archivos, `#define` reemplaza nombres y `#if` decide qué código se compila.
- Las macros no tienen tipo ni alcance, y un paréntesis o un `;` de más produce errores silenciosos o mensajes confusos.
- Para constantes y funciones simples, usá `constexpr`: cuesta lo mismo y lo chequea el compilador.
- `#define` sigue siendo la herramienta correcta para la compilación condicional: logs, placas distintas, versiones de librerías.
- Todo header empieza con `#pragma once` (o con guardas `#ifndef`) para que incluirlo dos veces no rompa nada.
