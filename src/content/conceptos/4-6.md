Una **cola de mensajes** es un lugar donde una parte del sistema deja **tareas pendientes** y otra parte las toma y las procesa cuando puede. Quien produce la tarea no espera a que se haga; quien la consume trabaja a su propio ritmo. En el backend del invernadero, la cola permite que la ingesta (ver [4.3](/conceptos/4-3)) responda enseguida a los equipos y que el trabajo pesado (evaluar alarmas, calcular resúmenes, enviar notificaciones) lo hagan otros procesos, llamados **workers**.

## Por qué te importa

La ingesta tiene que ser rápida y estable: si responde lento, los equipos acumulan pendientes, reintentan y cargan más al servidor. Pero cuando llegan lecturas, hay trabajo asociado: revisar si alguna dispara una alarma, actualizar el promedio horario, avisar por correo o por la app. Si todo eso se hace dentro de la ruta de ingesta, cualquier demora en esas tareas (un servidor de correo lento, un cálculo costoso) se convierte en lentitud de la ingesta.

Es el mismo patrón que en el firmware separa el control de la comunicación con una cola de FreeRTOS (ver [2.4](/conceptos/2-4)): quien produce deja el trabajo y sigue; quien consume lo hace a su ritmo.

## Cómo funciona

```text
equipos ──► ingesta ──► guarda lecturas
                    └─► encola "llegaron lecturas del dispositivo 17"
                                   │
                         ┌─────────┴─────────┐
                         ▼                   ▼
                     worker 1            worker 2
                 evalúa alarmas,      (más workers si
                 resúmenes, avisos     hay mucho trabajo)
```

- El **productor** (la ingesta) agrega un mensaje a la cola y responde.
- Los **consumidores** (workers) toman mensajes, hacen el trabajo y **confirman** que terminó. Si un worker se cae antes de confirmar, el mensaje vuelve a quedar disponible para otro.
- Si hay más trabajo del que los workers pueden hacer, los mensajes **esperan** en la cola. Se pueden agregar workers sin tocar la ingesta.

**Al menos una vez.** Como un mensaje vuelve a la cola si no se confirmó, puede procesarse dos veces (por ejemplo, el worker envió el correo pero se cayó antes de confirmar). El procesamiento tiene que ser **idempotente**, igual que la ingesta (ver [3.5](/conceptos/3-5)).

**Opciones de infraestructura**, de más simple a más compleja:

- Una **tabla en PostgreSQL** usada como cola. No agrega piezas; alcanza para volúmenes moderados.
- **Redis** con una librería de colas (por ejemplo, BullMQ en Node.js): rápida, con reintentos y tareas programadas.
- **RabbitMQ** o servicios administrados de colas: más funciones de enrutamiento y entrega.
- **Kafka**: para volúmenes muy grandes de eventos que varios sistemas leen.

## Ejemplo

Una cola hecha con una tabla de PostgreSQL. La ingesta inserta un trabajo; cada worker toma uno con `FOR UPDATE SKIP LOCKED`, que bloquea esa fila para los demás y hace que los otros workers salteen las filas ya tomadas.

```sql cola.sql
CREATE TABLE trabajos (
  id              BIGSERIAL PRIMARY KEY,
  tipo            TEXT NOT NULL,
  datos           JSONB NOT NULL,
  disponible_en   TIMESTAMPTZ NOT NULL DEFAULT now(),
  intentos        INT NOT NULL DEFAULT 0,
  creado          TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX trabajos_disponibles ON trabajos (disponible_en);

-- En la ingesta (4.3), en la misma transacción que guarda las lecturas:
-- INSERT INTO trabajos (tipo, datos) VALUES ('evaluar_alarmas', '{"dispositivo": 17}');
```

```js worker.js
async function procesarUnTrabajo(pool, manejadores) {
  const cliente = await pool.connect();
  try {
    await cliente.query("BEGIN");
    const { rows } = await cliente.query(
      `SELECT id, tipo, datos, intentos FROM trabajos
        WHERE disponible_en <= now()
        ORDER BY id
        LIMIT 1
        FOR UPDATE SKIP LOCKED`        // otros workers saltean esta fila mientras está tomada
    );
    if (rows.length === 0) {
      await cliente.query("COMMIT");
      return false;                     // no hay trabajo
    }

    const trabajo = rows[0];
    try {
      await manejadores[trabajo.tipo](trabajo.datos);   // tiene que ser idempotente
      await cliente.query("DELETE FROM trabajos WHERE id = $1", [trabajo.id]);   // confirmar
    } catch (error) {
      const espera = Math.min(3600, 10 * 2 ** trabajo.intentos);                  // backoff (ver 3.5)
      await cliente.query(
        `UPDATE trabajos SET intentos = intentos + 1,
                disponible_en = now() + make_interval(secs => $2)
          WHERE id = $1`,
        [trabajo.id, espera]
      );
    }
    await cliente.query("COMMIT");
    return true;
  } catch (error) {
    await cliente.query("ROLLBACK");
    throw error;
  } finally {
    cliente.release();
  }
}

async function bucleWorker(pool, manejadores) {
  for (;;) {
    const hubo = await procesarUnTrabajo(pool, manejadores);
    if (!hubo) await new Promise((r) => setTimeout(r, 1000));   // sin trabajo: esperar un segundo
  }
}

module.exports = { bucleWorker };
```

Encolar el trabajo en la **misma transacción** que guarda las lecturas garantiza que nunca queden lecturas sin su trabajo, ni trabajos sin sus lecturas. Si el manejador falla, el trabajo se reprograma con una espera creciente; si el worker se cae a mitad de camino, la transacción se deshace y el trabajo vuelve a estar disponible. Varios workers pueden correr a la vez sin tomar el mismo trabajo. Conviene además un límite de intentos, después del cual el trabajo se mueve a una tabla de "fallidos" para revisarlo a mano.

## Cuándo sí y cuándo no

Conviene una cola cuando:

- la ruta que recibe el pedido tiene trabajo lento o que puede fallar (correos, servicios externos, cálculos pesados),
- el volumen tiene picos y el procesamiento puede hacerse unos segundos o minutos después,
- se quiere reintentar tareas fallidas sin que el cliente se entere.

No hace falta (todavía) cuando:

- el trabajo asociado es rápido y la ingesta responde bien haciéndolo en el momento,
- el volumen es bajo y no hay picos,
- el resultado tiene que estar listo en la respuesta (por ejemplo, rechazar una lectura inválida).

Empezar con una tabla de PostgreSQL es razonable: no agrega infraestructura, y si el volumen crece, se puede pasar a Redis o a un sistema dedicado manteniendo el mismo diseño.

## Resumen

- Una cola separa a quien produce el trabajo de quien lo hace: la ingesta responde rápido y los workers procesan a su ritmo.
- Los mensajes se confirman al terminar; si un worker se cae, el mensaje vuelve a la cola.
- La entrega "al menos una vez" exige que el procesamiento sea idempotente.
- Una tabla de PostgreSQL con `FOR UPDATE SKIP LOCKED` alcanza para empezar; Redis, RabbitMQ o Kafka, para más volumen o más funciones.
- Encolá en la misma transacción que guarda los datos, y reintentá con espera creciente y un límite.
