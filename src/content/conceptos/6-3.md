Todo lo que entra al backend desde afuera es **entrada no confiable**, y los equipos del invernadero son "afuera" aunque los hayas fabricado vos: tienen sensores que se rompen, firmware con bugs, versiones viejas que mandan formatos viejos, y una clave que alguien pudo haber extraído. Que un equipo esté autenticado dice **quién** manda el dato, no que el dato esté bien. Por eso cada valor se valida **en la entrada**, antes de usarlo: tipo exacto, rango posible, tamaño, formato. Lo que no pasa se rechaza y se registra, sin corregirlo en silencio. Y lo que sí pasa se sigue tratando con cuidado cuando termina en otro lado: en una consulta SQL, en una página web o en un log.

## Por qué te importa

En [4.3](/conceptos/4-3) la ingesta de lecturas ya valida tipos y rangos. Esta lección explica el criterio detrás, para aplicarlo a cualquier dato que llegue: el estado que reportan los equipos, los eventos de riego, las alarmas, los nombres que un técnico carga en la pantalla del controlador.

Los datos malos de un equipo no se quedan en ese equipo. Una temperatura falsa de 0 °C dispara una alarma de helada a las tres de la mañana. Una versión de firmware con 10.000 caracteres llena la tabla y rompe el tablero. Un texto con código HTML, mostrado sin cuidado en el panel web, se ejecuta en el navegador del administrador. Y un valor pegado dentro de un SQL deja que un equipo comprometido lea o borre datos de otras organizaciones.

## Paso a paso

### 1. La frontera de confianza

Hay un punto donde los datos cruzan de "afuera" a "adentro": la ruta que los recibe. Ahí se validan, **una vez**, y se convierten en un objeto con la forma que el resto del código espera. Más adentro, las funciones trabajan con datos que ya se sabe que son válidos, sin repetir chequeos por todos lados. Validar a medias en distintos lugares termina con algún camino donde nadie validó.

### 2. Primero el tipo, tal como llegó

JavaScript convierte tipos con mucha facilidad, y esas conversiones esconden errores: `Number(null)` es `0`, `Number("")` es `0`, `Number("24,5")` es `NaN`, `Number(true)` es `1`. Si convertís antes de validar, un dato faltante se vuelve un cero válido. El orden correcto es preguntar primero si el valor ya es del tipo esperado (`typeof v === "number"`, `Number.isInteger(v)`, `typeof v === "string"`) y recién después mirar el rango.

Un caso concreto del firmware: cuando un sensor falla, la lectura suele ser `NaN`, y ArduinoJson serializa `NaN` como `null`. Si el backend hace `Number(temp)`, guarda 0 °C.

### 3. Rangos posibles y valores plausibles

Hay dos niveles:

- Lo imposible: humedad de 180 %, temperatura de 500 °C, un `rssi` positivo, una fecha de 1970. Fuera del rango físico del sensor o de lo que el sistema puede producir. Se **rechaza**.
- Lo improbable: la temperatura baja de 30 °C a 5 °C en un minuto, o el suelo pasa de 20 % a 90 % sin que haya habido riego. Puede ser un sensor que falla, o algo real (alguien abrió la puerta de una cámara fría). Se **guarda marcado** como sospechoso, para revisarlo, sin dispararle alarmas automáticas.

Los dos se registran. Un sensor que manda valores imposibles todos los días tiene que aparecer en algún lado (ver [4.7](/conceptos/4-7)).

### 4. Tamaños

Todo tiene un máximo: el cuerpo del pedido (`express.json({ limit })`), la cantidad de elementos de un lote, el largo de cada texto, la cantidad de campos. Sin máximos, un equipo con un bug (o alguien con su clave) manda un texto de 50 MB y el servidor se queda sin memoria. Los límites del tráfico en sí se ven en [4.4](/conceptos/4-4).

### 5. Campos conocidos

Se aceptan solo los campos esperados. Un campo desconocido puede ser un firmware nuevo con un formato que la API todavía no conoce, un error, o un intento de asignación masiva (ver [6.2](/conceptos/6-2)). En cualquier caso, conviene enterarse: se rechaza o se registra. Los campos que definen el acceso (organización, invernadero, dispositivo) nunca se leen del cuerpo: salen de la autenticación (ver [3.4](/conceptos/3-4)).

### 6. Cuidado al usar el dato en otro lado

Validar a la entrada no alcanza para todo. Un nombre de zona como `Norte's` es válido, y aun así rompe un SQL armado pegando textos. Cada destino tiene su regla:

- En SQL, siempre parámetros (`$1`, `$2`). Nunca se pega un valor en el texto de la consulta.
- En HTML, el texto se escapa al mostrarlo. React lo hace solo, salvo con `dangerouslySetInnerHTML`.
- Los logs van en formato JSON (ver [4.7](/conceptos/4-7)), así un texto con saltos de línea no inventa líneas de log falsas.
- Nunca se arma un comando de consola con datos de afuera.

### 7. Rechazar, no corregir

Recortar 180 % a 100 % o reemplazar un `null` por 0 "para que no falle" hace que el problema desaparezca de la vista y siga en los datos. Se rechaza el valor con un motivo claro, el equipo lo registra (y no lo reintenta, porque es un `4xx`, ver [3.5](/conceptos/3-5)), y el backend lo registra también.

### 8. En el otro sentido, lo mismo

El controlador tampoco confía en lo que recibe: la configuración que llega del backend (ver [3.3](/conceptos/3-3)), lo que lee de la NVS (ver [0.11](/conceptos/0-11)), lo que escribe un técnico por el puerto serie (ver [B.12](/conceptos/b-12)). Cada lado valida su entrada.

## Ejemplos

### Ejemplo 1. Una trampa de conversión

Lo mínimo para ver por qué el tipo se valida antes que el rango.

```js conversiones.js
console.log(Number(null));        // 0
console.log(Number(""));          // 0
console.log(Number("24.5"));      // 24.5
console.log(Number("24,5"));      // NaN
console.log(Number(true));        // 1
console.log(parseFloat("24abc")); // 24

function temperaturaMal(v) {
  const t = Number(v);
  return Number.isFinite(t) && t >= -30 && t <= 70 ? t : null;
}

function temperaturaBien(v) {
  return typeof v === "number" && Number.isFinite(v) && v >= -30 && v <= 70 ? v : null;
}

console.log(temperaturaMal(null));    // 0     (un sensor roto se vuelve una helada)
console.log(temperaturaBien(null));   // null  (se rechaza)
console.log(temperaturaMal("24"));    // 24    (acepta un formato que el contrato no permite)
console.log(temperaturaBien("24"));   // null
```

Qué observar: `temperaturaMal` parece prolija (convierte, chequea que sea finito, chequea el rango) y aun así acepta datos que no existen. El contrato de la API dice que `temp` es un número; un texto con un número adentro es otro formato, y aceptarlo hace que nadie se entere de que un firmware lo está mandando mal.

### Ejemplo 2. Validar el estado de los equipos con un esquema

En [4.7](/conceptos/4-7), cada controlador reporta su estado (firmware, señal, causa del último reinicio, memoria libre, tiempo encendido) y `actualizarEstado` lo guarda. Ese objeto viene del equipo y se valida antes. Con una librería de esquemas como **zod**, la validación se escribe como una descripción de la forma esperada:

```js validar-estado.js
const { z } = require("zod");

const EsquemaEstado = z.object({
  fw: z.string().regex(/^\d{1,3}\.\d{1,3}\.\d{1,3}$/),     // "2.4.1"
  rssi: z.number().int().min(-120).max(0),
  reinicio: z.number().int().min(0).max(20),                // código de esp_reset_reason()
  heap: z.number().int().min(0).max(8 * 1024 * 1024),
  activoS: z.number().int().min(0).max(10 * 365 * 24 * 3600),
}).strict();                                                 // campos desconocidos: error

function validarEstado(cuerpo) {
  const r = EsquemaEstado.safeParse(cuerpo);
  if (r.success) return { valor: r.data };
  return { errores: r.error.issues.map((i) => `${i.path.join(".") || "(raíz)"}: ${i.message}`) };
}

module.exports = { validarEstado };

// validarEstado({ fw: "2.4.1", rssi: -67, reinicio: 1, heap: 182000, activoS: 3600 })
//   -> { valor: { ... } }
// validarEstado({ fw: "2.4.1<script>", rssi: 12, reinicio: 1, heap: 182000, activoS: 3600 })
//   -> { errores: ["fw: ...", "rssi: ..."] }
// validarEstado({ fw: "2.4.1", rssi: -67, reinicio: 1, heap: 182000, activoS: 3600, admin: true })
//   -> { errores: ["(raíz): ..."] }   (el campo admin no está en el esquema)
```

```js estado.js
const express = require("express");
const { autenticarEquipo } = require("./autenticacion");   // 3.4
const { validarEstado } = require("./validar-estado");
const { actualizarEstado } = require("./estado-equipos");  // 4.7

const router = express.Router();

router.post("/api/v1/estado", express.json({ limit: "2kb" }), autenticarEquipo, async (req, res) => {
  const { valor, errores } = validarEstado(req.body);
  if (errores) {
    req.log.warn({ evento: "estado_invalido", dispositivo: req.equipo.id, errores });
    return res.status(400).json({ errores });
  }
  await actualizarEstado(req.db, req.equipo, valor);   // consultas con parámetros
  res.json({ ok: true });
});

module.exports = router;
```

Qué observar:

- El esquema es la documentación del contrato: se lee qué espera la API sin recorrer `if` por `if`.
- La versión de firmware tiene un formato estricto. Así nunca llega al tablero un texto con HTML, ni uno de 10.000 caracteres, y el tablero puede ordenar y filtrar por versión.
- `.strict()` rechaza campos desconocidos. Un firmware nuevo que agrega un campo falla ruidosamente en las pruebas, en lugar de perder el dato en silencio.
- El límite del cuerpo (`2kb`) corta los pedidos gigantes antes de leerlos.
- El rechazo va al log con el dispositivo (`req.log` es el logger de [4.7](/conceptos/4-7)), y el equipo recibe el motivo para registrarlo de su lado.

### Ejemplo 3. Marcar lo improbable

Las lecturas que pasan la validación de [4.3](/conceptos/4-3) pueden igual ser sospechosas. Esta función pura compara cada lectura con la anterior del mismo equipo y decide si marcarla:

```js plausibilidad.js
const MAX_CAMBIO_TEMP_POR_MIN = 2;      // °C por minuto
const MAX_SUBIDA_SUELO_POR_MIN = 5;     // puntos de humedad por minuto, sin riego

function evaluarPlausibilidad(anterior, actual, huboRiego) {
  if (!anterior) return { sospechosa: false };

  const minutos = (Date.parse(actual.momento) - Date.parse(anterior.momento)) / 60000;
  if (minutos <= 0) return { sospechosa: false };   // llegó desordenada: no se puede comparar

  const cambioTemp = Math.abs(actual.temp - anterior.temp) / minutos;
  if (cambioTemp > MAX_CAMBIO_TEMP_POR_MIN) {
    return { sospechosa: true, motivo: "salto de temperatura" };
  }

  const subidaSuelo = (actual.suelo - anterior.suelo) / minutos;
  if (!huboRiego && subidaSuelo > MAX_SUBIDA_SUELO_POR_MIN) {
    return { sospechosa: true, motivo: "humedad sube sin riego" };
  }
  return { sospechosa: false };
}

module.exports = { evaluarPlausibilidad };

// anterior: 14:30, 24.5 °C, suelo 41
// evaluarPlausibilidad(anterior, { momento: "...14:31...", temp: 24.8, suelo: 41 }, false)
//   -> { sospechosa: false }
// evaluarPlausibilidad(anterior, { momento: "...14:31...", temp: 5.0, suelo: 41 }, false)
//   -> { sospechosa: true, motivo: "salto de temperatura" }
```

La lectura sospechosa se guarda con una columna `sospechosa` y su motivo. Los gráficos la pueden mostrar distinta, las alarmas automáticas la ignoran hasta que se confirme con lecturas siguientes, y un reporte diario lista los equipos con muchas. Los umbrales dependen del cultivo y del sensor: son un punto de partida para ajustar con datos reales. La función recibe todo lo que necesita y no consulta nada, así que se prueba con una tabla de casos (ver [2.8](/conceptos/2-8)).

## Errores comunes

### Convertir antes de validar

```js
// Mal: null, "" y false se vuelven 0
const litros = Number(req.body.litros);

// Bien
const litros = req.body.litros;
if (typeof litros !== "number" || !Number.isFinite(litros) || litros < 0 || litros > 5000) {
  return res.status(400).json({ error: "litros inválidos" });
}
```

### Pegar valores en el SQL

```js
// Mal
await db.query(`SELECT * FROM zonas WHERE nombre = '${nombre}'`);

// Bien
await db.query("SELECT * FROM zonas WHERE nombre = $1", [nombre]);
```

### "El firmware ya valida"

Hay equipos con firmware de hace dos años, equipos con bugs que todavía no conocés, y claves que se pueden filtrar. Lo que valida el firmware sirve para no mandar basura; lo que valida el backend es lo que protege los datos.

### Corregir en silencio

Recortar al rango, reemplazar `null` por 0 o ignorar un campo mal escrito hace que el dato quede "bien" y el problema quede escondido. Rechazá y registrá.

### Mostrar textos del equipo como HTML

```jsx
// Mal: si fw trae "<img src=x onerror=...>", se ejecuta en el navegador del admin
<td dangerouslySetInnerHTML={{ __html: equipo.firmware }} />

// Bien: React escapa el texto
<td>{equipo.firmware}</td>
```

### Sin límites de tamaño

Un texto sin largo máximo, un lote sin cantidad máxima o un cuerpo sin límite convierten un bug de firmware en una caída del servidor.

Problemas:

1. Los valores se pegan en el SQL: `zona` o `duracion_s` pueden traer SQL.
2. `Number(litros)` convierte `null` (caudalímetro sin lectura) en 0 litros.
3. No hay validación de tipos ni de rangos: litros negativos, duraciones de un año.
4. No se verifica que la zona sea del invernadero del equipo: un controlador podría registrar riegos en zonas de otra organización (ver [6.2](/conceptos/6-2)).
5. No se verifica la coherencia: 500 litros en 90 segundos es imposible con ese caudalímetro.
6. No hay límite de tamaño del cuerpo.

```js riegos.js
const CAUDAL_MAXIMO_L_POR_S = 30 / 60;

function validarRiego(c) {
  if (typeof c !== "object" || c === null) return { error: "cuerpo inválido" };
  const { zona, litros, duracion_s: duracion } = c;
  if (!Number.isSafeInteger(zona) || zona <= 0) return { error: "zona inválida" };
  if (!Number.isInteger(duracion) || duracion < 1 || duracion > 3600) {
    return { error: "duracion_s entre 1 y 3600" };
  }
  if (typeof litros !== "number" || !Number.isFinite(litros) || litros < 0) {
    return { error: "litros inválidos" };
  }
  if (litros > duracion * CAUDAL_MAXIMO_L_POR_S * 1.1) {   // 10 % de margen
    return { error: "más litros de los que permite el caudalímetro" };
  }
  return { valor: { zona, litros, duracion } };
}

router.post("/api/v1/riegos", express.json({ limit: "1kb" }), autenticarEquipo, async (req, res) => {
  const { valor, error } = validarRiego(req.body);
  if (error) {
    req.log.warn({ evento: "riego_invalido", dispositivo: req.equipo.id, error });
    return res.status(400).json({ error });
  }

  const { rowCount } = await req.db.query(
    `INSERT INTO riegos (organizacion_id, dispositivo_id, zona_id, litros, duracion_s)
     SELECT $1, $2, z.id, $4, $5
       FROM zonas z
      WHERE z.id = $3 AND z.invernadero_id = $6 AND z.organizacion_id = $1`,
    [req.equipo.organizacion_id, req.equipo.id, valor.zona, valor.litros, valor.duracion,
     req.equipo.invernadero_id]
  );
  if (rowCount === 0) return res.status(404).json({ error: "zona no encontrada" });
  res.json({ ok: true });
});
```

El `INSERT ... SELECT` solo inserta si la zona existe y es del invernadero del equipo: la pertenencia se verifica en la misma consulta. Todos los valores van como parámetros. El chequeo de coherencia (litros contra duración) detecta un caudalímetro que cuenta pulsos de más, algo que ningún rango por separado detectaría. Si además los riegos llegan con reintentos, les falta un identificador para que sean idempotentes (ver [4.3](/conceptos/4-3)).

## Resumen

- Lo que manda un equipo es entrada no confiable, aunque esté autenticado: autenticar dice quién, validar dice si está bien.
- Se valida una vez, en la entrada: primero el tipo tal como llegó, después el rango, el tamaño y los campos permitidos.
- Lo imposible se rechaza y se registra; lo improbable se guarda marcado. Nada se corrige en silencio.
- Al usar el dato en otro lado, la regla de cada destino: parámetros en SQL, escapar en HTML, logs en JSON.
- El controlador aplica el mismo criterio a lo que recibe del backend, de la NVS o del puerto serie.
