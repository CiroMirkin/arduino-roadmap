Una **declaración anticipada** (*forward declaration*) le dice al compilador que un tipo existe, sin mostrarle cómo es por dentro: `class Pantalla;`. Con eso alcanza para declarar punteros, referencias y parámetros de ese tipo, sin incluir su header. Sirve para dos cosas: **cortar los includes circulares** (dos headers que se incluyen entre sí) y **reducir las dependencias** entre archivos, para que un cambio en un módulo no obligue a recompilar todo el proyecto.

## Por qué te importa

Cuando el controlador del invernadero se divide en módulos (ver [1.1](/conceptos/1-1)), los módulos se necesitan entre sí: el controlador le pasa datos a la pantalla, la pantalla quiere mostrar el estado del controlador. Si `controlador.h` incluye `pantalla.h` y `pantalla.h` incluye `controlador.h`, aparecen errores como `'Controlador' does not name a type` en archivos que parecen perfectamente escritos. Es uno de los errores más desconcertantes de C++ para quien viene de otros lenguajes.

Las declaraciones anticipadas lo resuelven, y además obligan a pensar en la dirección de las dependencias: quién conoce a quién. Un proyecto donde las dependencias van en una sola dirección es más fácil de entender, de probar y de modificar.

## Paso a paso

### 1. Tipo completo y tipo incompleto

Después de `class Pantalla;`, `Pantalla` es un **tipo incompleto**: el compilador sabe que existe, pero no qué tiene ni cuánto ocupa.

| Con un tipo incompleto | ¿Se puede? |
|---|---|
| declarar un puntero o una referencia: `Pantalla* p;` `Pantalla& r` | sí |
| un parámetro o retorno por puntero o referencia | sí |
| declarar una función que lo recibe por valor: `void f(Pantalla p);` | sí (solo declararla) |
| un miembro por valor: `Pantalla _pantalla;` | no: no se sabe cuánto ocupa |
| llamar a un método: `p->mostrar()` | no: no se sabe qué métodos tiene |
| `sizeof(Pantalla)`, crear un objeto | no |

La idea: lo que solo necesita saber *que existe* funciona; lo que necesita saber *cómo es*, no.

### 2. Por qué fallan los includes circulares

```cpp controlador.h
#pragma once
#include "pantalla.h"
class Controlador {
  Pantalla* _pantalla;
};
```

```cpp pantalla.h
#pragma once
#include "controlador.h"
class Pantalla {
  void mostrar(const Controlador& c);
};
```

Si `main.cpp` incluye primero `controlador.h`, el preprocesador pega `pantalla.h`, que intenta pegar `controlador.h`, pero `#pragma once` lo saltea (ya se está procesando). Entonces `Pantalla` se declara usando `Controlador`, que todavía no apareció: error. Las guardas evitan el bucle infinito, pero no el problema de orden.

### 3. Cortar el ciclo

```cpp pantalla.h
#pragma once

class Controlador;   // declaración anticipada: alcanza para una referencia

class Pantalla {
public:
  void mostrar(const Controlador& c);
};
```

```cpp pantalla.cpp
#include "pantalla.h"
#include "controlador.h"   // acá sí: hay que llamar a métodos de Controlador

void Pantalla::mostrar(const Controlador& c) {
  // c.temperatura(), c.regando()...
}
```

El patrón general: **en el header, declaraciones anticipadas para lo que solo se nombra; en el `.cpp`, los includes de lo que se usa.**

### 4. Menos includes, menos recompilación

Cada `#include` en un header es una dependencia para todos los que incluyan ese header. Si `reporte.h` incluye `pantalla.h`, cualquier cambio en `pantalla.h` recompila todos los archivos que incluyen `reporte.h`, aunque no tengan nada que ver con la pantalla. En un proyecto grande, eso convierte compilaciones de segundos en minutos.

Las librerías pesadas (BLE, gráficos, WiFi) son las que más pesan: si solo un `.cpp` las usa, que solo ese `.cpp` las incluya.

### 5. Ordenar la dirección de las dependencias

Una declaración anticipada corta el ciclo de compilación, pero los dos módulos siguen conociéndose. Muchas veces el mejor arreglo es de diseño: que la dependencia vaya en **una sola dirección**.

Si el controlador necesita avisarle a la pantalla, puede depender de una **interfaz** chica en lugar de la pantalla completa:

```cpp
class ObservadorEstado {
public:
  virtual void alCambiarEstado() = 0;
  virtual ~ObservadorEstado() = default;
};
```

El controlador conoce `ObservadorEstado`; la pantalla implementa esa interfaz y conoce al controlador. La flecha de dependencia va de la pantalla al controlador, nunca al revés. Es el patrón Observer de [1.6](/conceptos/1-6), usado para ordenar dependencias.

### 6. Declaraciones anticipadas de enums

Un `enum class` también se puede declarar por adelantado, siempre que se indique su tipo subyacente:

```cpp
enum class ModoRiego : uint8_t;   // alcanza para declarar funciones que lo reciben
void fijarModo(ModoRiego modo);
```

Un `enum` clásico sin tipo subyacente explícito no se puede declarar así.

## Ejemplos

### Ejemplo 1. Lo que se puede y lo que no con un tipo incompleto

```cpp tipo-incompleto.ino
class Pantalla;                         // solo "existe"

struct Reporte {
  Pantalla* pantalla = nullptr;         // ok: puntero
  void conectar(Pantalla& p);           // ok: referencia en un parámetro
  // Pantalla copia;                    // error: incomplete type
  // void dibujar() { pantalla->mostrar(); }   // error: incomplete type
};

class Pantalla {                        // ahora el tipo está completo
public:
  void mostrar() { Serial.println("[pantalla] actualizada"); }
};

void Reporte::conectar(Pantalla& p) {
  pantalla = &p;
  pantalla->mostrar();                  // ok: acá Pantalla ya es completo
}

Pantalla pantalla;
Reporte reporte;

void setup() {
  Serial.begin(115200);
  reporte.conectar(pantalla);
}

void loop() {}
```

Probá descomentar las dos líneas marcadas: el compilador da `field 'copia' has incomplete type` y `invalid use of incomplete type`. El mismo método, escrito después de la definición completa de `Pantalla`, compila.

### Ejemplo 2. Cortar un include circular

El controlador tiene un puntero a la pantalla para avisarle, y la pantalla recibe el controlador para leer el estado. Con declaraciones anticipadas en los headers y los includes en los `.cpp`, compila en cualquier orden.

```cpp controlador.h
#pragma once
#include <Arduino.h>

class Pantalla;   // no hace falta incluir pantalla.h

class Controlador {
public:
  void conectarPantalla(Pantalla* p) { _pantalla = p; }
  void registrarTemperatura(float t);
  float temperatura() const { return _temperatura; }

private:
  Pantalla* _pantalla = nullptr;
  float _temperatura = 0.0f;
};
```

```cpp pantalla.h
#pragma once

class Controlador;   // no hace falta incluir controlador.h

class Pantalla {
public:
  void mostrar(const Controlador& c);
};
```

```cpp controlador.cpp
#include "controlador.h"
#include "pantalla.h"     // se usa mostrar(): hace falta la clase completa

void Controlador::registrarTemperatura(float t) {
  _temperatura = t;
  if (_pantalla != nullptr) _pantalla->mostrar(*this);
}
```

```cpp pantalla.cpp
#include <Arduino.h>
#include "pantalla.h"
#include "controlador.h"  // se usa temperatura(): hace falta la clase completa

void Pantalla::mostrar(const Controlador& c) {
  Serial.printf("[pantalla] %.1f C\n", c.temperatura());
}
```

Ningún header incluye al otro, así que no hay ciclo. Los dos `.cpp` incluyen los dos headers, que es donde se usan los métodos. `*this` es una referencia al propio objeto: el controlador se pasa a sí mismo a la pantalla.

### Ejemplo 3. La dependencia en una sola dirección

El ejemplo 2 compila, pero el controlador todavía conoce a la pantalla. Si mañana también tiene que avisarle al reporte y al registro en la SD, va a conocer a todos. Con una interfaz, el controlador no conoce a nadie.

```cpp observador-estado.h
#pragma once

class ObservadorEstado {
public:
  virtual void alCambiarEstado() = 0;
  virtual ~ObservadorEstado() = default;
};
```

```cpp controlador.h
#pragma once
#include <Arduino.h>
#include "observador-estado.h"

class Controlador {
public:
  bool suscribir(ObservadorEstado& o) {
    if (_cantidad == 4) return false;
    _observadores[_cantidad++] = &o;
    return true;
  }
  void registrarTemperatura(float t) {
    _temperatura = t;
    for (size_t i = 0; i < _cantidad; i++) _observadores[i]->alCambiarEstado();
  }
  float temperatura() const { return _temperatura; }

private:
  ObservadorEstado* _observadores[4] = {};
  size_t _cantidad = 0;
  float _temperatura = 0.0f;
};
```

```cpp pantalla.h
#pragma once
#include "observador-estado.h"

class Controlador;

class Pantalla : public ObservadorEstado {
public:
  explicit Pantalla(const Controlador& c) : _controlador(c) {}
  void alCambiarEstado() override;
private:
  const Controlador& _controlador;
};
```

```cpp pantalla.cpp
#include "pantalla.h"
#include "controlador.h"

void Pantalla::alCambiarEstado() {
  Serial.printf("[pantalla] %.1f C\n", _controlador.temperatura());
}
```

```cpp main.ino
#include "controlador.h"
#include "pantalla.h"

Controlador controlador;
Pantalla pantalla(controlador);

void setup() {
  Serial.begin(115200);
  controlador.suscribir(pantalla);
  controlador.registrarTemperatura(26.5f);
}

void loop() {}
```

Las dependencias ahora forman una línea: `pantalla` → `controlador` → `observador-estado`. `controlador.h` no menciona a la pantalla de ninguna forma. Agregar el reporte o el registro en la SD como observadores no toca el controlador. Este principio (depender de interfaces chicas en lugar de módulos concretos) es la base de la arquitectura en capas de [2.1](/conceptos/2-1).

## Errores comunes

### Usar un tipo incompleto en el header

```cpp
// Mal: reporte.h
class Pantalla;
class Reporte {
  void avisar() { _pantalla->mostrar(); }   // invalid use of incomplete type
  Pantalla* _pantalla;
};

// Bien: el cuerpo, en reporte.cpp, que incluye pantalla.h
class Reporte {
  void avisar();
  Pantalla* _pantalla;
};
```

### Un miembro por valor de un tipo declarado por adelantado

```cpp
// Mal
class Pantalla;
class Controlador {
  Pantalla _pantalla;   // field has incomplete type
};

// Bien: si de verdad tiene que ser un miembro por valor, incluir el header
#include "pantalla.h"
class Controlador {
  Pantalla _pantalla;
};
// o guardar una referencia/puntero a una pantalla que vive afuera
```

### "Arreglar" un ciclo agregando más includes

Cuando aparece `does not name a type`, la tentación es agregar includes hasta que compile. Con un ciclo, eso no funciona o funciona por casualidad según el orden. Buscá qué header incluye a cuál, y cortá el ciclo con una declaración anticipada o con una interfaz.

### Declarar por adelantado algo que no es una clase

```cpp
// Mal: un alias con using/typedef no se puede declarar por adelantado así
class Temperatura;   // si en realidad es "using Temperatura = float;", da error

// Bien: incluir el header donde está el alias
#include "tipos.h"
```

## Ejercicio

El proyecto no compila: `alarmas.h` y `pantalla.h` se incluyen mutuamente, y el error dice `'Pantalla' has not been declared`. Reorganizá los headers para cortar el ciclo con declaraciones anticipadas, dejando los includes necesarios en los `.cpp`.

```cpp alarmas.h
#pragma once
#include "pantalla.h"

class Alarmas {
public:
  explicit Alarmas(Pantalla& pantalla) : _pantalla(pantalla) {}
  void activar(const char* motivo) { _activa = true; _pantalla.mostrarAlarma(motivo); }
  bool activa() const { return _activa; }
private:
  Pantalla& _pantalla;
  bool _activa = false;
};
```

```cpp pantalla.h
#pragma once
#include "alarmas.h"

class Pantalla {
public:
  void mostrarAlarma(const char* motivo) { Serial.println(motivo); }
  void dibujar(const Alarmas& alarmas) { if (alarmas.activa()) Serial.println("ALARMA"); }
};
```

## Resumen

- `class Pantalla;` declara que el tipo existe. Alcanza para punteros, referencias y parámetros, pero no para miembros por valor ni para llamar métodos.
- Dos headers que se incluyen entre sí producen errores de "tipo no declarado" aunque tengan guardas.
- Patrón: declaraciones anticipadas en los headers, includes en los `.cpp`, cuerpos que usan la otra clase en los `.cpp`.
- Menos includes en los headers significa menos dependencias y compilaciones más rápidas.
- La solución de fondo para un ciclo suele ser de diseño: que un módulo dependa de una interfaz chica, y las dependencias vayan en una sola dirección.
