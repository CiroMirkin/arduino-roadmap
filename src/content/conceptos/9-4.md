El **teorema CAP** dice que un sistema con datos en varios lugares unidos por una red no puede garantizar a la vez tres cosas: **consistencia** (todos ven el mismo dato, el último), **disponibilidad** (todo pedido recibe respuesta) y **tolerancia a particiones** (el sistema sigue funcionando aunque la red se corte entre sus partes). Como las particiones van a ocurrir, la tolerancia no es opcional, y la elección real es otra: **durante una partición**, cada parte del sistema elige entre responder con lo que sabe (disponibilidad) o negarse hasta poder confirmar (consistencia). Fuera de las particiones, también hay un compromiso: más consistencia cuesta más latencia.

## Por qué te importa

El sistema del invernadero ya es distribuido: el controlador y el backend tienen copias de la configuración, el cupo de agua, el estado de los riegos. En [5.3](/conceptos/5-3) viste la decisión aplicada a la configuración. Este concepto le da nombre al marco general, para tomar esas decisiones a propósito, operación por operación, en lugar de descubrirlas el día que se corta internet. También sirve para leer con criterio las promesas de las bases de datos distribuidas ("consistente y siempre disponible"), que suelen tener letra chica.

## Cómo funciona

*Partición.* Dos partes del sistema no se pueden comunicar, pero cada una sigue funcionando: el controlador sin internet, una réplica que perdió contacto con la principal, dos centros de datos sin enlace.

*Elegir consistencia (CP)* significa que, ante la duda, se rechaza la operación: "no puedo confirmar el saldo, intentá más tarde". Es lo correcto cuando un dato desactualizado causa un daño que no se deshace: vender dos veces lo mismo, superar un límite que no se puede superar.

*Elegir disponibilidad (AP)* significa que se responde con lo que se sabe, y los datos se reconcilian después (consistencia eventual, ver [5.3](/conceptos/5-3)). Es lo correcto cuando seguir funcionando importa más que la exactitud inmediata: un controlador que tiene que regar.

*No es una elección del sistema entero.* Cada operación puede elegir distinto. En el mismo sistema, la configuración es AP, el cupo de agua centralizado es CP, y el riego manual sin red puede ser AP con un límite local.

*PACELC* completa la idea: si hay partición (P), elegir entre disponibilidad (A) y consistencia (C); si no (E, *else*), elegir entre latencia (L) y consistencia (C). Una réplica sincrónica da consistencia pero cada escritura espera a dos servidores; una asincrónica responde rápido pero puede atrasarse.

*Un PostgreSQL solo* no es un sistema distribuido en este sentido: es consistente, y si se cae, no está disponible. El compromiso aparece al agregar réplicas, o al mirar el sistema completo con sus equipos.

## Ejemplo

Las decisiones del sistema del invernadero, operación por operación:

| Operación | Durante un corte | Por qué |
|---|---|---|
| Regar según los umbrales | Sigue (AP), con la última configuración | Las plantas no esperan; la configuración converge al volver la red |
| Guardar lecturas | Sigue (AP), en la cola local | Se reenvían después; la idempotencia evita duplicados |
| Cambiar la configuración desde la app | Se acepta en el backend; el controlador la recibe después | Un solo lugar de escritura, versiones crecientes |
| Riego manual desde la pantalla | Sigue (AP) con límite local | El daño máximo queda acotado; se reporta al volver |
| Descontar del cupo de agua compartido | Solo en el backend (CP) | Dos controladores no pueden gastar el mismo cupo |
| Alta de un usuario | Solo con el backend (CP) | Sin la base no se puede verificar que el email no exista |

Y el riego manual sin red, en el controlador:

```cpp riego-manual-sin-red.ino
#include <Arduino.h>

constexpr uint32_t MAX_MANUAL_SIN_RED_S = 300;      // 5 minutos por día sin confirmación

struct RiegoPendiente {
  uint32_t segundos;
  uint32_t millisInicio;
};

uint32_t segundosManualSinRedHoy = 0;               // se pone en 0 al cambiar el día (ver 7.1)
RiegoPendiente pendientes[16];
size_t cantidadPendientes = 0;

bool hayBackend() { return false; }                  // en el equipo real: estadoEnlace() (ver 7.2)
bool pedirRiegoAlBackend(uint32_t) { return false; } // el backend descuenta el cupo (CP)
void encenderBomba(uint32_t segundos) { Serial.printf("bomba %u s\n", static_cast<unsigned>(segundos)); }

bool riegoManual(uint32_t segundos) {
  if (hayBackend()) {
    return pedirRiegoAlBackend(segundos);           // con red: el backend decide
  }
  // Sin red: disponibilidad con un límite que acota el daño
  if (segundosManualSinRedHoy + segundos > MAX_MANUAL_SIN_RED_S) return false;
  if (cantidadPendientes == sizeof(pendientes) / sizeof(pendientes[0])) return false;
  segundosManualSinRedHoy += segundos;
  pendientes[cantidadPendientes++] = {segundos, millis()};   // se reporta al volver la red
  encenderBomba(segundos);
  return true;
}

void setup() {
  Serial.begin(115200);
  Serial.println(riegoManual(120) ? "regando" : "rechazado");   // regando
  Serial.println(riegoManual(240) ? "regando" : "rechazado");   // rechazado: superaría 300 s
}

void loop() {}
```

Con red, la decisión es del backend, que lleva el cupo compartido entre todos los controladores. Sin red, el controlador acepta, pero con un tope propio que acota el error posible, y guarda lo que hizo para reportarlo. Cuando vuelve la conexión, los riegos pendientes se envían (con identificador, para que sean idempotentes) y el cupo del backend converge. Es una decisión de negocio: alguien tiene que acordar con el productor cuánto riego sin control es aceptable.

## Cuándo sí y cuándo no

Pensar en estos términos sirve cuando:

- hay datos copiados en más de un lugar (equipos y backend, réplicas, cachés, servicios),
- se evalúa una base de datos distribuida o un servicio de nube con promesas de consistencia,
- se diseña qué hace cada parte del sistema sin red.

No hace falta invocarlo cuando:

- todo vive en una base, con transacciones (ver [5.2](/conceptos/5-2)): ahí la consistencia ya está resuelta,
- la operación no tiene copias que puedan diferir.

## Resumen

- Con datos en varios lugares unidos por una red, durante una partición hay que elegir entre responder (disponibilidad) y garantizar el último dato (consistencia).
- La elección se hace por operación, no para el sistema entero.
- Consistencia cuando un dato viejo causa un daño irreversible; disponibilidad cuando seguir funcionando importa más.
- Fuera de las particiones, el compromiso es entre latencia y consistencia (PACELC).
- Un límite local acota el daño de elegir disponibilidad, y los datos convergen al volver la red.
