En [1.1](/conceptos/1-1) viste cómo separar responsabilidades en módulos. Una **arquitectura en capas** agrega una regla de orden: los módulos se agrupan en niveles según qué tan cerca están del hardware, y cada nivel solo usa a los de abajo. En firmware se usan casi siempre tres: **drivers** (hablan con el hardware), **servicios** (funciones reutilizables que se apoyan en los drivers: conectividad, almacenamiento, sensores filtrados) y **aplicación** (las reglas del invernadero). Es la forma de salir del `.ino` de mil líneas sin terminar en cincuenta archivos que se llaman entre todos.

## Por qué te importa

El firmware de un equipo que funciona en el campo no se escribe una vez: se cambia durante años. Cambia el sensor porque el modelo se discontinuó, cambia el backend, se agrega un cultivo con otras reglas, se reemplaza el WiFi por un módem celular. En un `.ino` monolítico, cada uno de esos cambios toca código mezclado con todo lo demás.

Con capas, cada tipo de cambio queda contenido en una capa: un sensor nuevo es un driver nuevo; un cambio de backend toca el servicio de comunicación; una regla de cultivo nueva toca la aplicación. Además, la capa de aplicación (la más importante, la que decide si el cultivo vive o muere) queda separada del hardware y se puede probar sin él (ver [2.8](/conceptos/2-8)).

## Paso a paso

### 1. Las tres capas

```text
┌──────────────────────────────────────────────┐
│ Aplicación   reglas del invernadero:          │
│              cuándo regar, ventilar, alarmar  │
├──────────────────────────────────────────────┤
│ Servicios    conectividad, cola de envíos,    │
│              configuración, sensores filtrados│
├──────────────────────────────────────────────┤
│ Drivers      SHT31, relé, servo, ADC, BLE,    │
│              pantalla: un dispositivo cada uno│
└──────────────────────────────────────────────┘
                    hardware
```

| Capa | Sabe de... | No sabe de... | Cambia cuando... |
|---|---|---|---|
| Drivers | pines, registros, protocolos, librerías | riego, backend, pantalla | cambia el hardware |
| Servicios | cómo combinar drivers para algo útil | reglas del cultivo | cambia la infraestructura (red, almacenamiento) |
| Aplicación | reglas del invernadero | pines, I2C, HTTP | cambia el cultivo o el uso |

### 2. La regla de dependencia

**Cada capa solo usa a la de abajo.** La aplicación llama a servicios y (si hace falta) a drivers; los servicios llaman a drivers; los drivers no incluyen nada de las capas de arriba.

Cuando una capa de abajo necesita avisar algo hacia arriba (el driver BLE recibió una lectura, el servicio de conectividad perdió la red), no llama a la aplicación: ofrece un **callback** o un **observador** al que la aplicación se suscribe (ver [1.6](/conceptos/1-6) y [1.9](/conceptos/1-9)). Así la dependencia sigue yendo hacia abajo.

### 3. Drivers: un dispositivo, una interfaz chica

Un driver esconde todo lo específico de un dispositivo y ofrece una interfaz en términos útiles:

```cpp
class DriverSht31 {
public:
  explicit DriverSht31(uint8_t direccion = 0x44);
  bool pedirMedicion();
  bool actualizar();          // true cuando hay una medición nueva
  float temperatura() const;  // °C
  float humedad() const;      // %HR
};
```

Nadie fuera del driver sabe de I2C, del comando `0x2400` ni del CRC (ver [0.7](/conceptos/0-7)). Si mañana se cambia por otro sensor, se escribe otro driver con una interfaz parecida.

### 4. Servicios: combinar drivers en algo útil

Un servicio resuelve una necesidad del sistema usando uno o más drivers. Por ejemplo:

- **Clima**: usa los drivers de los sensores, filtra lecturas, detecta sensores desconectados y entrega una `Lectura` completa.
- **Conectividad**: maneja la conexión WiFi (reconexión, estado) con una máquina de estados (ver [B.10](/conceptos/b-10)).
- **Reporte**: la cola de pendientes y el envío al backend (ver [0.10](/conceptos/0-10)).
- **Configuración**: carga, valida y guarda la configuración en NVS (ver [0.11](/conceptos/0-11)).

Los servicios no saben de cultivos. El servicio de reporte envía lo que le den; no decide qué es importante.

### 5. Aplicación: las reglas del invernadero

La capa de aplicación recibe lecturas de los servicios, aplica las reglas (riego, ventilación, alarmas) y le pide a los servicios y drivers que actúen. Lo ideal es que su núcleo sean **funciones puras** como `decidirRiego` (ver [1.1](/conceptos/1-1)): reciben datos y devuelven decisiones. La parte que coordina (quién se llama primero, qué se hace con cada decisión) es delgada.

### 6. La estructura en carpetas

```text
src/
├── main.cpp            arma los objetos y llama a begin()/actualizar()
├── app/                aplicación: control, alarmas
├── servicios/          clima, conectividad, reporte, configuracion
└── drivers/            sht31, rele, servo, suelo, pantalla, ble
```

Con PlatformIO (ver [1.7](/conceptos/1-7)), una regla simple ayuda a mantener el orden: un archivo de `drivers/` nunca hace `#include` de algo de `servicios/` ni de `app/`. Basta con revisarlo de vez en cuando con una búsqueda.

## Ejemplos

### Ejemplo 1. Un sensor de suelo en tres capas

El caso más chico posible: el driver lee milivoltios, el servicio convierte con la calibración y filtra, y la aplicación decide.

```cpp capas-minimo.ino
#include <algorithm>

// --- Driver: solo sabe leer el pin ---
class DriverAdc {
public:
  explicit DriverAdc(uint8_t pin) : _pin(pin) {}
  uint32_t leerMv() const { return analogReadMilliVolts(_pin); }
private:
  uint8_t _pin;
};

// --- Servicio: convierte a % y filtra; no sabe de riego ---
class HumedadSuelo {
public:
  HumedadSuelo(const DriverAdc& adc, uint32_t mvSeco, uint32_t mvMojado)
    : _adc(adc), _mvSeco(mvSeco), _mvMojado(mvMojado) {}

  bool leer(float& porcentaje) const {
    uint32_t m[5];
    for (uint32_t& x : m) x = _adc.leerMv();
    std::sort(m, m + 5);
    uint32_t mv = m[2];                             // mediana
    if (mv < 200 || mv > 3000) return false;        // sensor desconectado
    float f = (static_cast<float>(_mvSeco) - mv) / (static_cast<float>(_mvSeco) - _mvMojado);
    porcentaje = constrain(f * 100.0f, 0.0f, 100.0f);
    return true;
  }
private:
  const DriverAdc& _adc;
  uint32_t _mvSeco, _mvMojado;
};

// --- Aplicación: la regla del cultivo ---
bool debeRegar(float humedad, bool regando) {
  return regando ? humedad < 55.0f : humedad < 35.0f;
}

DriverAdc adcCantero(2);
HumedadSuelo humedadCantero(adcCantero, 2600, 1150);
bool regando = false;

void setup() {
  Serial.begin(115200);
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo < 5000) return;
  ultimo = millis();

  float h;
  if (!humedadCantero.leer(h)) {
    Serial.println("sensor de suelo sin lectura: riego en pausa");
    regando = false;
    return;
  }
  regando = debeRegar(h, regando);
  Serial.printf("humedad %.0f%% -> %s\n", h, regando ? "regar" : "no regar");
}
```

Tres piezas, tres motivos de cambio. Si el sensor pasa a ser I2C, se cambia el driver. Si se mejora el filtro, se cambia el servicio. Si el cultivo pide otro umbral, se cambia `debeRegar`. Y la aplicación sabe qué hacer cuando el servicio no puede dar una lectura: no regar a ciegas.

### Ejemplo 2. El controlador completo, capa por capa

Los headers muestran qué ofrece cada capa y qué incluye. Los cuerpos son los de lecciones anteriores.

```cpp drivers/rele.h
#pragma once
#include <Arduino.h>

class Rele {
public:
  Rele(uint8_t pin, bool activoEnBajo = true);
  void begin();
  void encender();
  void apagar();
  bool encendido() const;
private:
  uint8_t _pin;
  bool _activoEnBajo;
  bool _encendido = false;
};
```

```cpp servicios/clima.h
#pragma once
#include "app/tipos.h"           // Lectura: el vocabulario común, sin dependencias
#include "drivers/sht31.h"
#include "drivers/adc.h"

class ServicioClima {
public:
  ServicioClima(DriverSht31& aire, DriverAdc& suelo);
  void begin();
  void actualizar();             // pide mediciones, sin bloquear
  bool hayLecturaNueva() const;
  Lectura ultima() const;        // con indicadores de qué sensores fallaron
private:
  DriverSht31& _aire;
  DriverAdc& _suelo;
  Lectura _ultima{};
  bool _nueva = false;
};
```

```cpp app/control.h
#pragma once
#include "app/tipos.h"           // solo tipos: nada de hardware

struct ConfigControl {
  float humedadMinima, humedadMaxima;
  float abrirSobreC, cerrarBajoC;
};

AccionRiego decidirRiego(const Lectura& l, bool regando, const ConfigControl& c);
AccionVentanas decidirVentanas(const Lectura& l, bool abiertas, const ConfigControl& c);
```

```cpp main.cpp
#include "drivers/sht31.h"
#include "drivers/adc.h"
#include "drivers/rele.h"
#include "servicios/clima.h"
#include "servicios/reporte.h"
#include "app/control.h"

// Drivers
DriverSht31 sht31(0x44);
DriverAdc adcSuelo(2);
Rele valvula(4);

// Servicios
ServicioClima clima(sht31, adcSuelo);
ServicioReporte reporte;

// Aplicación
ConfigControl config = {35.0f, 55.0f, 30.0f, 27.0f};

void setup() {
  Serial.begin(115200);
  valvula.begin();
  clima.begin();
  reporte.begin();
}

void loop() {
  clima.actualizar();
  reporte.actualizar();

  if (clima.hayLecturaNueva()) {
    Lectura l = clima.ultima();
    switch (decidirRiego(l, valvula.encendido(), config)) {
      case AccionRiego::Encender: valvula.encender(); break;
      case AccionRiego::Apagar:   valvula.apagar();   break;
      case AccionRiego::Ninguna:  break;
    }
    reporte.registrar(l);
  }
}
```

`app/tipos.h` (con `Lectura` y las acciones) no depende de nada, así que lo pueden incluir todas las capas sin romper la regla. `app/control.h` no incluye ningún driver: es la parte que se prueba en la PC. `main.cpp` es el único lugar que conoce a todas las capas, porque las arma y las conecta.

### Ejemplo 3. Migrar un monolito de a una pieza

Un `.ino` existente, con el sensor de temperatura leído directo dentro de `loop()`. El primer paso de la migración es extraer **solo** el driver, sin cambiar ningún comportamiento.

```cpp antes.ino
void loop() {
  Wire.beginTransmission(0x44);
  Wire.write(0x24); Wire.write(0x00);
  Wire.endTransmission();
  delay(20);
  Wire.requestFrom(0x44, 6);
  uint16_t crudo = (Wire.read() << 8) | Wire.read();
  float temperatura = -45.0f + 175.0f * crudo / 65535.0f;

  if (temperatura > 30.0f) abrirVentanas();
  // ... 400 líneas más ...
}
```

```cpp despues-paso-1.ino
#include "drivers/sht31.h"     // el driver de 0.7, con CRC y sin delay

DriverSht31 sensorAire(0x44);

void setup() {
  Wire.begin(8, 9);
  // ... lo demás, igual ...
}

void loop() {
  static uint32_t ultimoPedido = 0;
  static float temperatura = 0.0f;
  if (millis() - ultimoPedido >= 2000) {
    ultimoPedido = millis();
    sensorAire.pedirMedicion();
  }
  if (sensorAire.actualizar()) {
    temperatura = sensorAire.temperatura();
  }

  if (temperatura > 30.0f) abrirVentanas();
  // ... las mismas 400 líneas, sin tocar ...
}
```

El resto del `loop()` no cambió. Se compila, se prueba en el banco que la ventilación sigue funcionando igual, y recién después se da el paso siguiente (extraer el servo, después la decisión, después el envío). Este enfoque se llama a veces *estrangular* el monolito: el código nuevo crece alrededor del viejo hasta reemplazarlo, sin un momento en que nada funcione. Como bonus, el driver nuevo no usa `delay(20)` y valida el CRC, así que ya se ganó algo con el primer paso.

## Errores comunes

### Un driver que conoce la aplicación

```cpp
// Mal: drivers/suelo.cpp
#include "app/control.h"
float DriverSuelo::leer() {
  float h = convertir(analogReadMilliVolts(_pin));
  if (h < 35.0f) regar();   // el driver decide regar
  return h;
}

// Bien: el driver lee; la aplicación decide
float DriverSuelo::leer() { return convertir(analogReadMilliVolts(_pin)); }
```

### La aplicación hablando con el hardware directamente

```cpp
// Mal: app/control.cpp
if (digitalRead(2) == LOW) { /* tanque vacío */ }

// Bien: el dato llega en la Lectura, armada por el servicio de clima
if (!lectura.tanqueConAgua) { /* ... */ }
```

Cada `digitalRead`, `analogRead` o `Wire` en la capa de aplicación es una dependencia del hardware que impide probarla en la PC.

### Capas de un solo pasamanos

```cpp
// Mal: un "servicio" que solo repite al driver, sin agregar nada
class ServicioRele {
  void encender() { _rele.encender(); }
  void apagar() { _rele.apagar(); }
};
```

Si un servicio no agrega nada (ni reglas, ni combinación, ni manejo de errores), la aplicación puede usar el driver directamente. Las capas son para ordenar, no un trámite obligatorio.

### Reescribir todo de una vez

La reescritura completa parece más rápida y casi nunca lo es: el código viejo resolvía casos raros que nadie documentó. Migrá de a una pieza, probando en cada paso.

## Ejercicio

Este fragmento del controlador maneja la alarma de helada. Clasificá cada línea en driver, servicio o aplicación, y reescribilo en tres piezas: un driver para la sirena, un servicio que avise por el backend, y una función de aplicación que decida.

```cpp helada.ino
void revisarHelada(float temperaturaExterior) {
  if (temperaturaExterior < 2.0f) {
    digitalWrite(2, HIGH);                          // sirena
    HTTPClient http;
    http.begin("http://192.168.0.10:3000/api/invernaderos/2/alertas");
    http.addHeader("Content-Type", "application/json");
    http.POST("{\"tipo\":\"helada\"}");
    http.end();
  } else if (temperaturaExterior > 4.0f) {
    digitalWrite(2, LOW);
  }
}
```

<details>
<summary>Pista</summary>

La decisión (por debajo de 2 °C activar, por encima de 4 °C desactivar) no necesita saber cómo suena la sirena ni cómo se avisa. Que devuelva qué hacer, y que otro lo haga.

</details>

<details>
<summary>Ver solución</summary>

- Driver: `digitalWrite(2, ...)` (la sirena).
- Servicio: todo el bloque de `HTTPClient` (avisar al backend).
- Aplicación: las comparaciones con 2 °C y 4 °C.

```cpp drivers/sirena.h
class Sirena {
public:
  explicit Sirena(uint8_t pin) : _pin(pin) {}
  void begin() { pinMode(_pin, OUTPUT); apagar(); }
  void encender() { digitalWrite(_pin, HIGH); _sonando = true; }
  void apagar() { digitalWrite(_pin, LOW); _sonando = false; }
  bool sonando() const { return _sonando; }
private:
  uint8_t _pin;
  bool _sonando = false;
};
```

```cpp app/helada.h
enum class AccionHelada : uint8_t { Ninguna, Activar, Desactivar };

inline AccionHelada decidirHelada(float temperaturaExterior, bool activa) {
  if (!activa && temperaturaExterior < 2.0f) return AccionHelada::Activar;
  if (activa && temperaturaExterior > 4.0f) return AccionHelada::Desactivar;
  return AccionHelada::Ninguna;
}
```

```cpp main.cpp (fragmento)
AccionHelada a = decidirHelada(clima.ultima().temperaturaExterior, sirena.sonando());
if (a == AccionHelada::Activar) {
  sirena.encender();
  reporte.registrarAlerta("helada");   // el servicio la encola y la envía sin bloquear (ver 0.10)
} else if (a == AccionHelada::Desactivar) {
  sirena.apagar();
}
```

La versión original también tenía un bug que la separación deja a la vista: enviaba el aviso en *cada* llamada mientras hiciera menos de 2 °C, porque no recordaba si la alarma ya estaba activa. Ahora la decisión recibe el estado actual y solo devuelve `Activar` una vez. Además, el envío HTTP bloqueaba el `loop()` en plena helada; el servicio de reporte lo hace sin bloquear y reintenta si no hay red.

</details>

## Resumen

- Tres capas: drivers (un dispositivo cada uno), servicios (combinan drivers en algo útil) y aplicación (las reglas del invernadero).
- Las dependencias van solo hacia abajo. Para avisar hacia arriba, callbacks u observadores.
- Los drivers esconden pines y protocolos y entregan valores en unidades útiles. La aplicación no toca el hardware.
- `main.cpp` arma los objetos de todas las capas y los conecta; es el único que conoce a todas.
- Se migra un monolito de a una pieza, probando en cada paso, sin reescribir todo de una vez.
