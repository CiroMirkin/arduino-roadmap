En [B.5](/conceptos/b-5) y [B.8](/conceptos/b-8) viste cómo funcionan los punteros, las referencias y la memoria. Esta lección es sobre **decisiones de diseño**: quién crea cada objeto, quién es su **dueño**, cuánto tiempo vive y cómo se lo pasa a quien lo usa. En firmware hay una estrategia que simplifica todo: crear casi todos los objetos una sola vez, al arrancar, en **memoria estática**, y que el resto del programa solo los use a través de referencias.

## Por qué te importa

En un programa de escritorio, los objetos se crean y destruyen todo el tiempo, y el sistema operativo y la memoria abundante absorben los errores. En el controlador del invernadero, un objeto que se destruye mientras otro todavía lo usa reinicia el equipo, y una reserva de memoria que falla después de tres días de funcionamiento deja de regar.

Hay otro problema, más sutil: cuando hay objetos globales en varios archivos, C++ no garantiza en qué orden se construyen. Si el constructor de la pantalla usa el objeto de sensores, que vive en otro archivo, puede encontrarlo todavía sin construir. Las decisiones de esta lección evitan estas clases de errores por diseño, en lugar de perseguirlas con el depurador.

## Paso a paso

### 1. Quién es el dueño

El **dueño** de un objeto es quien decide cuándo se crea y cuándo se destruye. Los demás lo **usan**. Cada objeto debería tener exactamente un dueño, y quien lee el código debería poder saber cuál es.

En el controlador, la respuesta más simple es: **el programa es dueño de casi todo**. Los sensores, los actuadores, la pantalla, la conexión al backend y la configuración son objetos globales que se crean al arrancar y viven hasta que se apaga el equipo. Nadie los destruye, así que nadie puede usarlos después de destruidos.

### 2. Memoria estática

```cpp
// Todo se crea al arrancar, antes de setup()
Configuracion config;
Sensores sensores;
Actuadores actuadores;
ColaPendientes pendientes;
Reporte reporte(pendientes, config);
```

Con todos los objetos importantes como globales:

- El uso de memoria se conoce al compilar: el mensaje `Global variables use N bytes` lo dice. Si no entra, falla la compilación, no el equipo instalado.
- No hay `new` ni `delete` durante el funcionamiento, así que no hay fugas ni fragmentación.
- Las referencias entre objetos nunca quedan colgando, porque todos viven lo mismo.

Las variables locales siguen siendo para lo temporal: una lectura que se calcula y se pasa, un buffer para armar un mensaje.

### 3. La firma dice la relación

Cuando un objeto necesita otro, la forma de recibirlo documenta la relación:

| Firma | Significa |
|---|---|
| `Reporte(ColaPendientes& cola)` | lo necesita siempre y lo usa, pero no es su dueño |
| `Reporte(const Configuracion& config)` | lo necesita siempre y solo lo lee |
| `Reporte(Pantalla* pantalla = nullptr)` | es opcional: puede no existir |
| `void agregar(Lectura l)` | se queda con una copia propia |
| `std::unique_ptr<T>` como miembro | es el dueño: lo destruye cuando él se destruye |

En firmware con memoria estática, el último caso casi no aparece: los dueños son los globales, y todo lo demás recibe referencias.

### 4. El orden de construcción de los globales

Dentro de un mismo archivo, los objetos globales se construyen en el orden en que están declarados. **Entre archivos distintos, el orden no está definido.** Si el constructor de un global usa otro global de otro archivo, puede encontrarlo sin construir. Este problema tiene nombre propio: *static initialization order fiasco*.

La regla que lo evita:

- Los **constructores** solo guardan valores y referencias. No leen sensores, no usan otros globales, no tocan hardware.
- Cada objeto tiene un **`begin()`** que hace el trabajo real, y **`setup()`** los llama en el orden correcto, explícito, a la vista.

```cpp
void setup() {
  config.begin();       // primero: carga la configuración de la flash
  sensores.begin();     // usa la configuración (calibraciones)
  actuadores.begin();
  pantalla.begin();     // puede mostrar datos de sensores
  reporte.begin();
}
```

Guardar una referencia en el constructor es seguro aunque el otro objeto no esté construido todavía, porque solo se guarda su dirección. Lo peligroso es *usarlo*.

### 5. Un pool en lugar de `new`

Cuando la cantidad de objetos varía durante el funcionamiento (nodos que se conectan y desconectan, eventos pendientes), en lugar de crearlos con `new` se reserva un **pool**: un arreglo fijo con la cantidad máxima, y una marca de cuáles están en uso.

```cpp
struct ConexionNodo {
  bool enUso = false;
  uint8_t id = 0;
  uint32_t ultimoContactoMs = 0;
};

ConexionNodo conexiones[8];   // como máximo 8 nodos, siempre
```

Pedir un lugar es buscar uno libre; liberarlo es marcarlo como libre. No hay heap, y el límite queda explícito: si llega un noveno nodo, el código decide qué hacer, en lugar de descubrir el límite cuando falla una reserva.

### 6. Lo que se pasa a otro contexto tiene que sobrevivir

Cuando un objeto se pasa a algo que lo va a usar *más tarde* (un callback de BLE, una tarea de FreeRTOS, una interrupción), tiene que vivir al menos hasta entonces. Pasar la dirección de una variable local de `setup()` a una tarea que corre después es un error clásico: cuando la tarea la usa, esa memoria ya es de otra cosa. Con objetos globales, el problema desaparece.

## Ejemplos

### Ejemplo 1. Constructores livianos y `begin()` en orden

Tres objetos que dependen uno de otro. Los constructores solo guardan referencias; `setup()` los inicializa en el orden que importa.

```cpp orden-inicio.ino
struct Configuracion {
  float humedadMinima = 35.0f;
  bool cargada = false;

  void begin() {
    // acá se leería de la flash (ver 0.11)
    humedadMinima = 40.0f;
    cargada = true;
  }
};

class Sensores {
public:
  explicit Sensores(const Configuracion& config) : _config(config) {}   // solo guarda la referencia
  void begin() {
    Serial.printf("sensores: config %s\n", _config.cargada ? "cargada" : "SIN CARGAR");
  }
private:
  const Configuracion& _config;
};

class Pantalla {
public:
  Pantalla(const Configuracion& config, const Sensores& sensores)
    : _config(config), _sensores(sensores) {}
  void begin() {
    Serial.printf("pantalla: umbral %.0f%%\n", _config.humedadMinima);
  }
private:
  const Configuracion& _config;
  const Sensores& _sensores;
};

Configuracion config;
Sensores sensores(config);
Pantalla pantalla(config, sensores);

void setup() {
  Serial.begin(115200);
  delay(500);
  config.begin();      // el orden de inicialización está a la vista
  sensores.begin();
  pantalla.begin();
}

void loop() {}
```

Aunque estos objetos estuvieran en archivos distintos y se construyeran en otro orden, nada fallaría: los constructores no usan a nadie. El trabajo que depende de otros se hace en `begin()`, en el orden de `setup()`.

### Ejemplo 2. Firmas que documentan el diseño

El módulo de reporte necesita la cola de pendientes (siempre, y la modifica), la configuración (siempre, solo lectura) y, si existe, la pantalla para mostrar el estado de la conexión.

```cpp reporte.ino
struct Lectura { float temperatura; float humedadSuelo; };

struct Configuracion {
  uint32_t intervaloEnvioMs = 60000;
};

class ColaPendientes {
public:
  bool agregar(const Lectura& l) {
    if (_cantidad == 16) return false;
    _datos[_cantidad++] = l;
    return true;
  }
  size_t cantidad() const { return _cantidad; }
  void vaciar() { _cantidad = 0; }
private:
  Lectura _datos[16] = {};
  size_t _cantidad = 0;
};

class Pantalla {
public:
  void mostrarConexion(bool ok, size_t pendientes) {
    Serial.printf("[pantalla] backend %s, %u pendientes\n", ok ? "ok" : "sin conexión",
                  static_cast<unsigned>(pendientes));
  }
};

class Reporte {
public:
  Reporte(ColaPendientes& cola, const Configuracion& config, Pantalla* pantalla = nullptr)
    : _cola(cola), _config(config), _pantalla(pantalla) {}

  void registrar(Lectura l) {           // por valor: la lectura se copia a la cola
    _cola.agregar(l);
  }

  void actualizar() {
    if (millis() - _ultimoEnvio < _config.intervaloEnvioMs) return;
    _ultimoEnvio = millis();
    bool ok = enviarPendientes();
    if (_pantalla != nullptr) {          // opcional: puede no haber pantalla
      _pantalla->mostrarConexion(ok, _cola.cantidad());
    }
  }

private:
  bool enviarPendientes() {
    // acá iría el HTTP (ver 0.10); simulamos un envío exitoso
    _cola.vaciar();
    return true;
  }

  ColaPendientes& _cola;                 // la usa y la modifica; no es su dueño
  const Configuracion& _config;          // solo la lee
  Pantalla* _pantalla;                   // opcional
  uint32_t _ultimoEnvio = 0;
};

Configuracion config;
ColaPendientes cola;
Pantalla pantalla;
Reporte reporte(cola, config, &pantalla);   // en un nodo sin pantalla: Reporte reporte(cola, config);

void setup() {
  Serial.begin(115200);
}

void loop() {
  static uint32_t ultimaLectura = 0;
  if (millis() - ultimaLectura >= 10000) {
    ultimaLectura = millis();
    reporte.registrar({24.5f, 41.0f});
  }
  reporte.actualizar();
}
```

Leyendo solo el constructor de `Reporte` ya se sabe: la cola y la configuración son obligatorias, la configuración no se modifica, la pantalla es opcional, y `Reporte` no es dueño de ninguno. El mismo `Reporte` sirve en el controlador (con pantalla) y en un equipo sin pantalla.

### Ejemplo 3. Un pool fijo para las conexiones con los nodos

El controlador registra los nodos que se conectan por BLE (hasta 8) y libera su lugar si pasan 15 minutos sin noticias. Todo sin `new`.

```cpp pool-nodos.ino
struct EstadoNodo {
  bool enUso = false;
  uint8_t id = 0;
  float ultimaTemperatura = 0.0f;
  uint32_t ultimoContactoMs = 0;
};

class RegistroNodos {
public:
  static constexpr size_t MAXIMO = 8;
  static constexpr uint32_t SILENCIO_MAXIMO_MS = 15UL * 60UL * 1000UL;

  // Devuelve el lugar del nodo (existente o nuevo), o nullptr si no hay lugar
  EstadoNodo* obtener(uint8_t id) {
    EstadoNodo* libre = nullptr;
    for (EstadoNodo& n : _nodos) {
      if (n.enUso && n.id == id) return &n;
      if (!n.enUso && libre == nullptr) libre = &n;
    }
    if (libre != nullptr) {
      *libre = EstadoNodo{};       // limpiar lo que hubiera de antes
      libre->enUso = true;
      libre->id = id;
    }
    return libre;
  }

  void liberarInactivos() {
    for (EstadoNodo& n : _nodos) {
      if (n.enUso && millis() - n.ultimoContactoMs > SILENCIO_MAXIMO_MS) {
        Serial.printf("nodo %u sin noticias: se libera su lugar\n", n.id);
        n.enUso = false;
      }
    }
  }

  size_t enUso() const {
    size_t c = 0;
    for (const EstadoNodo& n : _nodos) if (n.enUso) c++;
    return c;
  }

private:
  EstadoNodo _nodos[MAXIMO];
};

RegistroNodos registro;

void alRecibirLectura(uint8_t idNodo, float temperatura) {
  EstadoNodo* n = registro.obtener(idNodo);
  if (n == nullptr) {
    Serial.printf("sin lugar para el nodo %u (máximo %u)\n", idNodo,
                  static_cast<unsigned>(RegistroNodos::MAXIMO));
    return;
  }
  n->ultimaTemperatura = temperatura;
  n->ultimoContactoMs = millis();
}

void setup() {
  Serial.begin(115200);
  for (uint8_t id = 1; id <= 10; id++) {
    alRecibirLectura(id, 20.0f + id);        // los nodos 9 y 10 no entran
  }
  Serial.printf("%u nodos registrados\n", static_cast<unsigned>(registro.enUso()));
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 60000) {
    ultimo = millis();
    registro.liberarInactivos();
  }
}
```

`obtener` devuelve un puntero porque el resultado puede ser "no hay lugar" (`nullptr`), y quien llama está obligado a considerarlo. El puntero apunta adentro del arreglo, que es global, así que nunca queda colgando; lo que puede pasar es que el lugar se libere y se reutilice para otro nodo, por eso no conviene guardar ese puntero para usarlo mucho después. La memoria del registro se ve en el mensaje de compilación, y el límite de 8 está escrito en un solo lugar.

## Errores comunes

### Un constructor global que usa otro global

```cpp
// Mal: pantalla.cpp
Pantalla::Pantalla() {
  _umbral = config.humedadMinima;   // config (de otro archivo) puede no estar construida
}

// Bien
Pantalla::Pantalla(const Configuracion& config) : _config(config) {}   // solo guardar
void Pantalla::begin() { _umbral = _config.humedadMinima; }            // usar en begin()
```

### Pasar la dirección de algo local a quien lo usa después

```cpp
// Mal
void setup() {
  Configuracion config;
  reporte.usarConfig(&config);   // config desaparece al terminar setup()
}

// Bien
Configuracion config;            // global: vive todo el programa
void setup() {
  reporte.usarConfig(&config);
}
```

### Propiedad ambigua

```cpp
// Mal: ¿quién borra el buffer? ¿Reporte o quien lo creó?
uint8_t* buffer = new uint8_t[512];
Reporte reporte(buffer);

// Bien: el buffer es parte de Reporte, o es global y Reporte solo lo usa
class Reporte {
  uint8_t _buffer[512];
};
```

Si al leer el código no se sabe quién libera algo, alguien lo va a liberar dos veces o ninguna.

### `new` para algo que tiene un máximo conocido

Si sabés que nunca va a haber más de 8 nodos, o más de 120 lecturas pendientes, un arreglo fijo es más simple y más seguro que reservar con `new` cada vez.

## Ejercicio

En este controlador, la pantalla a veces muestra "umbral: 0 %" al arrancar, y un callback guarda un puntero que después apunta a datos que no corresponden. Corregí el diseño.

```cpp problemas-vida.ino
// configuracion.cpp
Configuracion config;   // su constructor lee la flash

// pantalla.cpp
extern Configuracion config;
Pantalla pantalla;      // su constructor hace: _umbral = config.humedadMinima;

// controlador.ino
Lectura* ultimaRecibida = nullptr;

void alRecibirDeNodo(const uint8_t* datos, size_t largo) {
  Lectura l = decodificar(datos, largo);
  ultimaRecibida = &l;
}

void loop() {
  if (ultimaRecibida != nullptr) {
    mostrar(*ultimaRecibida);
  }
}
```

<summary>Pista</summary>

Hay dos problemas de tiempo de vida: el orden de construcción entre archivos, y la dirección de una variable local guardada en un global.

</details>

<details>
<summary>Ver solución</summary>

```cpp soluciones.ino
// configuracion.cpp
Configuracion config;                     // constructor vacío
void Configuracion::begin() { /* leer la flash */ }

// pantalla.cpp
Pantalla pantalla(config);                // solo guarda la referencia
void Pantalla::begin() { _umbral = _config.humedadMinima; }

// controlador.ino
Lectura ultimaRecibida;                   // copia propia, global
volatile bool hayLectura = false;

void alRecibirDeNodo(const uint8_t* datos, size_t largo) {
  ultimaRecibida = decodificar(datos, largo);   // copiar el valor, no guardar una dirección
  hayLectura = true;                            // (con candado si el callback es de otra tarea, ver B.11)
}

void setup() {
  config.begin();                         // primero la configuración...
  pantalla.begin();                       // ...después quien la usa
}

void loop() {
  if (hayLectura) {
    hayLectura = false;
    mostrar(ultimaRecibida);
  }
}
```

La pantalla leía `config` en su constructor, y como están en archivos distintos, a veces `config` todavía no se había construido ni leído la flash: de ahí el 0 %. Ahora el trabajo se hace en `begin()`, en el orden explícito de `setup()`.

El callback guardaba la dirección de `l`, una variable local que desaparece al terminar la función; después, `loop()` leía esa memoria, ya reutilizada por otra cosa. Ahora se copia el valor a una variable global que vive todo el programa.

</details>

## Resumen

- Cada objeto tiene un dueño. En firmware, la opción más simple es que el programa sea dueño de casi todo: objetos globales creados al arrancar.
- La memoria estática hace que el consumo se conozca al compilar, y elimina fugas, fragmentación y referencias colgantes.
- La firma documenta la relación: `T&` obligatorio, `const T&` solo lectura, `T*` opcional, por valor para una copia propia.
- Los constructores de globales solo guardan valores; el trabajo real va en `begin()`, llamado en orden desde `setup()`.
- Para cantidades variables con un máximo conocido, un pool fijo en lugar de `new`.
