**BLE** (*Bluetooth Low Energy*) es una versión de Bluetooth pensada para dispositivos que consumen poco y envían pocos datos, como sensores a batería. Los datos se organizan con **GATT**: un **servidor** expone **servicios**, cada servicio contiene **características**, y cada característica es un dato con un valor y un **UUID** que lo identifica. Un **cliente** se conecta al servidor y lee, escribe o se **suscribe** a una característica; con **notify**, el servidor le envía el valor cada vez que cambia.

## Por qué te importa

En el invernadero, los nodos sensores están repartidos por toda la superficie, funcionan a batería y no pueden tener cables hasta el controlador. BLE es la forma natural de comunicarlos: cada nodo es un servidor que se anuncia, mide y notifica sus lecturas; el controlador es un cliente que encuentra a los nodos, se conecta y recibe los datos.

BLE tiene muchas piezas, y si falta una, simplemente no pasa nada: no hay error, el controlador no recibe datos. Una característica sin la propiedad `NOTIFY`, un descriptor que falta, un UUID con un carácter distinto o un nodo que no vuelve a anunciarse después de una desconexión producen el mismo síntoma. Conocer el modelo completo permite revisar pieza por pieza.

## Paso a paso

### 1. Los roles

| Rol GATT | Rol de conexión | Qué hace | En el invernadero |
|---|---|---|---|
| Servidor | Periférico | tiene los datos, se anuncia, acepta conexiones | nodo sensor |
| Cliente | Central | escanea, se conecta, lee y se suscribe | controlador |

Un dispositivo puede tener los dos roles, pero en este sistema la división es clara.

### 2. Servicios, características y UUID

```text
Nodo sensor (servidor)
└── Servicio "lecturas del invernadero"   UUID 7b1e0001-...
    ├── Característica "lectura"          UUID 7b1e0002-...  propiedades: READ, NOTIFY
    └── Característica "intervalo"        UUID 7b1e0003-...  propiedades: READ, WRITE
```

- Un **servicio** agrupa datos relacionados.
- Una **característica** es un valor (hasta 512 bytes) con **propiedades** que dicen qué se puede hacer con él: `READ` (leer), `WRITE` (escribir), `NOTIFY` (recibir avisos).
- Cada uno se identifica con un **UUID**. Hay UUID cortos (16 bits) reservados para servicios estándar, como el de batería (`0x180F`). Para datos propios se usan UUID de 128 bits generados al azar (por ejemplo, con un generador de UUID en internet), que no chocan con los de nadie.

### 3. Advertising y escaneo

Un servidor BLE sin conexión se **anuncia**: emite periódicamente un paquete corto con su nombre y, opcionalmente, los UUID de sus servicios. El cliente **escanea**, recibe esos anuncios y decide a cuál conectarse. Filtrar por el UUID del servicio permite encontrar solo los nodos del invernadero, ignorando los auriculares y relojes que haya cerca.

Mientras está conectado, un periférico deja de anunciarse (según la configuración). Después de una desconexión, tiene que volver a hacerlo para que el cliente lo encuentre de nuevo. Ese es el ejemplo de los callbacks en [B.9](/conceptos/b-9).

### 4. Notify

Para recibir lecturas, el cliente podría leer la característica cada pocos segundos. Con `NOTIFY` es al revés: el cliente se suscribe una vez, y el servidor le envía el valor cada vez que llama a `notify()`. Llega antes, y el nodo no tiene que estar despierto esperando lecturas.

Para que funcione hacen falta tres cosas:

1. La característica tiene la propiedad `PROPERTY_NOTIFY`.
2. Tiene el descriptor **2902** (CCCD), donde el cliente escribe que se quiere suscribir. En la librería del ESP32 se agrega con `new BLE2902()`.
3. El cliente se suscribe (`registerForNotify`).

### 5. Cuántos bytes entran

Sin negociar nada, cada notificación lleva como máximo **20 bytes** de datos (el MTU por defecto, 23 bytes, menos 3 de cabecera). Se puede negociar un MTU mayor, pero para lecturas de sensores lo mejor es un formato binario compacto, como el de [B.1](/conceptos/b-1): la temperatura en décimas como `int16_t`, la humedad como `uint8_t`. Un JSON con los mismos datos ocupa cinco veces más.

### 6. La librería BLE del ESP32

El core de Arduino para ESP32 trae la librería BLE (`BLEDevice.h` y compañía), que es la que usan estos ejemplos. Ocupa bastante flash y RAM; si eso es un problema, la librería **NimBLE-Arduino** ofrece casi la misma API con mucho menos consumo de memoria.

Los callbacks de BLE (conexión, desconexión, notificación recibida) corren en la tarea de BLE, no en la de `loop()`. Igual que con las interrupciones, conviene que anoten lo que pasó y dejen el trabajo a `loop()`, protegiendo los datos compartidos (ver [B.11](/conceptos/b-11)).

## Ejemplos

### Ejemplo 1. Un nodo con una característica de lectura

El nodo más simple: un servidor con una característica que se puede leer. Se puede probar desde el celular con una app de BLE como *nRF Connect*: escaneás, te conectás a `nodo-norte` y leés la característica.

```cpp nodo-lectura.ino
#include <BLEDevice.h>
#include <BLEServer.h>

constexpr const char* UUID_SERVICIO = "7b1e0001-5c1d-4f6e-9a2b-1c3d4e5f6a7b";
constexpr const char* UUID_TEMPERATURA = "7b1e0002-5c1d-4f6e-9a2b-1c3d4e5f6a7b";

BLECharacteristic* caracteristicaTemp = nullptr;

void setup() {
  Serial.begin(115200);

  BLEDevice::init("nodo-norte");
  BLEServer* servidor = BLEDevice::createServer();
  BLEService* servicio = servidor->createService(UUID_SERVICIO);

  caracteristicaTemp = servicio->createCharacteristic(
      UUID_TEMPERATURA, BLECharacteristic::PROPERTY_READ);
  caracteristicaTemp->setValue("24.5");
  servicio->start();

  BLEAdvertising* anuncio = BLEDevice::getAdvertising();
  anuncio->addServiceUUID(UUID_SERVICIO);
  BLEDevice::startAdvertising();
  Serial.println("anunciándose como nodo-norte");
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 5000) {
    ultimo = millis();
    char texto[8];
    snprintf(texto, sizeof(texto), "%.1f", 20.0f + (millis() / 1000) % 10);   // simulado
    caracteristicaTemp->setValue(texto);   // el próximo READ devuelve este valor
  }
}
```

`setValue` cambia el valor guardado; el cliente lo ve cuando lo lee. Para la prueba con el celular, el texto es cómodo. En el ejemplo siguiente se pasa a binario.

### Ejemplo 2. Un nodo que notifica lecturas en binario

El nodo real envía cada 10 segundos una lectura de 6 bytes por notify, y vuelve a anunciarse si el controlador se desconecta.

```cpp nodo-notify.ino
#include <BLEDevice.h>
#include <BLEServer.h>
#include <BLE2902.h>

constexpr const char* UUID_SERVICIO = "7b1e0001-5c1d-4f6e-9a2b-1c3d4e5f6a7b";
constexpr const char* UUID_LECTURA = "7b1e0002-5c1d-4f6e-9a2b-1c3d4e5f6a7b";

// Formato de la lectura (6 bytes, little-endian):
// [0..1] temperatura en décimas de °C, int16_t
// [2]    humedad del suelo %, uint8_t
// [3]    humedad del aire %, uint8_t
// [4]    batería en décimas de V menos 20 (3,9 V -> 19), uint8_t
// [5]    código de estado (ver B.10), uint8_t

BLECharacteristic* caracteristicaLectura = nullptr;
volatile bool conectado = false;

class CallbacksServidor : public BLEServerCallbacks {
  void onConnect(BLEServer*) override { conectado = true; }
  void onDisconnect(BLEServer*) override {
    conectado = false;
    BLEDevice::startAdvertising();
  }
};

void armarLectura(float temp, int suelo, int aire, float bateria, uint8_t estado, uint8_t out[6]) {
  int16_t decimas = static_cast<int16_t>(lroundf(temp * 10.0f));
  uint16_t bits = static_cast<uint16_t>(decimas);
  out[0] = static_cast<uint8_t>(bits & 0xFF);
  out[1] = static_cast<uint8_t>(bits >> 8);
  out[2] = static_cast<uint8_t>(constrain(suelo, 0, 100));
  out[3] = static_cast<uint8_t>(constrain(aire, 0, 100));
  out[4] = static_cast<uint8_t>(constrain(lroundf(bateria * 10.0f) - 20, 0L, 255L));
  out[5] = estado;
}

void setup() {
  Serial.begin(115200);

  BLEDevice::init("nodo-norte");
  BLEServer* servidor = BLEDevice::createServer();
  servidor->setCallbacks(new CallbacksServidor());

  BLEService* servicio = servidor->createService(UUID_SERVICIO);
  caracteristicaLectura = servicio->createCharacteristic(
      UUID_LECTURA,
      BLECharacteristic::PROPERTY_READ | BLECharacteristic::PROPERTY_NOTIFY);
  caracteristicaLectura->addDescriptor(new BLE2902());   // permite suscribirse
  servicio->start();

  BLEDevice::getAdvertising()->addServiceUUID(UUID_SERVICIO);
  BLEDevice::startAdvertising();
}

void loop() {
  static uint32_t ultimo = 0;
  if (millis() - ultimo >= 10000) {
    ultimo = millis();
    uint8_t lectura[6];
    armarLectura(24.5f, 41, 68, 3.9f, 0, lectura);       // acá irían las lecturas reales
    caracteristicaLectura->setValue(lectura, sizeof(lectura));
    if (conectado) {
      caracteristicaLectura->notify();
    }
  }
}
```

El comentario con el formato no es decoración: es el contrato entre el nodo y el controlador, y los dos firmwares tienen que respetarlo. La batería se guarda como "décimas menos 20" para que el rango útil (2,0 a 4,5 V) entre en un byte. El valor se actualiza aunque no haya nadie conectado, así un cliente que se conecta puede leerlo de inmediato.

### Ejemplo 3. El controlador: buscar, conectar y suscribirse

El controlador escanea buscando el servicio del invernadero, se conecta al primer nodo que encuentra y se suscribe a sus lecturas. El callback de la notificación copia los bytes y `loop()` los interpreta.

```cpp controlador-ble.ino
#include <BLEDevice.h>

static BLEUUID UUID_SERVICIO("7b1e0001-5c1d-4f6e-9a2b-1c3d4e5f6a7b");
static BLEUUID UUID_LECTURA("7b1e0002-5c1d-4f6e-9a2b-1c3d4e5f6a7b");

portMUX_TYPE candado = portMUX_INITIALIZER_UNLOCKED;
uint8_t ultimaTrama[6];
volatile bool hayTrama = false;

BLEClient* cliente = nullptr;

// Corre en la tarea de BLE: solo copia
void alNotificar(BLERemoteCharacteristic*, uint8_t* datos, size_t largo, bool) {
  if (largo != sizeof(ultimaTrama)) return;
  portENTER_CRITICAL(&candado);
  memcpy(ultimaTrama, datos, largo);
  hayTrama = true;
  portEXIT_CRITICAL(&candado);
}

bool conectarANodo() {
  BLEScan* escaneo = BLEDevice::getScan();
  escaneo->setActiveScan(true);
  BLEScanResults* resultados = escaneo->start(5, false);   // escanea 5 segundos

  for (int i = 0; i < resultados->getCount(); i++) {
    BLEAdvertisedDevice dispositivo = resultados->getDevice(i);
    if (!dispositivo.isAdvertisingService(UUID_SERVICIO)) continue;

    Serial.printf("nodo encontrado: %s\n", dispositivo.getName().c_str());
    if (cliente == nullptr) cliente = BLEDevice::createClient();
    if (!cliente->connect(&dispositivo)) continue;

    BLERemoteService* servicio = cliente->getService(UUID_SERVICIO);
    BLERemoteCharacteristic* lectura =
        servicio ? servicio->getCharacteristic(UUID_LECTURA) : nullptr;
    if (lectura == nullptr || !lectura->canNotify()) {
      cliente->disconnect();
      continue;
    }
    lectura->registerForNotify(alNotificar);   // suscripción
    escaneo->clearResults();
    return true;
  }
  escaneo->clearResults();
  return false;
}

void interpretar(const uint8_t t[6]) {
  int16_t decimas = static_cast<int16_t>(t[0] | (t[1] << 8));
  float bateria = (t[4] + 20) / 10.0f;
  Serial.printf("%.1f C | suelo %d%% | aire %d%% | batería %.1f V | estado %d\n",
                decimas / 10.0f, t[2], t[3], bateria, t[5]);
}

void setup() {
  Serial.begin(115200);
  BLEDevice::init("controlador");
}

void loop() {
  static uint32_t ultimoIntento = 0;

  if ((cliente == nullptr || !cliente->isConnected()) && millis() - ultimoIntento >= 10000) {
    ultimoIntento = millis();
    Serial.println(conectarANodo() ? "conectado y suscripto" : "ningún nodo disponible");
  }

  if (hayTrama) {
    uint8_t copia[6];
    portENTER_CRITICAL(&candado);
    memcpy(copia, ultimaTrama, sizeof(copia));
    hayTrama = false;
    portEXIT_CRITICAL(&candado);
    interpretar(copia);
  }
}
```

El escaneo de 5 segundos bloquea `loop()` mientras dura; acá se hace solo cuando no hay conexión, cada 10 segundos. En el controlador real, la conexión BLE suele ir en su propia tarea de FreeRTOS (ver [2.4](/conceptos/2-4)) para no frenar la pantalla. El callback solo copia los 6 bytes dentro de una sección crítica y descarta tramas de otro tamaño; la interpretación se hace en `loop()`. Si el nodo se desconecta, `isConnected()` pasa a `false` y el controlador vuelve a buscar. Para varios nodos a la vez, se repite la conexión con un cliente por nodo.

## Errores comunes

### Notify sin descriptor 2902 o sin la propiedad

```cpp
// Mal: el cliente no se puede suscribir
caracteristica = servicio->createCharacteristic(UUID, BLECharacteristic::PROPERTY_READ);
caracteristica->notify();   // no llega a nadie

// Bien
caracteristica = servicio->createCharacteristic(
    UUID, BLECharacteristic::PROPERTY_READ | BLECharacteristic::PROPERTY_NOTIFY);
caracteristica->addDescriptor(new BLE2902());
```

### No volver a anunciarse

Sin un `onDisconnect` que llame a `startAdvertising()`, el nodo queda invisible después de la primera desconexión. Es el caso de [B.9](/conceptos/b-9).

### UUID distintos en cada firmware

Un solo carácter distinto entre el UUID del nodo y el del controlador hace que el controlador no encuentre el servicio. Definí los UUID en un header compartido entre los dos proyectos, en un solo lugar.

### Trabajo pesado en los callbacks

```cpp
// Mal: interpretar, dibujar y enviar al backend dentro del callback de BLE
void alNotificar(BLERemoteCharacteristic*, uint8_t* datos, size_t largo, bool) {
  interpretar(datos);
  dibujarPantalla();
  enviarAlBackend();
}

// Bien: copiar y avisar; el resto en loop() (ejemplo 3)
```

### Mensajes de más de 20 bytes

Texto o JSON que superan los 20 bytes llegan cortados si no se negoció un MTU mayor. Usá un formato binario de tamaño fijo, documentado en el código.

## Ejercicio

```cpp nodo-roto.ino
    lectura->notify();
  }

```

## Resumen

- El nodo es servidor (periférico): expone servicios con características y se anuncia. El controlador es cliente (central): escanea, se conecta y se suscribe.
- Cada servicio y característica tiene un UUID; para datos propios, UUID de 128 bits, definidos en un solo lugar.
- Para notify: propiedad `NOTIFY`, descriptor `BLE2902` y suscripción del cliente con `registerForNotify`.
- Cada notificación lleva hasta 20 bytes por defecto: usá un formato binario compacto y documentado.
- Los callbacks corren en la tarea de BLE: copiá los datos con protección y procesalos en `loop()`. Después de una desconexión, volvé a anunciarte.
